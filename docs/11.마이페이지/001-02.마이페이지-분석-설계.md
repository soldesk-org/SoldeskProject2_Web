## 2. GET /api/members/me 확장
------------------------------------------------------------------------
기존 05의 `GET /api/members/me`는 의도적으로 `phone`을 응답에서 뺐었다(비밀번호와 같은 톤의 보안 판단).
마이페이지는 본인 정보를 보여주는 화면이라 굳이 뺄 이유가 없어, **기존 엔드포인트에 `phone`/`foodBti`
필드를 추가**하는 쪽으로 결정했다(별도 `GET /api/mypage/profile` 같은 중복 엔드포인트를 만들지 않음 —
"필요한 만큼만" 원칙, 이미 존재하는 "내 정보 조회" 개념을 그대로 확장하는 게 더 단순함).

새 엔드포인트를 안 만들고 기존 계약을 바꾸는 결정이라, 05 문서(`001-04` 3-1장)에도 이 변경을 반영해뒀다.

## 3. 핵심 설계 결정
------------------------------------------------------------------------
### 3-1. 즐겨찾기/리뷰/방문기록 목록에 필요한 "음식점 이름" 문제
07이 카카오 ToS 준수를 위해 `restaurants` 테이블에 상호명/주소/좌표를 저장하지 않기로 했다(07 001-07
2-1장). 그런데 마이페이지의 즐겨찾기/방문기록/내 리뷰 목록은 정확히 그 정보(이 가게가 어디인지)를 보여줘야
의미가 있다 — `restaurantId`만으로는 사용자에게 아무것도 아니다.

**해결책**: 08(영수증OCR)의 `restaurantName` 파라미터, 07 상세 조회의 `name`/`address`/... 선택 파라미터와
같은 패턴을 그대로 확장한다. **즐겨찾기 등록 시점 / 리뷰 작성 시점에 프론트가 이미 화면에 갖고 있는
음식점 이름·주소·좌표를 함께 보내면, 그 값을 그 즐겨찾기/리뷰 행에 "스냅샷"으로 저장**한다.

- `Favorite`에 `restaurant_name_snapshot`/`address_snapshot`/`road_address_snapshot`/`latitude_snapshot`/
  `longitude_snapshot` 컬럼 추가(이름만 필수, 나머지는 선택)
- `Review`에도 동일하게 5개 스냅샷 컬럼 추가, `CreateReviewRequestDto`에 `restaurantName`(필수)/`address`/
  `roadAddress`/`latitude`/`longitude`(선택) 파라미터 추가

**이게 카카오 ToS 위반이 아닌가?** — 07 001-07 1-4장에서 이미 한 번 다룬 것과 같은 종류의 판단이 필요했다.
결론: **이건 카카오 검색 결과를 벌크로 캐싱해서 검색을 대체하는 것과는 다르다.** 사용자 본인이 실제로
남긴 리뷰/즐겨찾기 1건에 달린 "그 행위가 어느 가게에 대한 것이었는지"를 기록하는 개인 데이터이고, 프론트가
그 순간에 이미 화면에 표시하고 있던 값을 그대로 넘기는 것이지 백엔드가 카카오를 다시 조회해서 채우는 게
아니다. 다만 이 판단이 100% 확실한 건 아니라서(07이 이미 리뷰-id 저장 건으로 카카오에 문의를 넣어둔 상태,
001-07 1-4장), 그 답변에 따라 이 스냅샷 저장 방식도 재검토가 필요할 수 있음을 8장에 남겨둔다.

### 3-2. 즐겨찾기 — 신규 쓰기 API + 지연 생성 패턴 재사용
`FavoriteService`/`FavoriteController`(신규, `restaurant` 패키지 — 즐겨찾기가 조작하는 엔티티가 그 패키지
소속이라 같이 둠). 등록/해제 둘 다 **멱등(idempotent)** 하게 처리한다 — 이미 즐겨찾기한 걸 다시 등록하거나,
없는 걸 다시 해제해도 에러 없이 성공(05 프로필 사진 삭제 API와 같은 "관대한 API" 톤). 등록 시 그 음식점의
`Restaurant` 부가정보 행이 없으면 리뷰/영수증과 같은 패턴으로 그 자리에서 지연 생성한다(07 001-07 2-1장).

### 3-3. 방문기록 = "영수증 인증 성공 리뷰"
요청사항 확인 결과(001-01), 별도 "방문 추적" 인프라를 새로 만들지 않고 **`receipt_verified=true`인 리뷰를
그대로 방문기록으로 취급**하기로 확정했다. `ReviewRepository`에
`findByMemberIdAndReceiptVerifiedTrueAndStatusAndDeletedAtIsNullOrderByCreatedAtDesc` 추가 — 별도 테이블
없이 기존 리뷰 데이터를 다른 각도로 재조회하는 것뿐이라 스키마 변경이 없다.

`navigation_histories`(DB-테이블설계.md 5-4장에 설계만 있고 미구현)는 "길찾기 버튼 클릭"을 추적하는
용도라 이번 "방문기록"과는 의미가 다르다 — 코드가 없으므로 그대로 미구현 상태로 둔다(필요해지면 별도
기능으로 검토).

### 3-4. 음BTI — 필드만 추가
`members.food_bti VARCHAR(20) NULL` 컬럼만 추가하고, 값을 설정하는 API는 만들지 않는다(001-01 확인 사항).

채우는 자체 기능(퀴즈든 자동계산이든)을 별도로 만들 것으로 예상.

### 3-5. 검색 기록 (2026-07-22 신규)
DB-테이블설계.md 5-3장에 이미 `search_histories`(member_id NOT NULL, keyword, category_id, created_at) 테이블이
설계돼 있었지만, 07 개발 당시 "요구사항에 없다"는 이유로 실사용을 미뤄뒀던 것을 이번에 처음 실제로 붙였다.

- **기록 시점**: 로그인한 회원이 `GET /api/restaurants/search`를 **키워드와 함께** 호출할 때마다(07 001-02
  5-3장) 자동으로 한 행 저장. 카테고리 필터(`filter()`)는 "검색"이 아니라 별개 개념으로 보고 기록 대상에서
  제외했다 — `category_id` 컬럼은 설계상 있지만 이번엔 항상 비워둔다(향후 필터 기록도 원하면 채울 수 있게
  자리만 남겨둠).
- **트랜잭션 문제**: `RestaurantServiceImpl`은 클래스 전체가 `@Transactional(readOnly = true)`라 그 안에서
  바로 INSERT할 수 없다. `ReceiptSuccessRecorder`(08)와 같은 패턴으로 `SearchHistoryRecorder`(신규,
  `@Transactional` 단일 메서드)를 분리해서 해결.
- ~~중복 처리 안 함~~ → **(2026-07-22 변경)** 같은 키워드를 반복 검색하면 실제로 목록이 계속 늘어나는
  문제로 사용자가 지적, 그 즉시 수정함 — 같은 (member_id, keyword) 행이 이미 있으면 새로 만들지 않고
  `SearchHistory.touch()`로 `created_at`만 지금 시각으로 갱신한다("최근 검색어"가 맨 위로 다시 올라오는
  흔한 UX). `SearchHistoryRepository.findByMemberIdAndKeyword()` 추가, `created_at` 컬럼의
  `updatable = false` 제약도 이때 풀었다(원래는 생성 후 불변으로 설계했었음).
- **조회/삭제는 마이페이지 소유**: `GET /api/mypage/search-histories`(목록), `DELETE
  /api/mypage/search-histories/{id}`(개별 삭제, 본인 소유 아니면 `SEARCH_HISTORY_NOT_FOUND`), `DELETE
  /api/mypage/search-histories`(전체 삭제) — 즐겨찾기와 달리 검색 자체(쓰기)는 07의 검색 흐름에 자동으로
  얹혀서 일어나고, 별도의 "검색 기록 남기기" API는 없다(사용자가 명시적으로 호출하는 게 아니라 검색의
  부수효과이기 때문).

### 3-6. 패키지 구조 (2026-07-22 검색기록/리뷰수정삭제 반영 갱신)
```

 │   ├─ entity       SearchHistory (신규)
 │   ├─ repository   SearchHistoryRepository (신규)
 │   ├─ dto          FavoriteAddRequestDto, FavoriteResponseDto (신규)
 │   ├─ service      FavoriteService, FavoriteServiceImpl, SearchHistoryRecorder (신규 — 3-5장)
```

다시 모아 보여주는" 순수 조회 계층으로만 분리했다 — 이미 각 도메인에 있는 repository를 그대로 재사용하고
새 엔티티/테이블을 만들지 않는다.

### 3-7. 프로필 수정 UI + 비밀번호 재확인 게이트 (2026-07-22 3차 추가)
"회원정보가 보여만 지고 수정이 안 된다"(001-01 "추가 요청 2")는 지적으로, 1차 구현까지는 없었던 실제
수정 화면을 만들었다. 백엔드는 새로 만들 게 거의 없었다 — 05(회원정보수정)가 `PATCH /api/members/me` +
전화번호 인증 + 프로필 사진 업로드/삭제 API를 이미 전부 갖추고 있어서, 이번 작업은 **그 API들을 실제로
호출하는 화면을 붙이는 일**에 가까웠다.

- **전용 페이지 분리**: 기존 `tmp-map-test.html`에 텍스트 나열식으로 붙어있던 마이페이지 패널(1~2차 구현,
  1장/2장) 대신, `mypage-test.html`(신규 정적 페이지)을 별도로 만들었다. 프로필 수정 폼(닉네임/전화번호/
  비밀번호/프로필사진)과 즐겨찾기/방문기록/내 리뷰/검색기록 목록을 한 화면에 갖춘 좀 더 완성된 테스트
  페이지다 — `tmp-map-test.html`은 리뷰 작성/지도 검증용으로 계속 남겨두고 건드리지 않았다.
- **이메일/비밀번호 노출 규칙**: `GET /api/members/me`의 `social`(05 001-02 5-10장) 값으로 분기 — `false`면
  비밀번호 변경 필드를 보여주고, `true`면 그 필드 자체를 렌더링하지 않고 "소셜로그인 계정은 비밀번호를
  변경할 수 없습니다" 안내만 표시한다. 이메일은 소셜 여부와 무관하게 항상 플레이스홀더로 보여주기만 하고
  수정 입력란 자체가 없다(001-01 요구사항 원문 그대로).
- **비밀번호 재확인 게이트(신규 요구사항)**: 프로필 수정 폼 전체(`#profileEditFields`)를 기본적으로
  숨겨두고, 그 위에 비밀번호 입력 게이트(`#profileEditGate`)를 놓았다. `POST
  /api/members/me/verify-password`(05 001-02 5-11장, 신규 엔드포인트지만 회원정보수정 도메인 소관)로
  확인에 성공해야만 게이트가 걷히고 수정 필드가 보인다. 페이지를 (다시) 열 때마다 게이트가 다시 잠긴
  상태로 초기화된다 — 한 번 확인했다고 세션 내내 열려있지 않다(회원탈퇴의 "매번 재인증" 톤과 동일).
  **소셜 계정은 이 게이트 자체를 건너뛴다** — `social: true`면 비밀번호가 아예 없는 계정이라 확인할 대상이
  없으므로, 게이트 없이 곧바로 (비밀번호 필드만 빠진) 수정 폼을 보여준다.
- **엔드포인트를 마이페이지 도메인에 새로 만들지 않은 이유**: 비밀번호 검증 로직(`memberCredentialRepository`
  조회 + `passwordEncoder.matches()`)이 이미 05(회원정보수정)/04(비밀번호찾기)에 있어, 그대로 재사용하는
  게 새 도메인을 만드는 것보다 단순하다는 판단(CLAUDE.md 2장의 "필요한 만큼만" 원칙과 같은 결) — 게이트
  UI 자체는 마이페이지 화면의 일부이지만, API 소유권은 05에 둔다.

## 4. API 설계
------------------------------------------------------------------------
### 4-1. 프로필 조회/수정
기존 05 API 그대로 재사용:

- `POST /api/members/me/verify-password` (**2026-07-22 3차 신규** — 프로필 수정 화면 진입 게이트, 3-7장/

## 5. 에러 코드
------------------------------------------------------------------------
즐겨찾기 등록/해제를 멱등하게 설계해서(3-2장) `FAVORITE_ALREADY_EXISTS`/`FAVORITE_NOT_FOUND` 같은 코드는
필요 없다. **(2026-07-22 추가)** 리뷰 수정/삭제, 검색 기록 삭제는 "존재/소유권 확인"이 꼭 필요해 신규
에러 코드가 생겼다(`docs/10.리뷰/001-02` 4장에도 REVIEW_* 코드 기록):

| 코드 | 상황 | HTTP |
|---|---|---|
| NOT_LOGGED_IN | 전 구간 공통(로그인 필수 API에 헤더 없음/무효) | 401 |
| REVIEW_NOT_FOUND | 존재하지 않거나 이미 삭제된 리뷰 수정/삭제 시도 | 404 |
| REVIEW_ACCESS_DENIED | 본인이 작성하지 않은 리뷰 수정/삭제 시도 | 403 |
| SEARCH_HISTORY_NOT_FOUND | 본인 소유가 아니거나 존재하지 않는 검색 기록 개별 삭제 시도 | 404 |
