# 마이페이지 - 프론트엔드 연동 가이드

프론트엔드 전달용 API 요청 URL/스펙 정리 문서

## 1. 서버 접속 정보
------------------------------------------------------------------------
- 로컬 개발 서버: `http://localhost:8081`
- 이 문서의 API는 전부 **로그인 필요** — `Authorization: Bearer {accessToken}` 헤더 필수.
- 프로필 조회/수정은 **05(회원정보수정)에 이미 있는 API를 그대로 재사용**한다 — 마이페이지 전용 프로필 API를
  새로 만들지 않았다.

------------------------------------------------------------------------
## 2. 기능별 호출 흐름
------------------------------------------------------------------------
### 2-1. 마이페이지 진입
1. `GET /api/members/me` 호출 — 닉네임/이메일/전화번호/프로필사진/음BTI/`social` 여부를 한 번에 받는다
2. `GET /api/mypage/favorites`, `GET /api/mypage/reviews`, `GET /api/mypage/visits`,
   `GET /api/mypage/search-histories`를 병렬로 호출해서 각 탭에 채운다
3. **이메일은 화면에 표시만 하고 수정 UI를 두지 않는다**(001-01 요청사항 — "이메일 수정은 안되게 해도 될 듯")
4. **(2026-07-23 갱신)** 음BTI는 값이 없으면(`null`) "미설정" 같은 플레이스홀더로 표시하면 된다. 값을
   설정하는 화면/API가 이제 생겼다 — `docs/12.음BTI` 참고(`POST /api/food-bti/result`, 로그인 상태로 결과를
   계산하면 그 계정에 저장됨, 실 서버 라이브 검증 완료).
5. **(2026-07-22 신규) 프로필 "조회"와 "수정"은 화면을 분리하거나, 수정 영역을 기본적으로 잠가둘 것** —
   2-9장의 비밀번호 재확인 게이트를 통과해야만 수정 폼을 보여주는 것이 이번 요구사항이다.

### 2-2. 프로필 수정 (닉네임/전화번호/비밀번호)
05(회원정보수정)의 기존 흐름을 그대로 따른다 — 상세 스펙은 `docs/05.회원정보수정/001-04` 참고. 요약:
1. **(2026-07-22 신규) 수정 화면 진입 전 비밀번호 재확인 게이트를 먼저 통과시킬 것** — 2-9장 참고
2. 전화번호를 바꾸려면 `POST /api/members/me/phone/send-code` → `verify-code`로 먼저 인증
3. `PATCH /api/members/me`에 바꾼 항목만 담아 호출(닉네임 필수, 나머지는 값을 바꿀 때만 포함)
4. **비밀번호 변경 필드는 소셜로그인 회원에게는 아예 숨기는 것을 권장** — 소셜 계정으로 시도하면
   `SOCIAL_ACCOUNT_PASSWORD_CHANGE_NOT_ALLOWED`가 난다(이미 구현되어 있음, 프론트에서 미리 막아주면 더
   매끄럽다). `GET /api/members/me`의 `social` 필드(2-1장)로 바로 판별 가능 — 06(소셜로그인) 문서는 그
   판단 근거(왜 소셜 계정에 비밀번호가 없는지)를 다룬다.

### 2-3. 즐겨찾기 등록/해제
음식점 상세 화면(07)이나 목록/검색 결과 카드 어디서든, "즐겨찾기" 별 아이콘을 누르면:
1. 아직 즐겨찾기 안 한 상태 → `POST /api/restaurants/{restaurantId}/favorite` 호출, 바디에 **그 화면에
   이미 갖고 있는 음식점 이름**(`name`, 필수)과 주소/좌표(선택)를 실어 보낸다 — 07 상세 조회에 넘기는
   값과 같은 값을 그대로 재사용하면 된다
2. 이미 즐겨찾기한 상태 → `DELETE /api/restaurants/{restaurantId}/favorite` 호출(바디 없음)
3. 두 API 모두 **멱등**이라 현재 상태를 정확히 몰라도 안전하다 — 이미 등록된 걸 다시 등록해도, 없는 걸
   다시 해제해도 에러 없이 성공 응답이 온다. 다만 UI는 응답의 `favorite` 값으로 별 아이콘 상태를 갱신할 것

### 2-4. 즐겨찾기/방문기록 목록 표시
`GET /api/mypage/favorites`, `GET /api/mypage/visits` 둘 다 같은 형식(`MyPagePlaceResponseDto` 배열)으로
응답한다. `latitude`/`longitude`가 있으면 지도 미리보기나 "지도에서 보기" 버튼에 활용 가능. 목록 항목을
클릭해서 상세로 이동하고 싶으면, 이 응답에 이미 있는 `name`/`address`/`roadAddress`/`latitude`/`longitude`를
그대로 07 상세 조회(`GET /api/restaurants/{restaurantId}?name=...&...`)에 넘기면 된다(07 001-07 2-2장과
같은 패턴).

### 2-5. 내 리뷰 목록 표시
`GET /api/mypage/reviews`는 `restaurantName`을 포함하므로 별도 조회 없이 바로 "어느 가게에 남긴 리뷰인지"
표시할 수 있다. `receiptVerified: true`면 "인증" 뱃지를 붙여줄 것.

### 2-6. 리뷰 작성 시 주의(10.리뷰 문서 변경사항)
`POST /api/reviews`(10.리뷰) 요청에 **`restaurantName`이 이번에 필수 필드로 추가**됐다 — 마이페이지의
"내 리뷰"/"방문기록" 목록에 이름을 보여주기 위한 스냅샷이다. 리뷰 작성 폼을 이미 07/10 문서대로 구현해뒀다면,
제출 요청에 `restaurantName`(그리고 가능하면 `address`/`roadAddress`/`latitude`/`longitude`도)을 추가해야
한다 — 안 보내면 400 검증 에러가 난다. 상세는 `docs/10.리뷰/001-04` 참고.

### 2-7. 리뷰 수정/삭제 (2026-07-22 추가)
"내 리뷰" 목록(`GET /api/mypage/reviews`)의 각 항목에 수정/삭제 버튼을 단다 — 이 목록은 회원 기준으로
조회되므로 전부 본인 리뷰임이 보장된다. **음식점 상세의 일반 리뷰 목록(07)에는 이 버튼을 달지 말 것** —
그 응답엔 작성자가 나 자신인지 구분할 정보(memberId)가 없다(`docs/10.리뷰/001-04` 2-4장). 수정은
`PATCH /api/reviews/{reviewId}`, 삭제는 `DELETE /api/reviews/{reviewId}` — 상세 스펙은 `docs/10.리뷰/001-04`
4-3/4-4장 참고. 성공하면 마이페이지 리뷰 목록을 재조회해서 갱신할 것.

### 2-8. 검색 기록 조회/삭제 (2026-07-22 추가)
- 검색 기록은 **자동으로 쌓인다** — 로그인 상태에서 07의 검색창(`GET /api/restaurants/search`)에 키워드를
  입력해 검색할 때마다 서버가 알아서 기록한다. 프론트가 별도로 "이 검색어를 기록해줘" 요청을 보낼 필요는
  없음(2-3장 즐겨찾기와 달리 "기록 API" 자체가 없음).
- 마이페이지에서 `GET /api/mypage/search-histories`로 목록 표시, 항목별 "삭제" 버튼은
  `DELETE /api/mypage/search-histories/{id}`, "전체 삭제" 버튼은 `DELETE /api/mypage/search-histories`
- 검색 기록 항목을 클릭하면 그 키워드로 다시 검색(07 검색창에 채워넣고 재검색)하는 UX를 권장

### 2-9. 비밀번호 재확인 게이트 (2026-07-22 신규)
"마이페이지에서 프로필 수정 화면에 들어갈 때마다 비밀번호를 먼저 입력해야 하도록" 요구사항. 참고 구현:
`mypage-test.html`의 `#profileEditGate`/`#profileEditFields`.

1. 마이페이지(또는 프로필 수정 화면)에 진입하면 **수정 폼 전체를 기본적으로 숨기고** 비밀번호 입력 게이트만
   보여준다 — 화면을 나갔다 다시 들어오면 게이트는 다시 잠긴 상태로 초기화되어야 한다(세션 내내 열려있으면
   안 됨).
2. 입력한 비밀번호로 `POST /api/members/me/verify-password` 호출(상세 스펙은
   `docs/05.회원정보수정/001-04` 3-11장)
3. 성공(200)하면 그때부터 수정 폼(닉네임/전화번호/비밀번호/프로필사진)을 보여준다. 실패(401)하면 폼을 열지
   않고 에러 메시지만 표시한다.
4. **소셜 계정(`social: true`)은 이 게이트를 아예 건너뛴다** — 비밀번호가 없는 계정이라 확인할 대상이 없다.
   곧바로 (비밀번호 필드가 빠진) 수정 폼을 보여줄 것.

## 3. API 상세
------------------------------------------------------------------------
### 3-1. 프로필 조회
```
GET http://localhost:8081/api/members/me
Authorization: Bearer {accessToken}
```
응답(200):
```json
{
  "success": true, "email": "user@example.com", "nickname": "홍길동",
  "profileImageUrl": "http://localhost:8081/profile-images/xxxx.png",
  "phone": "010-1234-5678", "foodBti": null, "social": false
}
```
`social`(2026-07-22 추가)이 `true`면 소셜로그인 계정 — 비밀번호 관련 UI 전부(2-2장/2-9장)를 숨길 것.

### 3-2. 즐겨찾기 등록
```
POST http://localhost:8081/api/restaurants/16421356/favorite
Authorization: Bearer {accessToken}
Content-Type: application/json

{ "name": "농민백암순대 강남직영점", "address": "...", "roadAddress": "...", "latitude": 37.123, "longitude": 127.456 }
```
`name`만 필수, 나머지는 선택. 응답(200): `{ "success": true, "favorite": true }`

### 3-3. 즐겨찾기 해제
```
DELETE http://localhost:8081/api/restaurants/16421356/favorite
Authorization: Bearer {accessToken}
```
응답(200): `{ "success": true, "favorite": false }`

### 3-4. 즐겨찾기 목록
```
GET http://localhost:8081/api/mypage/favorites
Authorization: Bearer {accessToken}
```
응답(200):
```json
[
  { "restaurantId": "16421356", "name": "농민백암순대 강남직영점", "address": "...", "roadAddress": "...",
    "latitude": 37.123, "longitude": 127.456, "recordedAt": "2026-07-22T14:00:00" }
]
```
없으면 `[]`.

### 3-5. 방문기록
```
GET http://localhost:8081/api/mypage/visits
Authorization: Bearer {accessToken}
```
응답 형식은 3-4장과 동일(`MyPagePlaceResponseDto` 배열) — 영수증 인증까지 성공한 리뷰가 있는 가게만
나온다. 같은 가게를 인증 리뷰로 여러 번 남기면 그만큼 여러 번 나올 수 있다(가게 단위 중복 제거 안 함,
001-02 8장 참고).

### 3-6. 내 리뷰 목록
```
GET http://localhost:8081/api/mypage/reviews
Authorization: Bearer {accessToken}
```
응답(200):
```json
[
  { "reviewId": 12, "restaurantId": "16421356", "restaurantName": "농민백암순대 강남직영점",
    "rating": 5, "content": "정말 맛있었어요!",
    "keywords": [{ "keyword": "맛있어요", "sentiment": "POSITIVE" }],
    "receiptVerified": true, "createdAt": "2026-07-22T14:00:00" }
]
```
**(2026-07-22 태그 개편 반영)** `content`는 이제 순수 자유 텍스트, 태그는 `keywords` 배열로 구조화되어
내려온다(`#키워드` 합성 방식 폐지 — 상세는 `docs/10.리뷰/001-04` 2-2-1/2-3장 참고).

### 3-7. 리뷰 수정 (2026-07-22 추가)
```
PATCH http://localhost:8081/api/reviews/12
Authorization: Bearer {accessToken}
Content-Type: application/json

{ "rating": 4, "keywords": ["친절해요"], "content": "재방문 의사 있어요" }
```
응답(200): 3-6장과 같은 형식(`ReviewResponseDto`). 본인 리뷰가 아니면 `403 REVIEW_ACCESS_DENIED`.

### 3-8. 리뷰 삭제 (2026-07-22 추가)
```
DELETE http://localhost:8081/api/reviews/12
Authorization: Bearer {accessToken}
```
응답: `204 No Content`.

### 3-9. 검색 기록 목록 (2026-07-22 추가)
```
GET http://localhost:8081/api/mypage/search-histories
Authorization: Bearer {accessToken}
```
응답(200):
```json
[
  { "searchHistoryId": 1, "keyword": "순대", "createdAt": "2026-07-22T14:00:00" }
]
```
없으면 `[]`. 같은 키워드를 여러 번 검색했으면 그만큼 중복된 행으로 나온다(중복 제거 안 함, 001-02 8장).

### 3-10. 검색 기록 삭제 (2026-07-22 추가)
```
DELETE http://localhost:8081/api/mypage/search-histories/1        (개별 삭제)
DELETE http://localhost:8081/api/mypage/search-histories          (전체 삭제)
Authorization: Bearer {accessToken}
```
응답: `204 No Content`. 개별 삭제 시 본인 소유가 아니거나 존재하지 않는 id면 `404 SEARCH_HISTORY_NOT_FOUND`.

## 4. 에러 코드
------------------------------------------------------------------------
| 코드 | 상황 | HTTP |
|---|---|---|
| NOT_LOGGED_IN | Authorization 헤더 없음/무효 | 401 |
| VALIDATION_ERROR(기존 재사용) | 즐겨찾기 등록 시 `name` 누락 등 | 400 |
| REVIEW_NOT_FOUND(2026-07-22) | 존재하지 않거나 이미 삭제된 리뷰 수정/삭제 시도 | 404 |
| REVIEW_ACCESS_DENIED(2026-07-22) | 본인이 작성하지 않은 리뷰 수정/삭제 시도 | 403 |
| SEARCH_HISTORY_NOT_FOUND(2026-07-22) | 본인 소유가 아니거나 존재하지 않는 검색 기록 개별 삭제 시도 | 404 |
| INVALID_CREDENTIALS(2026-07-22 3차) | 비밀번호 재확인 게이트(2-9장)에서 비밀번호 불일치 | 401 |

즐겨찾기 등록/해제는 멱등하게 설계되어(2-3장) 별도의 "이미 있음"/"없음" 에러 코드가 없다.
