## 1. [미착수] 발급한 JWT access token을 검증/인가하는 필터가 없음
------------------------------------------------------------------------
**위치**: [MemberController.java](../../Project2/src/main/java/com/foodtrip/foodsearch/member/controller/MemberController.java), [SecurityConfig.java](../../Project2/src/main/java/com/foodtrip/foodsearch/common/config/SecurityConfig.java)

로그인 성공 시 JWT access token을 "발급"만 하고, 이 토큰으로 다른 API 요청을 인가(authorize)하는 로직(Spring Security 필터 등)이 아직 없다. 즉 지금은 토큰을 붙이든 안 붙이든 어떤 API도 막히지 않는다. 이번 구현 범위에는 보호가 필요한 API 자체가 아직 없어서 의도적으로 범위 밖으로 뺀 상태 — 지금 필터부터 만들면 보호할 대상이 없는 상태에서 인프라만 먼저 얹는 것이라 과설계가 될 수 있다고 판단해 보류함.

**제안**: 보호가 필요한 첫 API(마이페이지 등)가 생길 때 인가 필터를 같이 구현. 로그아웃 기능이 생기면 access token 블랙리스트(4장 참고)도 같은 필터에서 검사.

- 해당 없음 (기능 자체가 없어 테스트 대상 아님)

------------------------------------------------------------------------
## 2. [미착수] 계정 잠금 해제에 대한 관리 기능 없음 (자연 만료만 지원)
------------------------------------------------------------------------
**위치**: [LoginAttemptService.java](../../Project2/src/main/java/com/foodtrip/foodsearch/member/service/LoginAttemptService.java)

계정이 잠기면(`login:lock:{memberId}` 키 설정, TTL 30분) 관리자가 강제로 풀어주는 별도 API가 없다. 다만 Redis로 옮긴 뒤로는 **`redis-cli -a <비밀번호> DEL login:lock:{memberId}`** 명령 하나로 즉시 해제가 가능해졌다 — DB 방식일 때는 `locked_until` 컬럼을 직접 UPDATE해야 했던 것과 비교하면 운영 부담이 줄었다. 자연 만료 후 재시도 성공 케이스는 30분 대기가 필요해 자동화 테스트에는 포함하지 않았다.

**제안**: 사용자 문의가 실제로 들어오면, 위 `redis-cli DEL` 명령으로 우선 대응하고, 빈도가 잦아지면 그때 관리자 인증 체계와 함께 정식 API 추가 검토. 우선순위 낮음.

- 자동화 테스트 없음 (자연 만료 케이스는 대기시간 때문에 수동 검증도 생략)

------------------------------------------------------------------------
## 3. [정책 결정 대기] 계정 잠금 임계치(5회)/잠금 시간(30분)이 임의로 정한 값
------------------------------------------------------------------------
**위치**: [LoginAttemptService.java](../../Project2/src/main/java/com/foodtrip/foodsearch/member/service/LoginAttemptService.java) (`MAX_LOGIN_FAIL_COUNT`, `LOCK_DURATION`)

요구사항 문서([001-01](001-01.로그인-요구사항.md))에 계정 잠금 정책 자체가 명시되어 있지 않아서, 구현 시점에 5회/30분으로 임의로 정했다. 실제 서비스 정책이 확정되면 두 상수만 조정하면 되므로 코드 변경 자체는 간단함.

**제안**: 기획 쪽에서 정책(실패 허용 횟수, 잠금 시간)이 확정되면 상수 값 조정.

- 해당 없음 (값 자체가 정책 결정 사항)

## 4. [미착수] Access Token(JWT) 블랙리스트 — 로그아웃 기능이 생기면 필요
------------------------------------------------------------------------
**위치**: [JwtProvider.java](../../Project2/src/main/java/com/foodtrip/foodsearch/common/security/JwtProvider.java)

JWT는 원래 서버가 상태를 안 들고 있어도 검증 가능한(stateless) 게 장점이라, access token 자체를 Redis에 저장할 필요는 없다. 다만 지금 구조는 발급된 토큰이 **만료 전까지는 로그아웃해도 계속 유효**하다는 뜻이라, "로그아웃하면 그 토큰은 즉시 못 쓰게" 하려면 blacklist가 필요하다.

| 항목 | 설계안 |
|---|---|
| 키 | `blacklist:{jti}` (JWT에 고유 id 클레임(`jti`)을 새로 추가해야 함 — 현재 `JwtProvider.generateAccessToken()`은 `sub`/`email`/`role`만 넣고 `jti`가 없음) |
| 값 | 아무 값(존재 여부만 확인, 예: `"1"`) |
| TTL | 그 토큰의 남은 유효시간만큼만 (`exp - now`) → 어차피 만료되면 자동으로 무효라 그 이후엔 블랙리스트에 남아있을 필요 없음 |
| 검사 위치 | 1번 항목의 인가 필터를 만들 때 "서명 검증 통과 + `blacklist:{jti}` 없음"을 함께 확인하도록 구현 |

**제안**: 로그아웃 API(`POST /api/members/logout` 같은)를 만들 때 같이 구현. 지금은 로그아웃 자체가 없어서 미착수.

- 해당 없음 (기능 자체가 없어 테스트 대상 아님)
