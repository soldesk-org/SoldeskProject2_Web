# 로그인 - 프론트엔드 연동 가이드

## 1. 서버 접속 정보
------------------------------------------------------------------------
- 로컬 개발 서버: `http://localhost:8081`
  - ※ 8080이 아니라 **8081**입니다 (로컬 환경에 다른 프로세스가 8080을 점유하고 있어 변경됨)
- Base path: `/api`
- 로그인 요청 자체는 별도 인증 헤더 없이 호출하면 됩니다. `Content-Type: application/json` 필수.
- 로그인 성공 시 응답으로 JWT `accessToken`과 `refreshToken`을 함께 내려줍니다. (2026-07-19 갱신) 회원정보수정/소셜로그인 등 로그인이 필요한 API들이 이후 추가되어, 지금은 `accessToken`을 `Authorization: Bearer {accessToken}` 헤더로 붙여야 하는 보호된 API가 실제로 있습니다 — 자세한 목록은 [005.회원정보수정 연동가이드](../05.회원정보수정/001-04.회원정보수정-프론트엔드-연동-가이드.md) 참고.

------------------------------------------------------------------------
## 2. 로그인 흐름 (호출 순서)
------------------------------------------------------------------------
1. `POST /api/members/login` — 이메일 + 비밀번호(+ "로그인 상태 유지" 체크박스 값) 입력 후 로그인 요청 1회 호출로 끝
2. (선택) `accessToken`이 만료(60분)된 뒤 `POST /api/members/refresh` — 재로그인 없이 새 토큰 재발급

회원가입과 달리 인증번호 절차 없이 단일 API 호출입니다. 단, 아래처럼 실패 사유가 여러 가지이므로 `code` 값에 따라 분기 처리가 필요합니다 (5장 참고).

## 3. API 상세
------------------------------------------------------------------------
### 3-1. 로그인
```
POST http://localhost:8081/api/members/login
Content-Type: application/json

{
  "email": "user@example.com",
  "password": "P@ssw0rd1",
  "rememberMe": true
}
```
`rememberMe`는 "로그인 상태 유지" 체크박스 값입니다(2026-07-19 추가) — **선택 필드**이며, 체크 안 함/생략 시 서버가 자동으로 `false`로 처리합니다.

성공 응답 (200)
```json
{
  "success": true,
  "message": "로그인에 성공하였습니다.",
  "memberId": 1,
  "accessToken": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIiwiZW1haWwiOiJ1c2VyQGV4YW1wbGUuY29tIiwicm9sZSI6IlVTRVIiLCJpYXQiOjE3ODk3MTIwMDAsImV4cCI6MTc4OTcxNTYwMH0.xxxxxxxx",
  "refreshToken": "3fa2c1e0-8b1a-4e2d-9c3f-1a2b3c4d5e6f"
}
```
- `accessToken`은 JWT(HS256)이며 유효기간은 `rememberMe`와 무관하게 항상 고정 **60분**입니다.
- `refreshToken`은 임의의 문자열(UUID)이며, 유효기간이 `rememberMe`에 따라 달라집니다(2026-07-19 추가):
  - `rememberMe: true` → **14일**
  - `rememberMe: false` 또는 생략 → **24시간**
- 만료 전까지는 재로그인 없이 3-2번 API로 새 accessToken을 재발급받을 수 있습니다. **재발급 요청에는 `rememberMe`를 다시 보낼 필요가 없습니다** — 서버가 최초 로그인 때 선택한 값을 기억해서 재발급 때도 그대로 적용합니다.
- `accessToken`을 검사하는 보호된 API가 실제로 있습니다(1장 참고) — `Authorization: Bearer {accessToken}` 헤더로 붙여서 호출하시면 됩니다.

### 3-2. 토큰 재발급
```
POST http://localhost:8081/api/members/refresh
Content-Type: application/json

{
  "memberId": 1,
  "refreshToken": "3fa2c1e0-8b1a-4e2d-9c3f-1a2b3c4d5e6f"
}
```
성공 응답 (200)
```json
{
  "success": true,
  "message": "토큰이 재발급되었습니다.",
  "accessToken": "eyJhbGciOi... (새 토큰)",
  "refreshToken": "9b1dabc0-... (새 토큰, 기존 값은 이 시점부터 사용 불가)"
}
```
- `memberId`는 로그인 성공 응답에서 받은 값을 그대로 사용하면 됩니다.
- **재발급할 때마다 refreshToken도 같이 교체됩니다(회전).** 응답으로 받은 새 refreshToken으로 프론트가 들고 있던 값을 반드시 덮어써야 합니다 — 이전 refreshToken은 이 요청 이후 다시 쓸 수 없습니다(재사용 시 5장의 `INVALID_REFRESH_TOKEN` 에러).
- 실패(토큰 불일치/만료/다른 계정 조합 등)하면 401 `INVALID_REFRESH_TOKEN`이 내려오며, 이 경우 저장해둔 토큰을 지우고 다시 로그인시켜야 합니다.

## 4. 입력값 검증 규칙 (프론트 단에서도 동일하게 미리 검증 추천)
------------------------------------------------------------------------
| 필드 | 규칙 |
|---|---|
| email | 이메일 형식, 최대 100자 |
| password | 필수 입력, 최대 100자 (형식 검증은 회원가입 때 이미 완료되어 로그인에서는 별도 규칙 없음) |
| rememberMe (2026-07-19 추가) | 선택값(boolean). 생략 가능 — 생략하면 `false`와 동일하게 처리됨 |

## 5. 에러 응답 형식
------------------------------------------------------------------------
모든 에러는 아래 형식으로 내려옵니다. HTTP status와 `code`로 분기 처리하면 됩니다.
```json
{ "success": false, "code": "INVALID_CREDENTIALS", "message": "아이디 또는 비밀번호가 일치하지 않습니다." }
```

| code | 상황 | HTTP Status | 안내 문구(그대로 사용 가능) |
|---|---|---|---|
| INVALID_INPUT | 입력값 형식 오류 (이메일 형식 오류, 비밀번호 공란 등) | 400 | message 그대로 노출 |
| INVALID_CREDENTIALS | 이메일이 존재하지 않거나 / 회원가입이 완료되지 않았거나 / 비밀번호가 틀림 (세 경우 모두 동일하게 응답, 계정 존재 여부 비노출) | 401 | "아이디 또는 비밀번호가 일치하지 않습니다." |
| ACCOUNT_LOCKED | 비밀번호 5회 연속 실패로 30분간 잠김. 잠금 중에는 올바른 비밀번호를 입력해도 동일하게 응답됨 | 423 | "로그인 실패 횟수를 초과하여 계정이 잠겼습니다. 30분 후 다시 시도해주세요." |
| ACCOUNT_SUSPENDED | 정지된 계정 (비밀번호는 맞았지만 이용 제한 상태) | 403 | "이용이 정지된 계정입니다. 고객센터에 문의해주세요." |
| ACCOUNT_WITHDRAWN | 탈퇴 처리된 계정 (비밀번호는 맞았지만 탈퇴 상태) | 403 | "탈퇴 처리된 계정입니다." |
| INVALID_REFRESH_TOKEN | (`/api/members/refresh` 전용) refreshToken이 없거나 틀리거나 다른 회원의 것 | 401 | "유효하지 않은 재발급 토큰입니다. 다시 로그인해주세요." → 저장된 토큰 삭제 후 로그인 화면으로 이동 |

## 6. 참고 / 주의사항
------------------------------------------------------------------------
- **아이디/비밀번호가 틀린 경우와 존재하지 않는 이메일인 경우를 프론트에서 구분해서 보여주지 마세요.** 서버가 의도적으로 `INVALID_CREDENTIALS` 하나로 통일해서 내려줍니다(보안상 계정 존재 여부 비노출). 그대로 "아이디 또는 비밀번호가 일치하지 않습니다."만 띄우면 됩니다.
- **계정 잠금(`ACCOUNT_LOCKED`)은 로그인 실패 5회부터 발생**합니다. 5번째 틀린 시도의 응답부터 `INVALID_CREDENTIALS`가 아니라 `ACCOUNT_LOCKED`로 바뀌니, 프론트에서 "비밀번호를 여러 번 틀리면 잠길 수 있다"는 안내 문구를 미리 넣어두면 좋습니다. (실패 횟수를 프론트에서 별도로 세지 않아도 됩니다 — 서버가 판단해서 코드로 알려줍니다.)
- `ACCOUNT_LOCKED`는 30분 후 자동으로 풀립니다. 별도 "잠금 해제" API는 없습니다.
- **refreshToken 사용 시점**: 지금은 보호된 API가 없어서 당장 쓸 일은 없지만, 나중에 보호된 API가 401(만료 등)로 응답하면 그때 `/api/members/refresh`를 한 번 호출해서 새 accessToken을 받고 원래 요청을 재시도하는 흐름을 권장합니다. 재발급도 실패(`INVALID_REFRESH_TOKEN`)하면 그때는 재로그인시켜주세요.
- `ACCOUNT_SUSPENDED`/`ACCOUNT_WITHDRAWN`은 비밀번호가 정확했을 때만 내려옵니다. 즉 이 코드를 받았다면 사용자가 자기 계정 상태를 정확히 안 것이므로, 메시지를 그대로 노출해도 괜찮습니다.
- 로그인 성공 후 "메인 페이지로 이동"은 아직 프론트에 페이지가 없어서 서버 응답에 별도 리다이렉트 정보는 없습니다. `success: true` 받으면 프론트에서 원하는 페이지로 이동시켜주시면 됩니다.
- **(2026-07-19 추가) "로그인 상태 유지"를 체크하지 않았을 때 브라우저를 닫으면 바로 로그아웃되길 원하신다면, 서버의 24시간 TTL만으로는 부족합니다.** 서버는 "체크 안 하면 24시간 뒤 자동 만료"까지만 보장하고, "브라우저를 닫는 순간"은 알 방법이 없습니다. 완전한 "브라우저 종료 시 로그아웃" 동작을 원하시면 프론트에서 토큰 저장 위치를 아래처럼 나눠주세요:
  - `rememberMe: true` → `localStorage`에 저장(브라우저를 껐다 켜도 유지, 서버 TTL 14일과 자연스럽게 맞음)
  - `rememberMe: false` → `sessionStorage`에 저장(탭/창을 닫으면 즉시 사라짐 — 서버의 24시간 TTL은 "혹시 탭을 계속 켜두고 방치했을 때"의 보조 안전장치 역할)
- 현재 CORS 설정은 별도로 열려있지 않습니다. 프론트 개발 서버 주소가 정해지면 알려주시면 CORS 허용 처리하겠습니다.
