------------------------------------------------------------------------

### 1-1. 추가/수정된 파일

- 신규 엔티티/리포지토리 없음 (기존 `Member`, `MemberCredential`, `MemberRepository`, `MemberCredentialRepository` 그대로 재사용)
- 신규 설정 없음 (기존 `SecurityConfig`의 `PasswordEncoder`(Argon2) Bean 그대로 재사용)

### 1-2. 로그인 로직 (MemberServiceImpl.login)
1. `memberRepository.findByEmail(email)` → 없으면 `INVALID_CREDENTIALS`
2. `memberCredentialRepository.findByMemberId(memberId)` → 없으면(가입 미완료 상태) `INVALID_CREDENTIALS`
3. `passwordEncoder.matches(입력 비밀번호, password_hash)` → 불일치 시 `INVALID_CREDENTIALS`
4. 모두 통과 시 `LoginResponseDto(true, "로그인에 성공하였습니다.", memberId)` 반환
5. 조회 전용 로직이므로 `@Transactional(readOnly = true)`로 처리 (회원가입의 `signUp()`은 쓰기 트랜잭션이라 별도로 유지)

이메일 미존재 / 가입 미완료(credential 없음) / 비밀번호 불일치 세 가지 경우를 모두 동일한 `INVALID_CREDENTIALS`(401)로 응답하여
계정 존재 여부가 노출되지 않도록 설계안(001-02 8장)대로 구현함.

## 1-6. 2차 구현 (2026-07-17): "남은 작업" 4가지 항목 반영
------------------------------------------------------------------------
1-4에서 미룬 4가지 항목을 모두 구현함. 요구사항 문서에 정책 수치가 명시되어 있지 않아, 아래와 같이 임의의 기본값으로 확정하고 진행함(향후 정책 변경 시 상수만 조정하면 됨).

### 확정한 정책
| 항목 | 확정 내용 |
|---|---|
| 계정 잠금 정책 | 비밀번호 5회 연속 실패 시 30분 잠금. `LoginAttemptRecorder`의 `MAX_LOGIN_FAIL_COUNT=5`, `LOCK_DURATION_MINUTES=30` 상수로 관리 |
| last_login_at 갱신 | 로그인 성공 시(비밀번호 일치 + 계정 상태 정상) `members.last_login_at`을 현재 시각으로 갱신 |
| 세션/토큰 발급 | JWT(HS256) access token만 발급. 로그인 응답의 `accessToken` 필드로 반환하며, 별도 refresh token 저장(`refresh_tokens` 테이블)이나 인증 필터(권한 검사)는 이번 범위에 포함하지 않음 — 보호가 필요한 API가 아직 없어 토큰 발급까지만 구현 |
| status(SUSPENDED/WITHDRAWN) 처리 | 비밀번호가 일치한 이후에만 상태를 확인해 각각 `ACCOUNT_SUSPENDED`(403) / `ACCOUNT_WITHDRAWN`(403)으로 응답. 틀린 비밀번호로 계정 상태(존재 여부·정지 여부)를 추측할 수 없도록, 상태 확인을 비밀번호 검증 뒤에 배치 |

### 계정 잠금 구현 방식(트랜잭션 분리)
로그인 실패 기록(`login_fail_count` 증가, 임계치 도달 시 `locked_until` 설정)은 로그인 요청 자체가 예외로 끝나더라도 DB에 반드시 남아야 한다.
하지만 `login()`은 실패 시 `CustomException`을 던져 `@Transactional`이 롤백되므로, 같은 트랜잭션 안에서 카운트를 올리면 그 변경도 함께 롤백되어 버린다.
이를 위해 `LoginAttemptRecorder`라는 별도 Bean을 두고 `@Transactional(propagation = Propagation.REQUIRES_NEW)`로 실패 기록만 즉시 커밋되는 별도 트랜잭션에서 처리하도록 분리함.

### 신규/수정 파일
```
com.foodtrip.foodsearch
 ├─ common
 │   ├─ exception    ErrorCode (ACCOUNT_LOCKED/ACCOUNT_SUSPENDED/ACCOUNT_WITHDRAWN 추가)
 │   └─ security      JwtProvider (신규, HS256 access token 발급)
 └─ member
     ├─ entity        Member (updateLastLoginAt/getLastLoginAt 추가)
     │                MemberCredential (isLocked/increaseLoginFailCount/lockUntil/resetLoginFailCount/getter 추가)
     ├─ service        MemberServiceImpl.login() 재작성 (잠금 확인 → 비밀번호 대조 → 상태 확인 → 성공 처리 → JWT 발급)
     │                LoginAttemptRecorder (신규, REQUIRES_NEW 트랜잭션으로 실패 카운트 기록)
     └─ dto            LoginResponseDto (accessToken 필드 추가)
```
- `pom.xml`: `io.jsonwebtoken:jjwt-api/jjwt-impl/jjwt-jackson:0.12.6` 추가
- `application.yml`: `jwt.secret`(`${JWT_SECRET}`), `jwt.expiration-minutes`(`${JWT_EXPIRATION_MINUTES:60}`) 추가
- `.env`/`.env.example`: `JWT_SECRET`(256bit 이상 랜덤 값), `JWT_EXPIRATION_MINUTES=60` 추가

### 최종 로그인 처리 순서 (MemberServiceImpl.login)
1. email로 members 조회 → 없으면 `INVALID_CREDENTIALS`
2. member_id로 member_credentials 조회 → 없으면 `INVALID_CREDENTIALS`
3. `credential.isLocked(now)` 확인 → 잠긴 상태면 `ACCOUNT_LOCKED`(423, 비밀번호 검증 전에 즉시 차단)
4. `passwordEncoder.matches()` 대조 → 불일치 시 `LoginAttemptRecorder.recordFailureAndCheckLocked()`로 실패 기록(별도 트랜잭션 커밋) 후, 이번 시도로 막 잠겼으면 `ACCOUNT_LOCKED`, 아니면 `INVALID_CREDENTIALS`
5. 비밀번호 일치 시 `members.status` 확인 → `SUSPENDED`면 `ACCOUNT_SUSPENDED`, `WITHDRAWN`이면 `ACCOUNT_WITHDRAWN`
6. 모두 통과 시 `credential.resetLoginFailCount()`, `member.updateLastLoginAt(now)` 갱신 + `JwtProvider`로 access token 발급 → `LoginResponseDto(true, "로그인에 성공하였습니다.", memberId, accessToken)` 반환

### API 응답 변경
Response (성공, 200):
```json
{ "success": true, "message": "로그인에 성공하였습니다.", "memberId": 1, "accessToken": "eyJhbGciOi..." }
```
Response (계정 잠금, 423):
```json
{ "success": false, "code": "ACCOUNT_LOCKED", "message": "로그인 실패 횟수를 초과하여 계정이 잠겼습니다. 30분 후 다시 시도해주세요." }
```
Response (정지 계정, 403):
```json
{ "success": false, "code": "ACCOUNT_SUSPENDED", "message": "이용이 정지된 계정입니다. 고객센터에 문의해주세요." }
```
Response (탈퇴 계정, 403):
```json
{ "success": false, "code": "ACCOUNT_WITHDRAWN", "message": "탈퇴 처리된 계정입니다." }
```

## 4. 3차 구현 (2026-07-17): 부족한 내용 중 2건 수정
------------------------------------------------------------------------
[001-05.부족한-내용.md](001-05.부족한-내용.md) 코드 리뷰에서 발견하고 실증까지 마친 항목 중, 우선순위가 높다고 판단한 2건을 수정함.
(회원가입 [001-05.부족한-내용.md](../01.회원가입/001-05.부족한-내용.md)에서 발견된 항목 중에서도 GlobalExceptionHandler는 공유 컴포넌트라 여기서 같이 수정함)

### 4-1. 동시 로그인 실패 시 계정 잠금이 씹히는 문제 (브루트포스 방어 무력화) 수정
**원인**: `LoginAttemptRecorder.recordFailureAndCheckLocked()`가 `MemberCredential`을 SELECT로 읽어와 자바에서 `login_fail_count + 1`을 계산한 뒤 그 절대값으로 UPDATE(flush)하는 read-modify-write 구조였음. 동시에 여러 로그인 실패 요청이 들어오면 서로 다른 요청이 같은 시작값을 읽고 각자 계산한 값으로 덮어써서 일부 증가분이 유실됨(lost update) — 001-05 문서에서 8개 동시 요청 시 `login_fail_count`가 4에 그치고 잠기지 않는 것을 실증함.

**수정**:
- `MemberCredentialRepository`에 `@Modifying @Query`로 원자적 증가 쿼리 `incrementLoginFailCount(memberId)` 추가 (`UPDATE MemberCredential c SET c.loginFailCount = c.loginFailCount + 1 WHERE c.memberId = :memberId`)
- 잠금 시각 설정도 `lockIfNotAlreadyLocked(memberId, until)` 원자적 쿼리로 분리, `WHERE ... AND c.lockedUntil IS NULL` 조건으로 이미 잠긴 계정의 잠금 해제 시각을 다른 동시 요청이 다시 덮어쓰지 않도록 함
- `LoginAttemptRecorder`가 엔티티를 직접 수정하는 대신 위 두 원자적 쿼리를 호출하도록 재작성
- 더 이상 쓰이지 않게 된 `MemberCredential.increaseLoginFailCount()` / `lockUntil()` 엔티티 메서드는 삭제 (dead code 정리)

**검증**: 001-05에서 버그를 재현했던 것과 동일한 스크립트(8개의 잘못된 비밀번호 로그인을 `Promise.all`로 동시 발사)를 수정 후 재실행 →
```
statuses: [423, 401, 401, 423, 401, 423, 423, 401]
final login_fail_count: 8  locked_until: 2026-07-17T00:56:11.000Z
```
8번 실패가 정확히 8로 집계되고(유실 없음), 임계치를 넘은 시점부터 423 `ACCOUNT_LOCKED`가 정상적으로 섞여 나옴을 확인. `login.spec.js`에 회귀 테스트 "동시에 여러 번 틀린 비밀번호로 로그인해도 실패 카운트가 유실되지 않고 정확히 잠긴다" 추가.

### 4-2. GlobalExceptionHandler 내부 예외 노출/로그 없음 수정 (회원가입과 공유)
**원인**: catch-all `@ExceptionHandler(Exception.class)`가 `e.getMessage()`를 그대로 클라이언트 응답에 내려주고 서버 로그는 전혀 남기지 않았음. 회원가입 001-05 문서의 동시가입 버그를 재현하는 과정에서 SQL 구문·테이블/컬럼/제약조건명이 그대로 API 응답 JSON에 노출되는 것을 실제로 확인함.

**수정**: `GlobalExceptionHandler`에 SLF4J `Logger` 추가 → `log.error("Unhandled exception", e)`로 서버 로그에 전체 스택트레이스를 남기고, 클라이언트에는 `e.getMessage()` 대신 고정 문구("일시적인 오류가 발생했습니다. 잠시 후 다시 시도해주세요.")만 응답하도록 변경.

**검증**: 회원가입 001-05의 동시가입 재현 스크립트를 재실행하여 (a) 클라이언트 응답에 SQL이 더 이상 노출되지 않고 고정 문구만 오는 것, (b) 서버 로그(`ERROR ... GlobalExceptionHandler : Unhandled exception` + `org.springframework.dao.DataIntegrityViolationException: could not execute statement ...` 전체 스택트레이스)에는 원인이 그대로 남는 것을 둘 다 확인함.

## 6. 4차 구현 (2026-07-17): Redis 연동 일괄 반영
------------------------------------------------------------------------
Redis/Docker 인프라 구축(`docs/00.공통/Redis-Docker-구축-가이드.md`) 완료 후, [001-05.부족한-내용.md](001-05.부족한-내용.md)의 Redis 전환 계획을 실제로 구현함. 4장에서 DB 원자적 UPDATE로 고쳤던 로그인 잠금 로직을 Redis 기반으로 다시 옮기고, refresh token을 새로 구현했다.

### 6-1. 로그인 실패 카운트/잠금: DB → Redis
**왜 다시 옮기는가**: 4장의 DB 원자적 UPDATE 방식도 정확하게 동작하지만(lost update 없음), Redis 인프라가 이제 갖춰졌고 애초에 001-05 5장(당시 번호)에서 이쪽을 Redis로 옮기는 걸 계획해뒀던 부분이라 이번에 실제로 전환함. TTL 기반 잠금은 `locked_until` 컬럼과 `now()`를 비교하는 코드 자체가 없어져서 더 단순해짐.

**구현**:
- `LoginAttemptService`(신규, Redis 기반) — 기존 `LoginAttemptRecorder`(DB 기반) 대체, 해당 파일 삭제
  - `login:fail:{memberId}` 키를 `INCR`(원자적)로 증가
  - 실패 카운트가 임계치(5회) 이상이면 `login:lock:{memberId}` 키를 `SET NX EX 1800`(30분)로 설정 — `NX`라서 이미 잠긴 상태를 동시 요청이 다시 연장하지 않음
  - 로그인 성공 시 두 키 모두 `DEL`
  - 실패 카운트 키에는 안전장치로 24시간 TTL을 걸어, 재시도 없이 이탈한 계정의 키가 무한정 남지 않도록 함
- `MemberCredentialRepository`의 `incrementLoginFailCount()`/`lockIfNotAlreadyLocked()`(4장에서 추가했던 DB 원자적 쿼리)와 `MemberCredential`의 `isLocked()`/`resetLoginFailCount()` 메서드는 더 이상 쓰이지 않아 삭제. `login_fail_count`/`locked_until` DB 컬럼 자체는 스키마 호환을 위해 남겨두되, 더 이상 갱신하지 않음(주석으로 명시)
- 이제 Redis 연산이 JPA 트랜잭션 밖에서 일어나므로, 4장에서 썼던 "실패 기록을 별도 트랜잭션(REQUIRES_NEW)으로 커밋"하는 우회가 필요 없어짐(Redis는 애초에 JPA 트랜잭션 롤백 대상이 아님)

**검증**: 001-05에서 DB 방식 버그를 재현했던 것과 동일한 스크립트(잘못된 비밀번호 로그인 8개 동시 발사)를 Redis 전환 후 재실행 → `login:fail:{memberId}`가 정확히 8까지 증가하고, 임계치를 넘은 시점부터 423 `ACCOUNT_LOCKED`가 정상적으로 섞여 나옴을 확인. 기존 회귀 테스트(`login.spec.js`의 "동시에 여러 번 틀린 비밀번호..." 케이스)도 Redis 조회로 갈아끼운 뒤 그대로 통과.

### 6-2. Refresh Token 신규 구현 (Redis 기반)
**구현**:
- `RefreshTokenService`(신규) — `refresh:{memberId}` 키에 UUID 랜덤 문자열을 저장, TTL은 `jwt.refresh-expiration-days`(기본 14일)
  - `issue(memberId)`: 새 토큰 발급 및 저장(기존 값 덮어씀 → 1인 1세션)
  - `matches(memberId, token)`: Redis에 저장된 값과 일치하는지 확인
  - (로그아웃용 `revoke(memberId)`는 호출하는 곳이 없어 만들지 않음 — 로그아웃 API를 구현할 때 그때 추가. `redisTemplate.delete(key)` 한 줄이라 필요해지면 바로 추가 가능)
- 로그인 성공 시(`MemberServiceImpl.login()`) accessToken과 함께 refreshToken도 발급 → `LoginResponseDto`에 `refreshToken` 필드 추가
- `POST /api/members/refresh` 신규 엔드포인트 — `RefreshRequestDto(memberId, refreshToken)`를 받아 Redis에 저장된 값과 일치하면 새 accessToken 발급 + refreshToken도 회전(rotate, 재사용 방지)해서 `RefreshResponseDto(accessToken, refreshToken)`로 응답
- 신규 에러코드 `INVALID_REFRESH_TOKEN`(401) — 토큰 불일치, 존재하지 않음, 다른 회원의 memberId로 시도 등 모두 이 코드로 통일

**API 응답 변경**
Response (로그인 성공, 200):
```json
{ "success": true, "message": "로그인에 성공하였습니다.", "memberId": 1, "accessToken": "eyJ...", "refreshToken": "3fa2c1e0-..." }
```
Response (재발급 성공, 200):
```json
{ "success": true, "message": "토큰이 재발급되었습니다.", "accessToken": "eyJ...", "refreshToken": "9b1d..." }
```
Response (재발급 실패, 401):
```json
{ "success": false, "code": "INVALID_REFRESH_TOKEN", "message": "유효하지 않은 재발급 토큰입니다. 다시 로그인해주세요." }
```

**검증**: Playwright로 3개 케이스 추가 — (1) 정상 재발급 시 새 access/refresh token을 받고 Redis 값도 교체되며, 회전되어 무효화된 이전 refresh token으로 재요청하면 401이 나는 것, (2) 로그인한 적 없는 계정(Redis에 토큰 자체가 없음)의 재발급 시도가 401인 것, (3) A의 refresh token을 B의 memberId와 함께 보내면 401인 것 — 모두 통과 확인.

## 7. 5차 구현 (2026-07-19): 로그인 상태 유지(rememberMe)
------------------------------------------------------------------------
[001-02 11장](001-02.로그인-분석-설계.md#11-로그인-상태-유지remember me-설계-2026-07-19-요구사항-추가) 설계대로, refresh token TTL을 로그인 요청의 `rememberMe` 값에 따라 두 단계로 나눔.

### 7-1. 구현
- **`RefreshTokenService`**: 생성자에 `jwt.refresh-expiration-hours-short`(신규 설정값, 기본 24시간) 추가 — 기존 `jwt.refresh-expiration-days`(기본 14일)는 그대로 유지
  - `issue(memberId)` → `issue(memberId, boolean rememberMe)`로 시그니처 변경. Redis 값 형식을 기존 `"{token}"`에서 `"{token}:{tier}"`(`LONG`/`SHORT`)로 바꿔, tier를 토큰과 함께 저장
  - `matches(memberId, token)`은 저장된 값에서 tier를 떼고 토큰만 비교하도록 수정(기존 호출부는 변경 없음)
  - `isRememberMe(memberId)`(신규): 현재 저장된 토큰의 tier가 `LONG`인지 확인 — `refresh()`가 회전 전에 이 값을 읽어서 재발급 시 같은 tier를 유지하는 데 사용
- **`LoginRequestDto`**: `rememberMe`(Boolean, 선택값, 검증 어노테이션 없음) 필드 추가
- **`MemberServiceImpl.login()`**: `Boolean.TRUE.equals(request.getRememberMe())`로 boolean 변환 후 `issue(memberId, rememberMe)` 호출 — `null`(필드 생략)은 `false`(짧은 세션)로 처리됨
- **`MemberServiceImpl.refresh()`**: 토큰 검증(`matches`) 직후, 회전(재발급) 전에 `refreshTokenService.isRememberMe(memberId)`로 현재 tier를 읽어 그대로 `issue()`에 넘김 — 클라이언트가 재발급 요청마다 `rememberMe`를 다시 보낼 필요 없음
- **`SocialLoginServiceImpl`**: [006(소셜로그인)](../06.소셜로그인/001-02.소셜로그인-분석-설계.md)은 체크박스가 있는 폼이 아니라 리다이렉트 콜백이라, `issue(memberId, true)`로 고정 호출해 기존 동작(항상 14일)을 그대로 유지함(001-02 11-4장)

신규 `ErrorCode` 없음.
