## 1. 요구사항 정리
------------------------------------------------------------------------
- 입력값: 이메일, 비밀번호
- **(2026-07-19 요구사항 추가) 로그인 상태 유지 체크박스** — 11장 참고
- 입력받은 비밀번호를 Argon2로 암호화한 뒤 DB에 저장된 password_hash와 대조
- 이메일 존재 여부, 비밀번호 일치 여부를 확인
- 불일치(이메일 없음 / 비밀번호 틀림) 시 동일하게 "아이디 또는 비밀번호가 일치하지 않습니다" 응답 (계정 존재 여부 노출 방지)
- 일치 시 "로그인에 성공하였습니다" 응답 (메인 페이지 이동은 프론트 미개발로 이번 범위 제외)
- 프론트 연결 없음 → REST API + Postman/테스트 코드로 검증

------------------------------------------------------------------------
## 2. 전체 플로우
------------------------------------------------------------------------
1) 클라이언트가 이메일 + 비밀번호로 로그인 요청
2) email로 members 조회
   - 없으면 → 로그인 실패 처리(회원가입과 달리 이메일 존재 여부를 노출하지 않도록 INVALID_CREDENTIALS로 통일)
3) 조회된 member_id로 member_credentials 조회
   - 없으면(가입 미완료 상태) → 마찬가지로 INVALID_CREDENTIALS 처리
4) 입력한 비밀번호를 Argon2(PasswordEncoder.matches)로 password_hash와 대조
   - 불일치 → INVALID_CREDENTIALS 처리, "아이디 또는 비밀번호가 일치하지 않습니다"
   - 일치 → "로그인에 성공하였습니다" 응답
5) (선택) members.status 확인 - WITHDRAWN/SUSPENDED 회원은 로그인 거부

※ member_credentials.login_fail_count / locked_until 컬럼은 이미 스키마에 존재하나,
   요구사항 문서에 잠금 정책이 명시되지 않아 이번 구현 범위에서는 값 갱신을 하지 않고 추후 과제로 남김 (9. 확인 필요 사항 참고)

## 3. 패키지 구조
------------------------------------------------------------------------
기존 회원가입 기능과 동일 패키지(`com.foodtrip.foodsearch`)에 로그인 관련 파일만 추가

com.foodtrip.foodsearch
 ├─ member
 │   ├─ controller  : MemberController (기존 파일에 로그인 엔드포인트 추가)
 │   ├─ service     : MemberService, MemberServiceImpl (기존 파일에 login() 추가)
 │   ├─ dto         : LoginRequestDto, LoginResponseDto (신규)
 │   ├─ entity      : Member, MemberCredential (기존 그대로 사용)
 │   └─ repository  : MemberRepository, MemberCredentialRepository (기존 그대로 사용)
 └─ common
     ├─ exception   : ErrorCode (INVALID_CREDENTIALS 추가), CustomException, GlobalExceptionHandler (기존 그대로 사용)
     └─ config      : SecurityConfig (Argon2 Bean, 기존 그대로 사용)

신규 엔티티/리포지토리/설정 없이 기존 회원가입 구현 자산을 그대로 재사용

## 4. 데이터 모델
------------------------------------------------------------------------
[DB-테이블설계.md](../00.공통/DB-테이블설계.md) 기준, 로그인 기능은 아래 2개 테이블만 조회

### 4-1. members (회원) - 조회만 수행
| 컬럼명 | 타입 | 설명 |
|---|---|---|
| member_id | BIGINT UNSIGNED | PK |
| email | VARCHAR(255) | 로그인 조회 키 |
| status | VARCHAR(20) | ACTIVE/SUSPENDED/WITHDRAWN (선택적으로 로그인 차단 판단에 사용) |

### 4-2. member_credentials (인증정보) - 조회만 수행 (이번 범위에서는 갱신 없음)
| 컬럼명 | 타입 | 설명 |
|---|---|---|
| member_id | BIGINT UNSIGNED | FK→members, UNIQUE |
| password_hash | VARCHAR(255) | Argon2 해시값, matches()로 대조 |
| login_fail_count | INT UNSIGNED | 이번 범위 미사용(값 갱신 안 함) |
| locked_until | DATETIME | 이번 범위 미사용 |

## 5. API 설계
------------------------------------------------------------------------
### 5-1. 로그인
POST /api/members/login
Request:
{
  "email": "user@naver.com",
  "password": "P@ssw0rd!"
}
Response (성공, 200):
{ "success": true, "message": "로그인에 성공하였습니다.", "memberId": 1 }
Response (실패, 401):
{ "success": false, "message": "아이디 또는 비밀번호가 일치하지 않습니다." }

처리:
 - 입력값 유효성 검사 (이메일 형식, 비밀번호 공백 여부)
 - email로 members 조회 → 없으면 INVALID_CREDENTIALS
 - member_id로 member_credentials 조회 → 없으면 INVALID_CREDENTIALS
 - passwordEncoder.matches(입력 비밀번호, password_hash) → 불일치 시 INVALID_CREDENTIALS
 - 일치 시 LoginResponseDto(true, "로그인에 성공하였습니다.", memberId) 반환
 - (선택) members.status가 ACTIVE가 아니면 INVALID_CREDENTIALS 또는 별도 에러코드로 차단

## 6. 검증 규칙
------------------------------------------------------------------------
- 이메일: 형식 검증(@Email), 필수값(@NotBlank)
- 비밀번호: 필수값(@NotBlank), 별도 형식 검증은 로그인 단계에서 불필요(가입 시 이미 검증됨) - 단, 과도하게 긴 입력값(DoS성 입력) 방지를 위해 최대 길이 정도만 제한

------------------------------------------------------------------------
## 7. Argon2 검증 설계
------------------------------------------------------------------------
- 회원가입에서 등록된 `PasswordEncoder`(Argon2PasswordEncoder) Bean을 동일하게 주입받아 사용 ([SecurityConfig.java](../../Project2/src/main/java/com/foodtrip/foodsearch/common/config/SecurityConfig.java))
- 암호화(encode)는 회원가입에서만 수행하고, 로그인에서는 `passwordEncoder.matches(rawPassword, encodedPassword)`로 대조만 수행
- matches() 내부적으로 저장된 해시 문자열에 포함된 salt/파라미터를 그대로 사용하므로 별도 처리 불필요

## 9. 확인이 필요한 사항
------------------------------------------------------------------------
- 로그인 실패 시 login_fail_count 증가 및 locked_until 계정 잠금 정책 적용 여부 (요구사항 문서에 명시 없음, 컬럼은 이미 존재)

- members.status가 SUSPENDED/WITHDRAWN인 경우 로그인 차단 처리 여부 및 이 경우 노출할 메시지(계정 상태를 노출할지, 동일하게 실패 메시지로 통일할지)

## 11. 로그인 상태 유지(rememberMe) 설계 (2026-07-19 요구사항 추가)
------------------------------------------------------------------------
"로그인 상태 유지" 체크박스를 켜면 로그인이 오래 유지되고, 끄면(또는 아무것도 선택하지 않으면) 짧게 유지되도록 해달라는 요구사항. 이 문서가 작성된 시점(1~10장)에는 JWT/refresh token 자체가 없었고, 이후 [001-03 6-2장](001-03.로그인-구현-테스트.md#6-2-refresh-token-신규-구현-redis-기반)에서 refresh token이 추가되었으므로, 이번 설계는 그 refresh token의 TTL(Redis 만료시간)을 요청에 따라 두 단계로 나누는 방식으로 구현한다.

### 11-1. 전체 플로우
1) 로그인 요청에 `rememberMe`(boolean, 선택값) 필드를 추가로 받음
2) `rememberMe: true` → refresh token을 긴 TTL(기존과 동일, 기본 14일)로 발급
3) `rememberMe: false` 또는 필드 생략 → refresh token을 짧은 TTL(신규, 기본 24시간)로 발급
4) **토큰 재발급(`POST /api/members/refresh`) 시에는 클라이언트가 `rememberMe`를 다시 보내지 않는다** — 서버가 현재 저장된 refresh token의 tier(LONG/SHORT)를 Redis에서 읽어, 회전(rotate) 후에도 같은 tier를 그대로 유지한다. 재발급마다 클라이언트가 최초 선택을 기억해뒀다가 매번 실어 보내야 하는 부담을 없앰

### 11-2. Redis 저장 방식 변경
기존 `RefreshTokenService`는 `refresh:{memberId}` 키에 토큰 문자열만 저장했는데, tier 정보를 함께 저장해야 회전 시에도 tier를 유지할 수 있다. 값 형식을 `"{token}:{tier}"`(예: `"3fa2c1e0-...:LONG"`)로 바꾸고, 토큰 비교(`matches()`)는 tier 부분을 잘라내고 비교한다. DB 테이블이 아니라 Redis TTL 자체로 관리하는 기존 설계([001-03 6-2장](001-03.로그인-구현-테스트.md#6-2-refresh-token-신규-구현-redis-기반))는 그대로 유지.

### 11-3. accessToken(JWT)은 영향 없음
accessToken의 유효기간(기본 60분)은 `rememberMe`와 무관하게 항상 고정이다. "로그인 상태 유지"는 재로그인 없이 얼마나 오래 새 accessToken을 계속 발급받을 수 있는지(=refresh token 수명)에만 영향을 준다 — accessToken 자체를 더 오래 유지하는 방식은 채택하지 않음(탈취 시 피해 범위를 짧게 유지하려는 기존 JWT 설계 원칙 그대로 따름).

### 11-4. 소셜로그인은 대상 밖
[006(소셜로그인)](../06.소셜로그인/)은 폼이 아니라 플랫폼 리다이렉트 콜백이라 체크박스를 넣을 화면 자체가 없음 — 소셜로그인은 항상 긴 세션(`rememberMe=true` 취급)으로 발급해 기존 동작(14일)을 그대로 유지한다.

### 11-5. 검증 규칙
| 필드 | 규칙 |
|---|---|
| rememberMe | 선택값(boolean). 생략하거나 `false`면 짧은 세션, `true`면 긴 세션. 별도 형식 검증 불필요 |

### 11-6. 확인이 필요한 사항
- **짧은 세션의 정확한 길이(기본 24시간)**: 요구사항에 구체적인 시간이 명시되지 않아 임의로 24시간(하루)을 기본값으로 잡음 — "브라우저를 닫으면 로그아웃"과 가장 가까운 백엔드 쪽 근사치로 판단했으나, 실제로는 더 짧게(예: 시간 단위) 또는 더 길게 조정이 필요할 수 있음
- **"브라우저 종료 시 로그아웃"은 백엔드만으로 구현 불가**: 짧은 TTL을 주는 것은 "그 시간이 지나면 자동 만료"일 뿐, 사용자가 브라우저를 닫는 시점을 서버가 알 방법이 없음 — 실제로 "브라우저 닫으면 즉시 로그아웃"을 원한다면 프론트에서 `refreshToken`을 `sessionStorage`(탭/창 종료 시 사라짐)에 저장하는 방식과 병행해야 함(001-04 참고)
- **accessToken TTL도 rememberMe에 따라 늘릴지**: 이번 설계는 accessToken을 건드리지 않기로 했으나, 요구사항이 "완전히 로그인 상태 유지"를 의도한 것이라면 accessToken 재발급 주기(프론트가 얼마나 자주 refresh를 호출해야 하는지)에 대한 별도 논의가 필요할 수 있음
