### 1-3. 설계 문서 작성 이후 구현 중 새로 발견한 사항 — 미인증 회원 정리 배치가 소셜 계정을 삭제할 뻔함
설계 문서(001-02)에서는 다루지 않았던, 구현 중 코드를 다시 살펴보다 발견한 심각한 버그 가능성이다.

기존 [회원가입 기능](../01.회원가입/001-03.회원가입-구현-테스트.md)에는 `UnverifiedMemberCleanupScheduler`가 있어, 매시 정각에 `member_credentials`가 없는 회원 row를 "회원가입을 끝까지 완료하지 않고 이탈한 회원"으로 간주해 24시간 뒤 자동 삭제한다. 그런데 **소셜로그인 계정은 설계상 원래부터 비밀번호가 없어 `member_credentials`가 영구히 생성되지 않는다** — 즉 이 스케줄러 기준으로는 소셜 계정도 "미완료 이탈 회원"과 똑같이 보여서, 아무 문제 없이 정상적으로 쓰이고 있는 소셜 계정이 가입 24시간 뒤에 통째로 삭제될 뻔했다.

**수정**: `MemberRepository.findUnverifiedMemberIdsCreatedBefore()` 쿼리에 `AND m.memberId NOT IN (SELECT sa.memberId FROM SocialAccount sa)` 조건을 추가해 소셜 계정을 정리 대상에서 제외했다.

### 1-4. 설계 대비 실제 구현 확정 사항 (001-02 8장 "확인이 필요한 사항" 중 구현 단계에서 결정한 것)
- **닉네임 자동 보정 알고리즘**(8장 미확정 항목): `SocialLoginServiceImpl.normalizeNickname()`/`resolveUniqueNickname()`로 구현. 플랫폼이 준 닉네임에서 한글/영문/숫자만 남기고(정규식 `[^가-힣a-zA-Z0-9]` 제거) 10자로 자르며, 빈 값이 되면 `"user"`로 대체한다. 이미 쓰이는 닉네임이면 뒤에 숫자를 붙이되(1, 2, 3...) 10자를 넘지 않도록 base 문자열을 필요한 만큼 잘라서 붙인다.
- **구글 닉네임 소스**(8장 미확정 항목): 구글은 별도 "닉네임" 필드가 없어 `name`(성명)을 후보로 쓰고, 그마저 없으면(이론상 거의 없음) 위 정규화 로직에서 이메일 로컬파트로 대체된다.
- **동일 이메일의 타 플랫폼 소셜 계정 충돌**(8장 미확정 항목) — **(2026-07-22 정책 변경)**: 처음엔 "자동
  연결하지 않고 거부"로 구현했었으나, 실사용 중 정확히 이 상황(일반 가입 이메일로 카카오 로그인)을 겪고
  나서 "그냥 계정 연동으로 해달라"고 확정 지시받아 구현을 바꿈. `SocialLoginServiceImpl.handleCallback()`의
  `else` 분기(신규 소셜 연동 시도)에서 `memberRepository.existsByEmail()` 체크 후 바로 예외를 던지던 것을,
  `memberRepository.findByEmail()`로 그 기존 회원을 찾아 `checkAccountStatus()`(정지/탈퇴 계정 가드는 유지)
  통과 후 그 회원에 새 `SocialAccount` 행을 연결하고 그 회원으로 로그인시키는 방식으로 교체함(001-02
  2-4-1장 참고). `EMAIL_ALREADY_REGISTERED` 에러 코드는 이제 이 흐름에서 발생하지 않음.
- **전화번호 중복 시 처리**(001-02에 명시되지 않았던 세부사항): 네이버가 준 전화번호가 이미 다른 회원이 쓰고 있으면(phone_hash 중복), 소셜 로그인 자체를 실패시키지 않고 전화번호 자동 채움만 건너뛰도록 구현함 — 사용자는 필요하면 [회원정보수정](../05.회원정보수정/)에서 인증 후 직접 등록할 수 있음.
- **네이버 unlink-callback 실제 파라미터 스펙**(8장 미확정 항목): 여전히 확인되지 않아, 일단 어떤 파라미터가 오든 로그만 남기고 200으로 응답하는 최소 구현(스텁)으로 남겨둠 — 4장 "남은 작업" 참고.

### 2-1. 테스트 방식의 근본적인 제약 — 실제 플랫폼 로그인 동의화면은 자동화할 수 없음
카카오/네이버/구글의 OAuth 인가(authorize) 단계는 실제 사용자가 브라우저에서 로그인하고 "동의" 버튼을 눌러야 `code`가 발급된다. Playwright 같은 API 테스트 도구로는(또는 브라우저 자동화로도) 이 동의화면을 우회할 방법이 없어, **콜백의 "성공 happy path"(신규가입/기존로그인/토큰 발급까지 전부 성공)는 자동화 테스트(Playwright 스위트)에는 포함하지 못했다.** 이는 이 프로젝트에서 기존에 뿌리오 SMS 실발송을 자동화하지 못했던 것([001-03(회원가입) 6-2장](../01.회원가입/001-03.회원가입-구현-테스트.md#6-2-실제-sms-발송은-검증하지-않음-의도된-범위-제한))과 같은 종류의, 외부 서비스 의존으로 인한 의도된 범위 제한이다.

대신 자동화 스위트는 아래 두 가지 방식으로 실제 코드 경로를 최대한 검증했고(2-2장), **카카오 happy path는 2026-07-19에 실사용자(개발자 본인) 계정으로 수동 확인까지 완료했다(2-4장).**
1. **실제 플랫폼 API를 그대로 호출하되, 성공하지 않아도 되는 부분만 검증**: 인가 URL 생성(`GET /api/auth/{provider}/authorize`)은 실제로 각 플랫폼의 인가 서버로 302 리다이렉트되는 것까지 확인 가능하고, 콜백에 **유효한 state + 가짜 code**를 실제로 보내면 카카오/네이버/구글의 실제 토큰 발급 API가 각자의 방식으로 "코드 자체가 무효하다"는 오류를 반환한다(카카오는 `invalid_grant`/`authorization code not found`(KOE320), 네이버는 `no valid data in session`, 구글은 `invalid_grant`/`Malformed auth code`) — 이 응답을 우리 코드가 의도한 대로 `SOCIAL_LOGIN_FAILED`로 변환하는지는 실제 네트워크 호출로 검증됨. (카카오는 최초 테스트 시 이와 다른 `invalid_client` 오류가 나 원인을 조사·수정했다 — 3장 참고)
2. **로그인 이후 로직은 JWT를 직접 발급해 검증**: `jwtHelper.js`(신규)에 `JwtProvider.generateAccessToken()`과 동일한 HS256 서명 방식으로 accessToken을 직접 만드는 `mintAccessToken()`을 추가하고, `dbHelper.js`에 `insertSocialAccount()`(신규), `redisHelper.js`에 `activateAccessToken()`(신규, `AccessTokenSessionService.register()`와 동일하게 Redis에 세션 등록)을 추가해 "이미 소셜로그인이 된 상태"를 직접 만든 뒤, 회원정보수정 비밀번호 변경 차단 가드와 연동 해제 로직을 검증했다. (기존 이메일/전화번호 인증을 DB에 직접 시딩해 우회 검증해온 이 프로젝트의 기존 패턴과 같은 접근이다.)

### 2-4. 카카오 실사용자 로그인 수동 검증 (2026-07-19, happy path 최초 확인)
3장의 `client_secret` 수정 이후, 개발자 본인의 실제 카카오 계정으로 `http://localhost:8081/api/auth/kakao/authorize`에 브라우저로 접속해 로그인 동의화면까지 통과하는 전체 플로우를 수동으로 확인했다. 2-1장에서 설명한 자동화 한계(실제 로그인 동의화면은 Playwright로 우회 불가) 때문에 여태 자동화 스위트에는 포함하지 못했던 "성공 happy path"가 실사용자 계정으로는 처음 확인된 것이다.

**결과**: `GET /oauth/kakao` 콜백이 200과 함께 기존 `LoginResponseDto` 형식 그대로 응답함을 확인.
```json
{ "success": true, "message": "로그인에 성공하였습니다.", "memberId": 992,
  "accessToken": "eyJhbGciOiJIUzUxMiJ9...", "refreshToken": "44c0cbbe-59f5-4161-a812-06816ba077a9" }
```

DB에 직접 접속해 생성된 row를 확인한 결과, 설계(001-02 2-3장/4-1장) 그대로 반영됨을 확인:
- `members`: 카카오 계정의 실제 이메일로 신규가입, `status='ACTIVE'`, 닉네임은 카카오 프로필의 실명이 그대로 반영됨(카카오 계정에 별도 "닉네임"이 설정돼 있지 않아 `properties.nickname` 대신 실명이 내려온 것으로 추정 — 이 값 자체를 서버가 다듬거나 검증하지 않고 그대로 신뢰함), `phone`은 카카오가 전화번호를 안 줘서 설계대로 `null`
- `social_accounts`: `provider='KAKAO'`, 카카오가 발급한 `provider_user_id`/`access_token`/`refresh_token`/`token_expired_at`이 전부 정상 저장됨

이 확인으로 3장에서 미확인 상태로 남겨뒀던 "카카오 로그인 리다이렉트 URI 미등록" 우려도 함께 해소됨 — 실제로는 등록돼 있었거나(콘솔 화면 캡처 당시와 달라졌을 가능성) 등록 없이도 동작하는 상태였던 것으로 보인다(4장 "남은 작업"에서 이 항목 제거함).

**참고**: 네이버/구글은 이번에 실사용자 확인을 진행하지 않아 여전히 happy path가 미검증 상태다(4장 참고).

## 3. 카카오 `invalid_client` 오류 원인 확인 및 수정 (2026-07-19)
------------------------------------------------------------------------
2-1장의 카카오 콜백 테스트에서, 유효한 `state` + 가짜 `code`로 카카오 토큰 발급 API를 호출했을 때 코드가 가짜라서 나는 것과는 다른 종류의 오류(`invalid_client`/`Bad client credentials`/`KOE010`)가 처음 확인됐었다.

**원인 확인**: 사용자가 카카오 개발자 콘솔 화면을 직접 캡처해 확인해준 결과, "카카오 로그인" 클라이언트 시크릿이 **활성화(ON)** 상태였고(코드: `GEx2v7MWuTDFLlofbBeCDYRb4LxBF3cS`), 이번 최초 구현은 요청사항 원문에 시크릿 값이 없어 `client_secret` 파라미터 없이 호출하고 있었던 것이 원인이었다.

**수정**: `KakaoOAuthClient`가 `oauth.kakao.client-secret`(신규 설정값, `KAKAO_CLIENT_SECRET` 환경변수) 를 토큰 발급 요청(`POST https://kauth.kakao.com/oauth/token`)의 `client_secret` 폼 파라미터로 포함하도록 수정. `.env`/`.env.example`/`application.yml`에 반영함.

**수정 후 재확인**: 동일한 방식(유효한 state + 가짜 code)으로 다시 테스트하니 오류가 `invalid_client`(KOE010, 인증 정보 자체 오류)에서 `invalid_grant`/`authorization code not found`(KOE320, "코드가 가짜라서 나는 정상적인 거부")로 바뀜 — 네이버/구글이 가짜 코드에 보이던 반응(`no valid data in session`, `invalid_grant`)과 같은 종류가 되어, client_id/client_secret 조합 자체는 더 이상 문제가 없음을 확인함.

**후속 확인(2-4장)**: 카카오 로그인 리다이렉트 URI 미등록 우려도 실사용자 테스트로 해소됨 — `client_secret` 수정만으로 실제 로그인이 끝까지 정상 동작함을 확인함(2-4장 참고).

## 4. 프로필 사진 자동 채움 구현 (2026-07-19)
------------------------------------------------------------------------
[001-02 1장/2-3-6장/2-4-4장](001-02.소셜로그인-분석-설계.md) 설계대로, 신규 가입 시점에 플랫폼이 준 프로필 사진 URL을 그대로 저장하도록 구현함. 파일 저장/서빙/수정 API 자체는 [005(회원정보수정) 001-03 4장](../05.회원정보수정/001-03.회원정보수정-구현-테스트.md#4-3차-구현-2026-07-19-프로필-사진-등록변경삭제)에서 구현했고, 이 기능에서는 그 결과물에 값만 채워 넣음.

### 4-1. 구현
- **`SocialUserProfile`**(record)에 `profileImageUrl` 필드 추가
- **`KakaoOAuthClient`**: `kakao_account.profile.profile_image_url`에서 파싱
- **`NaverOAuthClient`**: `response.profile_image`에서 파싱
- **`GoogleOAuthClient`**: `picture`에서 파싱
- **`Member.createSocial(email, nickname, profileImageUrl)`**: 파라미터 추가, `SocialLoginServiceImpl.createSocialMember()`에서 `profile.profileImageUrl()`을 그대로 전달

신규 `ErrorCode` 없음 — 플랫폼이 사진 URL을 안 줘도(드묾) 그냥 `null`로 저장되고 가입 자체는 실패하지 않는다.

### 4-2. 실사용자 검증 결과
[001-03 2-4장](001-03.소셜로그인-구현-테스트.md#2-4-카카오-실사용자-로그인-수동-검증-2026-07-19-happy-path-최초-확인)에서 실사용자 계정(memberId 992)으로 카카오 로그인을 확인했던 시점은 이 프로필 사진 기능을 구현하기 **이전**이라, 그 계정의 `profile_image_url`은 여전히 `null`이다(소급 반영되지 않음 — 정상). 이 기능 구현 이후 새로 가입하는 카카오/네이버/구글 계정부터 적용된다. Playwright 자동화로는 실제 플랫폼 동의화면을 거칠 수 없어([001-03 2-1장](#2-1-테스트-방식의-근본적인-제약--실제-플랫폼-로그인-동의화면은-자동화할-수-없음)와 동일한 이유) 이 필드가 실제로 채워지는 것까지는 자동/수동 어느 쪽으로도 재검증하지 않음 — 코드 리뷰 수준으로만 확인됨(5장 "남은 작업" 참고).

## 5. 구글 프로필 사진 URL 저장 실패 버그 수정 (2026-07-20)
------------------------------------------------------------------------
4장 구현 이후 실사용자 계정으로 구글 로그인(`GET /api/auth/google/authorize`)을 실제로 시도하던 중(다른 컴퓨터 환경, 4-2장에서 남겨뒀던 "실사용자 미검증" 항목을 실제로 검증하려던 시도), 매번 `500 SOCIAL_LOGIN_FAILED`("회원 생성 중 충돌이 발생했습니다. 다시 시도해주세요: null")로 신규가입 자체가 실패하는 것을 발견함.

**원인 확인**: 서버 로그에서 실제 원인을 확인한 결과, MariaDB 에러 `1406 Data too long for column 'profile_image_url'` — 구글이 내려주는 프로필 사진 URL(`picture` 필드)이 `members.profile_image_url` 컬럼(`VARCHAR(500)`, [DB-테이블설계.md](../00.공통/DB-테이블설계.md)의 최초 설계값)보다 길어서 INSERT 자체가 실패하고 있었음. `SocialLoginServiceImpl.createSocialMember()`의 `catch (DataIntegrityViolationException e)` 블록이 부르는 `extractConstraintName()`은 유니크 제약 위반(`ConstraintViolationException`)만 잡아내도록 만들어져 있어서, 이런 "컬럼 길이 초과" 종류의 예외는 원인 이름을 못 뽑아내 메시지에 `null`로 나왔던 것 — 문제의 원인을 더 알기 어렵게 만들고 있었음.

**수정**:
1. `Member.profileImageUrl` 컬럼 길이를 `VARCHAR(500)` → `VARCHAR(2000)`으로 확장(`ddl-auto=update`로 자동 `ALTER TABLE`, [005(회원정보수정) 001-02 4-3장](../05.회원정보수정/001-02.회원정보수정-분석-설계.md#4-3-members--스키마-변경-없음)/[DB-테이블설계.md](../00.공통/DB-테이블설계.md) 동시 갱신)
2. `SocialLoginServiceImpl.createSocialMember()`의 catch 블록에 `log.error(...)`를 추가해, `extractConstraintName()`이 원인을 못 찾는 경우에도 서버 로그에서 실제 예외를 바로 확인할 수 있도록 함(이번처럼 메시지에 `null`만 찍혀서 원인 파악이 늦어지는 상황 재발 방지)

**검증**: 수정 후 재기동 시 `alter table if exists members modify column profile_image_url varchar(2000)` DDL이 정상 적용됨을 로그로 확인. 실사용자 구글 로그인 재시도로 최종 확인 예정(4-2장/6장 "남은 작업" 갱신).
