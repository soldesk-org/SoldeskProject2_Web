## 1. 요구사항 정리
------------------------------------------------------------------------
- 대상 소셜 플랫폼: 카카오, 네이버, 구글 3종
- 각 플랫폼에서 받아오는 값
  | 플랫폼 | 받아오는 값 |
  |---|---|
  | 네이버 | 이메일, 별명(닉네임), 휴대전화번호, 프로필 사진 |
  | 구글 | 이메일, 개인정보(프로필 — 이름 등), 프로필 사진(`.../auth/userinfo.profile` 스코프로 조회, **구글 계정 특성상 사실상 항상 제공됨**) |
  | 카카오 | 이메일, 닉네임, 프로필 사진(`profile_image`) |
- **(2026-07-19 요구사항 추가) 프로필 사진**: 세 플랫폼 모두 제공(구글은 사실상 필수, 나머지는 선택) — 신규가입 시점에 플랫폼이 준 URL을 그대로 회원 정보에 반영. 실제 파일 저장/서빙/수정 API는 [005.회원정보수정 001-02 2-8장](../05.회원정보수정/001-02.회원정보수정-분석-설계.md#2-8-프로필-사진-등록변경삭제-2026-07-19-요구사항-추가)에서 구현한 것을 그대로 재사용 — 이 문서에서는 "가입 시점에 플랫폼 URL을 어떻게 반영하는지"만 다룸(2-3-6장)
- 소셜로그인은 받아온 정보를 그대로 써서 자동으로 회원가입/로그인 처리 — 회원가입 때처럼 별도 입력을 받거나 이메일/전화번호 인증을 다시 요구하지 않음
- **이메일 충돌 처리**: 이미 일반(이메일+비밀번호) 회원가입이 되어 있는 이메일로 소셜로그인을 시도하면 실패 처리하고, "이미 생성된 계정이 있으니 그 계정으로 로그인하라"고 안내해야 함
- **소셜 계정은 비밀번호 수정 불가** ([001-02(회원정보수정) 1-1장](../05.회원정보수정/001-02.회원정보수정-분석-설계.md#1-1-소셜-로그인-가드에-대한-판단)에서 "소셜로그인 기능이 만들어지는 시점에 함께 추가"하기로 미뤄둔 항목 — 이번 기능에서 실제로 구현)
- 소셜로그인으로 끌고 오지 못한 값(예: 카카오/구글은 전화번호를 안 줌)은 [회원정보수정](../05.회원정보수정/) 화면에서 추가로 등록할 수 있으나, 그 값은 반드시 인증을 거쳐야 함 → 이미 구축된 `PATCH /api/members/me` + 이메일/전화번호 인증 API를 그대로 재사용(신규 개발 불필요, 2-5장 참고)
- 플랫폼별 연동 해제(unlink) 기능 필요 (2-6장 참고)
- 프론트 연결 없음 → REST API + Postman/테스트 코드로 검증

## 2. 전체 플로우
------------------------------------------------------------------------
### 2-1. 로그인 시작 (프론트 → 각 플랫폼 인가 화면으로 이동)
1. 프론트에서 `GET /api/auth/{provider}/authorize` 호출(또는 이 주소로 그냥 이동)
2. 서버는 CSRF 방지용 `state` 값을 생성해 Redis에 단기 저장하고, 그 플랫폼의 인가 URL(`client_id`, `redirect_uri`, `scope`, `state` 포함)로 **302 리다이렉트**
3. 사용자가 그 플랫폼 로그인/동의 화면에서 로그인 및 정보 제공에 동의

`{provider}`는 `kakao`/`naver`/`google` 중 하나.

### 2-2. 콜백 처리 (플랫폼 → 우리 서버로 인가코드 전달)
1. 플랫폼이 요청사항에 명시된 콜백 URL(`GET /oauth/{provider}?code=...&state=...`)로 사용자를 리다이렉트시킴 — **이 URL은 각 플랫폼 개발자 콘솔에 등록된 값 그대로 써야 하므로 `/api/...` 프리픽스를 붙이지 않고 요청사항의 경로를 그대로 사용**(5장 참고)
2. `state` 값이 2-1에서 Redis에 저장해둔 값과 일치하는지 확인(불일치/만료 시 `INVALID_OAUTH_STATE`)
3. 받은 인가코드(`code`)로 플랫폼의 토큰 발급 API를 호출해 그 플랫폼의 `access_token`(+ `refresh_token`) 획득
4. 그 `access_token`으로 플랫폼의 사용자 정보 조회 API를 호출해 이메일/닉네임/전화번호(있는 경우) 획득
5. 3~4단계 중 하나라도 실패(네트워크 오류, 플랫폼 응답 오류 등)하면 `SOCIAL_LOGIN_FAILED`
6. 조회한 이메일로 기존 회원 여부 판단 후 2-3(신규가입)/2-4(기존로그인) 중 하나로 분기
7. 우리 서비스의 `accessToken`/`refreshToken`(JWT + Redis, 기존 로그인 인프라 그대로 재사용)을 발급해 응답

### 2-3. 신규 가입 (그 이메일로 가입된 회원이 아예 없는 경우)
1. `Member.createPending(email)` 대신, 소셜 전용 생성 메서드로 즉시 `ACTIVE` 상태의 회원을 만듦(이메일 인증 절차 없이 바로 확정 — 요구사항상 소셜 정보는 재인증하지 않으므로 회원가입의 "PENDING → 인증 → 확정" 2단계가 필요 없음)
2. 닉네임: 플랫폼이 준 닉네임을 쓰되, 이미 DB에 있는 닉네임과 겹치면 뒤에 임의 숫자를 붙여 유일하게 만듦(구글처럼 닉네임을 안 주는 경우엔 이메일 로컬파트를 기반으로 생성 — 8장에서 최종 확인 필요)
3. 전화번호: 네이버만 제공 — 있으면 회원가입과 동일하게 AES-256-GCM 암호화 + HMAC 해시 후 저장, 없으면 `null`(회원가입 때와 달리 소셜 신규가입은 전화번호가 선택값)
4. `member_credentials` row는 만들지 않음(비밀번호 자체가 없는 계정 — 1-1장의 "비밀번호 수정 불가" 근거이자, 4-2장에서 다룰 소셜 계정 판별 기준)
5. `social_accounts`에 `provider`/`provider_user_id`/플랫폼 토큰을 저장(4-1장)
6. **(2026-07-19 요구사항 추가) 프로필 사진**: 플랫폼이 준 사진 URL을 그대로 `members.profile_image_url`에 저장 — [005(회원정보수정)](../05.회원정보수정/)처럼 우리 서버로 파일을 내려받아 복사하지 않고 외부 URL 문자열만 저장한다(간단함 우선, 플랫폼이 그 URL을 계속 유효하게 유지해준다고 가정). 값이 없으면(드묾) `null` — **(2026-07-19 확정)** 이 경우 프론트가 [005 2-8-3장](../05.회원정보수정/001-02.회원정보수정-분석-설계.md#2-8-프로필-사진-등록변경삭제-2026-07-19-요구사항-추가)처럼 닉네임 첫 글자 이니셔널 배지를 표시함(서버가 대체 이미지를 내려주지 않음)
7. 2-2-7의 우리 서비스 토큰 발급으로 진행

### 2-4. 기존 로그인 (이미 같은 `provider`+`provider_user_id`로 연동된 회원)
1. `social_accounts`에서 `(provider, provider_user_id)`로 회원을 바로 찾음(이메일 재조회 불필요 — 사용자가 그 사이 이메일을 바꿨을 수도 있으므로 이 조합을 우선 신뢰)
2. 계정 상태 확인: `SUSPENDED`면 `ACCOUNT_SUSPENDED`, `WITHDRAWN`이면 `ACCOUNT_WITHDRAWN` (일반 로그인과 동일한 기존 로직 재사용, [001-02(로그인)](../02.로그인/001-02.로그인-분석-설계.md) 참고) — 소셜로그인은 비밀번호가 없어 로그인 실패 잠금(`LoginAttemptService`)은 애초에 적용 대상이 아님
3. `social_accounts`의 플랫폼 토큰(`access_token`/`refresh_token`/`token_expired_at`)을 최신 값으로 갱신
4. **닉네임/프로필 사진은 재동기화하지 않음**(2026-07-19 추가) — 최초 가입 시점(2-3장)에 반영한 값을 그대로 유지한다. 재로그인마다 플랫폼 최신 정보로 덮어쓰면, 회원이 [005(회원정보수정)](../05.회원정보수정/)에서 직접 바꾼 닉네임/사진이 다음 로그인 때 플랫폼 값으로 되돌아가버리는 문제가 생기기 때문(8장에서 최종 정책 확인 필요로 남김)
5. 2-2-7의 우리 서비스 토큰 발급으로 진행

### 2-4-1. 이메일 충돌 (그 이메일로 이미 "다른 방식"의 회원이 있는 경우) — **(2026-07-22 정책 변경: 계정 연동)**
처음엔 "자동 연결하지 않고 거부"(`EMAIL_ALREADY_REGISTERED`)로 보수적으로 설계했었으나(8장에 확인 필요로
남겨뒀던 항목), 실사용 중 정확히 이 시나리오(일반 가입한 이메일로 카카오 로그인)를 겪고 나서 **"같은
이메일이면 같은 사람이니 그냥 계정을 연동해달라"**고 확정 지시받아 정책을 바꿨다.

- **이메일이 일반(비밀번호) 회원의 것과 같으면**: 더 이상 거부하지 않는다. 그 소셜 계정을 기존 일반 회원에
  자동으로 연결(`social_accounts`에 새 row 추가)하고, **그 회원으로 곧바로 로그인시킨다**(같은 memberId,
  같은 닉네임/데이터 — 별도 확인 절차나 비밀번호 재확인 없이, 소셜 플랫폼이 인증한 이메일을 그대로 신뢰).
- **이메일이 다른 플랫폼의 소셜 회원과 같으면** (예: 카카오로 가입한 `a@x.com`이 있는데 같은 이메일로 네이버
  로그인을 시도): 위와 같은 로직으로 동일하게 처리된다 — `social_accounts`에 (NAVER, providerUserId) row가
  추가로 생기고, 두 플랫폼 모두 같은 memberId로 로그인 가능해진다(사실상 카카오/네이버/구글 중 어느 걸로
  로그인해도 항상 같은 계정으로 귀결).
- **계정 상태 확인은 그대로 적용**: 연동 대상 기존 회원이 `SUSPENDED`/`WITHDRAWN`이면 2-4장과 동일하게
  `ACCOUNT_SUSPENDED`/`ACCOUNT_WITHDRAWN`으로 막는다 — "계정 연동"이 정지/탈퇴 계정 우회 수단이 되지 않도록.
- **위험 고지**: 이메일 소유권을 소셜 플랫폼의 인증에만 의존한다 — 만약 어떤 플랫폼이 이메일 인증 없이
  사용자가 임의로 이메일을 등록하게 허용한다면(카카오/네이버/구글은 실제로는 자체 인증을 거치므로 이 위험은
  낮다고 판단) 타인 계정에 소셜 로그인을 연결당할 이론적 여지가 있음 — 8장에 남겨둠.

### 2-5. 소셜 계정의 회원정보수정 (신규 개발 없음 — 기존 기능 재사용/한 곳만 보강)
- 이메일/닉네임/전화번호 변경: [005.회원정보수정](../05.회원정보수정/)에서 이미 만든 `PATCH /api/members/me` + 이메일/전화번호 인증 API(`.../email/send-code` 등)를 그대로 사용 — 계정이 소셜이든 아니든 로직 차이 없음
- **비밀번호 변경만 신규로 막아야 함**: `MemberServiceImpl.updateProfile()`에 `password`가 제출됐을 때 그 회원이 `social_accounts`에 row가 있으면(=소셜 계정) `SOCIAL_ACCOUNT_PASSWORD_CHANGE_NOT_ALLOWED`(신규 에러코드)로 거부하는 가드 한 줄만 추가

### 2-6. 플랫폼 연동 해제
1. 사용자가 "소셜 연동 해제" 요청 → `DELETE /api/auth/{provider}/unlink` (로그인 상태 필요, 001-02(회원정보수정)의 `Authorization: Bearer {accessToken}` 인증 방식 재사용)
2. `social_accounts`에서 회원의 그 `provider` row를 조회해 플랫폼 토큰을 꺼낸 뒤, 요청사항에 명시된 각 플랫폼의 연동 해제 API를 호출
   - 네이버: `GET https://nid.naver.com/oauth2.0/token?grant_type=delete&client_id=...&client_secret=...&access_token=...&service_provider=NAVER`
   - 구글: `POST https://oauth2.googleapis.com/revoke?token={token}`
   - 카카오: `POST https://kapi.kakao.com/v1/user/unlink` (`Authorization: Bearer {access_token}`)
3. 성공하면 `social_accounts`에서 그 row를 삭제
4. 회원 자체가 탈퇴되는 것은 아님(로그인 수단 하나만 제거) — 단, 그 회원에게 남은 로그인 수단(비밀번호 또는 다른 소셜 연동)이 하나도 없어지는 경우의 처리 방침은 8장에서 확인 필요

### 2-7. 네이버 연결 끊기 콜백 (2-6과 별개 — 네이버 쪽에서 먼저 끊었을 때 통보받는 웹훅)
요청사항의 "네이버 연결 끊기 Callback URL(`http://localhost:8081/api/auth/naver/unlink-callback`)"은 우리가 능동적으로 호출하는 API가 아니라, **사용자가 네이버 프로필에서 직접 연결 끊기를 하거나 네이버 회원을 탈퇴했을 때 네이버 쪽이 우리 서버로 알려주는 수신용 엔드포인트**다.
1. `GET /api/auth/naver/unlink-callback`을 네이버 개발자센터의 "연결 끊기 콜백" 설정에 그대로 등록
2. 네이버가 이 URL로 호출하면(쿼리 파라미터로 회원 식별값 전달 — 정확한 파라미터명은 네이버 개발자 문서 확인 필요, 8장 참고) 해당 `social_accounts`(provider=NAVER) row를 찾아 삭제
3. 이미 우리 쪽에서 2-6으로 먼저 해제한 상태라 row가 없으면 그냥 무시(200 응답)

## 3. 인증 및 토큰 발급 방식 — 신규 로직 없이 기존 인프라 재사용
------------------------------------------------------------------------
- 소셜 로그인이 성공하면 [001-02(로그인) 발급 로직](../02.로그인/001-02.로그인-분석-설계.md)과 완전히 동일하게 `JwtProvider.generateAccessToken(memberId, email, role)` + `AccessTokenSessionService.register(...)` + `RefreshTokenService.issue(memberId)`를 그대로 호출해 우리 서비스의 `accessToken`/`refreshToken`을 발급한다. 응답 DTO도 기존 `LoginResponseDto`(success, message, memberId, accessToken, refreshToken)를 그대로 재사용 — 신규 필드 불필요
- 이후 이 토큰으로 호출하는 다른 모든 API(회원정보수정, 로그아웃 등)는 소셜/일반 계정을 구분하지 않음 — JWT의 `sub`(memberId)만 보고 동작하므로 이미 완성돼 있는 인증 방식([001-02(회원정보수정) 3장](../05.회원정보수정/001-02.회원정보수정-분석-설계.md))을 그대로 탄다
- `state` 파라미터(2-2장)는 로그인 세션이 아니라 OAuth 플로우 자체의 CSRF 방지용 — `AccessTokenSessionService`와는 별개로, Redis에 `oauth:state:{state}` → `provider`(TTL 5분) 형태의 신규 키를 하나 추가한다(`OAuthStateService` 같은 이름의 얇은 신규 서비스, 기존 `PasswordResetTokenService`/`FindEmailVerificationSessionService`와 동일한 패턴)

## 5. API 설계
------------------------------------------------------------------------
### 5-1. 로그인 시작
```
GET /api/auth/{provider}/authorize
```
`{provider}`: `kakao` | `naver` | `google`
응답: 302 리다이렉트 → 그 플랫폼의 인가 화면 URL (`state` 포함)

### 5-2. 콜백 (플랫폼 개발자 콘솔에 등록되는 고정 경로 — 요청사항 원문 그대로)
```
GET /oauth/kakao?code=...&state=...
GET /oauth/naver?code=...&state=...
GET /oauth/google?code=...&state=...
```
응답(성공, 200) — 기존 `LoginResponseDto` 재사용
```json
{ "success": true, "message": "로그인에 성공하였습니다.", "memberId": 123, "accessToken": "...", "refreshToken": "..." }
```
**(2026-07-22 변경)** 이메일이 이미 다른 방식(일반 가입 또는 다른 플랫폼 소셜)의 회원과 같아도 더 이상
실패로 응답하지 않는다 — 2-4-1장대로 그 회원에 자동 연동되어 위와 동일한 `LoginResponseDto` 200 응답이
온다(그 회원의 `memberId`로). `EMAIL_ALREADY_REGISTERED` 에러 코드는 이제 이 흐름에서 발생하지 않는다
(계정 상태가 SUSPENDED/WITHDRAWN인 경우는 여전히 각각의 에러로 막힘, 2-4-1장).

### 5-3. 연동 해제
```
DELETE /api/auth/{provider}/unlink
Authorization: Bearer {accessToken}
```
응답(성공, 200): `{ "success": true, "message": "연동이 해제되었습니다." }`

### 5-4. 네이버 연결 끊기 콜백 (네이버 → 우리 서버, 수신 전용)
```
GET /api/auth/naver/unlink-callback
```
응답: `200 OK` (네이버 쪽 스펙상 별도 바디 요구사항 확인 필요, 8장 참고)

## 8. 확인이 필요한 사항
------------------------------------------------------------------------
- **소셜로그인 앱의 "개발중"/"공개" 상태**: 요청사항 원문에 그대로 있던 질문 — 카카오/네이버는 앱이 "개발중" 상태면 개발자센터에 등록한 테스트 계정만 로그인할 수 있다. 지금은 프론트 연결도 없는 개발 단계라 아직 필요 없을 수 있음(요청사항 원문 의견과 동일) — 실제 사용자 테스트가 필요해지는 시점에 다시 논의
- **닉네임 형식 자동 보정 방식**(6장): 플랫폼이 준 닉네임이 우리 규칙(2~10자, 특수문자 불가)에 안 맞을 때 정확히 어떻게 다듬을지(자르기/치환/랜덤 생성 등) 구체적인 알고리즘은 미정
- **구글 닉네임 소스**: 구글은 "닉네임" 개념이 없고 프로필 정보(이름 등)만 내려줌 — 이름을 그대로 닉네임으로 쓸지, 이메일 로컬파트를 쓸지 확인 필요
- ~~동일 이메일의 타 플랫폼 소셜 계정 충돌~~ → **(2026-07-22 완료)** "자동으로 계정을 합쳐달라"로 확정, 2-4-1장 참고. 남은 리스크: 이메일 소유권을 소셜 플랫폼 인증에만 의존하는 것에 대한 고지(2-4-1장 마지막 항목)
- **연동 해제 후 로그인 수단이 하나도 안 남는 경우**(2-6장): 마지막 남은 로그인 수단의 해제를 막을지, 그냥 허용하고 "로그인 불가 계정"이 되도록 둘지 결정 필요
- **네이버 unlink-callback의 실제 페이로드 형식**(2-7장): 네이버 개발자 문서에서 실제로 어떤 파라미터로 회원을 식별해 알려주는지 확인 필요(현재는 문서에 URL만 있고 페이로드 스펙이 없음)
- **소셜 신규가입 시 `role` 기본값**: 일반 회원가입과 동일하게 `USER`로 확정할지(사업자 소셜가입은 이번 범위에 없다고 가정) 확인 필요
- **소셜 로그인 최초 진입 시 `last_login_at` 갱신 여부**: 일반 로그인처럼 매번 갱신할지 확인 필요(로직상 문제는 없으나 명시적으로 확정 안 됨)
- **(2026-07-19 추가) 재로그인 시 프로필 사진(및 닉네임) 재동기화 여부**(2-4-4장): 이번 설계는 "최초 가입 시점에만 반영, 이후 재로그인 때는 그대로 유지"로 정했음 — 사용자가 소셜 플랫폼에서 사진을 바꿔도 우리 서비스에는 반영되지 않는다는 뜻. 항상 최신으로 동기화할지, 회원이 직접 커스터마이징한 적 없을 때만 동기화할지 등 정책 확인 필요
- **(2026-07-19 추가) 프로필 사진 URL을 외부 링크 그대로 저장하는 방식의 리스크**: 플랫폼이 나중에 그 URL을 만료시키거나(카카오는 특히 이미지 URL이 시간이 지나면 깨지는 경우가 알려져 있음) 접근 정책을 바꾸면 우리 쪽에서 깨진 이미지가 노출될 수 있음 — 서버가 파일을 내려받아 직접 호스팅할지(005의 저장 방식 재사용) 여부는 이번 범위에서 결정하지 않음
