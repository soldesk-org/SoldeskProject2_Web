## 2. 핵심 설계 결정
------------------------------------------------------------------------
### 2-1. 기존 HTTP 포트를 없애지 않고, TLS 커넥터를 "추가"하는 방식을 선택한 이유
가장 단순한 해결책은 `server.ssl.enabled=true`로 8081 포트 자체를 HTTPS로 바꾸는 것이다. 하지만 이 프로젝트는
이미 카카오 로그인이 **실사용자 로그인까지 확인 완료**된 상태이고(06.소셜로그인), 그 카카오 개발자 콘솔에는
Callback URL이 `http://localhost:8081/oauth/kakao`로 등록되어 있다(네이버/구글도 마찬가지, 06 001-01 1-1장).
8081 포트를 HTTPS 전용으로 바꾸면:
- 카카오/네이버/구글이 로그인 완료 후 그 URL로 리다이렉트를 시도하는데, 서버는 더 이상 그 포트에서 HTTP를
  받지 않으므로 콜백 자체가 실패한다
- 이 URL은 외부 플랫폼(카카오/네이버/구글) 개발자 콘솔에 등록된 값이라 우리 코드만으로는 바꿀 수 없고,
  각 플랫폼 콘솔에서 팀원이 직접 값을 바꿔야 하는데 그 권한/계정 정보가 이 세션에는 없음

그래서 **8081(HTTP)은 그대로 두고, 별도 포트(기본 8443)에 TLS 커넥터를 하나 더 추가**하는 방식을 선택했다.
같은 Spring Boot 애플리케이션이 두 포트를 동시에 서비스한다 — 로그인 등 민감정보가 오가는 화면은 8443
(HTTPS)으로 접속하고, 소셜로그인 콜백처럼 외부 시스템에 등록된 값은 8081(HTTP)을 그대로 쓰는 식으로 당분간
공존시킨다.

### 2-2. 자체 서명(self-signed) 인증서 — 브라우저 경고는 정상, 개발/팀 테스트 용도로 한정
정식 인증기관(CA)이 발급하는 인증서는 실제 소유 중인 도메인이 있어야 발급 가능하다(Let's Encrypt 포함). 이
프로젝트는 아직 프로덕션 도메인이 정해지지 않아(06 001-04 등 여러 문서에서 "프론트 주소 미정"으로 남겨둔
상태와 같은 이유), 로컬 `keytool`로 직접 서명한 인증서를 사용한다.

- 브라우저가 "이 사이트는 안전하지 않습니다" 같은 경고를 띄우는 것은 **예상된 정상 동작**이다 — 브라우저가
  신뢰하는 CA 목록에 없는, 우리가 직접 서명한 인증서이기 때문. 로컬 테스트 시 "고급 > 계속 진행" 등으로
  넘어가면 된다.
- **경고가 뜬다는 것 자체가 "TLS가 작동하고 있다"는 증거이기도 하다** — 인증서 신뢰 여부와 별개로, 핸드셰이크
  자체는 정상적으로 이뤄지고 그 이후 트래픽은 실제로 암호화된다. 개발자도구 Network 탭에 여전히 평문으로
  보이는 이유는 001-01의 "먼저 짚어야 할 것" 참고 — 그건 브라우저가 자신의 요청을 보여주는 것뿐이다.
- 인증서는 `CN=localhost`, SAN에 `localhost`/`127.0.0.1` 포함, 유효기간 825일(브라우저가 허용하는 일반적인
  상한 근처)로 생성. `keytool -genkeypair`로 로컬에서 직접 생성하며, **개인키가 담긴 파일이라 git에 커밋하지
  않는다**(`.gitignore`에 `keystore/` 추가) — 팀원마다 각자 로컬에서 생성해야 한다(001-04 실행 가이드 참고).

### 2-3. Spring Boot 4 / Tomcat 11의 API 변경 대응
이 프로젝트는 Spring Boot 4.0.7(Tomcat 11.0.22)을 쓰는데, 다음 두 가지가 이전 버전(Spring Boot 2/3, Tomcat
9 이하) 자료에서 흔히 보이는 코드와 달랐다:
- `TomcatServletWebServerFactory`가 `org.springframework.boot.web.embedded.tomcat` 패키지가 아니라
  `org.springframework.boot.tomcat.servlet` 패키지로 이동했다(Spring Boot 4의 패키지 재구성)
- 커넥터의 keystore 설정을 `Http11NioProtocol.setKeystoreFile()`처럼 프로토콜 객체에 직접 세팅하는 옛날
  방식은 Tomcat 11에 더 이상 없다 — 대신 `SSLHostConfig`/`SSLHostConfigCertificate` 객체를 만들어
  `Connector.addSslHostConfig()`로 등록하는 최신 Tomcat 네이티브 API를 써야 한다

`HttpsConnectorConfig`는 `WebServerFactoryCustomizer<TomcatServletWebServerFactory>`를 구현해서, 활성화
설정(`https-connector.enabled`)이 켜져 있을 때만 새 `Connector`를 만들어 `SSLHostConfig`로 keystore를
연결하고, `factory.addAdditionalConnectors()`로 기존 팩토리에 추가 커넥터로 등록한다.

### 2-4. 팀 전체 기본값은 꺼둠 (opt-in)
`https-connector.enabled` 기본값을 `false`로 뒀다 — 이 프로젝트는 팀원 5명이 각자 로컬에서 서버를 띄워
개발하는 구조라(CLAUDE.md 1장 "호스팅 모델 이유"와 같은 맥락), 기본값을 켜두면 keystore 파일이 없는 팀원의
서버가 기동 실패하거나(설정에 따라) 예상치 못한 포트가 추가로 열리는 변화를 모두에게 강제하게 된다. 필요한
사람만 `.env`에 `HTTPS_CONNECTOR_ENABLED=true`를 추가하고 keystore를 직접 생성해서 켜는 방식으로 설계했다
(CLAUDE.md 2장의 "필요할 때만 인프라를 만든다" 원칙과 같은 결).

## 3. 설정 항목
------------------------------------------------------------------------
`application.yml`에 커스텀 프로퍼티 섹션 `https-connector`를 추가(다른 커스텀 섹션 `jwt`/`phone-crypto`
등과 같은 패턴):

| 키 | 환경변수 | 기본값 | 설명 |
|---|---|---|---|
| `https-connector.enabled` | `HTTPS_CONNECTOR_ENABLED` | `false` | HTTPS 커넥터 활성화 여부 |
| `https-connector.port` | `HTTPS_CONNECTOR_PORT` | `8443` | HTTPS 커넥터 포트 |
| `https-connector.key-store` | `SSL_KEY_STORE` | `./keystore/localhost.p12` | keystore 파일 경로 |
| `https-connector.key-store-password` | `SSL_KEY_STORE_PASSWORD` | (없음) | keystore 비밀번호 |
| `https-connector.key-store-type` | `SSL_KEY_STORE_TYPE` | `PKCS12` | keystore 형식 |
| `https-connector.key-alias` | `SSL_KEY_ALIAS` | `localhost` | 인증서 별칭 |

## 4. 기존 API 계약 변경 없음
------------------------------------------------------------------------
로그인/회원정보수정 등 기존 API의 요청/응답 스펙, 에러 코드는 전혀 바뀌지 않는다 — 같은 API를 어느 포트
(8081 HTTP / 8443 HTTPS)로 부르느냐만 다르다. 그래서 이 기능은 별도의 "API 설계" 장이 없다(엔드포인트
추가/변경이 없는 순수 전송 계층 변경).

------------------------------------------------------------------------
## 5. 정적 리소스(테스트 페이지) 호환성
------------------------------------------------------------------------
`Project2/src/main/resources/static/*.html`의 모든 테스트 페이지(`mypage-test.html`, `tmp-map-test.html`,
`recommend-test.html`, `foodbti-test.html` 등)는 API 호출 시 `API_BASE = ''`(빈 문자열, 상대 경로) 패턴을
쓰고 있어서, 이 페이지들을 `https://localhost:8443/...`으로 열면 `fetch('/api/...')` 같은 상대 경로 호출도
자동으로 `https://`를 따라간다 — 페이지 코드를 하나도 안 고쳐도 HTTP/HTTPS 양쪽에서 그대로 동작한다(코드
전수 확인 완료, `http://localhost:8081`을 하드코딩한 페이지가 하나도 없었음).

## 8. 확인이 필요한 사항 / 남은 작업
------------------------------------------------------------------------
- **프로덕션 정식 인증서 미적용**: 도메인이 정해지면 Let's Encrypt 등으로 정식 인증서를 발급받아 이
  keystore를 교체해야 함(자체 서명 인증서는 팀 내부/로컬 테스트 전용, 001-02 2-2장)
- **소셜로그인 콜백을 HTTPS로 전환할지 여부**: 프로덕션 배포 시점에 카카오/네이버/구글 개발자 콘솔에서
  Callback URL을 `https://` 도메인으로 재등록해야 함 — 외부 플랫폼 설정이라 이 세션에서 처리 불가, 담당
  팀원이 배포 시점에 진행 필요
- **HTTP → HTTPS 강제 리다이렉트 미적용**: 지금은 둘 다 열려있고 선택적으로 쓰는 구조 — 실제로 "HTTPS만
  쓰게 강제"하고 싶으면 HTTP 커넥터에서 HTTPS로 리다이렉트하는 필터/설정 추가 검토 필요(001-01 "이번
  범위에서 제외된 것" 참고)
- **팀 전체 기본 활성화 여부**: 지금은 opt-in(기본 꺼짐, 2-4장) — 이후 팀 논의로 기본 활성화하기로 정해지면
  `application.yml`의 기본값과 이 문서를 함께 갱신해야 함
