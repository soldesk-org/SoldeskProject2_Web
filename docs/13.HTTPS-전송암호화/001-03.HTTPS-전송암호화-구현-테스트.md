## 1. 구현 결과 (2026-07-23)
------------------------------------------------------------------------
### 1-1. 실제 구현 파일
```
com.foodtrip.foodsearch.common.config
 └─ HttpsConnectorConfig (신규) — WebServerFactoryCustomizer<TomcatServletWebServerFactory> 구현
```
`application.yml`에 `https-connector` 설정 섹션 추가(001-02 3장), `.env.example`에 관련 6개 키 추가.
`Project2/keystore/`(신규 디렉터리, git 미추적)에 자체 서명 keystore 생성.

### 1-2. keystore 생성 명령 (실제 실행한 것)
```bash
keytool -genkeypair \
  -alias localhost \
  -keyalg RSA -keysize 2048 -validity 825 \
  -storetype PKCS12 \
  -keystore ./keystore/localhost.p12 \
  -storepass {임의 생성한 비밀번호} -keypass {동일} \
  -dname "CN=localhost, OU=Eattyway Dev, O=Soldesk, L=Seoul, ST=Seoul, C=KR" \
  -ext "SAN=dns:localhost,ip:127.0.0.1"
```
비밀번호는 Node `crypto.randomBytes`로 생성한 32자 랜덤 값을 `.env`의 `SSL_KEY_STORE_PASSWORD`에 저장
(실제 값은 `.env`에만 있고 문서/커밋 이력에는 남기지 않음 — 다른 외부 연동 비밀값과 동일한 취급).

### 1-3. Spring Boot 4 / Tomcat 11 API 대응 (001-02 2-3장 설계의 실제 구현)
컴파일 과정에서 두 차례 API 불일치가 나서 수정:
1. `import org.springframework.boot.web.embedded.tomcat.TomcatServletWebServerFactory` → 컴파일 에러
   (`package ... does not exist`) → `org.springframework.boot.tomcat.servlet.TomcatServletWebServerFactory`로
   수정(Spring Boot 4 패키지 재구성 확인 후)
2. `Http11NioProtocol.setKeystoreFile()`/`setKeystorePass()`/`setKeystoreType()`/`setKeyAlias()`,
   `factory.addAdditionalTomcatConnectors()` → 전부 컴파일 에러(`cannot find symbol`) → Tomcat 11 소스
   (`tomcat-embed-core-11.0.22.jar`)를 직접 역참조(`javap`)해서 확인 후, `SSLHostConfig`/
   `SSLHostConfigCertificate` + `Connector.addSslHostConfig()` + `factory.addAdditionalConnectors()`
   (Tomcat/Spring Boot 이름 그대로, "Tomcat" 빠짐)로 교체 — 001-02 2-3장 최종 코드가 이 경로

## 2. 검증 (2026-07-23)
------------------------------------------------------------------------
### 2-1. 컴파일
`./mvnw.cmd compile` — 위 2차례 API 수정 후 정상 통과.

### 2-2. 실 서버 기동 + 두 포트 동시 서비스 확인
서버 재기동 후:
- `curl http://localhost:8081/api/food-bti/questions` → `200`(기존 HTTP 정상 유지)
- `curl -k https://localhost:8443/api/food-bti/questions` → `200`(HTTPS 커넥터도 같은 API에 정상 응답,
  `-k`는 자체 서명 인증서라 curl의 인증서 검증을 건너뛰는 옵션 — 001-02 2-2장에서 설명한 "경고가 뜨는 게
  정상"과 같은 이유)
- `curl -k https://localhost:8443/mypage-test.html`, `.../foodbti-test.html` → 둘 다 `200`(정적 테스트
  페이지도 HTTPS 포트로 정상 서빙됨, 001-02 5장 검증)

### 2-3. 인증서 실제 내용 확인 (`openssl s_client`)
```
subject=C=KR, ST=Seoul, L=Seoul, O=Soldesk, OU=Eattyway Dev, CN=localhost
issuer=C=KR, ST=Seoul, L=Seoul, O=Soldesk, OU=Eattyway Dev, CN=localhost
notBefore=Jul 23 01:30:19 2026 GMT
notAfter=Oct 25 01:30:19 2028 GMT
```
`subject`와 `issuer`가 동일 — 자체 서명 인증서임을 그대로 보여줌(예상대로). TLS 핸드셰이크 자체가
`openssl s_client`로 성공적으로 완료되고 인증서 정보까지 정상 추출된다는 것은, 8443 포트가 실제로 TLS
프로토콜로 통신하고 있다는 증거(001-02 2-2장 "핸드셰이크는 정상적으로 이뤄지고 그 이후 트래픽은 실제로
암호화된다"를 직접 확인).

### 2-4. 로그인 API를 HTTPS로 호출
```bash
curl -k -X POST https://localhost:8443/api/members/login \
  -H "Content-Type: application/json" \
  -d '{"email":"test@naver.com","password":"test"}'
```
→ `200` 정상 응답(accessToken 발급). **이번 요청사항의 핵심 목표였던 "로그인 요청을 암호화된 채널로 보낼
수 있는가"가 실제로 동작함을 확인.**

### 2-5. 기존 HTTP 커넥터 회귀 없음
`curl http://localhost:8081/api/food-bti/questions` → HTTPS 커넥터 추가 이후에도 여전히 `200` — 001-02
2-1장에서 의도한 대로 기존 HTTP 포트가 그대로 살아있어 소셜로그인 콜백(06) 호환성이 깨지지 않았음을 확인
(콜백 자체를 실제 카카오/네이버/구글로 재호출하는 종단 검증까지는 하지 않았음 — 포트/프로토콜이 그대로
유지된다는 것만 확인, 실제 소셜로그인 재검증은 06 문서 소관).
