## 요청사항 원문 요약
------------------------------------------------------------------------
로그인 등 API 호출 시 브라우저 네트워크 탭에서 비밀번호/전화번호 같은 민감정보가 평문으로 그대로 보이는
문제를 해결해달라는 요청. "해결하는 방법이 있는 것으로 안다"는 언급 — 표준적인 해결책인 HTTPS(TLS) 전송
암호화를 가리키는 것으로 판단하고 그대로 진행함.

------------------------------------------------------------------------
## 먼저 짚어야 할 것: 브라우저 개발자도구에 보이는 것과 실제 "평문 노출"은 다른 문제
------------------------------------------------------------------------
이 문서를 읽는 사람이 오해하기 쉬운 부분이라 먼저 정리한다.

- **브라우저 개발자도구(Network 탭)의 Request Payload는 HTTPS를 적용해도 계속 평문으로 보인다.** 이건
  버그가 아니라 당연한 동작이다 — 개발자도구는 "내 브라우저가 암호화하기 직전/해독한 직후의 내용"을
  보여주는 도구이지, 네트워크 위를 실제로 흘러다니는 바이트를 보여주는 게 아니다. 본인이 보낸 자기 요청을
  자기 브라우저에서 보는 것이므로 항상 평문으로 보이는 게 정상이다.
- **진짜 문제는 "네트워크 경로 위에서" 그 값이 평문으로 흘러가는지 여부다.** 지금까지 서버가 순수 HTTP만
  제공했기 때문에, 같은 와이파이를 쓰는 제3자나 중간 경유 장비가 패킷을 가로채면(패킷 캡처) 비밀번호를
  그대로 읽을 수 있는 상태였다. HTTPS(TLS)는 바로 이 구간 — 브라우저와 서버 사이의 실제 네트워크 전송
  구간 — 을 암호화한다.
- 이번 작업은 **`localhost`(내 컴퓨터 자기 자신) 개발 환경 기준**이라, loopback 트래픽은 애초에 이 컴퓨터
  밖으로 나가지 않아 제3자가 가로챌 방법이 원천적으로 없다 — 즉 지금 이 순간 로컬 개발 환경에서는 실질적인
  보안 위험이 크지 않다. 하지만 (a) 나중에 실제 서버(Azure VM)에 배포해서 여러 사람이 같은 와이파이/네트워크
  에서 접속하는 시나리오, (b) 테스트 중 다른 사람 화면 공유나 패킷 캡처 도구로 관찰당하는 시나리오에서는
  실질적 위험이 된다. 그래서 "지금 당장 로컬에서 급하지 않아도, 언제든 켤 수 있는 형태로" 미리 만들어두는
  것으로 판단했다.

## 이번 범위 정리
------------------------------------------------------------------------
- 애플리케이션에 HTTPS(TLS) 커넥터를 추가해서, 원하면 암호화된 채널로 로그인/회원정보수정 등 모든 API를
  호출할 수 있게 한다
- 자체 서명(self-signed) 인증서를 로컬에서 생성해서 사용 — 실제 인증기관(CA) 인증서는 도메인이 있어야
  발급 가능한데, 지금은 프로덕션 도메인이 없으므로 이번 범위 밖(8장 참고)
- 기존 HTTP 포트(8081)는 그대로 유지 — 소셜로그인(06)의 카카오/네이버/구글 콜백 URL이 각 플랫폼 개발자
  콘솔에 이미 `http://localhost:8081/oauth/{provider}`로 등록되어 있어, 그 포트의 프로토콜을 바꾸면 실사용
  확인까지 끝난 카카오 로그인이 깨진다(2-1장에서 상세 설명) — 그래서 HTTP를 없애지 않고 HTTPS 커넥터를
  "추가"하는 방식으로 설계함
- 팀 전체 기본값은 꺼둔 채로(`HTTPS_CONNECTOR_ENABLED` 기본 false) 필요한 사람만 켤 수 있게 함(2-1장,
  기존 팀 개발 환경을 갑자기 깨뜨리지 않기 위함)

------------------------------------------------------------------------
## 이번 범위에서 제외된 것
------------------------------------------------------------------------
- 프로덕션(실제 배포) 환경의 정식 TLS 인증서(Let's Encrypt 등) 발급/적용 — 도메인이 정해진 뒤의 작업
- HTTP → HTTPS 강제 리다이렉트(HSTS 등) — 지금은 "옵션으로 켤 수 있는" 단계, 강제 전환은 프로덕션 배포
  시점에 재검토
- 소셜로그인 콜백 URL을 HTTPS로 전환하는 것(각 플랫폼 개발자 콘솔 설정 변경 필요, 외부 시스템이라 이
  세션에서 직접 처리 불가)
