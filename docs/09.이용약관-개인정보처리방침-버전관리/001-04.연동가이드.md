# 09. 이용약관/개인정보처리방침 버전관리 — 연동 가이드

## 1. 공개 API

### `GET /api/terms/{docType}`
`docType` = `SERVICE` | `PRIVACY` (대소문자 무관, 서버가 대문자로 정규화).

```json
{
  "termsDocumentId": 1,
  "docType": "SERVICE",
  "versionLabel": "2026-08-01",
  "title": "Eattyway 서비스 이용약관",
  "content": "<h2 id=\"chapter1\">제1장 총칙</h2> ...",
  "effectiveDate": "2026-08-01",
  "changeSummary": "...",
  "createdAt": "2026-08-14T10:00:00"
}
```

`content`는 `<h2 id="...">` 제목 태그를 포함한 HTML 문자열이다. 프론트는 이 HTML을 그대로
`innerHTML`에 넣고, `h2[id]`를 스캔해서 좌측 목차를 자동 생성한다(`assets/js/terms-service.js`의
`buildToc()` 참고). **새 버전을 등록할 때 목차에 넣고 싶은 제목은 반드시 `<h2 id="고유값">...</h2>`
형태로 작성해야 한다.**

### `GET /api/terms/{docType}/versions`
```json
[{ "termsDocumentId": 2, "versionLabel": "2026-09-01", "title": "...", "effectiveDate": "2026-09-01", "current": false },
 { "termsDocumentId": 1, "versionLabel": "2026-08-01", "title": "...", "effectiveDate": "2026-08-01", "current": true }]
```
최신순 정렬. `current`는 "오늘 기준으로 실제 적용 중인 버전"에만 true (미래 예약 버전은 항상 false).

### `GET /api/terms/{docType}/versions/{termsDocumentId}`
위 상세 응답과 동일한 형태(과거/미래 특정 버전 하나).

### `GET /api/notices` / `GET /api/notices/{noticeId}`
목록은 `noticeId/docType/title/effectiveDate/postedAt/noticeType`. 상세는 여기에
`previousVersion`/`newVersion`(둘 다 위 "버전 상세" 형태, `previousVersion`은 최초 버전 공지의 경우
`null`)이 추가된다.

## 2. 관리자 API (`Authorization: Bearer {ADMIN 토큰}` 필수, 그 외 이 프로젝트 API처럼 인가 헤더 없이는
`401 NOT_LOGGED_IN`, ADMIN이 아니면 `403 ADMIN_ACCESS_DENIED` — SecurityConfig가 처리하므로 컨트롤러
자체는 별도 체크 없음)

### `POST /api/admin/terms/{docType}/versions`
```json
{
  "title": "Eattyway 서비스 이용약관",
  "content": "<h2 id=\"chapter1\">...</h2>",
  "effectiveDate": "2026-09-15",
  "changeSummary": "제7조 위치기반서비스 조항 신설",
  "noticeType": "MINOR",
  "versionLabel": "2026-09-15"
}
```
- `noticeType`은 **그 docType에 이미 버전이 하나라도 있으면 필수**(`MINOR` 또는 `MAJOR`), 최초 버전
  등록 시에는 생략 가능(생략하면 검증 자체를 건너뜀).
- 시행일(`effectiveDate`)이 오늘로부터 `MINOR`면 14일, `MAJOR`면 30일 이상 남아있지 않으면
  `400 TERMS_NOTICE_LEAD_TIME_TOO_SHORT`.
- 성공 시 새 버전이 즉시 저장되고, 이전 버전이 있었다면 **같은 트랜잭션 안에서 변경 공지도 함께
  게시**된다(별도 API 호출 불필요). 응답:
```json
{ "success": true, "message": "새 버전이 등록되고 변경 공지가 게시되었습니다.", "termsDocumentId": 3, "noticeId": 2 }
```
  최초 버전이면 `noticeId`는 `null`.

### `GET /api/admin/terms/{docType}/versions`, `GET /api/admin/notices`
관리자 화면 전용 목록(관리자 페이지 "약관 관리" 탭이 사용). 공개 API와 데이터는 거의 동일하되
`AdminNoticeResponseDto`에 `createdByAdminMemberId`, `termsDocumentId`, `previousTermsDocumentId`가
추가로 들어있다.

## 3. 프론트 페이지

- `terms-service` / `terms-privacy` — 현재 버전을 자동 로드하고, 하단 select에서 과거 버전을 고르면
  같은 화면에서 다시 렌더링한다(페이지 이동 없음).
- `notices` — 공지 목록, 행 클릭 시 `notice-detail?id={noticeId}`로 이동.
- `notice-detail?id={noticeId}` — 변경 전/후 카드를 나란히 표시. `id` 쿼리 파라미터가 없거나 존재하지
  않는 공지면 안내 문구만 표시.
- `admin` (관리자 페이지) — "약관 관리" 탭에서 새 버전 등록 + 목록 확인. 등록 폼 제출은
  `POST /api/admin/terms/{docType}/versions`를 그대로 호출.

## 4. 다른 기능이 알아둘 점

- **회원가입 약관 동의 체크박스(`signup-terms.js`)는 이 기능과 데이터 연동이 없다** — 체크박스 상태만
  관리하고 실제 텍스트는 안 가져온다. 즉 이번 변경으로 회원가입 플로우에 영향 없음(회귀 없음 확인).
- 알림 벨(`notification` 패키지, 회원 개인별)과 이번 "공지 게시판"(`terms_change_notices`, 공개)은
  완전히 별개의 테이블/API다. 관리자의 "공지 발송"(`/api/admin/notification-broadcasts`)과 헷갈리지
  말 것 — 그건 알림 벨에 발송하는 기존 기능이고, 이번 기능은 공개 게시판 글을 만드는 것이다.
