```

 ├─ client
```

## 2. 핵심 설계 결정
------------------------------------------------------------------------
### 2-1. 팀원의 recommendation_api.py를 건드리지 않는다
`recommendation_api.py`의 `KakaoLocalClient.search()`가 `category_group_code: "FD6"`(음식점)로
하드코딩돼 있어(001-01 "조사 결과" 참고), 그 서버의 `/api/recommend`는 카페/공원 검색에 못 쓴다. 대신
카카오 호출이 아예 없는 순수 LLM 분석 엔드포인트 `/api/keywords`(`extractor.analyze_search()`만 호출,
`recommendation_api.py`에 이미 있던 것)를 그대로 재사용한다 — 팀원 코드는 한 줄도 수정하지 않는다.

### 2-2. AI 분석과 실제 장소 검색을 분리
- **AI 분석**(어떤 느낌의 공원/카페를 찾는지 문장으로 이해) → `RecommendationClient.analyzeKeywords()`가
  Python `/api/keywords`를 호출, `atmosphere_keywords` 등을 받아 안내 문구에 반영
- **실제 장소 검색**(카카오에서 실제 좌표/이름 찾기) → 우리 쪽 신규 `NearbyPlaceKakaoClient`가 직접 카카오
  로컬 API를 호출

이렇게 나눈 이유는 "AI 학습으로 하게 해줘"라는 요청을 살리면서도(문장 분석은 진짜로 LLM이 함), 팀원 코드의
카테고리 하드코딩 문제를 우회하기 위함이다.

### 2-3. 카페 검색 - CE7 카테고리로 충분
카카오 로컬 API가 카페(CE7)는 공식 category_group_code를 제공하므로, `NearbyPlaceKakaoClient.
searchCafesNearby()`가 `category_group_code=CE7` + 좌표 + 반경 + `sort=distance`로 검색한다. 07의
`KakaoLocalSearchClient`처럼 "음식점"으로 시작하는 카테고리만 남기는 필터는 이번엔 적용하지 않았다 —
CE7 카테고리 자체가 이미 카페로 충분히 좁혀져 있어서 불필요.

### 2-4. 공원 검색 - 카카오에 전용 카테고리가 없어 키워드 검색 + 필터링
카카오 로컬 API 공식 문서의 category_group_code 목록(어린이집, 학교, 주차장, 관광명소, 음식점, 카페 등)에
**공원은 없다**. 그래서 `searchParksNearby()`는 category_group_code 없이 순수 키워드("공원")로 검색한다.
카테고리 제한이 없는 만큼 무관한 결과가 섞이는 걸 실측으로 확인해서, 아래 필터를 순서대로 적용한다:
1. `category_name`에 "주차장"이 포함된 것 제외 — "역삼문화공원 제2호공영주차장"처럼 공원 이름을 딴
   주차장이 실제로 검색됨을 확인(2026-07-25 라이브 테스트)
2. `category_name` 최상위가 "음식점"인 것 제외 — "메가MGC커피 역삼문화공원점"처럼 공원 이름을 딴 카페
   지점도 섞여 나옴을 확인
3. `category_name` 또는 `place_name`에 "공원"이 실제로 포함된 것만 최종적으로 남김

필터링으로 결과가 줄어들 수 있어, 원하는 개수(size)보다 넉넉하게(최대 45건, 카카오 3페이지 한도) 미리
가져온 뒤 필터링하고 나서 size만큼 자른다.

### 2-5. 후속 추천의 기준 좌표 - 방금 추천된 1위 결과
"그 전에 추천한 그 옆에" 요청을 "추천 결과 중 1위(가장 위에 나온 곳)의 좌표를 기준으로 검색"으로
해석했다. 프론트(`recommend-test.html`)가 `renderResults()` 직후 1위 결과를 `anchorPlace`로 저장해두고,
"괜찮아요" 클릭 시 그 좌표를 그대로 요청에 실어 보낸다.

### 2-6. 랜덤 프롬프트는 프론트에서 결정
PARK/CAFE 중 어느 걸 보여줄지는 백엔드가 정하지 않고 프론트(`Math.random() < 0.5`)가 정한다 — 서버는
`type` 파라미터를 받아 그 타입에 맞는 결과만 돌려주는 단순한 역할만 한다(상태 없는 API, 서버가 굳이
"이번엔 뭘 보여줄지" 기억할 이유가 없음).

### 2-7. 로그인/이력 저장 없음
18(추천-피드백)과 달리 이 후속 추천은 `recommendation_histories`에 기록하지 않는다 — 메인 추천 자체의
피드백과 성격이 다르고(부가 제안일 뿐), 로그인 여부와 무관하게 항상 동작하게 해서 단순함을 유지했다
(001-01 "이번 범위에서 제외된 것" 참고).

### 2-8. 후속 추가(2026-07-25, 같은 날) — 지도에 도보 코스로 시각화
"도보 코스로 짜줘" 요청으로 프론트(`recommend-test.html`)에 코스 시각화를 추가했다. 조사해보니 이
프로젝트가 쓰는 지도/장소 API(NCP Maps, 카카오 로컬 API) 어느 쪽에도 **도보(보행자) 경로를 계산해주는
공개 API가 없다**(둘 다 자동차 경로 API만 제공, 도보 길찾기는 별도 유료/전용 서비스가 필요) — 그래서
실제 인도를 따라가는 turn-by-turn 경로는 만들 수 없다는 걸 사용자에게 먼저 설명했다.

대신 백엔드가 이미 거리순으로 정렬해서 내려주는 응답(2-4/2-3장, 카카오 `sort=distance`)을 그대로
활용해서, 프론트에서 **음식점 → 가까운 순서 1·2·3위를 네이버 지도 `Polyline`으로 직선 연결**하고 마커에
순서 번호를 표시한다(가까운 3곳까지만 "코스"로 묶고, 나머지는 "다른 후보"로 마커만 남김 — 5곳을 전부
지그재그로 이으면 실제 걷는 순서로는 부자연스러워서 3곳으로 제한). 이 선이 실제 도로 경로가 아니라
직선 거리 기준이라는 점을 안내 문구에도 명시했다("지도의 점선은 가까운 순서로 이은 코스예요 - 실제 도로
경로는 아니고 직선 거리 기준입니다"). 백엔드 API/응답 형식은 이번 추가로 변경되지 않았다(순수 프론트
렌더링 변경).

### 2-9. 후속 추가 2(2026-07-25, 같은 날) — 후속 추천 프롬프트에 "닫기" 버튼 추가
후속 추천 안내("밥 먹고 산책/카페 어때요?")에 원래 "괜찮아요" 버튼 하나만 있었는데, 사용자가 화면
스크린샷과 함께 "버튼이 하나만 있는데?"로 지적해서 발견 — 후속 추천이 필요 없을 때 안내 자체를 닫을
방법이 없었다. `followupDismissBtn`("닫기")을 추가해서, 누르면 `#followupSection`을 그냥 숨긴다(별도
API 호출 없음, 순수 프론트 상태 변경).

### 2-10. 후속 추가 3(2026-07-25, 같은 날) — 추천 마커를 메인 지도와 같은 카테고리 이미지로 통일
"앞으로 추천쪽에서도 마커 미지 메인 페이지에서 사용하고 있는 그 이미지 여러개 있을거야 그거로 해서
음식점 종류에 맞춰서" 요청 — `recommend-test.html`의 추천 결과 마커가 기존엔 파란 원+순위 번호였는데,
`tmp-map-test.html`(메인 지도)이 이미 쓰고 있는 카테고리별 마커 이미지(`img/markers/marker-*.png`, 10종,
27×35px, `scaledSize` 필수 — 2026-07-23에 겪었던 "size만 주면 원본 크기 그대로 렌더링되는" 버그를 다시
겪지 않도록 그대로 재사용)로 통일했다.

메인 지도는 우리 DB가 이미 분류해둔 `RestaurantSummaryResponseDto.category`(11개 공식 카테고리 중 하나)를
그대로 키로 쓰지만, AI 추천 결과는 카카오 원본 `category_name`(예: "음식점 > 한식")만 갖고 있어서 그
문자열에 포함된 키워드로 우리 10개 카테고리 중 하나를 프론트에서 직접 매칭한다(07의
`classifyByKakaoCategoryName()` 2차 신호와 같은 방식, 백엔드 API 호출 없이 클라이언트에서 문자열
포함 여부만 검사). 매칭되는 이미지가 없으면(그 외/미분류) 기존 파란 번호 마커로 대체 — 순위 정보 자체가
아예 없어지지 않도록 하기 위함.

## 3. API 설계
------------------------------------------------------------------------
### 3-1. 후속 코스 추천 (신규)
```
POST /api/recommendation/nearby-course
Content-Type: application/json

{
  "type": "PARK",              // "PARK" 또는 "CAFE"
  "anchorName": "미도인 강남",   // 선택, AI 안내 문구용
  "x": 127.027187506638,
  "y": 37.5021014097588
}
```
응답(200)
```json
{
  "type": "PARK",
  "message": "미도인 강남 근처에서 산책하기 좋은 공원 5곳을 찾았어요(산책하기 좋은, 공원).",
  "places": [
    {
      "placeId": "10657560", "placeName": "역삼문화공원",
      "categoryName": "여행 > 공원 > 도시근린공원",
      "addressName": "서울 강남구 역삼동 635-1", "roadAddressName": null,
      "placeUrl": "http://place.map.kakao.com/10657560",
      "x": "127.03041938929663", "y": "37.50133927181133", "distanceMeters": 298
    }
  ]
}
```
로그인 불필요(recommend()와 같은 톤).

## 4. 에러 코드
------------------------------------------------------------------------
새 에러 코드는 추가하지 않음 — 기존 `KAKAO_LOCAL_SEARCH_FAILED`(카카오 호출 실패), `RECOMMENDATION_
SERVICE_UNAVAILABLE`(AI 분석 서버 통신 실패)를 그대로 재사용한다.

------------------------------------------------------------------------
## 5. DB
------------------------------------------------------------------------
스키마 변경 없음 — 이 기능은 아무것도 저장하지 않는다(2-7장).

## 6. 확인이 필요한 사항 / 남은 작업
------------------------------------------------------------------------
- 실제 도로를 따라가는 도보 경로(turn-by-turn) 시각화는 여전히 안 됨(2-8장) — 필요해지면 유료 보행자
  경로 API(예: Naver Cloud Platform의 다른 상품, 또는 OSRM 같은 오픈소스 라우팅 서버 자체 구축) 연동 검토
- 팀원의 `recommendation_api.py`가 나중에 category_group_code를 파라미터화하면, 지금의 우회 설계
  (NearbyPlaceKakaoClient 직접 검색)를 그 서버 호출로 단순화할 수 있음 — 지금은 팀원 코드를 안 건드리는
  쪽을 우선했다(2-1장)
- 카카오 category_name 키워드 매칭(2-10장)이 07의 백엔드 `RestaurantCategoryMatchingService`만큼
  정교하지 않음 — 프론트에서 간단한 문자열 포함 검사만 하므로, 애매한 카테고리(예: "이색음식점")는
  매칭이 안 돼 기본 번호 마커로 대체될 수 있음(의도된 동작, 완벽한 분류가 목적이 아님)
