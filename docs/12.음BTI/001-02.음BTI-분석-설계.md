## 1. 패키지 구조
------------------------------------------------------------------------
새 도메인 패키지 `com.foodtrip.foodsearch.foodbti`(원본은 도메인 구분 없이 `controller`/`service`/`dto`
최상위 패키지에 있었으나, 이 프로젝트는 도메인별 패키지 구조를 쓰므로 그 관례를 따름).
```
com.foodtrip.foodsearch
 └─ foodbti (신규 패키지)
     ├─ dto         FoodBtiQuestionDto, FoodBtiChoiceDto, FoodBtiAnswerRequestDto,
     │              FoodBtiResultResponseDto, FoodBtiScoreDto
     ├─ service     FoodBtiService(인터페이스), FoodBtiServiceImpl
     └─ controller  FoodBtiController
```
`members.food_bti` 컬럼(11.마이페이지에서 이미 추가됨)을 그대로 사용 — 스키마 변경 없음. `Member` 엔티티에
`updateFoodBti(String)` 메서드만 추가(2-2장).

## 2. 핵심 설계 결정
------------------------------------------------------------------------
### 2-1. 채점 로직은 원본 그대로 포팅, DTO 이름/컨벤션만 이 프로젝트 스타일로 조정
질문 문구, 성향 4축(L/S, F/N, A/T, P/I), 점수 계산 방식(각 축에서 더 많이 선택된 알파벳 채택, 동점이면
앞쪽 알파벳 우선), 결과 코드별 이름/설명/추천 음식 생성 로직은 원본(`FoodBtiService`)과 완전히 동일하다 —
로직을 바꾸면 다른 팀원이 이미 검증해둔 결과와 달라지므로, 이번 작업의 책임은 "연동"이지 "재설계"가 아니다.

바뀐 것은 오직 코드 스타일뿐이다:
- DTO 클래스명 `FoodBtiQuestionDTO` → `FoodBtiQuestionDto` 등(이 프로젝트는 `Dto`로 표기, `CreateReviewRequestDto`
  등 기존 관례와 통일)
- `FoodBtiAnswerDTO`의 필드명 `answer`(단수) → `FoodBtiAnswerRequestDto.answers`(복수, 12개 배열이라는
  의미를 명확히) — 이름만 바뀌었을 뿐 의미와 검증 규칙(정확히 12개)은 동일
- 답변 개수/값 검증을 원본의 수동 `if`+`IllegalArgumentException`에서 이 프로젝트의 표준 방식(Jakarta
  Bean Validation `@Size(min=12,max=12)` + `GlobalExceptionHandler`가 처리하는 `CustomException`/
  `ErrorCode.INVALID_INPUT`)으로 교체 — 다른 모든 API와 같은 형식의 에러 응답(`{success,code,message}`)이
  나오도록 통일

### 2-2. 로그인하면 결과를 실제로 저장 (원본에 없던 신규 연동)
원본 `FoodBtiService.calculateResult()`는 결과를 계산해서 반환만 하고 어디에도 저장하지 않았다. 이 프로젝트의
`members.food_bti` 컬럼(11.마이페이지에서 추가, 지금까지 항상 `null`)을 채우는 것이 이번 연동의 핵심 목적이므로,
`FoodBtiServiceImpl.calculateResult()`에 다음을 추가했다:

- `Authorization` 헤더로 로그인 상태를 판별하되, **07(음식점 검색)/RestaurantServiceImpl의
  `resolveMemberIdOrNull()` 패턴을 그대로 재사용** — 로그인 없이도 토큰 없이 호출 가능해야 하므로(질문 조회와
  같은 톤), 무효/누락 토큰이면 401로 막는 게 아니라 그냥 "비로그인"으로 처리하고 결과 계산은 계속 진행한다
- 로그인 상태(유효한 토큰)면 `Member.updateFoodBti(resultType)`으로 그 회원의 `food_bti`를 갱신
- 응답 DTO에 `saved`(boolean) 필드를 추가해서 "이번 호출로 실제로 저장됐는지"를 프론트가 바로 알 수 있게 함
  (05 001-02 5-11장의 `verifyPassword`가 상태를 안 바꾸는 것과 반대로, 이건 상태를 바꾸는 호출이라 결과에
  그 사실을 명시하는 게 사용자 혼란을 줄임)
- **재퀴즈 시 이전 결과를 덮어쓴다** — 이력을 남기지 않고 `food_bti` 컬럼 하나만 최신값으로 갱신(1-1장
  001-01 "이번 범위에서 제외된 것" 참고)

### 2-3. 질문 조회는 완전 공개, 결과 계산은 "선택적 로그인"
- `GET /api/food-bti/questions`: 인증 전혀 없음 — 로그인 여부와 무관하게 항상 같은 질문 12개 반환
- `POST /api/food-bti/result`: 로그인 없이 호출 가능(결과 계산만, 저장 없음) + 로그인 상태면 추가로 저장
  (2-2장) — 이 프로젝트에서 "필수 로그인"(401)도 "완전 공개"도 아닌 세 번째 패턴인데, 07의 검색 API가
  이미 같은 패턴(로그인하면 검색 기록을 남기고, 안 하면 그냥 검색만 되는 것, `docs/11.마이페이지/001-02`
  3-5장)을 쓰고 있어 새로운 패턴이 아니다.

### 2-4. JPA 엔티티를 만들지 않음(질문/결과는 전부 코드 상수)
질문 12개와 결과 코드별 이름/설명/추천 음식은 원본처럼 서비스 코드 안에 하드코딩된 상수로 유지한다. 이
프로젝트의 다른 "고정 목록" 패턴(10.리뷰의 `ReviewKeywordCatalog`처럼 코드 상수를 백엔드 검증의 유일한
출처로 삼는 방식)과 같은 결 — 질문/결과 콘텐츠를 팀원이 자주 바꿀 상황이 아니라면 DB 테이블화보다 코드가
더 단순하다(8장에서 확장 필요성 재검토 여지 남김).

## 3. API 설계
------------------------------------------------------------------------
### 3-1. 질문 목록 조회
```
GET /api/food-bti/questions
```
인증 불필요. 질문 12개를 배열로 반환(순서 고정).

### 3-2. 결과 계산 (+ 로그인 시 저장)
```
POST /api/food-bti/result
Authorization: Bearer {accessToken} (선택)
```
요청 필드: `answers`(필수, 정확히 12개 문자열 배열, 각 값은 `L/S/F/N/A/T/P/I` 중 하나 — 질문 순서와 1:1
대응). `Authorization` 헤더가 있고 유효하면 결과를 그 회원의 `members.food_bti`에 저장(2-2장).

------------------------------------------------------------------------
## 4. 에러 코드
------------------------------------------------------------------------
| 코드 | 상황 | HTTP |
|---|---|---|
| INVALID_INPUT(기존 재사용) | `answers`가 12개가 아니거나, 값이 `L/S/F/N/A/T/P/I` 중 하나가 아님 | 400 |

`NOT_LOGGED_IN`이 나오지 않는다는 점이 이 프로젝트의 다른 대부분 쓰기 API와 다르다 — 2-3장 설계상 비로그인
호출도 정상 응답이기 때문(단지 저장이 안 될 뿐).

`Member` 엔티티에 `updateFoodBti(String)` 메서드만 추가.

## 7. 원본 저장소와의 관계 / 향후 동기화
------------------------------------------------------------------------
`SoldeskProject2_Web_MBTI`는 이 프로젝트와 같은 GitHub 원격(`soldesk-org/SoldeskProject2_Web`)을 보는 별도
로컬 체크아웃(브랜치 `feature/web-map-responsive`)이다. 이번 연동은 그 브랜치의 코드를 **복사해서 포팅**한
것이지, git으로 머지/서브트리 연결을 한 것이 아니다 — 즉 원본 브랜치가 이후 수정되어도 이 프로젝트에
자동으로 반영되지 않는다. 원본 쪽에서 로직이 바뀌면(질문 문구 수정, 새 결과 코드 콘텐츠 추가 등) 이 문서와
`FoodBtiServiceImpl`을 수동으로 다시 맞춰야 한다.
