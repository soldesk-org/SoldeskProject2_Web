## 2. 핵심 설계 결정
------------------------------------------------------------------------
### 2-1. 자체 개발 대신 검증된 오픈소스 라이브러리 채택
사용자가 "Github에서 찾아줘봐 한국인이 만든 모델이나 그런 욕설 방지 스크립트"로 명확히 요청 — 조사 결과
[korcen](https://github.com/KR-korcen/korcen)(Tanat05, MIT License, PyPI 배포)을 채택했다. 순수 Python
+ 정규표현식 기반(딥러닝 프레임워크 불필요)이라 `pip install korcen` 한 줄로 가볍게 붙일 수 있으면서도,
기존 `NicknameProfanityFilter`(단순 단어목록 부분일치)보다 훨씬 강화된 정규화 로직(자모 분리, 특수문자
치환, 반복 문자 등 회피 기법 대응)을 갖추고 있다.

### 2-2. 새 Python 서버로 분리 (기존 서버에 얹지 않음)
`business-verify`/`keyword-extraction`은 팀원이 만든 서버라 함부로 라우터를 추가하지 않고, 이 프로젝트가
새로 소유하는 기능이니 `review-filter`라는 별도 Python 프로젝트로 만들었다. 포트도 기존 두 서버(둘 다
기본 8000)와 겹치지 않게 **8002**를 기본값으로 잡아서, 세 서버를 동시에 켜둘 수 있게 했다(07/12 001-04에
이미 기록된 "business-verify/recommendation 포트가 겹친다"는 한계를 이번 서버에서는 처음부터 피함).

### 2-3. korcen의 실제 판정 동작 확인 (실측)
`korcen.check(text)`와 `korcen.general(text)`가 테스트한 모든 케이스에서 동일하게 동작함을 실측으로
확인했고(카테고리별 함수 `sexual`/`belittle`/`special` 등은 서로 겹치지 않는 별도 판정이라 종합 판단에는
안 맞음), 최종적으로 `korcen.check()` 하나만 사용하기로 결정했다.

**주의할 점(라이브러리의 의도된 동작, 버그 아님)**: "씨발", "존나" 같은 아주 흔한 감탄사성 비속어는
`korcen`이 의도적으로 걸러내지 않는다(과잉 차단 방지) — 반면 "병신", "개새끼", "좆같다", 초성 축약("ㅅㅂ")은
정상적으로 걸러진다. 이 프로젝트도 라이브러리의 이 기본 판단을 그대로 신뢰하고 별도로 조정하지 않았다.

### 2-4. 검사 대상은 `content`(자유 텍스트)만, `keywords`(태그)는 제외
`keywords`는 애초에 `ReviewKeywordCatalog`(10.리뷰 001-02 2-4장)의 고정 20개 목록 중에서만 골라야 하는
구조라, 사용자가 임의 텍스트를 넣을 방법이 없다 — 검사할 필요가 없음. `content`가 비어있으면(태그만
등록하는 경우) 필터 서버 호출 자체를 생략한다(불필요한 네트워크 호출 방지).

### 2-5. 필터 서버 장애 시 "통과"(fail-open) — 신뢰성보다 가용성 우선
`ReviewFilterClient.containsProfanity()`는 Python 서버와 통신이 안 되면 예외를 던지지 않고 그냥
`false`(비속어 아님)를 반환한다. 리뷰 작성이라는 핵심 기능이 부가 기능(욕설 필터) 서버 하나가 꺼져
있다고 완전히 막히면 안 된다고 판단했다 — 08(영수증OCR)의 "매칭 실패해도 업로드는 성공"과 같은 톤.
읽기 타임아웃도 5초로 짧게 잡아서, 필터 서버가 응답이 느려도 리뷰 작성 자체가 오래 걸리지 않게 했다.

### 2-6. 별도 REST API를 새로 만들지 않음
"관리자가 미리 문구를 검사해볼 수 있는 API" 같은 것도 고려할 수 있었지만, 이번 요청 범위는 "리뷰 작성/
수정을 막는다"였으므로 `ReviewServiceImpl` 내부에서만 `ReviewFilterClient`를 호출하고, 별도 컨트롤러/
엔드포인트는 만들지 않았다("필요한 만큼만" 원칙).

## 3. API 설계
------------------------------------------------------------------------
### 3-1. (신규, Python 서버) 욕설 판별
```
POST http://localhost:8002/check
Content-Type: application/json

{ "text": "진짜 병신같은 서비스네요" }
```
응답(200)
```json
{ "profanity": true }
```
Spring 쪽에 노출되는 REST API는 아님 — `ReviewFilterClient`가 서버 내부에서만 호출.

### 3-2. 기존 API 동작 변경 (10.리뷰)
```
POST /api/reviews
PATCH /api/reviews/{reviewId}
```
`content`에 욕설/비속어가 감지되면 기존 검증(태그 허용 목록, 내용 필수 여부) 통과 후 **추가로**
`400 REVIEW_CONTENT_PROFANITY`로 거부된다. 요청/응답 필드 자체는 변경 없음.

## 6. 로컬 실행 방법
------------------------------------------------------------------------
```
cd SoldeskProject2_Python/review-filter
python -m venv venv
./venv/Scripts/python.exe -m pip install -r requirements.txt
./venv/Scripts/python.exe -m uvicorn main:app --port 8002
```
`.env`(선택)로 `ALLOWED_ORIGINS` 조정 가능(기본값 `*`). Spring 쪽은 `REVIEW_FILTER_BASE_URL` 환경변수로
주소를 바꿀 수 있고, 생략 시 `http://localhost:8002`를 기본값으로 쓴다.

## 7. 확인이 필요한 사항 / 남은 작업
------------------------------------------------------------------------
- **팀 공용 서버로 배포하지 않음** — 지금은 로컬에서 각자 켜야 하는 구조(business-verify/recommendation과
  동일한 한계). 팀 전체가 상시 쓰려면 Azure VM에 올리는 것도 검토 가능하지만 이번 범위 밖
- **필터 서버가 꺼져 있으면 욕설이 그대로 통과됨**(2-5장 fail-open 설계의 트레이드오프) — 필터 서버가 항상
  켜져 있는지 확인하는 모니터링은 14(관리자-권한)의 `GET /api/admin/status`에 아직 포함 안 됨, 필요하면
  추가 검토
- **닉네임 필터(`NicknameProfanityFilter`)는 그대로 단어목록 방식** — korcen으로 통일하는 건 이번 범위 밖
- **korcen의 "씨발/존나 허용" 판단을 이 서비스 정책에 맞게 커스터마이징할지**는 아직 확정 안 됨(2-3장) —
  실사용 중 문제가 되면 korcen의 커스텀 필터 경로(`CUSTOM_INCLUDE_FILE`)로 단어를 추가하는 것도 가능
