## 1. 아키텍처
------------------------------------------------------------------------
```
com.foodtrip.foodsearch.recommendation
 ├─ entity      RecommendationHistory (신규 JPA 엔티티)
 ├─ repository  RecommendationHistoryRepository (신규)
 ├─ service     RecommendationService / RecommendationServiceImpl (신규 - 기존엔 서비스 계층이 없었음)
 ├─ controller  RecommendationController (전면 수정)
 └─ dto         RecommendResponseDto(historyId 필드 추가), RecommendationFeedbackRequestDto(신규),
                RecommendationFeedbackResponseDto(신규)
```
기존엔 `RecommendationController`가 `RecommendationClient`(Python 서버 프록시)를 직접 호출해서 응답을
그대로 돌려주기만 했다(001-06/001-04, 07/12와 같은 "얇은 프록시" 톤). 이번에 그 사이에
`RecommendationServiceImpl`을 끼워 넣어, 로그인 여부에 따라 `recommendation_histories`에 이력을 남기고
`historyId`를 응답에 실어 보내는 역할을 추가했다.

## 2. 핵심 설계 결정
------------------------------------------------------------------------
### 2-1. 피드백 단위 = 질문(요청) 1건, 개별 추천 결과 아님
사용자가 "강남역 주변 분위기 좋은 파스타집 추천해줘 그 질문에서 피드백"으로 명확히 확정 — 추천 응답에
들어있는 여러 음식점 각각에 피드백을 남기는 게 아니라, "이 질문에 대한 추천 전체가 도움이 됐는지"를
한 번만 남긴다. 그 결과 `recommendation_results`(개별 결과 저장용, `final_score` NOT NULL이라 Python
서버가 안 주는 값을 억지로 만들어 넣어야 했을 것)는 이번에 전혀 건드리지 않아도 됐다 — 범위가 크게
줄어든 결정이었다(001-01 "이번 범위에서 제외된 것" 참고).

### 2-2. `recommendation_histories`는 로그인한 경우에만 기록
`SHOW FULL COLUMNS`로 확인한 결과 `member_id`가 원래부터 `NOT NULL`로 설계돼 있었다 — 즉 이 테이블은
처음부터 "회원 전용 이력"으로 기획된 것. `/api/recommendation/query` 자체는 07(검색)/12(음BTI)와 같은
"로그인 필수 아님" 톤을 계속 유지해야 하므로(추천 자체는 비로그인도 됨), `resolveMemberIdOrNull()` 패턴을
그대로 재사용해서 로그인 안 한 요청은 이력 저장을 건너뛰고 `historyId: null`인 채로 기존과 동일하게
응답한다. 로그인한 요청만 이력이 남고, 그 결과로만 피드백을 남길 수 있다.

### 2-3. 새 컬럼 2개만 추가 (`was_helpful`, `feedback_at`)
원래 기획 스케치엔 `was_helpful` 하나만 있었지만, "언제 피드백을 남겼는지"를 별도 컬럼 없이 확인할
방법이 없어서(`updated_at`은 이력 자체의 다른 수정에도 갱신될 수 있는 범용 컬럼) `feedback_at`을 같이
추가했다 — 10(리뷰) `keywords` 등 이 프로젝트 다른 기능에서도 "행위 시각을 상태 컬럼과 별도로 남긴다"는
패턴을 이미 쓰고 있음(예: `phone_verifications.verified_at`).
- `was_helpful BIT`(nullable) — `NULL`은 "아직 피드백 안 남김", `1`/`0`이 각각 👍/👎
- `feedback_at DATETIME`(nullable) — 피드백을 남긴 시각, 안 남겼으면 `NULL`

새 엔티티(`RecommendationHistory`)를 만들고 `ddl-auto=update`로 기존 테이블에 컬럼만 추가되는 걸 기대하는
방식을 택했다 — 이 테이블은 원래 기획된 컬럼(`recommendation_type`, `query_text`, `extracted_keywords`,
`current_latitude`, `current_longitude`, `max_budget`, `created_at`, `updated_at`)이 이미 있었으므로
그것들도 엔티티에 전부 매핑하고, 피드백 관련 2개만 신규로 추가한 것.

### 2-4. `recommend` 응답에 `historyId` 필드 추가 (하위 호환 유지)
`RecommendResponseDto`(record)에 `history_id`(JSON 스네이크케이스, 팀원 Python 응답 필드들과 통일된
네이밍) 필드를 6번째로 추가했다. 비로그인 요청은 `null`로 내려간다. 프론트는 이 값의 유무로 "피드백
버튼을 보여줄지"를 판단하면 된다. 기존 필드는 순서/이름 그대로 유지되어 있어 기존 연동 코드에 영향 없음.

### 2-5. `PATCH /api/recommendation/{historyId}/feedback` — 신규 엔드포인트, 로그인 필수
- 본인이 만든 이력에만 피드백을 남길 수 있어야 하므로 `Authorization` 헤더 필수(생략 시 `NOT_LOGGED_IN`)
- `recommendationHistoryRepository.findByRecommendationHistoryIdAndMemberId(historyId, memberId)`로
  "존재하지 않음"과 "다른 회원 소유"를 구분하지 않고 하나의 `404 RECOMMENDATION_HISTORY_NOT_FOUND`로
  합쳤다 — 14(관리자)/16(리뷰 신고) 이전부터 이 프로젝트가 일관되게 써온 "다른 회원 레코드의 존재 여부를
  노출하지 않는다"는 보안 패턴을 그대로 따름
- 같은 이력에 여러 번 `PATCH`를 보내면 마지막 값으로 덮어써진다(멱등, 재전송 시 에러 아님) — "이미
  피드백을 남겼습니다" 같은 별도 차단은 두지 않았다(11.마이페이지 즐겨찾기의 "멱등 API" 톤과 유사, 사용자
  입장에서 마음이 바뀌면 다시 누를 수 있어야 자연스럽다고 판단)

### 2-6. `resolveMemberId`/`resolveMemberIdOrNull` 복제
07/08/12와 동일하게, 패키지가 달라 공유 유틸로 뽑지 않고 `RecommendationServiceImpl`에 작은 private
헬퍼로 그대로 복제했다(`CLAUDE.md` 2장에 기록된 이 프로젝트의 확립된 컨벤션).

## 3. API 설계
------------------------------------------------------------------------
### 3-1. 추천 요청 (기존 API, 응답에 필드 1개 추가)
```
POST /api/recommendation/query
Authorization: Bearer {accessToken}   (선택 - 없어도 동작함)
Content-Type: application/json

{ "text": "강남에 있는 분위기 좋은 파스타집 추천해줘", "x": 127.0276, "y": 37.4980, "radius": 3000, "size": 10 }
```
응답(200, 기존 필드 + 신규 `history_id`)
```json
{
  "analysis": { "...": "..." },
  "recommendation_rule": "...",
  "data_notice": "...",
  "total_candidates": 12,
  "recommendations": [ "..." ],
  "history_id": 1
}
```
`Authorization` 헤더가 없거나 유효하지 않으면 `history_id: null` — 그 외 동작은 기존과 완전히 동일.

### 3-2. 추천 피드백 제출 (신규)
```
PATCH /api/recommendation/{historyId}/feedback
Authorization: Bearer {accessToken}   (필수)
Content-Type: application/json

{ "wasHelpful": true }
```
응답(200)
```json
{ "success": true, "message": "피드백이 저장되었습니다." }
```

## 4. 에러 코드
------------------------------------------------------------------------
| 코드 | 상황 | HTTP |
|---|---|---|
| RECOMMENDATION_HISTORY_NOT_FOUND(신규) | 이력이 없거나 본인 소유가 아님 | 404 |
| NOT_LOGGED_IN(기존 재사용) | 피드백 요청에 Authorization 헤더가 없음/무효 | 401 |

## 5. DB
------------------------------------------------------------------------
`recommendation_histories`에 컬럼 2개 추가(`ddl-auto=update`로 적용):
| 컬럼 | 타입 | NULL | 설명 |
|---|---|---|---|
| was_helpful | BIT | YES | 피드백 값(NULL=미제출, 1=도움됨, 0=아쉬움) |
| feedback_at | DATETIME | YES | 피드백 제출 시각(NULL=미제출) |

기존에 이미 있던 컬럼(`recommendation_type`, `query_text`, `extracted_keywords`, `current_latitude`,
`current_longitude`, `max_budget` 등)은 이번에 처음으로 실제 값이 채워지기 시작한다(이전엔 테이블 자체가
0행이었음). `current_latitude`/`current_longitude`가 `DECIMAL(38,2)`로 정의돼 있어 소수점 둘째 자리까지만
저장됨을 실측으로 확인 — 위경도 기준 오차가 꽤 크지만(약 1km 단위), 이 컬럼은 검색 로직에 실제로 쓰이지
않는 "요청 당시 위치 스냅샷" 기록용이라 기능에는 영향 없음. 원래 기획 때부터 있던 컬럼 정의라 이번 범위
에서 손대지 않음(참고 사항으로만 기록).

`recommendation_results`는 이번에 손대지 않음(2-1장).

## 6. 확인이 필요한 사항 / 남은 작업
------------------------------------------------------------------------
- DB 다이어그램(ERD) 재작성 — 이번 컬럼 추가로 최근 배포한 ERD Artifact가 낡아짐, 사용자가 나중에 직접
  다시 요청하겠다고 함(auto-memory에 기록)
- `recommendation_results`(개별 결과 피드백/저장)는 여전히 미착수 — 필요해지면 별도 기능으로 재검토
- 피드백 데이터를 실제로 추천 로직 개선에 활용하는 것은 팀원의 Python 서비스 쪽 몫, 이번 범위 밖
