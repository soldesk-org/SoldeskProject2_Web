## 4. 리뷰 임시저장(초안 자동저장) 구현 및 검증 (2026-07-22)
------------------------------------------------------------------------
001-02 2-6장 설계대로 `Project2/src/main/resources/static/tmp-map-test.html`에 순수 프론트엔드 기능으로 구현.

### 4-1. 구현
- **저장 키**: `tmp_review_draft_{restaurantId}` (`localStorage`, 음식점별 분리)
- **저장 트리거 (4곳)**: 별점 클릭, 키워드 칩 선택/해제, `#reviewContentInput`의 `input` 이벤트, 상세 패널
  닫기(`closeDetailPanel`)
- **저장 안 함 처리**: 별점 5(기본값) + 키워드 없음 + 빈 텍스트인 "완전 기본 상태"면 오히려
  `localStorage.removeItem()`으로 지움 — 빈 초안이 계속 쌓이는 것 방지
- **복원**: `openDetailPanel(r)`이 호출될 때 `loadReviewDraft(r.restaurantId)`로 저장된 값이 있으면 별점/
  키워드/텍스트를 채우고 "작성 중이던 리뷰 임시저장이 복원되었습니다." 안내 표시
- **정리**: `submitReview()` 성공 시 `clearReviewDraft(currentDetailRestaurantId)`로 그 음식점의 초안 삭제

### 4-2. Playwright 검증
서버 재기동(정적 리소스라 핫리로드 없음) 후 두 시나리오를 실제 브라우저로 검증:

**시나리오 1 — 자동저장 → 복원**: 별점 4점 클릭, 키워드 칩 1개 선택, 내용 입력 → 상세 패널 닫기 →
`localStorage` 확인(`{"rating":4,"keywords":["음식이 맛있어요"],"content":"임시저장 테스트 내용입니다"}`) →
같은 음식점 재오픈 → 별점/키워드/내용이 그대로 복원되고 안내 문구("작성 중이던 리뷰 임시저장이
복원되었습니다.")가 표시됨을 확인. **통과.**

**시나리오 2 — 제출 시 초안 삭제**: 로그인 상태(`mintAccessToken`/`activateAccessToken`로 테스트 회원 세션
발급)로 리뷰 내용 입력 → `localStorage`에 초안 존재 확인 → 제출 버튼 클릭 → 서버 응답 정상(에러 없음) →
`localStorage`에서 그 음식점 초안이 삭제됨을 확인 → 같은 음식점 재오픈 시 폼이 빈 상태(초안 복원 안내 없음)
임을 확인. **통과.**

검증에 쓴 테스트 회원/Redis 세션은 검증 직후 정리(`deleteMemberByEmail`, `cleanupAccessKey`). 검증 스크립트
(Playwright ad-hoc `.js`)는 검증 완료 후 삭제(프로젝트 공통 원칙).

## 5. 리뷰 수정/삭제 구현 및 검증 (2026-07-22)
------------------------------------------------------------------------
001-02 2-7장 설계대로 `Review.update()`/`Review.delete()` 추가, `ReviewServiceImpl`에 소유권 검증(본인 아니면
`REVIEW_ACCESS_DENIED`) + 평점 캐시 재계산 로직 구현. `ReviewController`에 `PATCH`/`DELETE /api/reviews/{id}`
2개 엔드포인트 추가.

### 5-1. Playwright 검증
테스트 회원으로 리뷰 작성 → 수정 → (다른 회원으로 수정 시도) → 삭제 순서로 실제 API 호출까지 확인:
- 수정: `{rating:2, content:"CRUD 테스트 수정됨"}`으로 PATCH → 200과 함께 갱신된 값 정상 응답
- **소유권 검증**: 별도 테스트 회원(작성자 아님)의 토큰으로 같은 리뷰 수정 시도 → `403 REVIEW_ACCESS_DENIED`
  정상 확인
- 삭제: DELETE → `204 No Content` → 이후 그 음식점 리뷰 목록(`GET .../reviews`) 조회 시 삭제된 리뷰가
  더 이상 나오지 않음을 확인(소프트 삭제가 조회 쿼리에 정상 반영됨)

검증에 쓴 테스트 회원 2명과 리뷰 행은 확인 직후 DB에서 직접 삭제해 정리함(이 검증 중 이전 세션의 리뷰
임시저장 검증 때 정리를 놓쳤던 리뷰 1건도 함께 발견해 같이 정리함 — "테스트 후 정리" 원칙을 다시 한번 확인).

### 5-2. 프론트(테스트 페이지) 연동
마이페이지(11) "내 리뷰" 목록에 수정/삭제 버튼을 붙임 — 그 목록은 이미 회원 기준으로 조회되므로(전부
본인 리뷰) 소유권 확인 UI 없이 바로 노출. 수정은 `prompt()`로 별점/내용을 받는 최소 UI(검증용, 폴리싱
아님). 자세한 프론트 연동은 001-04 참고.

## 6. 태그 전면 개편 구현 및 검증 (2026-07-22)
------------------------------------------------------------------------
001-02 2-4장 설계대로 `#키워드` 합성 방식을 완전히 걷어내고 `review_keywords` 구조화 저장으로 전환.

### 6-1. 구현
- `ReviewKeywordCatalog`(신규) — 긍정/부정 각 10개 상수 목록, `isValid()`/`sentimentOf()`
- `ReviewKeywordDao`(신규, `@Component`, `JdbcTemplate` 직접 사용 — JPA 엔티티로 매핑하지 않음, 001-02
  2-4장의 이유): `insertAll()`, `deleteByReviewId()`, `findKeywordsByReviewId()`,
  `findKeywordsByReviewIds()`(배치, 마이페이지/목록 조회용)
- `ReviewServiceImpl.create()`/`update()`에 `validateKeywords()` 추가(허용 목록 밖 값이면
  `REVIEW_KEYWORD_NOT_ALLOWED`) + `content`/`keywords` 둘 다 비었으면 `REVIEW_CONTENT_REQUIRED`
- `update()`는 `deleteByReviewId()` 후 `insertAll()`로 전체 교체, `delete()`도 `deleteByReviewId()` 호출
- `ErrorCode`에 `REVIEW_KEYWORD_NOT_ALLOWED`/`REVIEW_CONTENT_REQUIRED` 추가
- `MyPageServiceImpl.getReviews()`도 `ReviewKeywordDao`로 배치 조회해서 마이페이지 "내 리뷰" 목록에 태그 포함

### 6-2. 덤으로 발견한 버그: 죽은 엔티티의 DDL 되돌리기 시도
`review_keywords` 테이블이 FK로 참조하는 `restaurant_category_mappings`의 타입을 다른 작업(DB 스키마 정리,
`docs/00.공통/DB-테이블설계.md` 참고)에서 손보던 중, 사용되지 않는 `RestaurantCategoryMapping` 엔티티가
옛 `Long` 타입을 그대로 갖고 있어 서버 재기동마다 Hibernate가 컬럼 타입을 되돌리려다 실패하는 에러가 나고
있음을 발견 — 이 리뷰 태그 작업과 직접 관련은 없지만 같은 재기동 사이클에서 계속 걸리적거려서 그 자리에서
같이 정리(엔티티+repository 삭제, 아무 코드도 참조하지 않음을 `grep`으로 확인 후 진행).

### 6-3. Playwright 검증
`tmp-map-test.html`/`mypage-test.html` 양쪽에서 실제 브라우저로 확인:
- 긍정 10개 + 부정 10개, 총 20개 칩이 정확한 문구로 렌더링되는 것 확인
- 태그 여러 개 선택 + 텍스트 없이 등록 → 성공(태그만으로 리뷰 성립 확인)
- 텍스트만 입력 + 태그 없이 등록 → 성공
- 태그도 텍스트도 없이 등록 시도 → `400 REVIEW_CONTENT_REQUIRED` 확인
- 등록된 리뷰를 DB에서 직접 조회해 `review_keywords`에 정확한 `keyword`/`sentiment` 값으로 저장됐는지 확인
- 리뷰 수정(태그 교체) → 이전 태그가 지워지고 새 태그로 완전히 바뀌는 것 확인
- 리뷰 삭제 → 연결된 `review_keywords` 행도 함께 정리되는 것 확인
- 목록에 없는 임의 문자열을 태그로 보내는 경우 → `400 REVIEW_KEYWORD_NOT_ALLOWED` 확인

검증에 쓴 테스트 리뷰/태그 행은 확인 직후 삭제해 정리함.

## 7. 영수증 인증 필수화 + 관리자 리뷰 태그 표시 (2026-07-23)
------------------------------------------------------------------------
"영수증 리뷰로만 등록 가능하게, 일반 리뷰 안 됨"이라는 확정 지시(001-01 배경 참고)와, "리뷰 관리자쪽에
보일 때도 무슨 태그를 선택했는지 보이게"라는 14(관리자-권한) 쪽 요청이 같이 들어와서 함께 구현했다.

### 7-1. 구현
- `CreateReviewRequestDto.receiptId`에 `@NotNull` 추가(001-02 2-3장)
- `ReviewServiceImpl.create()`: `receiptId`가 없으면 `REVIEW_RECEIPT_REQUIRED`(방어적, 컨트롤러 검증과
  이중), 있어도 (본인 소유 + 이 음식점 인증) 조건을 만족하지 못하면 `REVIEW_RECEIPT_NOT_VERIFIED`로 즉시
  거부 — 기존의 "조건 안 맞으면 미인증으로 조용히 등록" 폴백 분기를 제거
- `ErrorCode`에 `REVIEW_RECEIPT_REQUIRED`/`REVIEW_RECEIPT_NOT_VERIFIED` 추가
- `tmp-map-test.html`: `submitReview()`에 `currentReceiptId` 없으면 서버 호출 전에 바로 안내하는 프론트
  가드 추가, "리뷰 작성" 섹션 제목 옆에 "영수증 인증 필수" 안내 문구 추가
- `AdminReviewResponseDto`에 `keywords: List<String>` 필드 추가, `AdminServiceImpl.listReviews()`가
  `ReviewKeywordDao.findKeywordsByReviewIds()`로 배치 조회해서 채움(마이페이지 "내 리뷰" 목록이 이미 쓰던
  것과 같은 배치 조회 패턴 재사용, 001-02 6장 6-1 참고)
- `admin-test.html`의 "리뷰 관리" 테이블에 "태그" 컬럼 추가

### 7-2. 검증 (실 서버 + 실 DB, e2e/jwtHelper·redisHelper·dbHelper 재사용해 로그인 없이 토큰 직접 발급)
throwaway 회원/관리자 계정을 만들어 검증 후 전부 삭제(테스트 데이터 정리 원칙):
- 영수증 없이 리뷰 작성 시도 → `400`, `@NotNull` 검증이 먼저 걸려 `INVALID_INPUT`으로 응답(001-02 4장에서
  예상한 대로)
- 다른 회원 소유 영수증으로 시도 → `400 REVIEW_RECEIPT_NOT_VERIFIED`
- 본인 소유지만 다른 음식점 영수증으로 시도 → `400 REVIEW_RECEIPT_NOT_VERIFIED`
- 본인 소유 + 같은 음식점 영수증(+ 태그 2개 포함) → `200`, `receiptVerified: true`로 정상 등록
- 관리자로 `GET /api/admin/reviews` 조회 → 방금 등록한 리뷰의 `keywords` 필드에 선택한 태그 2개가 정확히
  포함됨을 확인
- `admin-test.html`/`tmp-map-test.html` 정적 리소스는 서버 재기동 후 `curl`로 변경 내용이 실제로 서빙되는
  것까지 확인(이 세션에서 반복 확인된 "정적 파일은 재기동해야 반영" 이슈에 대한 표준 확인 절차)
