## 1. 서버 접속 정보
------------------------------------------------------------------------
- 로컬 개발 서버: `http://localhost:8081`
- 리뷰 작성(`POST /api/reviews`)/수정(`PATCH /api/reviews/{id}`)/삭제(`DELETE /api/reviews/{id}`)는
  **로그인 필요** — `Authorization: Bearer {accessToken}` 헤더 필수. 없거나 무효 토큰이면 `401 NOT_LOGGED_IN`.
  수정/삭제는 **본인이 작성한 리뷰만** 가능(다른 회원 리뷰를 시도하면 `403 REVIEW_ACCESS_DENIED`, 2026-07-22 추가).
- 리뷰 목록 조회(`GET /api/restaurants/{restaurantId}/reviews`)는 로그인 불필요.

## 2. 기능별 호출 흐름
------------------------------------------------------------------------
### 2-1. 음식점 상세 화면에서 리뷰 목록 표시
1. 07 상세 화면 진입 시(또는 리뷰 탭 클릭 시) `GET /api/restaurants/{restaurantId}/reviews` 호출
2. 응답 배열이 비어있으면 "아직 리뷰가 없습니다" 같은 안내 표시(빈 배열이지 에러 아님)
3. `receiptVerified: true`인 리뷰는 "영수증 인증" 뱃지를 붙여서 구분 표시 권장

### 2-2. 리뷰 작성 (2026-07-22 태그 전면 개편 반영)
1. 별점(1~5, 필수), 태그(선택, 긍정/부정 고정 20개 중 여러 개 가능, 2-2-1장), 자유 텍스트(선택) —
   **별점은 필수, 태그와 텍스트는 둘 중 하나는 있어야 함**(둘 다 비어있으면 `400 REVIEW_CONTENT_REQUIRED`
   — 프론트에서도 미리 막는 것을 권장)
2. **(2026-07-23 정책 변경) `receiptId`는 이제 필수다** — 08(영수증OCR)로 이 음식점을 상대로 방문 인증에
   성공한 영수증의 `receiptId`가 반드시 있어야 리뷰 작성 화면 자체를 열 수 있게 프론트에서 미리 막을 것을
   권장(영수증 인증 없이 제출하면 `400`, 4-3장). 예전엔 없어도 그냥 생략 가능했지만 이제는 일반 리뷰가
   허용되지 않는다.
3. **선택한 태그는 `keywords: string[]`로 그대로 보낸다**(2026-07-22 이전엔 `content` 앞에 `#태그`로
   합쳐 보내던 임시 방식이었으나 폐지됨 — 이제 `content`는 순수 자유 텍스트, `keywords`는 별도 필드). 예:
   ```json
   { "keywords": ["맛있어요", "친절해요"], "content": "정말 맛있었어요!" }
   ```
4. `POST /api/reviews` 호출 성공 시 폼을 초기화하고, 방금 등록한 리뷰가 보이도록 목록을 재조회
   (`refreshReviewList` 패턴)
5. **제출 성공 시 그 음식점의 임시저장 초안(3장)을 반드시 지울 것** — 안 지우면 다음에 들어왔을 때 이미
   제출한 내용이 "복원"돼서 사용자가 혼란스러워함

#### 2-2-1. 고정 태그 목록 (2026-07-22 신규 — 프론트에 하드코딩 필요)
서버가 태그 목록을 내려주는 조회 API는 없다 — 아래 20개 문구를 **정확히 그대로** 프론트에도 하드코딩해야
한다(다르면 서버가 `400 REVIEW_KEYWORD_NOT_ALLOWED`로 거부한다).

| 긍정(10개) | 부정(10개) |
|---|---|
| 맛있어요 / 재료가 신선해요 / 양이 많아요 / 가성비가 좋아요 / 깨끗해요 / 친절해요 / 차분해요 / 대기시간짧아요 / 음식이빨리나와요 / 가게가예뻐요 | 맛이 아쉬워요 / 재료가 신선하지 않아요 / 양이 적어요 / 가격이 비싸요 / 지저분해요 / 불친절해요 / 소란스러워요 / 대기시간길어요 / 음식이늦게나와요 / 가게가부산스러워요 |

### 2-3. 리뷰 목록에서 태그 보여주기 (2026-07-22 갱신)
서버가 `keywords: [{ keyword, sentiment }]` 배열로 구조화해서 내려주므로(4-2장), 예전처럼 `content`에서
`#` 토큰을 직접 파싱할 필요가 없다. `sentiment`(`"POSITIVE"`/`"NEGATIVE"`)로 칩 색상만 구분해서 그대로
렌더링하면 된다.

### 2-4. 리뷰 수정/삭제 (2026-07-22 추가)
- **음식점 상세 화면(07)의 일반 리뷰 목록(`GET /api/restaurants/{id}/reviews`)에는 수정/삭제 버튼을 달지
  말 것** — 이 응답(`ReviewResponseDto`)에는 작성자 `memberId`가 없어서, 프론트가 "이게 내 리뷰인지"를
  판단할 방법이 없다(의도적 — 익명 조회 API에 다른 회원의 memberId를 노출하지 않기 위함).
- **수정/삭제 버튼은 마이페이지(`docs/11.마이페이지`)의 "내 리뷰" 목록(`GET /api/mypage/reviews`)에서만
  달 것** — 그 API는 이미 회원 기준으로 조회하므로 응답에 있는 리뷰는 전부 확실히 본인 것이다.
- 수정: 별점/내용 입력받아 `PATCH /api/reviews/{reviewId}` 호출 → 성공 시 마이페이지 리뷰 목록과(열려있다면)
  음식점 상세의 리뷰 목록 둘 다 재조회해서 갱신
- 삭제: 확인 후 `DELETE /api/reviews/{reviewId}` 호출(바디 없음) → 성공 시(204) 같은 방식으로 목록 재조회

## 3. 리뷰 임시저장(초안 자동저장) — 프론트 전용 기능, 서버 API 없음
------------------------------------------------------------------------
이 기능은 **백엔드 API가 없다.** 전부 프론트 `localStorage`로 구현하는 게 계약이다(001-02 2-6장). 참고
구현이 필요하면 `tmp-map-test.html`을 그대로 참고해도 되고, 아래 규칙만 지키면 프레임워크가 달라도(React 등)
그대로 이식 가능하다.

- **저장 키**: `tmp_review_draft_{restaurantId}` (음식점마다 별도 키)
- **저장 값**: `{ rating: number, keywords: string[], content: string }` (JSON)
- **저장 시점**: 별점 변경, 키워드 토글, 텍스트 입력(매 keystroke 또는 debounce), 화면 이탈(상세 패널 닫기/
  다른 음식점으로 이동) — 최대한 자주 저장해도 부담 없는 크기라 굳이 debounce 안 해도 무방
- **"빈 초안"은 저장하지 말고 지울 것**: 별점이 기본값(예: 5)이고 키워드도 텍스트도 없는 완전 초기 상태면
  `localStorage.removeItem()`으로 정리 — 그래야 아무것도 안 쓴 음식점까지 "복원할 초안이 있다"고 잘못
  판단하지 않는다
- **복원 시점**: 그 음식점의 상세 화면(리뷰 작성 폼)이 열릴 때마다 초안이 있으면 불러와서 폼을 채우고,
  "작성 중이던 리뷰가 복원되었습니다" 같은 안내를 짧게 보여줄 것(사용자가 왜 폼에 값이 차 있는지 헷갈리지
  않도록)
- **삭제 시점**: 리뷰 제출이 **성공**했을 때만 그 음식점의 초안을 지운다(제출 실패/취소 시에는 남겨둬야
  사용자가 다시 쓸 수 있음)

## 4. API 상세
------------------------------------------------------------------------
### 4-1. 리뷰 작성
```
POST http://localhost:8081/api/reviews
Authorization: Bearer {accessToken}
Content-Type: application/json

{
  "restaurantId": "16421356",
  "rating": 4,
  "keywords": ["맛있어요", "친절해요"],
  "content": "정말 맛있었어요!",
  "receiptId": 12,
  "restaurantName": "농민백암순대 강남직영점",
  "address": "...", "roadAddress": "...", "latitude": 37.123, "longitude": 127.456
}
```
**(2026-07-23 정책 변경)** `receiptId`는 이제 **필수**다 — 없으면 `400 INVALID_INPUT`(`@NotNull` 검증),
있어도 본인 소유가 아니거나 다른 음식점 영수증이면 `400 REVIEW_RECEIPT_NOT_VERIFIED`(4-3장, 001-02 2-3장).
**(2026-07-22 마이페이지 기능 추가로 변경)** `restaurantName`이 이제 **필수** 필드다 — 마이페이지의
"내 리뷰"/"방문기록" 목록에 이름을 보여주기 위한 스냅샷으로 저장된다(서버가 카카오 데이터를 저장하지
않는 원칙이라, 08 영수증 업로드의 `restaurantName`과 같은 이유). 안 보내면 400 검증 에러. `address`/
`roadAddress`/`latitude`/`longitude`는 선택 — 있으면 마이페이지 목록에서 지도 미리보기 등에 활용 가능
(상세는 `docs/11.마이페이지/001-04` 참고).
**(2026-07-22 태그 개편으로 변경)** `keywords`는 선택 배열(2-2-1장 고정 목록 중에서만), `content`도 여전히
선택이지만 **`keywords`와 `content` 둘 다 비어있으면 안 됨**(400 `REVIEW_CONTENT_REQUIRED`). `content`는
이제 순수 자유 텍스트다 — `#태그` 합성 방식은 폐지됨.

성공 응답(200):
```json
{
  "reviewId": 55, "nickname": "홍길동", "rating": 4,
  "content": "정말 맛있었어요!",
  "keywords": [
    { "keyword": "맛있어요", "sentiment": "POSITIVE" },
    { "keyword": "친절해요", "sentiment": "POSITIVE" }
  ],
  "receiptVerified": true, "createdAt": "2026-07-22T14:35:00"
}
```
**(2026-07-23 정책 변경)** `receiptVerified`는 이제 사실상 항상 `true`다 — 조건이 안 맞으면(본인 소유가
아니거나 다른 음식점 영수증) 예전처럼 `false`로 조용히 등록되지 않고 `400 REVIEW_RECEIPT_NOT_VERIFIED`로
아예 등록 자체가 거부된다(2-2장/001-02 2-3장).

### 4-3. 리뷰 작성 관련 에러
| code | 상황 | HTTP |
|---|---|---|
| INVALID_INPUT | `receiptId` 누락 등 `@Valid` 검증 실패(2026-07-23 신규 케이스) | 400 |
| REVIEW_RECEIPT_NOT_VERIFIED | 영수증이 본인 소유가 아니거나 다른 음식점 것임(2026-07-23 신규) | 400 |
| REVIEW_CONTENT_REQUIRED | `content`와 `keywords` 둘 다 비어있음 | 400 |
| REVIEW_KEYWORD_NOT_ALLOWED | 고정 20개 목록에 없는 태그 문자열 | 400 |

실패 응답(401):
```json
{ "success": false, "code": "NOT_LOGGED_IN", "message": "로그인 상태가 아닙니다." }
```

### 4-2. 음식점별 리뷰 목록
```
GET http://localhost:8081/api/restaurants/16421356/reviews
```
성공 응답(200): 최신순 배열, 페이징 없음.
```json
[
  { "reviewId": 55, "nickname": "홍길동", "rating": 4, "content": "...",
    "keywords": [{ "keyword": "맛있어요", "sentiment": "POSITIVE" }],
    "receiptVerified": true, "createdAt": "2026-07-22T14:35:00" },
  { "reviewId": 54, "nickname": "김철수", "rating": 5, "content": "...", "keywords": [],
    "receiptVerified": false, "createdAt": "2026-07-21T19:10:00" }
]
```
리뷰가 없으면 `[]`. **(2026-07-22 추가)** 태그를 안 남긴 리뷰는 `keywords: []`.

### 4-3. 리뷰 수정 (2026-07-22 추가)
```
PATCH http://localhost:8081/api/reviews/55
Authorization: Bearer {accessToken}
Content-Type: application/json

{ "rating": 3, "keywords": ["맛이 아쉬워요"], "content": "다시 가봤는데 예전만 못하네요" }
```
`keywords`를 보내면(빈 배열 포함) 기존 태그를 전부 지우고 새 목록으로 통째로 교체한다(부분 추가/삭제 아님).
성공 응답(200): 4-1장과 같은 형식(`ReviewResponseDto`, 갱신된 값).
실패 응답(403, 본인 리뷰가 아님):
```json
{ "success": false, "code": "REVIEW_ACCESS_DENIED", "message": "본인이 작성한 리뷰만 수정/삭제할 수 있습니다." }
```
실패 응답(404): `{ "success": false, "code": "REVIEW_NOT_FOUND", "message": "리뷰를 찾을 수 없습니다." }`
실패 응답(400, 목록에 없는 태그): `{ "success": false, "code": "REVIEW_KEYWORD_NOT_ALLOWED", "message": "..." }`
실패 응답(400, 태그/내용 둘 다 없음): `{ "success": false, "code": "REVIEW_CONTENT_REQUIRED", "message": "..." }`

### 4-4. 리뷰 삭제 (2026-07-22 추가)
```
DELETE http://localhost:8081/api/reviews/55
Authorization: Bearer {accessToken}
```
성공: `204 No Content`(본문 없음). 실패 응답은 4-3장과 동일(403/404).
