## 2. 핵심 설계 결정
------------------------------------------------------------------------
### 2-1. 음식점 "부가정보" 지연 생성과의 연결
07이 카카오 ToS 준수를 위해 `restaurants` 테이블을 "음식점 기본정보를 저장하지 않고, 우리 서비스가 실제로
상호작용한 음식점만 부가정보 행으로 지연 생성"하는 구조로 재설계했다(07 001-07 2-1장). 리뷰 작성은 그
"실제 상호작용"의 대표 사례다 — `create()`가 `restaurantRepository.findByRestaurantIdAndDeletedAtIsNull(id)
.orElseGet(() -> ...save(Restaurant.createExtras(id)))`로, **그 음식점에 대한 첫 리뷰가 등록되는 순간**
비로소 `Restaurant` 행이 생긴다. 이 설계 덕분에 리뷰 기능은 "음식점이 우리 DB에 미리 있어야 한다"는 전제가
전혀 없다 — 카카오 place id 형식만 맞으면 어떤 음식점이든 바로 리뷰를 남길 수 있다.

### 2-2. 로그인 필수(작성) / 공개(조회)
- `POST /api/reviews`: **로그인 필수** — Authorization 헤더 없음/무효 토큰이면 바로 `401 NOT_LOGGED_IN`
  (05 회원정보수정, 07 사업자 등록 API와 같은 "무효 토큰=바로 401" 패턴, CLAUDE.md 2장의 "두 번째 보호된
  엔드포인트부터 인라인 헬퍼로 처리" 원칙을 그대로 따름 — 별도 필터 없이 `resolveMemberId()` private
  헬퍼 복제)
- `GET /api/restaurants/{restaurantId}/reviews`: 공개 — 비로그인도 조회 가능

### 2-3. 영수증 인증 필수 (2026-07-23 정책 변경 — 예전엔 선택이었음)
~~예전엔~~ `CreateReviewRequestDto.receiptId`가 있을 때만 검증하고, 없거나 검증에 실패해도 그냥 미인증
리뷰로 조용히 등록했다. "영수증 리뷰로만 등록 가능하게 해줘, 일반 리뷰 안 됨"이라는 확정 지시로 정책이
바뀌어, 이제 `receiptId`가 `@NotNull`(컨트롤러 검증, 없으면 `400 INVALID_INPUT`)이고, 서비스 레벨에서도
한 번 더 확인한다(REVIEW_RECEIPT_REQUIRED — 방어적 이중 체크, `resolveMemberId()` 패턴처럼 이 서비스가
컨트롤러 검증에만 의존하지 않는다는 원칙과 같은 톤).

그 영수증이 (a) 존재하고 (b) 요청한 회원 본인 것이고 (c) 지금 리뷰를 쓰는 `restaurantId`와 일치하는 세
조건을 모두 만족해야만 `200`으로 등록된다 — 하나라도 안 맞으면 `400 REVIEW_RECEIPT_NOT_VERIFIED`로 명확히
거부한다(예전의 "미인증으로 조용히 등록" 폴백은 없어짐, 08의 "매칭 실패해도 업로드는 성공"이라는 잠정
원칙은 여전히 영수증 업로드/OCR 자체에는 적용되지만 리뷰 등록 시점에는 더 이상 적용되지 않음).
`receiptVerified` 필드는 이제 사실상 항상 `true`다(검증을 통과해야만 리뷰가 만들어지므로) — 다만 응답
DTO에서 필드 자체를 없애지는 않았다(과거 리뷰 데이터 호환, 프론트 표시 로직 재사용).

### 2-4. 키워드 태그 — 긍정/부정 20개 고정 목록 + `review_keywords` 구조화 저장 (2026-07-22 전면 개편)
~~예전엔~~ `CreateReviewRequestDto`에 키워드 전용 필드가 없어서, 프론트가 선택한 키워드를
`"#키워드1 #키워드2\n자유텍스트"` 형태로 `content`에 합성해 보내는 임시 방식이었다. "네이버처럼 리뷰 태그를
넣어야 하는데, 긍정/부정 각 10개씩 고정 목록으로 바꾸고 테이블에도 저장되게 해달라"는 확정 지시로 전면
개편했다.

**고정 태그 목록** (`ReviewKeywordCatalog`, 신규):

| 긍정(10개) | 부정(10개) |
|---|---|
| 맛있어요 / 재료가 신선해요 / 양이 많아요 / 가성비가 좋아요 / 깨끗해요 / 친절해요 / 차분해요 / 대기시간짧아요 / 음식이빨리나와요 / 가게가예뻐요 | 맛이 아쉬워요 / 재료가 신선하지 않아요 / 양이 적어요 / 가격이 비싸요 / 지저분해요 / 불친절해요 / 소란스러워요 / 대기시간길어요 / 음식이늦게나와요 / 가게가부산스러워요 |

사용자 확인 과정에서 "대기시간" 쌍의 방향(짧아요/길어요)이 나머지 9쌍과 반대로 보인다는 피드백을 받아
짧아요=긍정/길어요=부정으로 확정했다.

**저장 위치 — 팀원이 만들어둔 `review_keywords` 테이블 재사용**: 다른 팀원이 AI 추천 기능용으로 이미
만들어둔 `review_keywords`(`review_id`, `keyword`, `sentiment` ENUM('POSITIVE','NEGATIVE'), `score`,
`created_at`)가 마침 이번에 필요한 스키마와 정확히 일치해서 새 테이블을 만들지 않고 그대로 재사용했다
(`docs/00.공통/DB-테이블설계.md` 참고). **단, `sentiment`가 실제 MySQL ENUM 타입이라 이 컬럼을 JPA
`@Entity`로 매핑하면 `ddl-auto=update`가 재기동마다 스키마를 임의로 바꾸려 들 위험이 있다** — 다른
팀원이 이 테이블을 동시에 계속 발전시키고 있어서 그 위험을 감수할 수 없었다. 그래서 `ReviewKeywordDao`
(신규, `@Component`, JPA가 아니라 `JdbcTemplate` 직접 사용)로만 이 테이블에 접근하도록 설계했다 —
이 프로젝트에서 JPA를 쓰지 않는 유일한 테이블이다.

- `ReviewKeywordCatalog.isValid(keyword)`가 허용 목록의 유일한 출처(백엔드 검증) — 목록에 없는 값을 보내면
  `400 REVIEW_KEYWORD_NOT_ALLOWED`(4장)
- `CreateReviewRequestDto`/`UpdateReviewRequestDto`에 `keywords: List<String>`(선택) 필드 추가
- **별점은 여전히 필수, `content`(자유 텍스트)와 `keywords`는 "둘 중 하나는 있어야" 하는 관계로 바뀜** —
  태그만 선택하고 텍스트 없이 등록하는 것도, 텍스트만 쓰고 태그 없이 등록하는 것도 가능. 둘 다 비어있으면
  `400 REVIEW_CONTENT_REQUIRED`(네이버 리뷰 UX와 동일한 톤 — 태그만으로도 리뷰가 성립)
- 리뷰 응답(`ReviewResponseDto`)에도 `keywords: [{ keyword, sentiment }]` 배열로 구조화해서 내려줌 — 예전처럼
  프론트가 `content`에서 `#` 토큰을 직접 파싱할 필요가 없어짐
- 리뷰 수정은 기존 태그를 전부 지우고(`deleteByReviewId`) 새로 받은 목록을 다시 넣는 방식(전체 교체, 부분
  patch 아님 — 2-7장의 "별점+내용 통째로 교체" 방침과 동일하게 태그도 통째로 교체)
- 리뷰 삭제 시 연결된 태그도 함께 정리(`deleteByReviewId`)

### 2-5. 평점 캐시 갱신
리뷰 등록 성공 시마다 `refreshRatingCache()`가 그 음식점의 `AVG(rating)`/`COUNT(*)`를 다시 계산해
`Restaurant.avgRating`/`reviewCount`에 저장한다(07의 목록/검색/상세 응답에 쓰이는 캐시값, 07 001-02 5-0장).
매 리뷰마다 전체 재계산이라 리뷰 수가 아주 많아지면 비효율적일 수 있지만, 지금 규모에서는 단순함이 우선
(증분 계산 최적화는 필요해지면 나중에).

### 2-6. 리뷰 임시저장(초안 자동저장) — 순수 프론트엔드 기능
2026-07-22 추가 요청("리뷰 적다가 잠시 나갔다 올 때 임시저장도 가능하게"). **백엔드 변경 없음** — 서버에
초안을 저장하는 API를 만들지 않고, 프론트(`tmp-map-test.html`)가 `localStorage`에 음식점별로
(`tmp_review_draft_{restaurantId}`) 별점/키워드/텍스트를 저장했다가 복원하는 방식으로 구현. 서버 API가
필요 없다고 판단한 이유:
- 로그인 여부와 무관하게 동작해야 자연스러움(작성 중엔 아직 제출 전이라 서버에 남길 이유가 약함)
- 기기 간 동기화(다른 브라우저에서도 이어쓰기)까지는 요구사항에 없었음 — 필요해지면 그때 서버 저장으로
  전환 검토(7장)

상세 로직(저장 트리거/정리 시점)은 001-03 4장.

### 2-7. 리뷰 수정/삭제 — 본인 소유만 (2026-07-22 추가)
"리뷰 작성·수정·삭제 다 되어야 해" 확정 지시로 추가. 설계는 최대한 단순하게:
- **수정**: 작성 때와 같은 필드(별점+내용) 전체를 교체하는 방식(부분 patch 아님) — 화면도 "다시 작성" 톤으로
  단순화. 키워드 칩도 `content`에 합성돼 있으므로(2-4장) 수정 시 통째로 새 `content` 문자열을 보내면 됨.
- **삭제**: 소프트 삭제(`deletedAt` + `status='DELETED'`) — `Restaurant`/`Menu` 등 이 프로젝트 전반의 삭제
  패턴과 동일. `deletedAt IS NULL` 조건이 이미 모든 조회 쿼리에 걸려 있어(3-2장 등) 별도 필터링 코드 추가 없이
  자동으로 목록에서 빠짐.
- **소유권 검증**: `review.getMemberId().equals(요청자 memberId)`가 아니면 `REVIEW_ACCESS_DENIED`(403) —
  다른 회원의 리뷰는 존재를 알 수는 있지만(404가 아니라 403) 손댈 수 없음. 관리자 강제 삭제(신고 처리 등)는
  이번 범위 밖(7장).
- **평점 캐시 재계산**: 수정(별점이 바뀔 수 있음)/삭제 둘 다 `refreshRatingCache()`를 다시 호출해 그 음식점의
  `avgRating`/`reviewCount`를 갱신한다(2-5장과 동일한 이유) — 삭제된 리뷰의 별점이 평균에 계속 남아있으면
  안 되므로 필수.
- **음식점 부가정보 행이 없는 극단적 케이스**: 수정/삭제 시점에 그 리뷰가 가리키는 `Restaurant` 행이 어떤
  이유로 이미 없어졌다면(이론상 발생하지 않아야 하지만) 평점 캐시 갱신만 건너뛰고 리뷰 수정/삭제 자체는
  정상 진행한다(방어적 null 체크).

## 3. API 설계
------------------------------------------------------------------------
### 3-1. 리뷰 작성
```
POST /api/reviews
Authorization: Bearer {accessToken} (필수)
```
요청 필드: `restaurantId`(필수, 문자열), `rating`(필수, 1~5), `content`(선택, 최대 1000자), `keywords`(선택,
**2026-07-22 신규** — 고정 태그 목록 중 문자열 배열, 2-4장), `content`/`keywords` 둘 중 하나는 있어야 함,
`receiptId`(**필수, 2026-07-23 정책 변경** — 08 업로드 응답의 `receiptId`, 본인 소유 + 이 음식점 인증
영수증이어야 함, 2-3장), `restaurantName`(**2026-07-22 마이페이지 기능 추가로 신규 필수** — 11(마이페이지)
"내 리뷰"/"방문기록" 목록 표시용 스냅샷, 상세는 11 001-02 3-1장), `address`/`roadAddress`/`latitude`/
`longitude`(선택, 같은 스냅샷 목적)

### 3-2. 음식점별 리뷰 목록
```
GET /api/restaurants/{restaurantId}/reviews
```
로그인 불필요. 정렬은 `status='NORMAL' AND deleted_at IS NULL`인 리뷰를 **최신순**으로 전부 반환(페이징 없음
— 리뷰가 아주 많아지는 음식점이 생기면 페이징 추가 검토, 7장).

### 3-3. 리뷰 수정 (2026-07-22 추가)
```
PATCH /api/reviews/{reviewId}
Authorization: Bearer {accessToken} (필수)
```
요청 필드: `rating`(필수, 1~5), `content`(선택, 최대 1000자), `keywords`(선택, **2026-07-22 신규**, 2-4장) —
작성과 같은 검증 규칙(`content`/`keywords` 둘 중 하나는 있어야 함), 태그는 통째로 교체(기존 목록 삭제 후
새 목록 삽입). 스냅샷 필드(2-1장/11 001-02 3-1장)는 수정 대상 아님(음식점 자체를 바꾸는 게 아니므로).

### 3-4. 리뷰 삭제 (2026-07-22 추가)
```
DELETE /api/reviews/{reviewId}
Authorization: Bearer {accessToken} (필수)
```
성공 시 `204 No Content`(본문 없음).

## 4. 에러 코드
------------------------------------------------------------------------
| 코드 | 상황 | HTTP |
|---|---|---|
| NOT_LOGGED_IN | 작성/수정/삭제 시 Authorization 헤더 없음/무효 | 401 |
| VALIDATION_ERROR(기존 재사용) | `rating` 범위(1~5) 밖, `restaurantId` 누락 등 `@Valid` 검증 실패 | 400 |
| REVIEW_NOT_FOUND(신규, 2026-07-22) | 존재하지 않거나 이미 삭제된 `reviewId`로 수정/삭제 시도 | 404 |
| REVIEW_ACCESS_DENIED(신규, 2026-07-22) | 본인이 작성하지 않은 리뷰를 수정/삭제 시도(2-7장) | 403 |
| REVIEW_KEYWORD_NOT_ALLOWED(신규, 2026-07-22) | `keywords`에 고정 목록(2-4장)에 없는 값이 포함됨 | 400 |
| REVIEW_CONTENT_REQUIRED(신규, 2026-07-22) | `content`와 `keywords` 둘 다 비어있음(2-4장) | 400 |
