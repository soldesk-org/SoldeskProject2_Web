# 09. 이용약관/개인정보처리방침 버전관리 — 분석/설계

## 1. 기존 상태 확인

- `Project2/src/main/resources/static/terms-service.html`, `terms-privacy.html` — 순수 정적 페이지.
  본문/목차/버전 배지(`#termsVersion`, `#termsEffectiveAt`)가 전부 하드코딩돼 있었다.
- `docs/09.이용약관-개인정보처리방침`에 언급된 "레거시 txt 원본 파일"은 이 저장소(main 브랜치 워크트리)에는
  존재하지 않았다 — 대신 두 정적 HTML 페이지 자체가 최신 확정 본문(2026-08-06 운영팀 전달본)을 그대로
  담고 있었으므로, "지어내지 않고 기존 내용을 그대로 옮긴다"는 원칙에 따라 이 HTML 본문을 v1 시드
  콘텐츠로 사용했다.
- `com.foodtrip.foodsearch.admin` 패키지 확인 결과, `/api/admin/**` 전체가 `SecurityConfig`에서
  `hasRole("ADMIN")`으로 이미 막혀 있고(`JwtAuthenticationFilter`가 JWT의 `role` 클레임으로
  `SecurityContext`를 채움), 그 외 모든 API는 각 서비스가 `resolveMemberId()`를 개별 구현하는 패턴이었다
  (`report.service.ReportServiceImpl` 등에서 확인).
- `com.foodtrip.foodsearch.notification` 패키지는 회원 개인별 알림 벨이고, 이번에 만드는 "공지 게시판"과는
  전혀 다른 개념이라 재사용하지 않고 새 테이블/도메인으로 분리했다(요청사항에서도 명시적으로 구분 지시).

## 2. 스키마 설계

### 2-1. `terms_documents` (약관 버전)

| 컬럼 | 타입 | 비고 |
|---|---|---|
| terms_document_id | BIGINT PK | |
| doc_type | VARCHAR(20) | `SERVICE` \| `PRIVACY`. review_reports.status 등 기존 관례를 따라 진짜 JPA enum이 아닌 문자열 상수(`TermsDocument.DOC_TYPE_*`)로 관리 — ddl-auto=update 환경에서 네이티브 ENUM 매핑 시 스키마 변경 위험이 있다는 게 리뷰 태그(review_keywords) 사례로 이미 확인됐다. |
| version_label | VARCHAR(40) | 화면 노출용 라벨(예: "2026-08-01"). 관리자가 안 주면 시행일자로 자동 생성. |
| title | VARCHAR(200) | |
| content | LONGTEXT | HTML 그대로 저장(관리자 전용 입력이라 신뢰 수준이 기존 정적 페이지와 동일 — XSS 새니타이즈는 이번 범위에 포함하지 않음, 아래 6장 참고). `<h2 id="...">` 제목이 프론트 목차 자동 생성의 소스가 된다. |
| effective_date | DATE | 시행일자. |
| change_summary | TEXT | 공지에 노출되는 변경 요약. |
| created_at | DATETIME | |

"현재 버전"은 별도 `is_current` 컬럼이 아니라 **"시행일이 오늘 이하인 것 중 가장 최근 것"으로 매 조회마다
파생 계산**한다(`TermsDocumentRepository.findFirstByDocTypeAndEffectiveDateLessThanEqualOrderBy...`). 컬럼으로
관리하면 새 버전을 넣을 때마다 이전 행의 플래그를 갱신하는 로직이 별도로 필요한데, "시행일 되면 자동
전환"이 이 기능의 핵심이라 파생 계산이 더 정확하다(예약된 미래 버전은 시행일 전까지 자동으로 "아직
아님"을 유지).

## 3. API 설계

공개:
- `GET /api/terms/{docType}` — 현재 버전 전체(본문 포함)
- `GET /api/terms/{docType}/versions` — 버전 목록(요약, `current` 플래그 포함)
- `GET /api/terms/{docType}/versions/{termsDocumentId}` — 특정 과거 버전 전체
- `GET /api/notices` — 공지 목록
- `GET /api/notices/{noticeId}` — 공지 상세(변경 전/후 본문 포함)

관리자(`/api/admin/**`, 기존 SecurityConfig가 이미 hasRole("ADMIN")로 막아줌 — 컨트롤러에서 별도 인가
체크 안 함):
- `POST /api/admin/terms/{docType}/versions` — 새 버전 등록. **이전 버전이 있으면 같은 요청 안에서 변경
  공지까지 함께 게시한다**(요청사항 3번 "하나로 묶는 게 낫다"는 지침을 그대로 따름 — CLAUDE.md 2장의
  "필요한 만큼만" 원칙과도 맞음). 최초 버전(그 타입의 첫 등록)은 비교 대상이 없으므로 공지를 만들지
  않는다.
- `GET /api/admin/terms/{docType}/versions` — 관리자용 버전 목록(공개 목록과 같은 데이터, 관리자 화면
  전용 진입점으로 분리)
- `GET /api/admin/notices` — 관리자용 공지 목록(작성자 admin id 등 추가 필드 포함)

## 4. 14일/30일 사전고지 규칙 — 어디서, 어떻게 검증하는가

`AdminTermsServiceImpl.createVersion()` 한 곳에서만 검증한다(업무 규칙은 그 규칙이 실제로 적용되는 단일
지점에서 강제한다는, 이 프로젝트가 17.리뷰-필터링 등에서 이미 따르던 패턴).

- 그 문서 타입의 **이전 버전이 없으면**(최초 등록) 검증하지 않는다 — 비교/고지할 대상 자체가 없다.
- 이전 버전이 있으면 `noticeType`(`MINOR`/`MAJOR`)이 필수이고, `LocalDate.now()`부터
  `effectiveDate`까지의 일수(`ChronoUnit.DAYS.between`)가 MINOR는 14일, MAJOR는 30일 이상이어야 한다.
  못 미치면 `400 TERMS_NOTICE_LEAD_TIME_TOO_SHORT`로 거부한다.
- 관리자 화면(`admin.js`)에도 같은 규칙으로 즉시 안내하는 힌트 텍스트를 넣었지만, 이건 UX 보조 수단일
  뿐이고 **신뢰의 기준은 항상 서버 쪽 검증**이다(클라이언트 검증 우회 가능성을 항상 전제).

## 5. 변경 전/후 비교(diff) 화면 — 판단 근거

요구사항에서 실제 line-diff 알고리즘은 선택사항("작은 프로젝트 규모상 과함")이라고 명시했다. 이번
구현은 **두 버전의 전체 본문을 "변경 전"/"변경 후" 카드로 나란히 보여주는 방식**을 택했다(진짜 diff
알고리즘/하이라이팅은 만들지 않음). 이유:

- 약관 본문은 문단 단위 재구성이 잦아(조항 삽입/순서 변경 등) 순수 텍스트 diff가 오히려 읽기 어려운
  결과를 낼 수 있다.
- 두 버전 다 각자 목차(h2 자동 스캔)를 갖고 있어, 나란히 두고 같은 조 번호끼리 훑어보는 것만으로도
  실사용에는 충분하다고 판단했다.
- **이 부분은 사용자가 검토 시 재확인해야 할 판단 사항**이다 — "nice to have"로 언급된 문단 단위
  하이라이팅은 이번 범위에 넣지 않았다.

## 6. 판단 사항(사용자 재확인 필요)

1. **docs 폴더 배치**: 저장소 현재 상태(main 워크트리)에는 `docs/09.이용약관-개인정보처리방침` 폴더 자체가
   없었다(txt 원본도, 001 문서 세트도 없음). "이미 존재하는 09 폴더를 리스트럭처링하라"는 지시를 따를 수
   없어서, 대신 `docs/09.이용약관-개인정보처리방침-버전관리` 새 폴더를 만들어 001-01~04 문서 세트를
   채웠다. 폴더 번호(09)는 주제상 가장 자연스러운 자리라고 판단했지만, 이 저장소의 다른 docs 번호
   부여 관례(예: develop 브랜치의 실제 관례)와 다를 수 있으니 최종 번호/이름은 검토 후 조정 가능.
2. **content를 HTML로 그대로 저장**: 관리자만 새 버전을 등록할 수 있고(Security로 이미 막힘), 기존
   정적 페이지도 원래 신뢰된 운영팀 텍스트를 그대로 HTML로 심어뒀던 것과 같은 수준이라 별도 새니타이즈
   로직을 추가하지 않았다. 관리자 계정이 탈취되는 경우까지 고려한 저장 시점 새니타이즈는 이번 범위 밖.
3. **버전 목록/공지 목록에서 "관리자용"과 "공개용" API를 분리**했지만 실제 응답 내용은 거의 동일(관리자
   쪽에 `createdByAdminMemberId` 등 몇 필드만 추가)하다 — 완전히 새로운 조회 로직을 만들기보다 필드만
   더 넣은 별도 DTO로 처리, 과한 분기 없이 단순하게 유지했다.
