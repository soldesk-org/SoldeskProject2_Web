### 1-2. 설계 대비 실제 구현
설계 문서(001-02)에서 정한 내용을 그대로 구현했으며, 별도로 방향이 바뀐 부분은 없음. 아래는 구현하면서 구체적으로 확정한 세부사항.

- **비밀번호 재설정 토큰 저장소**: 설계대로 `password_reset_tokens` 테이블을 만들지 않고 Redis만 사용 (`PasswordResetTokenService`). 키 `pwreset:{SHA-256(rawToken)}` → 값 `memberId`, TTL 1시간. `StringRedisTemplate.opsForValue().getAndDelete()`로 조회+삭제를 원자적으로 처리해 1회용을 보장함
- **원본 토큰**: `SecureRandom` 32바이트 → `Base64.getUrlEncoder().withoutPadding()`으로 인코딩(URL 쿼리스트링에 그대로 써도 안전한 문자셋)
- **이메일 마스킹**: `EmailMasker.mask()`를 설계(6장) 그대로 구현 — 로컬파트/도메인명 모두 "2자 이상이면 앞 2자, 아니면 앞 1자" + 고정 마스크(`***`/`****`) + TLD는 그대로 노출
- **재설정 URL**: `application.yml`의 `password-reset.frontend-url`(기본값 `http://localhost:5173/reset-password`, `PASSWORD_RESET_FRONTEND_URL` 환경변수로 override) + `?token=` + rawToken

### 1-3. 설계 문서 작성 이후 구현 중 새로 발견/결정한 사항
**비밀번호 재설정 요청(5-2)의 메일 발송 실패 처리 — 001-02 10장 "확인이 필요한 사항"에서 열어뒀던 항목**

구현 도중 실제로 문제가 재현됨: 이 프로젝트는 현재 Gmail 앱 비밀번호가 만료되어 모든 메일 발송이 `MAIL_SEND_FAIL`로 실패하는 상태([001-03.회원가입-구현-테스트.md](../01.회원가입/001-03.회원가입-구현-테스트.md) 참고, 아직 미해결). `requestPasswordReset()`에서 `mailService.sendPasswordResetMail()` 예외를 그대로 흘려보내도록 처음 작성했더니:
- 이메일이 **존재하지 않는** 경우 → 메일 발송 자체를 시도하지 않으므로 200 성공
- 이메일이 **존재하는** 경우 → 메일 발송을 시도하다 `MAIL_SEND_FAIL`로 500 실패

즉 응답의 HTTP 상태코드(200 vs 500)만으로 "이 이메일이 가입된 이메일인지 아닌지"가 그대로 드러나 버림 — 001-02 문서 전체를 관통하는 "계정 존재 여부 비노출" 원칙이 메일 서버 장애 상황에서 깨지는 것을 실제 테스트로 확인함(아래 2-3장 참고).

**결정 및 수정**: `requestPasswordReset()`에서 `mailService.sendPasswordResetMail()` 호출을 `try-catch(CustomException)`로 감싸, 메일 발송 실패도 흡수하고 항상 동일한 200 성공 응답을 반환하도록 수정함. Redis에는 토큰이 이미 발급되어 있으므로(TTL 1시간 뒤 자동 소멸) 데이터 정합성 문제는 없음 — 다만 사용자는 메일을 받지 못하므로 실질적으로 재설정을 완료할 수 없는 상태가 됨(Gmail 문제 해결 전까지는 이 흐름 자체가 실사용 불가, 별도 이슈로 관리 중).

## 3. 3차 구현 (2026-07-18): SMS(뿌리오) 인증으로 이메일 전체공개
------------------------------------------------------------------------
[001-02 12장](001-02.이메일찾기-비밀번호찾기-분석-설계.md#12-sms-인증으로-이메일-전체-공개-설계-ppurio-연동-2026-07-18-요구사항-추가) 설계대로, 이메일 찾기(닉네임+전화번호 조회) 이후 전화번호 SMS 인증에 성공하면 마스킹 없이 전체 이메일을 공개하는 기능을 구현함. SMS 연동 공통 컴포넌트(`PhoneAuthService`, `PpurioSmsService`, `PhoneVerification`)는 [01.회원가입 001-03 6장](../01.회원가입/001-03.회원가입-구현-테스트.md#6-6차-구현-2026-07-18-sms뿌리오-전화번호-본인인증)에서 구현한 것을 그대로 재사용함.

### 3-1. 구현
- **`FindEmailVerificationSessionService`**(신규, `member/service` 패키지): 이메일 찾기 성공 시 `memberId`를 그대로 응답에 노출하지 않기 위한 단기 조회 세션 토큰 서비스. `PasswordResetTokenService`와 같은 패턴(Redis + SHA-256 해시 저장)이되, 재설정 토큰과 달리 세션 동안(TTL 10분) 여러 번(발송→확인→공개조회) 조회해야 해서 `consume()`(조회+삭제) 대신 `resolve()`(조회만, TTL 자연만료)로 단순화함. Redis 키: `findemail:session:{SHA-256(rawToken)}` → `memberId`
- **`MemberServiceImpl.findEmail()`**: 회원을 찾으면 마스킹된 이메일과 함께 `findEmailVerificationSessionService.issue(memberId)`로 발급한 `verificationToken`을 응답에 포함하도록 변경 (`FindEmailResponseDto`에 `verificationToken` 필드 추가)
- **`MemberController`/`MemberService`에 엔드포인트 3개 추가** (모두 `verificationToken`으로 세션의 memberId를 확인한 뒤 처리, 001-02 12-2장)
  - `POST /api/members/find-email/verify-phone/send-code`: 세션의 회원과 요청 전화번호의 `phone_hash`가 일치하는지 재확인(다른 회원 번호로 SMS 인증을 시도하는 것을 막기 위함, 불일치 시 `PHONE_NOT_FOUND`) 후 `phoneAuthService.sendVerificationCode(memberId, phone, PURPOSE_FIND_EMAIL)`
  - `POST /api/members/find-email/verify-phone/confirm`: `phoneAuthService.verifyCode(memberId, phone, code, PURPOSE_FIND_EMAIL)`
  - `POST /api/members/find-email/reveal`: `phoneAuthService.isRecentlyVerified(memberId, PURPOSE_FIND_EMAIL, 10)`(10분 이내 인증 완료 여부)를 확인해 통과하면 `member.getEmail()`을 마스킹 없이 그대로 응답
- **`PhoneAuthService.isRecentlyVerified()`**(신규 메서드): 001-02 12-4장에서 열어뒀던 "전체 이메일 조회의 유효시간"을 10분으로 확정해 구현. 전화번호 일치 여부가 아니라 "인증 완료 후 경과 시간"만 확인 — reveal 단계에서는 전화번호를 다시 넘기지 않는 흐름이라 별도 메서드로 분리함
- **`ErrorCode`**: `INVALID_VERIFICATION_TOKEN`(400, "유효하지 않거나 만료된 조회 정보입니다") 추가 — `verificationToken`이 없거나 만료된 경우 공통으로 사용

### 3-2. 설계 문서 대비 확정한 사항
- **12-4장 "memberId 노출 방식" 확인 필요 항목**: 설계 단계에서 제안했던 두 방안(memberId 직접 노출 vs 단기 토큰) 중, 더 안전한 단기 토큰 방식(`FindEmailVerificationSessionService`)으로 확정해서 구현함
- **12-4장 "전체 이메일 조회 유효시간" 확인 필요 항목**: 10분으로 확정 (`PhoneAuthService.isRecentlyVerified()`의 `REVEAL_VALID_MINUTES`)

### 3-3. 실제 SMS 발송은 검증하지 않음 (의도된 범위 제한)
[01.회원가입 001-03 6-2장](../01.회원가입/001-03.회원가입-구현-테스트.md#6-2-실제-sms-발송-검증-2026-07-20-진행--아래-6-5장-참고)과 동일한 이유로, 뿌리오 계정이 아직 발급되지 않아 이번 구현에서는 `/api/members/find-email/verify-phone/send-code`를 실제로 호출하는 테스트는 진행하지 않았다(사용자 요청에 따른 의도된 범위 제한, 2026-07-20 라이브 테스트는 [01.회원가입 001-03 6-5장](../01.회원가입/001-03.회원가입-구현-테스트.md) 참고 — 그쪽에서 공용 `PpurioSmsService`를 검증하면 이 기능도 같은 서비스를 재사용하므로 함께 검증됨). 이 변경(엔티티/서비스/DTO 추가, `FindEmailResponseDto`에 필드 추가)이 기존 이메일찾기/비밀번호찾기 15개 테스트를 깨뜨리지 않는지는, 전체 Playwright 스위트를 재실행해 확인함 → [01.회원가입 001-03 6-4장](../01.회원가입/001-03.회원가입-구현-테스트.md#6-4-전체-스위트-재실행-결과-2026-07-18-5050-통과)의 50/50 통과 결과에 포함됨 (회원가입 쪽 PHONE_NOT_VERIFIED 게이트 추가와 같은 시점에 함께 재실행함).
