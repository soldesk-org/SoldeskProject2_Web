## 1. 요구사항 정리
------------------------------------------------------------------------
### 1-1. 이메일 찾기
- 입력값: 닉네임, 전화번호
- DB에서 닉네임 + 전화번호가 모두 일치하는 회원을 조회, 일치하면 이메일을 `ab***@gm****.com` 형태로 마스킹하여 응답
- **(2026-07-18 요구사항 추가) SMS 본인인증 도입 결정** — 전화번호로 SMS 인증번호를 발송해 본인 확인에 성공하면 마스킹 없이 전체 이메일을 공개하는 기능 추가. 상세 설계는 12장 참고. 인증에 실패하거나 인증을 진행하지 않으면 기존처럼 마스킹된 이메일만 제공
- 프론트 연동 없음 (요구사항 문서 명시)

### 1-2. 비밀번호 찾기
- **요청 단계**: 입력값 이메일 → DB에 존재하는 이메일이면 재설정 메일 발송, 존재하지 않아도 프론트에서는 "발송됨"처럼 보이되 실제 메일은 안 감 (이메일 존재 여부 비노출 — 로그인의 INVALID_CREDENTIALS 설계와 같은 원칙)
- 메일에는 비밀번호 재설정 URL 포함, URL 유효시간 1시간
- 유효시간이 지났거나(만료) 위조된 토큰 값으로 접근하면 처리 불가
- **재설정 단계**: 새 비밀번호 / 새 비밀번호 확인 입력 → DB에는 요구사항 문서의 "암호화 환경"(Argon2, 단방향)으로 암호화하여 저장 — 회원가입/로그인과 동일한 `PasswordEncoder` 재사용

## 2. 전체 플로우
------------------------------------------------------------------------
### 2-1. 이메일 찾기
1) 클라이언트가 닉네임 + 전화번호로 조회 요청
2) 입력한 전화번호를 `PhoneCryptoService.hash()`로 해시(phone_hash)한 뒤, `nickname` + `phone_hash`가 모두 일치하는 회원을 조회
   - 닉네임만 맞고 전화번호가 틀린 경우, 반대의 경우, 둘 다 틀린 경우를 구분하지 않고 모두 동일하게 "일치하는 회원 없음" 처리 (계정 존재 여부/부분 일치 여부 비노출 — 로그인 설계와 같은 원칙)
3) 일치하는 회원이 있으면 이메일을 마스킹(6장)하여 응답, 없으면 MEMBER_NOT_FOUND
4) 탈퇴(WITHDRAWN) 회원은 조회 대상에서 제외 (11장 참고)

### 2-2. 비밀번호 찾기 - 재설정 요청
1) 클라이언트가 이메일로 재설정 요청
2) email로 members 조회 + member_credentials 존재(가입 완료) 확인
   - 없으면: 아무 것도 하지 않고 **동일한 성공 응답**만 반환 (이메일 존재 여부 비노출, 요구사항 문서의 "실제 전송은 안 됨"과 일치)
   - 있으면: 재설정 토큰을 발급(7장)하고, 토큰이 담긴 재설정 URL을 이메일로 발송
3) 응답은 성공 여부와 무관하게 동일한 메시지("입력하신 이메일로 재설정 안내를 보냈습니다." 등)로 통일

### 2-3. 비밀번호 찾기 - 재설정 확정
1) 클라이언트가 메일의 URL에 담긴 토큰 + 새 비밀번호 + 새 비밀번호 확인으로 요청
2) 토큰을 해시하여 Redis에서 조회 → 없거나 만료됐으면 INVALID_RESET_TOKEN
3) 새 비밀번호 / 새 비밀번호 확인 일치 여부, 비밀번호 정책(회원가입과 동일 정규식) 검증
4) 토큰에 매핑된 memberId로 `member_credentials.password_hash`를 Argon2로 재암호화하여 갱신, `password_updated_at` 갱신
5) 사용한 토큰은 Redis에서 즉시 삭제 (1회용 처리 — 재사용/재생 공격 방지)

------------------------------------------------------------------------

## 4. 데이터 모델
------------------------------------------------------------------------
### 4-1. members / member_credentials — 조회 + 일부 갱신
이메일 찾기는 `members`(nickname, phone_hash, email, status) 조회만 수행.
비밀번호 찾기는 `members`(email 조회) + `member_credentials`(password_hash 갱신) 사용. 신규 컬럼 없음.

### 4-2. 비밀번호 재설정 토큰 저장소: DB 테이블 대신 Redis 사용 (설계 변경)
[DB-테이블설계.md 1-5장](../00.공통/DB-테이블설계.md)에는 `password_reset_tokens` 테이블이 정의되어 있으나, 이번 구현에서는 **이 테이블을 사용하지 않고 Redis로 대체**한다.

**사유**: 이 프로젝트는 로그인 실패 카운트/잠금([`LoginAttemptService`](../../Project2/src/main/java/com/foodtrip/foodsearch/member/service/LoginAttemptService.java))과 refresh token([`RefreshTokenService`](../../Project2/src/main/java/com/foodtrip/foodsearch/member/service/RefreshTokenService.java))을 이미 "TTL이 있는 1회성/단기성 데이터"라는 이유로 DB가 아닌 Redis에 저장하도록 전환해뒀다([001-03 로그인 4차 구현](../02.로그인/001-03.로그인-구현-테스트.md#6-4차-구현-2026-07-17-redis-연동-일괄-반영) 참고). 비밀번호 재설정 토큰도 정확히 같은 성격(유효시간 1시간, 1회용, 만료되면 그냥 버려도 되는 데이터)이므로 같은 방식을 따른다. DB 테이블 + 별도 만료 정리 배치를 새로 만드는 대신 Redis TTL로 만료를 자동 처리하면 구현/운영 부담이 더 적다.

이 판단에 따라 `password_reset_tokens` 테이블은 실제로 생성하지 않으며, `DB-테이블설계.md`의 해당 항목은 (`refresh_tokens`와 마찬가지로) 문서상 설계와 실제 구현이 다른 항목으로 남는다. 필요 시 팀 공유 문서에 반영 필요 (11장 참고).

**Redis 키 구조** (`PasswordResetTokenService`, `RefreshTokenService`와 동일한 스타일)
| 키 | 값 | TTL | 비고 |
|---|---|---|---|
| `pwreset:{SHA-256(rawToken)}` | memberId | 1시간 | 발급 시 SET, 사용 성공 시 즉시 DELETE(1회용) |

- 이메일 링크에는 원본 토큰(`rawToken`, SecureRandom 기반 고엔트로피 랜덤 문자열)만 노출하고, Redis에는 그 토큰의 SHA-256 해시만 저장한다. 전화번호(7장 PhoneCryptoService)처럼 되돌려 쓸 필요가 없는 값이라 별도 비밀키 없는 단순 해시로 충분하다 — 목적은 Redis 스냅샷/백업이 유출되더라도 원본 토큰이 그대로 노출되지 않도록 하는 것.
- 토큰 자체가 이미 memberId를 값으로 담고 있으므로, DB 테이블 설계안의 `is_used`/`used_at` 같은 별도 컬럼 없이 "DELETE되면 사용됨/무효"로 단순화된다.

## 5. API 설계
------------------------------------------------------------------------
### 5-1. 이메일 찾기
POST /api/members/find-email
Request:
```json
{ "nickname": "홍길동", "phone": "010-1234-5678" }
```
Response (성공, 200):
```json
{ "success": true, "message": "일치하는 회원 정보를 찾았습니다.", "maskedEmail": "ab***@gm****.com" }
```
Response (실패, 400):
```json
{ "success": false, "code": "MEMBER_NOT_FOUND", "message": "일치하는 회원 정보를 찾을 수 없습니다." }
```
처리:
- 입력값 검증 (닉네임/전화번호 형식 — 회원가입과 동일 규칙)
- `phoneCryptoService.hash(request.getPhone())`로 조회용 해시 계산
- `memberRepository.findByNicknameAndPhoneHash(nickname, phoneHash)`로 조회, WITHDRAWN 상태 제외
- 없으면 MEMBER_NOT_FOUND, 있으면 이메일을 마스킹해 응답

### 5-2. 비밀번호 재설정 요청
POST /api/members/password-reset/request
Request:
```json
{ "email": "user@example.com" }
```
Response (성공, 200 — 이메일 존재 여부와 무관하게 항상 이 응답):
```json
{ "success": true, "message": "입력하신 이메일로 비밀번호 재설정 안내를 보냈습니다." }
```
처리:
- 입력값 검증 (이메일 형식)
- email로 members 조회 + member_credentials 존재 확인 (둘 다 있어야 "가입 완료된 회원") — 실패해도 예외를 던지지 않고 조용히 종료
- 성공 시: `PasswordResetTokenService.issue(memberId)`로 rawToken 발급 → `MailService.sendPasswordResetMail(email, resetUrl)`로 발송 (resetUrl = 프론트 재설정 페이지 URL + `?token=` + rawToken, 11장 참고)
- 메일 발송 실패(`MAIL_SEND_FAIL`) 시에는 회원가입과 달리 rawToken이 이미 Redis에 저장돼 있어도 사용자가 메일을 받지 못했으므로 무해 — 어차피 1시간 뒤 자동 만료되고, 응답은 그대로 동일 성공 메시지로 통일할지 500으로 알릴지는 확인 필요(11장)

### 5-3. 비밀번호 재설정 확정
POST /api/members/password-reset/confirm
Request:
```json
{ "token": "Xy82f...(rawToken)", "newPassword": "N3wP@ss1", "newPasswordConfirm": "N3wP@ss1" }
```
Response (성공, 200):
```json
{ "success": true, "message": "비밀번호가 재설정되었습니다." }
```
Response (실패, 400):
```json
{ "success": false, "code": "INVALID_RESET_TOKEN", "message": "유효하지 않거나 만료된 링크입니다." }
```
처리:
- `newPassword` 형식 검증 (회원가입과 동일 정규식: 8~20자, 영문+숫자+특수문자)
- `newPassword` != `newPasswordConfirm` → PASSWORD_CONFIRM_MISMATCH
- `PasswordResetTokenService.consume(token)`으로 memberId 조회 겸 즉시 삭제 (원자적 1회 사용 처리) → 없으면 INVALID_RESET_TOKEN
- `member_credentials.password_hash = passwordEncoder.encode(newPassword)`, `password_updated_at` 갱신

## 6. 이메일 마스킹 규칙 설계
------------------------------------------------------------------------
요구사항 문서의 예시 `ab***@gm****.com` 기준으로, `EmailMasker` 유틸리티에서 아래 규칙으로 고정 마스킹한다 (원본 길이에 비례하지 않는 고정형 — 짧은 로컬파트/도메인이라도 규칙은 동일하게 적용해 마스킹 강도가 입력 길이로 추론되지 않게 함).

| 구간 | 규칙 | 예시 (`abcdef@gmail.com`) |
|---|---|---|
| 로컬파트(@ 앞) | 앞 2자만 노출, 나머지는 고정 `***` | `ab***` |
| 도메인 이름(마지막 `.` 앞까지) | 앞 2자만 노출, 나머지는 고정 `****` | `gm****` |
| TLD(마지막 `.` 이후) | 그대로 노출 | `.com` |

- 로컬파트가 2자 이하인 경우: 1자만 노출 + `***` (예: `a@gmail.com` → `a***@gm****.com`)
- 도메인 이름이 2자 이하인 경우: 1자만 노출 + `****`
- 이 규칙은 이번 요구사항 문서에 명시된 예시 하나만 기준으로 정한 것이라 다른 케이스(멀티 서브도메인 등)는 최대한 보수적으로 마스킹하는 쪽으로 처리 (11장 참고)

## 7. 비밀번호 재설정 토큰 상세 설계
------------------------------------------------------------------------
- **발급**: `SecureRandom` 기반 32바이트 랜덤 값을 Base64 URL-safe 인코딩 (URL 쿼리스트링에 그대로 넣어도 안전, refresh token의 UUID보다 엔트로피가 큼 — 이메일로 전송되어 유출 경로가 하나 더 있는 값이므로 더 높은 엔트로피를 사용)
- **저장**: 위 rawToken을 그대로 저장하지 않고 SHA-256 해시로 저장 (4-2장 이유 참고), 키 TTL 1시간
- **검증/소비**: `consume(rawToken)` 메서드가 조회 + 삭제를 한 번에 수행(`GETDEL` 또는 `GET` 후 `DELETE`)하여, 같은 토큰으로 동시에 두 번 요청이 와도 하나만 성공하도록 함(레이스 컨디션 방지 — 로그인/회원가입에서 `saveAndFlush` + 제약조건으로 레이스를 막은 것과 같은 목적, 여기서는 Redis 원자적 삭제로 대체)
- **만료**: Redis TTL로 자동 처리, 별도 배치/스케줄러 불필요
- **재발급**: 같은 이메일로 재설정을 다시 요청하면 새 토큰을 발급한다. 이전에 발급된 토큰의 즉시 무효화는 이번 범위에 포함하지 않음(memberId별로 키를 하나만 유지하는 refresh token과 달리, 토큰 자체가 키이므로 이전 토큰도 "먼저 쓰는 사람이 임자"로 살아있게 됨 — 필요 시 개선 여지 있음, 11장 참고)

## 8. 검증 규칙
------------------------------------------------------------------------
| 필드 | 규칙 |
|---|---|
| nickname (이메일 찾기) | 회원가입과 동일: 한글/영문/숫자 2~10자 |
| phone (이메일 찾기) | 회원가입과 동일: `010-XXXX-XXXX` 형식 |
| email (재설정 요청) | 이메일 형식(@Email), 필수값 |
| token (재설정 확정) | 필수값(@NotBlank) |
| newPassword / newPasswordConfirm | 회원가입과 동일 정규식(8~20자, 영문+숫자+특수문자), 둘 다 필수값 + 서로 일치해야 함 |

| INVALID_INPUT | 입력값 형식 오류 (기존 재사용) | 400 | 입력값 형식이 올바르지 않습니다. |
| MEMBER_NOT_FOUND | 닉네임+전화번호 조합이 일치하는 회원 없음 (신규) | 400 | 일치하는 회원 정보를 찾을 수 없습니다. |

| PASSWORD_CONFIRM_MISMATCH | 새 비밀번호와 확인이 다름 (신규) | 400 | 새 비밀번호가 일치하지 않습니다. |

※ 비밀번호 재설정 요청(5-2)은 이메일 존재 여부와 무관하게 항상 200 성공으로 응답하므로 이 흐름에는 실패용 에러코드가 없음 (요구사항 문서의 "존재하지 않아도 보낸 것처럼" 요건과 일치)

## 12. SMS 인증으로 이메일 전체 공개 설계 (Ppurio 연동, 2026-07-18 요구사항 추가)
------------------------------------------------------------------------
1-1장/10장에서 보류했던 "전화번호 인증에 성공하면 이메일을 전부 보여준다"를 실제로 설계함. 연동 스펙과 공통 컴포넌트(PhoneAuthService/PpurioSmsService/PhoneVerification)는 [00.공통/SMS-인증-Ppurio-연동-가이드.md](../00.공통/SMS-인증-Ppurio-연동-가이드.md), [01.회원가입 001-02 8-1장](../01.회원가입/001-02.회원가입-분석-설계.md#8-1-sms-전화번호-인증-설계-ppurio-연동-2026-07-18-요구사항-추가)에서 이미 설계한 것을 그대로 재사용하고, 이 장에서는 이메일 찾기 쪽에서 그것을 어떻게 조합해 쓰는지만 다룸.

### 12-1. 전체 플로우
기존 이메일 찾기(2-1장)의 3번 단계("일치하는 회원이 있으면 이메일을 마스킹하여 응답") 뒤에 선택적 인증 단계를 추가하는 구조. 회원가입의 SMS 인증(찾는 대상이 아직 없는 "가입 예정자"의 전화번호를 인증)과 달리, 여기서는 **이미 DB에서 특정된 기존 회원**의 전화번호를 인증한다는 점이 다름 — 그래서 `PhoneVerification`의 `purpose='FIND_EMAIL'`로 구분해서 저장한다(00.공통 가이드 6-2장).

1) 클라이언트가 닉네임 + 전화번호로 조회 요청 (기존 `POST /api/members/find-email`, 2-1장과 동일)
2) 일치하는 회원이 있으면 **마스킹된 이메일 + 해당 회원의 memberId**를 응답 (전체 이메일은 아직 안 줌)
   - memberId를 그대로 응답에 노출하는 것이 부담스러우면, 비밀번호 재설정 토큰(7장)과 같은 방식으로 "조회 세션 토큰"을 발급해 그 안에 memberId를 담아 응답하는 방법도 있음 (12-4장 "확인이 필요한 사항" 참고)
3) 클라이언트가 그 memberId(또는 조회 세션 토큰) + 전화번호로 SMS 인증번호 발송 요청 → `PhoneAuthService`가 해당 전화번호로 SMS 발송, `phone_verifications`에 `purpose='FIND_EMAIL'`로 저장
4) 클라이언트가 인증번호 입력 → 검증 성공 시 `is_verified=1`
5) 클라이언트가 (인증이 완료된) memberId로 "전체 이메일 조회"를 요청하면, 마스킹 없이 원본 이메일을 응답
   - 인증이 안 되어 있거나 만료/미완료 상태면 PHONE_NOT_VERIFIED로 거부

### 12-2. API 설계 (신규 3개, 기존 find-email과 별도 엔드포인트)
#### 12-2-1. 전체 이메일 공개용 SMS 인증번호 발송
```
POST /api/members/find-email/verify-phone/send-code
{ "memberId": 1, "phone": "010-1234-5678" }
```
처리: memberId로 members 조회 → phone_hash와 요청 phone의 해시가 일치하는지 재확인(다른 사람 번호로 인증 시도 방지) → `PhoneAuthService`로 SMS 발송, `phone_verifications`에 `purpose='FIND_EMAIL'` 저장

#### 12-2-2. SMS 인증번호 확인
```
POST /api/members/find-email/verify-phone/confirm
{ "memberId": 1, "phone": "010-1234-5678", "code": "123456" }
```
처리: `phone_verifications`(memberId + purpose='FIND_EMAIL') 최신 레코드로 검증(00.공통 가이드 6-3장과 동일 로직) → 성공 시 `is_verified=1`

#### 12-2-3. 전체 이메일 조회
```
POST /api/members/find-email/reveal
{ "memberId": 1 }
```
Response (성공, 200):
```json
{ "success": true, "message": "이메일을 확인했습니다.", "email": "abcdef@gmail.com" }
```
처리: memberId로 `phone_verifications`(purpose='FIND_EMAIL')의 최신 레코드가 `is_verified=1`이고 아직 유효(예: 인증 완료 후 10분 이내 — 12-4장 참고)한지 확인 → 아니면 `PHONE_NOT_VERIFIED`, 맞으면 `members.email`을 마스킹 없이 그대로 응답

### 12-3. 예외/에러코드 추가
| 코드 | 상황 | HTTP Status |
|---|---|---|
| PHONE_NOT_FOUND | SMS 발송 이력이 없는 전화번호로 확인 요청 (00.공통과 공유) | 400 |
| INVALID_CODE / EXPIRED_CODE | 인증번호 불일치/만료 (00.공통과 공유) | 400 |
| PHONE_NOT_VERIFIED | 전체 이메일 조회 시점에 SMS 인증이 안 되어 있음 (00.공통과 공유) | 400 |
| SMS_SEND_FAIL | SMS 발송 실패 (00.공통과 공유) | 500 |

### 12-4. 확인이 필요한 사항 (이 장 한정)
- **memberId를 응답/요청에 그대로 노출하는 방식이 안전한가**: 12-1장 2번에서 언급한 대로, 순차 증가하는 PK를 그대로 클라이언트에 노출하면 다른 memberId를 넣어 무차별로 SMS 인증 시도(비용 발생)를 걸 위험이 있음. 12-2-1에서 phone_hash 재검증으로 1차 방어는 되지만, 애초에 "닉네임+전화번호로 찾은 조회 세션"임을 증명하는 단기 토큰(예: 비밀번호 재설정 토큰과 같은 Redis 기반, TTL 5~10분)을 memberId 대신 발급하는 방식이 더 안전 — 최종 채택 여부는 팀 확인 필요
- **전체 이메일 조회(12-2-3)의 유효시간**: 인증 완료 후 얼마나 지나면 다시 인증해야 하는지(위 설계안은 임의로 10분을 예시로 듦) 미정
- **SMS 인증 자체의 비용 어뷰징 방지**: 존재하지 않는 닉네임+전화번호 조합으로는 애초에 MEMBER_NOT_FOUND라 SMS 발송 단계까지 못 가지만, 실제 존재하는 회원의 전화번호를 알아내 무한정 SMS 인증을 요청하는 것을 막을 재발송 제한 정책이 필요(00.공통 가이드 8장의 동일 항목과 함께 결정)
