## 1. 요구사항 정리
------------------------------------------------------------------------
- 수정 가능 항목: 이메일, 비밀번호(+비밀번호 확인), 닉네임, 전화번호 — 회원가입 때 받은 값 전부
- **소셜 로그인 계정은 비밀번호 변경 불가** — 다만 소셜 로그인 기능 자체가 아직 구현되어 있지 않음(1-1장 참고)
- **이메일/전화번호를 실제로 변경할 때는 회원가입과 동일한 방식으로 재인증 필요** (기존 `/api/mail/*`, `/api/phone/*` 인증 로직 재사용)
- 회원정보 수정 페이지 진입 시 **비밀번호/전화번호를 제외한 나머지(이메일, 닉네임)는 자동으로 채워져 있어야 함**
- **(2026-07-19 요구사항 추가) 회원 탈퇴 기능** — 회원정보수정 화면에서 탈퇴도 처리할 수 있어야 함. 1-1장과 같은 이유로 **소셜 로그인 계정은 이번 범위에서 제외하고 일반(이메일/비밀번호) 회원만 대상으로 설계**(현재 시점에는 모든 회원이 일반 회원이라 사실상 전체 회원이 대상)
- **(2026-07-19 요구사항 추가) 프로필 사진 등록/변경/삭제** — 회원가입/회원정보수정/소셜로그인 전체에 걸친 요구사항([06.소셜로그인 001-02 참고](../06.소셜로그인/001-02.소셜로그인-분석-설계.md), 실제 파일 업로드/서빙은 이 문서(005)에서 한 번만 구현하고 다른 두 기능은 재사용). **일반/소셜 계정 모두 선택 항목**(구글만 플랫폼 특성상 사실상 항상 제공됨) — 파일 업로드 방식으로 등록하며, 사진이 없으면 기본 프로필로 대체 표시해야 하나 **실제 기본 이미지 자산은 아직 미정(추후 상의 후 등록, 2-8장 참고)**
- 프론트 연결 없음 → REST API + Postman/테스트 코드로 검증

### 1-1. 소셜 로그인 가드에 대한 판단
요구사항은 "소셜 로그인으로 로그인한 경우 비밀번호 수정 불가"이지만, 이 프로젝트에는 아직 소셜 로그인 기능 자체가 없다(DB 설계상 `social_accounts` 테이블은 존재하나 이를 채우는 코드가 없음 — 사업자 회원가입 때의 `business_profiles`와 달리, 이 테이블은 아직 아무도 사용하지 않는 완전히 빈 테이블). 지금 시점에는 **모든 회원이 일반(이메일/비밀번호) 가입 회원**이라 이 가드가 실제로 걸릴 일이 없다.

이전 세션에서 확인된 방침(관리자 페이지 관련 논의)대로 "아직 필요 없는 기능은 미리 만들지 않는다"는 원칙에 따라, 이번 구현에서는 **소셜 로그인 여부를 판별하는 코드(= `social_accounts` 조회)를 만들지 않는다.** 대신 이 문서에 설계만 남겨두고, 실제 구현은 소셜 로그인 기능이 만들어지는 시점에 함께 추가하는 것을 제안한다 (8장 "확인이 필요한 사항" 참고).

## 2. 전체 플로우
------------------------------------------------------------------------
### 2-1. 회원정보 수정 페이지 진입 (자동 채움)
1) 클라이언트가 로그인 시 발급받은 `accessToken`을 `Authorization: Bearer {accessToken}` 헤더에 실어 조회 요청
2) 토큰에서 memberId를 꺼내 현재 회원 정보 조회
3) **이메일, 닉네임만** 응답 (비밀번호는 원래 응답 불가 항목, 전화번호는 요구사항에 따라 의도적으로 제외 — 8장 참고)

### 2-2. 이메일 변경 (실제로 값이 바뀌는 경우에만)
1) 새 이메일 인증번호 발송 요청 (로그인 상태 필요) → 6자리 인증번호 생성, 발송
2) 새 이메일 인증번호 확인 요청 → 일치하면 `is_verified=1` 처리
3) 최종 저장(2-4) 시점에 "그 새 이메일이 인증완료 상태인지"를 확인

기존 회원가입의 `EmailVerification`/`EmailAuthService`를 그대로 재사용하되, 회원가입용 발송(`sendVerificationCode`)은 호출 시 **새 members row를 만드는** 부작용이 있어 이미 존재하는 회원에게는 그대로 쓸 수 없다. 그래서 `purpose` 컬럼을 추가해 이메일 인증도 전화번호 인증(001-02(회원가입) 8-1장)과 같은 방식으로 "이미 존재하는 회원의 재인증" 흐름을 분리한다 (4-1장 참고).

### 2-3. 전화번호 변경 (제출한 경우에만)
1) 새 전화번호 SMS 인증번호 발송 요청(로그인 상태 필요)
2) 새 전화번호 SMS 인증번호 확인 요청
3) 최종 저장(2-4) 시점에 그 전화번호가 인증완료 상태인지 확인

전화번호는 이미 `PhoneVerification.purpose`가 있어서(001-02(회원가입) 8-1장), `purpose='PROFILE_PHONE_UPDATE'`만 추가하면 기존 `PhoneAuthService`의 범용 메서드(`sendVerificationCode`/`verifyCode`/`isVerified`)를 그대로 재사용할 수 있다 — 신규 서비스 코드가 필요 없음.

### 2-4. 회원정보 저장 (닉네임/이메일/전화번호/비밀번호)
1) 클라이언트가 `accessToken` + 닉네임(필수) + 이메일(선택, 값이 바뀌는 경우만) + 전화번호(선택, 값을 바꿀 때만) + 비밀번호/비밀번호 확인(선택) 제출
2) 토큰에서 memberId 확인(로그인 상태 아니면 거부)
3) 비밀번호를 바꾸려는 요청이면: 비밀번호/비밀번호 확인 일치 검증(회원가입 8-2장과 동일 원칙) → Argon2 재해시 → `member_credentials.password_hash` 갱신
4) 닉네임이 현재 값과 다르면: 중복 확인(본인 제외) → 갱신
5) 이메일이 현재 값과 다르면: 그 이메일로 `PROFILE_EMAIL_UPDATE` 인증이 완료되어 있는지 확인(미인증이면 거부) → 중복 확인(본인 제외, 이론상 인증 단계에서 이미 걸러지지만 레이스 컨디션 방어용으로 한 번 더) → 갱신
6) 전화번호가 제출되었으면: 그 전화번호로 `PROFILE_PHONE_UPDATE` 인증이 완료되어 있는지 확인(미인증이면 거부) → 중복 확인(본인 제외) → 암호화/해시 후 갱신
7) 완료 응답

### 2-5. 회원 탈퇴 (2026-07-19 요구사항 추가)
1) 클라이언트가 `accessToken` + 현재 비밀번호를 함께 제출 (본인 확인 — accessToken 탈취만으로 탈퇴가 되지 않도록 재인증 요구, 회원가입/로그인에서 쓰던 "민감한 동작 전 비밀번호 재확인" 관례와 동일선상)
2) 토큰에서 memberId 확인(로그인 상태 아니면 `NOT_LOGGED_IN`) + 이미 탈퇴 처리된 계정이면 `ACCOUNT_WITHDRAWN`(동시에 두 번 탈퇴를 시도하는 경우의 방어)
3) `member_credentials.password_hash`와 제출한 비밀번호를 Argon2로 비교(불일치 시 `INVALID_CREDENTIALS`, 로그인의 비밀번호 불일치 처리와 동일 코드 재사용)
4) `members.status`를 `'WITHDRAWN'`으로, `withdrawn_at`을 현재 시각으로 갱신 (닉네임/이메일/전화번호 등 기존 데이터는 그대로 보존 — 별도 익명화/삭제는 이번 범위 밖, 8장 참고)
5) 현재 로그인 세션 무효화: 로그아웃과 동일하게 `refreshTokenService.revoke(memberId)` + `accessTokenSessionService.revoke(jti)` 호출 — 탈퇴 직후 같은 토큰으로 더 이상 요청을 보낼 수 없도록 함
6) 완료 응답

### 2-8. 프로필 사진 등록/변경/삭제 (2026-07-19 요구사항 추가)
1) **등록/변경**: 로그인 상태에서 이미지 파일을 업로드(`multipart/form-data`) → 서버가 로컬 디스크에 저장하고 URL을 발급해 `members.profile_image_url`에 기록. 기존에 등록돼 있던 사진이 있으면(직접 업로드한 파일인 경우에 한해) 교체 후 이전 파일을 정리
2) **삭제**: 로그인 상태에서 삭제 요청 → `profile_image_url`을 `null`로 되돌림(다시 삭제해도 에러 없이 그대로 성공 — 멱등)
3) **조회**: 기존 `GET /api/members/me`(2-1장) 응답에 `profileImageUrl` 필드를 추가 — 값이 없으면(직접 등록도 안 했고 소셜 로그인으로 받아온 사진도 없으면) `null`을 그대로 응답한다. **(2026-07-19 확정) "기본 프로필"은 서버가 이미지 파일을 내려주는 방식이 아니라, 프론트가 `profileImageUrl: null`일 때 `nickname`(같은 응답의 필드) 첫 글자를 원형 배지로 렌더링하는 방식으로 확정함** — 예: 닉네임 `eric7378` → 원형 배지에 대문자 `E`. 서버는 별도 기본 이미지 자산을 준비할 필요가 없어졌다. `profile-image.default-url` 설정값은 혹시 나중에 "이니셔널 대신 고정 이미지"로 바꾸고 싶을 때를 위해 그대로 남겨두되(비어있으면 지금처럼 `null`), 당장은 쓰이지 않는 보조 옵션임
4) **회원가입 시점 등록**: 회원가입 API(`POST /api/members/signup`) 자체에는 파일 업로드를 추가하지 않는다 — 이미 JSON 계약으로 확정/문서화돼 있는 엔드포인트를 멀티파트로 바꾸면 기존 연동이 깨진다(9장 "확인이 필요한 사항"에서 다루는 트레이드오프). 대신 **회원가입 → 로그인 → (사진을 고른 경우) 이 절의 업로드 API를 그대로 재사용**하는 2단계 흐름으로 안내한다 — [01.회원가입 001-02](../01.회원가입/001-02.회원가입-분석-설계.md)에 같은 내용을 상호 참조로 남겨둠
5) **소셜로그인 신규가입 시 자동 채움**: [06.소셜로그인 001-02 2-3장](../06.소셜로그인/001-02.소셜로그인-분석-설계.md)에서 플랫폼이 준 프로필 사진 URL을 그대로 `profile_image_url`에 저장 — 파일을 우리 서버로 복사하지 않고 외부 URL을 그대로 씀(회원이 나중에 이 절의 API로 직접 업로드하면 그때부터는 우리가 저장한 파일로 교체됨)

**저장 방식**: 클라우드 스토리지(S3 등)를 새로 도입하지 않고 로컬 디스크에 저장 + 정적 리소스로 그대로 서빙(`/profile-images/**`). 파일명은 서버가 `UUID`로 생성해 경로 추측/충돌을 막고, 이미지 형식(jpg/png/gif/webp)과 용량(기본 5MB)을 검증한다.

## 3. 인증(로그인 상태 확인) 방식 — 이 기능에서 새로 필요해진 것
------------------------------------------------------------------------
지금까지 구현된 API 중 로그인 상태를 확인하는 곳은 로그아웃(`POST /api/members/logout`)뿐이었고, 그마저도 `accessToken`을 **요청 바디**에 실어 보내는 방식이었다(로그아웃은 POST라 바디가 자연스러움). 회원정보수정은 **조회(GET)가 필요한 첫 기능**이라 바디 방식이 맞지 않는다(GET 요청은 바디를 안 싣는 것이 표준) — 그래서 이번 기능부터는 표준적인 `Authorization: Bearer {accessToken}` 헤더 방식으로 로그인 상태를 확인한다.

### 인증 확인 로직 (신규 공통 로직, `MemberServiceImpl`에 private 헬퍼로 추가하는 정도로 충분 — Spring Security나 필터 체인 같은 프레임워크 도입은 이번에도 하지 않음)
1. `Authorization` 헤더에서 `Bearer ` 접두사를 뗀 토큰 문자열 추출 (없으면 `NOT_LOGGED_IN`)
2. `JwtProvider.parseClaims(token)`으로 서명/만료 검증 (실패 시 `NOT_LOGGED_IN`, 로그아웃의 기존 처리와 동일)
3. 클레임에서 `memberId`(subject)와 `jti` 추출
4. **`AccessTokenSessionService`에 그 `jti`가 아직 등록되어 있는지 확인** (신규 메서드 `isActive(jti)` 필요 — 지금은 `register`/`revoke`만 있고 조회 메서드가 없음). 로그아웃되었거나 다른 사유로 무효화된 토큰을 걸러내기 위함. 등록되어 있지 않으면 `NOT_LOGGED_IN`

※ 로그아웃의 기존 "로그인 상태 확인" 로직(`refreshTokenService.exists(memberId)` 확인)과 미묘하게 다른 기준이다 — 로그아웃은 "이 회원이 활성 세션을 갖고 있는지"(refresh token 존재)를 보고, 여기서는 "이 access token 자체가 아직 유효한지"(`AccessTokenSessionService` 등록 여부)를 본다. 후자가 이번 기능처럼 "지금 들고 있는 이 토큰으로 계속 인증된 요청을 보내도 되는지"를 확인하는 목적에 더 정확하다. 로그아웃 로직 자체를 이 기준으로 바꾸는 것은 이번 범위에 포함하지 않음(8장 참고).

|---|---|---|---|
| (기존 컬럼 전부 동일) | | | |
| purpose | VARCHAR(20) | NOT NULL, DEFAULT `'SIGNUP'` (신규) | `'SIGNUP'`(회원가입) / `'PROFILE_EMAIL_UPDATE'`(회원정보수정, 신규) |

기존 회원가입 코드(`EmailAuthService.sendVerificationCode`/`verifyCode`)는 전부 `purpose='SIGNUP'`으로 저장/조회하도록 맞춰야 하므로, `EmailVerificationRepository.findTopByMemberIdOrderByCreatedAtDesc(memberId)`를 `findTopByMemberIdAndPurposeOrderByCreatedAtDesc(memberId, purpose)`로 바꾸는 리팩터링이 필요하다(phone_verifications 도입 때와 동일한 패턴).

### 4-2. phone_verifications — 신규 컬럼 없음, `purpose` 값만 추가
이미 `purpose` 컬럼이 있으므로(001-02(회원가입) 4-4장) 새로운 값 `'PROFILE_PHONE_UPDATE'`만 상수로 추가하면 됨. 테이블/엔티티 변경 없음.

### 4-3. members — 스키마 변경 없음
`nickname`, `phone`, `phone_hash`, `email` 컬럼을 그대로 갱신 대상으로 사용. 전화번호 암호화(`PhoneAttributeConverter`)/해시(`PhoneCryptoService`)도 회원가입과 완전히 동일하게 재사용.

회원 탈퇴(2-5장)는 `status`(`'WITHDRAWN'`으로 변경, [DB-테이블설계.md](../00.공통/DB-테이블설계.md)에 이미 정의된 값)와 `withdrawn_at`(탈퇴 처리 시각) 컬럼을 사용 — 둘 다 로그인 기능(001-02(로그인))에서 이미 검증(`STATUS_WITHDRAWN` 상태의 회원은 로그인 차단)에 쓰이고 있던 기존 컬럼으로, 엔티티(`Member`)에 컬럼 매핑만 이미 되어 있고 값을 채우는 코드(`withdraw()` 메서드)가 없던 상태였다. 별도 익명화(닉네임/이메일 마스킹 등)나 `deleted_at`(논리 삭제, 다른 목적의 컬럼) 처리는 하지 않는다 — 소프트 삭제 없이 상태값만 바꾸는 방식.

프로필 사진(2-8장)도 `profile_image_url`(VARCHAR(2000), 2026-07-20 기준 — [001-03 참고](001-03.회원정보수정-구현-테스트.md), 최초 설계 시점엔 VARCHAR(500)이었으나 구글 등 일부 플랫폼 URL이 500자를 넘어 저장 실패하는 문제가 실사용 중 발견되어 확장함) 컬럼을 그대로 사용 — [DB-테이블설계.md 1-1장](../00.공통/DB-테이블설계.md)에 이미 정의돼 있었으나 지금까지 값을 채우는 코드가 전혀 없던 컬럼이다.

### 4-4. member_credentials — 스키마 변경 없음
`password_hash`, `password_updated_at` 갱신에 기존 `MemberCredential.updatePassword()`(비밀번호 재설정 기능에서 이미 만들어둔 메서드, [04.이메일찾기 001-02 참고](../04.이메일찾기-비밀번호찾기/001-02.이메일찾기-비밀번호찾기-분석-설계.md))를 그대로 재사용.

## 5. API 설계
------------------------------------------------------------------------
아래 6개 엔드포인트 전부 `Authorization: Bearer {accessToken}` 헤더 필요(없거나 무효면 `NOT_LOGGED_IN`, 401).

### 5-1. 내 정보 조회 (자동 채움용)
```
GET /api/members/me
Authorization: Bearer {accessToken}
```
Response(성공, 200)
```json
{ "success": true, "email": "user@example.com", "nickname": "홍길동" }
```
비밀번호는 원래 응답에 포함하지 않고(보안), **전화번호도 요구사항에 따라 의도적으로 응답에 포함하지 않는다**.
~~이 판단은~~ **(2026-07-22 번복)** 마이페이지(11) 기능 추가로 `phone`이 다시 응답에 포함되도록 바뀌었다 —
5-10장 참고.

### 5-2. 이메일 변경 인증번호 발송
```
POST /api/members/me/email/send-code
Authorization: Bearer {accessToken}
Content-Type: application/json

{ "email": "new-user@example.com" }
```
Response: `{ "success": true, "message": "인증번호가 발송되었습니다." }` (기존 `MailResponseDto` 재사용)
처리: 새 이메일이 **본인의 현재 이메일과 같으면** `INVALID_INPUT`("변경할 이메일이 현재 이메일과 같습니다" 등 — 8장 확인 필요) / 다른 회원이 이미 쓰는 이메일이면 `DUPLICATE_EMAIL` / `EmailVerification`(member_id=본인, purpose=`PROFILE_EMAIL_UPDATE`) 신규 저장 후 메일 발송

### 5-3. 이메일 변경 인증번호 확인
```
POST /api/members/me/email/verify-code
Authorization: Bearer {accessToken}
Content-Type: application/json

{ "email": "new-user@example.com", "code": "123456" }
```
Response: `{ "success": true, "message": "이메일 인증이 완료되었습니다." }`
처리: purpose=`PROFILE_EMAIL_UPDATE` 최신 레코드 기준으로 회원가입과 동일한 만료/일치 검증(`EXPIRED_CODE`/`INVALID_CODE`)

### 5-4. 전화번호 변경 인증번호 발송
```
POST /api/members/me/phone/send-code
Authorization: Bearer {accessToken}
Content-Type: application/json

{ "phone": "010-9999-8888" }
```
Response: `{ "success": true, "message": "인증번호가 발송되었습니다." }` (기존 `PhoneResponseDto` 재사용)
처리: `phoneAuthService.sendVerificationCode(memberId, phone, PURPOSE_PROFILE_UPDATE)` 그대로 호출(신규 로직 없음)

### 5-5. 전화번호 변경 인증번호 확인
```
POST /api/members/me/phone/verify-code
Authorization: Bearer {accessToken}
Content-Type: application/json

{ "phone": "010-9999-8888", "code": "123456" }
```
Response: `{ "success": true, "message": "전화번호 인증이 완료되었습니다." }`
처리: `phoneAuthService.verifyCode(memberId, phone, code, PURPOSE_PROFILE_UPDATE)` 그대로 호출

### 5-6. 회원정보 저장
```
PATCH /api/members/me
Authorization: Bearer {accessToken}
Content-Type: application/json

{
  "nickname": "새닉네임",
  "email": "new-user@example.com",
  "phone": "010-9999-8888",
  "password": "N3wP@ss1",
  "passwordConfirm": "N3wP@ss1"
}
```
`email`/`phone`/`password`+`passwordConfirm`은 전부 선택 필드 — 값을 바꾸지 않는 항목은 아예 필드를 보내지 않으면 된다(닉네임만 필수).

Response(성공, 200): `{ "success": true, "message": "회원정보가 수정되었습니다." }`
처리(2-4장 순서 그대로):
- `password`가 있는데 `passwordConfirm`과 다르면 `PASSWORD_CONFIRM_MISMATCH`
- `nickname`이 현재 값과 다르면 중복 확인(본인 제외) → `DUPLICATE_NICKNAME`
- `email`이 현재 값과 다르면 `PROFILE_EMAIL_UPDATE` 인증 완료 여부 확인 → 미인증 시 `EMAIL_NOT_VERIFIED`, 중복 시 `DUPLICATE_EMAIL`
- `phone`이 있으면 `PROFILE_PHONE_UPDATE` 인증 완료 여부 확인 → 미인증 시 `PHONE_NOT_VERIFIED`, 중복 시 `DUPLICATE_PHONE`
- 전부 통과하면 한 번에 반영

### 5-7. 회원 탈퇴 (2026-07-19 요구사항 추가)
```
DELETE /api/members/me
Authorization: Bearer {accessToken}
Content-Type: application/json

{ "password": "P@ssw0rd1" }
```
Response(성공, 200): `{ "success": true, "message": "회원탈퇴가 완료되었습니다." }`
처리(2-5장 순서 그대로): 이미 탈퇴된 계정이면 `ACCOUNT_WITHDRAWN` / 비밀번호 불일치면 `INVALID_CREDENTIALS` / 성공 시 `status='WITHDRAWN'` + `withdrawn_at` 갱신 후 refresh token·access token 세션 모두 무효화

닉네임/이메일/전화번호 변경(5-6)과 마찬가지로 `PATCH /api/members/me`에 통합하지 않고 별도 엔드포인트로 분리한 이유: 탈퇴는 정보 수정과 성격이 다른(되돌릴 수 없는) 동작이라 URL로도 명확히 구분하는 것이 안전하고, REST 관례상 리소스 삭제는 `DELETE`가 자연스러움.

### 5-8. 프로필 사진 등록/변경 (2026-07-19 요구사항 추가)
```
POST /api/members/me/profile-image
Authorization: Bearer {accessToken}
Content-Type: multipart/form-data

profileImage: (파일, jpg/png/gif/webp, 기본 5MB 이하)
```
Response(성공, 200): `{ "success": true, "message": "프로필 사진이 등록되었습니다.", "profileImageUrl": "http://localhost:8081/profile-images/{uuid}.png" }`

`PATCH /api/members/me`(JSON)에 통합하지 않고 별도 멀티파트 엔드포인트로 분리한 이유: 기존 `PATCH /api/members/me`는 이미 JSON 계약으로 확정/테스트돼 있어(001-03 참고), 여기에 파일 필드를 추가하려면 전체를 `multipart/form-data`로 바꿔야 해서 기존 계약이 깨진다. 사업자 회원가입(`POST /api/members/signup/business`)에서 이미 쓰던 "특정 필드만 파일인 별도 엔드포인트" 패턴을 그대로 따름.

### 5-9. 프로필 사진 삭제
```
DELETE /api/members/me/profile-image
Authorization: Bearer {accessToken}
```
Response(성공, 200): `{ "success": true, "message": "프로필 사진이 삭제되었습니다.", "profileImageUrl": null }` — 삭제 후에는 프론트가 닉네임 이니셔널 배지를 보여준다(2-8-3장 참고)

이미 사진이 없는 상태에서 호출해도 동일하게 200 성공(멱등) — 실패할 이유가 없는 동작이라 별도 에러 케이스를 두지 않음.

### 5-10. 내 정보 조회 응답 변경
5-1(`GET /api/members/me`)의 응답에 `profileImageUrl` 필드가 추가됨: `{ "success": true, "email": "...", "nickname": "...", "profileImageUrl": "..." | null }`

**(2026-07-22 추가)** 마이페이지(11) 기능 추가로 `phone`/`foodBti`/`social` 3개 필드가 더 붙었다:
```json
{ "success": true, "email": "...", "nickname": "...", "profileImageUrl": "...",
  "phone": "010-1234-5678" | null, "foodBti": null, "social": false }
```
- `phone`: 예전엔(5-1) 요구사항상 의도적으로 뺐었지만, 본인 정보를 보여주는 마이페이지 화면이라 굳이 뺄 이유가
  없다고 판단해 다시 포함(`docs/11.마이페이지/001-02` 2장). 미등록이면 `null`
- `foodBti`: 값이 없으면(퀴즈를 안 풀었으면) `null`. **(2026-07-23 갱신)** 값을 채우는 기능이 이제 연동됨 —
  `docs/12.음BTI` 참고(`POST /api/food-bti/result`, 로그인 상태로 결과를 계산하면 저장됨, 실 서버 라이브
  검증 완료).
- `social`: `social_accounts`에 이 회원 row가 있으면 `true` — 5-11장 비밀번호 재확인 게이트와 아래 참고의
  비밀번호 입력 UI를 프론트가 미리 숨길 수 있도록 추가한 순수 UI 힌트 필드다. **주의**: 이 필드가 없어도
  소셜 계정의 비밀번호 변경 자체는 이미 서버가 `SOCIAL_ACCOUNT_PASSWORD_CHANGE_NOT_ALLOWED`로 막고 있다
  (1-1장/06.소셜로그인 2-5장) — `social` 필드는 그 차단을 프론트에서 미리 반영해 UX를 매끄럽게 하기 위한
  것일 뿐, 이 필드가 보안 경계는 아니다.

### 5-11. 비밀번호 재확인 (2026-07-22 마이페이지 기능 추가로 신규)
```
POST /api/members/me/verify-password
Authorization: Bearer {accessToken}
Content-Type: application/json

{ "password": "P@ssw0rd1" }
```
Response(성공, 200): `{ "success": true, "message": "비밀번호가 확인되었습니다." }`
Response(실패, 401): `{ "success": false, "code": "INVALID_CREDENTIALS", "message": "..." }`

회원탈퇴(5-7장)의 재인증 패턴을 그대로 복제한 것 — 상태를 바꾸는 부수효과가 전혀 없고, 딱 하나만 확인한다.
`docs/11.마이페이지`에서 "마이페이지의 프로필 수정 화면에 들어갈 때마다 비밀번호를 다시 입력해야 수정 폼이
열리도록" 요청받아 추가했다(11 001-02 참고) — 그 게이트 UI 자체는 마이페이지 소관이지만, 엔드포인트는
`MemberController`(이 도메인)에 둔 이유는 비밀번호 검증 로직(`memberCredentialRepository`+`passwordEncoder`)이
이미 이 컨트롤러/서비스에 있어 그대로 재사용하는 게 자연스럽기 때문(새 도메인을 만들지 않음). 소셜 계정은
애초에 `member_credentials` row가 없어 이 API를 호출할 대상이 없다 — 프론트는 5-10장의 `social` 필드로
게이트 자체를 건너뛰어야 한다.

## 6. 검증 규칙
------------------------------------------------------------------------
| 필드 | 규칙 |
|---|---|
| nickname | 회원가입과 동일: 한글/영문/숫자 2~10자 |
| email | 회원가입과 동일: 이메일 형식, 최대 100자 |
| phone | 회원가입과 동일: `010-XXXX-XXXX` |
| password / passwordConfirm | 회원가입과 동일: 8~20자, 영문+숫자+특수문자, 서로 일치해야 함 |
| code | 숫자 6자리 |
| Authorization 헤더 | 필수, `Bearer {accessToken}` 형식이 아니거나 없으면 `NOT_LOGGED_IN` |
| password (탈퇴 확인용) | 필수(빈 값이면 `INVALID_INPUT`), 형식 검증은 하지 않고 실제 비밀번호와 일치하는지만 확인 |
| profileImage | 파일 필수(없으면 `INVALID_INPUT`), 이미지 형식(jpg/png/gif/webp) + 용량(기본 5MB) 제한 위반 시 `INVALID_PROFILE_IMAGE` |

## 7. 예외/에러 코드 설계
------------------------------------------------------------------------
프로필 사진(`INVALID_PROFILE_IMAGE`) 1개만 신규, 나머지는 전부 기존 `ErrorCode` 재사용.
| 코드 | 상황 | HTTP Status |
|---|---|---|
| NOT_LOGGED_IN | Authorization 헤더 없음/형식 오류/토큰 무효/세션 만료 | 401 |
| INVALID_INPUT | 입력값 형식 오류 | 400 |
| PASSWORD_CONFIRM_MISMATCH | 비밀번호와 비밀번호 확인이 다름 | 400 |
| EMAIL_NOT_VERIFIED | 새 이메일이 인증 미완료 상태 | 400 |
| PHONE_NOT_VERIFIED | 새 전화번호가 인증 미완료 상태 | 400 |
| INVALID_CODE / EXPIRED_CODE | 이메일/전화번호 인증번호 불일치/만료 (공통 재사용) | 400 |
| DUPLICATE_NICKNAME | 다른 회원이 이미 쓰는 닉네임 | 409 |
| DUPLICATE_EMAIL | 다른 회원이 이미 쓰는 이메일 | 409 |
| DUPLICATE_PHONE | 다른 회원이 이미 쓰는 전화번호 | 409 |
| INVALID_CREDENTIALS | 탈퇴 시 제출한 비밀번호가 실제 비밀번호와 불일치 (로그인과 동일 코드 재사용) | 401 |
| ACCOUNT_WITHDRAWN | 이미 탈퇴 처리된 계정으로 탈퇴를 다시 시도 | 403 |
| INVALID_PROFILE_IMAGE (신규) | 이미지 형식이 아니거나 용량 초과 | 400 |
| MAIL_SEND_FAIL | 이메일 발송 실패 | 500 |
| SMS_SEND_FAIL | SMS 발송 실패 (뿌리오 계정 미발급으로 현재 항상 발생, [00.공통 가이드](../00.공통/SMS-인증-Ppurio-연동-가이드.md) 참고) | 500 |

## 8. 확인이 필요한 사항
------------------------------------------------------------------------
- **소셜 로그인 비밀번호 변경 차단**: 1-1장에서 설명한 대로, 소셜 로그인 기능 자체가 없어 이번 구현에서는 판별 로직을 만들지 않음. 소셜 로그인 기능을 실제로 만들 때 `social_accounts` 테이블 존재 여부로 이 가드를 함께 추가하는 것을 제안
- **전화번호를 자동 채움에서 제외하는 이유**: 요구사항 문서에 이유가 명시되어 있지 않음. 이메일 찾기(001-02(이메일찾기) 1-1장)에서도 전화번호를 민감하게 다뤘던 것과 비슷한 맥락으로 추정하고 설계했으나, 실제 의도(단순 누락인지 의도적 보안 조치인지) 확인 필요
- **이메일/전화번호를 "값이 그대로인데도" 다시 제출하면 무조건 재인증을 요구할지**: 이번 설계는 "실제로 값이 바뀔 때만" 재인증을 요구하도록 했음(요구사항 문구 "수정 할 때"를 "값이 실제로 바뀔 때"로 해석). "무조건"이라는 표현이 "항상 재인증 절차 자체를 다시 밟아야 한다"는 의미라면 설계를 수정해야 함
- **`AccessTokenSessionService.isActive()` 신규 메서드와 로그아웃 로직의 기준 차이**: 3장에서 설명한 대로, 로그아웃은 `refreshTokenService.exists(memberId)`를 보고 이 기능은 `AccessTokenSessionService`의 jti 등록 여부를 본다. 두 기준을 통일할지(로그아웃도 이번 기준으로 바꿀지)는 이번 범위 밖으로 남겨둠
- **닉네임/이메일/전화번호를 동시에 바꾸다가 일부만 실패하면**: 이번 설계는 하나의 트랜잭션으로 묶어서 전부 성공하거나 전부 롤백되는 것을 전제로 함(회원가입의 레이스 컨디션 방어 패턴과 동일하게 `saveAndFlush` + 제약조건 이름 판별 적용 예정) — 부분 성공을 허용할지는 논의된 바 없음
- **탈퇴/정지 회원의 정보 수정 허용 여부**: 로그인 자체가 막히는 상태(001-02(로그인) 참고)라 사실상 도달 불가능할 것으로 보이나, 방어적으로 상태 체크를 추가할지는 미정
- **탈퇴 후 닉네임/이메일/전화번호 재사용 가능 여부(2026-07-19 추가)**: 2-5장 설계는 탈퇴 시 데이터를 익명화하지 않고 `status`만 바꾸므로, 탈퇴한 회원의 닉네임/이메일/전화번호는 여전히 DB에 남아 UNIQUE 제약을 계속 점유한다. 회원가입/정보수정의 중복 확인 로직(`existsByEmail` 등)이 현재 `status`를 고려하지 않으므로, 탈퇴한 계정의 정보를 다른 사람이 재사용(재가입)하려 하면 여전히 `DUPLICATE_*`로 막힌다 — 이 부분은 이번 요구사항 범위 밖이라 별도 확인 후 개선 필요(회원가입 기능 쪽 기존 로직에도 영향을 주는 변경이라 이번 기능 단독으로 처리하지 않음)
- **탈퇴 확인 방식**: 이번 설계는 비밀번호 재확인만 요구함(2-5장). "정말 탈퇴하시겠습니까" 같은 프론트 측 확인 모달이나, 탈퇴 사유 입력, 일정 기간 후 실제 삭제(유예기간) 등의 추가 정책은 요구사항에 명시되지 않아 반영하지 않음
- ~~기본 프로필 이미지 자산~~ → **(2026-07-19 확정)** 서버가 기본 이미지 파일을 제공하는 방식 대신, **프론트가 `profileImageUrl: null`일 때 닉네임 첫 글자로 이니셔널 원형 배지를 렌더링**하는 방식으로 확정함(스크린샷 기준, 2-8-3장 참고) — 더 이상 별도 이미지 자산을 준비/등록할 필요가 없어짐. `profile-image.default-url` 설정은 혹시 나중에 필요해질 경우를 대비해 코드에는 남겨뒀지만 당장 채울 필요는 없음
