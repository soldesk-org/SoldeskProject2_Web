### 1-3. 설계 대비 실제 구현
설계 문서(001-02)에서 정한 내용을 그대로 구현했으며, 별도로 방향이 바뀐 부분은 없음. 아래는 구현하면서 구체적으로 확정한 세부사항.

- **인증 방식**: 설계(001-02 3장)대로 Spring Security/필터 체인을 도입하지 않고, `MemberServiceImpl`에 `resolveMemberId(String authorizationHeader)` private 헬퍼 하나만 추가해 `Authorization: Bearer {accessToken}` 헤더를 파싱 → `jwtProvider.parseClaims()`로 서명/만료 검증 → `accessTokenSessionService.isActive(jti)`로 로그아웃 여부까지 확인 → `sub` claim에서 memberId를 꺼내는 방식으로 구현함. 이 6개 엔드포인트 전용 헬퍼이며 기존 `logout()`의 `refreshTokenService.exists()` 기반 검증과는 별도로 유지(001-02 3장에서 이미 범위 밖으로 명시한 대로).
- **PATCH 저장 로직의 순서**: `updateProfile()`에서 비밀번호 확인 불일치를 가장 먼저 검사(다른 필드를 건드리기 전에 실패시켜 부분 반영을 방지) → 닉네임 변경 → 이메일 변경(인증 여부 확인 후 중복 체크) → 전화번호 변경(인증 여부 확인 후 중복 체크) → `saveAndFlush()` + `DataIntegrityViolationException` 캐치(기존 회원가입/로그인 기능에서 쓰던 레이스 컨디션 방어 패턴 재사용) → 마지막에 비밀번호 변경 순으로 구현. 비밀번호는 별도 테이블(`member_credentials`)이라 `members` 테이블 `saveAndFlush()`와는 별도 트랜잭션 스텝으로 처리하되, `@Transactional`로 메서드 전체를 감싸 두 테이블 갱신이 함께 롤백되도록 함.
- **본인 재제출 시 중복 예외 방지**: `existsByNicknameAndMemberIdNot`/`existsByEmailAndMemberIdNot`/`existsByPhoneHashAndMemberIdNot` 3개를 새로 추가해, 값이 실제로 바뀔 때만(`!member.getX().equals(request.getX())`) 검증/갱신하도록 구현. 재확인 결과를 아래 2장 테스트(#5)에서 검증함.

### 1-4. 설계 문서 작성 이후 구현 중 새로 발견한 사항 — `@RequestHeader` 필수 파라미터로 인한 500 오류
설계 문서(001-02 8장)에서는 다루지 않았던 문제로, 실제 Playwright 테스트로 발견함.

컨트롤러에 `@RequestHeader("Authorization") String authorizationHeader`(기본값 `required = true`)로 처음 작성했더니, Authorization 헤더 자체가 없는 요청에서는 `resolveMemberId()`가 호출되기도 전에 Spring MVC가 `MissingRequestHeaderException`을 던져 `GlobalExceptionHandler`가 처리하지 못하는 `500 Unhandled exception`이 발생함(설계 의도는 `401 NOT_LOGGED_IN`이었음).

**수정**: 6개 엔드포인트 전부 `@RequestHeader(value = "Authorization", required = false)`로 변경. 헤더가 없으면 `authorizationHeader`가 `null`로 들어오고, `resolveMemberId()`가 이미 `null` 체크를 하고 있어 의도대로 `401 NOT_LOGGED_IN`이 반환됨(아래 2장 테스트 #1로 검증).

### 1-5. `email_verifications.purpose` 컬럼 DDL 확인
설계(001-02 4-1장)대로 `columnDefinition = "VARCHAR(20) DEFAULT 'SIGNUP'"`을 지정해, 기존에 row가 있는 테이블에 NOT NULL 컬럼을 안전하게 추가할 수 있는지 서버 기동 로그로 확인함.

```
Hibernate:
    alter table if exists email_verifications
       add column purpose VARCHAR(20) DEFAULT 'SIGNUP' not null
```

기동 중 DDL 오류 없이 정상 적용됨.

### 2-1. 테스트 방식 / 시딩
- 회원가입(`/api/members/signup`) + 로그인(`/api/members/login`) API를 그대로 호출해 실제 accessToken을 발급받은 뒤, `Authorization: Bearer {accessToken}` 헤더로 6개 엔드포인트를 호출하는 방식으로 검증함.
- **이메일 인증**: 메일 발송 자체(Daum SMTP)는 실제로 정상 동작하지만(2026-07-19 수동 확인 — 실제 이메일 주소로 보내면 200과 함께 정상 발송됨), 테스트 코드는 관례상 실제 수신함이 없는 `@example.com`(RFC 2606 예약 도메인) 주소를 사용하므로 메일 서버 쪽에서 반송되어 `500 MAIL_SEND_FAIL`이 발생한다(`signup.spec.js`의 기존 확인 사항과 동일한 이유). `POST /api/members/me/email/send-code`가 이 환경에서도 동일하게 `500 MAIL_SEND_FAIL`을 반환하는지만 확인하고, 이후 `verify-code`→저장 흐름은 `dbHelper.js`의 `insertEmailVerification()`(이번에 `purpose` 파라미터를 추가함)으로 `email_verifications` row를 직접 시딩해 우회 검증함.
- **전화번호 인증**: 기존 SMS(뿌리오) 관련 테스트와 동일한 이유로(계정 미발급) 실제 SMS 발송은 검증하지 않고, `dbHelper.js`의 기존 `insertPhoneVerification(memberId, phone, purpose, verified)`을 `purpose='PROFILE_PHONE_UPDATE'`로 호출해 인증 완료 상태를 직접 시딩함.
- `dbHelper.js`의 `insertEmailVerification()`에 `purpose` 파라미터(기본값 `'SIGNUP'`)를 추가하고, INSERT 쿼리에 `purpose` 컬럼을 포함하도록 수정함(1-5장의 DDL 변경에 맞춘 테스트 헬퍼 갱신).

## 3. 2차 구현 (2026-07-19): 회원 탈퇴
------------------------------------------------------------------------
[001-02 2-5장/5-7장](001-02.회원정보수정-분석-설계.md#2-5-회원-탈퇴-2026-07-19-요구사항-추가) 설계대로, 회원정보수정 기능에 회원 탈퇴를 추가함. 소셜 로그인은 아직 구현되어 있지 않아 1-1장의 원칙대로 이번에도 소셜 계정 판별 로직 없이 **일반(이메일/비밀번호) 회원만을 대상**으로 구현함(현재 시점엔 사실상 전체 회원).

### 3-1. 구현
- **`Member.withdraw()`**(신규): `status`를 `'WITHDRAWN'`으로, `withdrawnAt`을 현재 시각으로 갱신. 두 컬럼 모두 로그인 기능에서 이미 매핑/사용 중이던 기존 컬럼이라 엔티티/DB 스키마 변경 없음(`getWithdrawnAt()` getter만 추가, 테스트 검증용).
- **`MemberServiceImpl.withdraw(authorizationHeader, request)`**(신규): 인증 확인 → 이미 `WITHDRAWN` 상태면 `ACCOUNT_WITHDRAWN`(재탈퇴 방지) → `member_credentials.password_hash`와 제출한 비밀번호 Argon2 비교(불일치 시 `INVALID_CREDENTIALS`, 로그인과 동일 코드 재사용) → `member.withdraw()` → `refreshTokenService.revoke(memberId)` + `accessTokenSessionService.revoke(jti)`로 로그아웃과 동일하게 세션 무효화.
- **인증 헬퍼 리팩터링**: 기존 `resolveMemberId(authorizationHeader)`는 `Long`(memberId)만 반환해 `jti`를 알 수 없었는데, 탈퇴 시점에 세션을 무효화하려면 `jti`도 필요함. `resolveMemberId()`의 로직을 `resolveAuthenticatedClaims(authorizationHeader)`(JWT `Claims` 전체를 반환)로 옮기고, `resolveMemberId()`는 그 위에서 `getSubject()`만 꺼내는 얇은 래퍼로 변경. 기존 5개 메서드는 그대로 `resolveMemberId()`를 쓰고, `withdraw()`만 `resolveAuthenticatedClaims()`를 직접 사용.
- **`WithdrawRequestDto`**(신규): `password`(`@NotBlank`) 1개 필드. **`WithdrawResponseDto`**(신규): `success`, `message`.
- **`MemberController.withdraw()`**(신규): `DELETE /api/members/me`, 다른 5개 엔드포인트와 동일하게 `@RequestHeader(value = "Authorization", required = false)` 적용(1-4장에서 확인한 500 오류를 처음부터 피함).

### 4-3. 설계 문서 작성 이후 구현 중 새로 발견한 사항 — `GlobalExceptionHandler`의 catch-all이 정적 리소스 404까지 500으로 바꿔버림
005(회원정보수정) `@RequestHeader` 500 버그([001-03 1-4장](#1-4-설계-문서-작성-이후-구현-중-새로-발견한-사항--requestheader-필수-파라미터로-인한-500-오류))와 같은 종류의 버그를 실제 curl 테스트로 또 발견함.

존재하지 않는 프로필 사진 URL(`GET /profile-images/{없는파일}`)을 요청하면 Spring이 내부적으로 `NoResourceFoundException`을 던지는데, 이게 정상적인 404가 아니라 `GlobalExceptionHandler`의 `@ExceptionHandler(Exception.class)` catch-all에 먼저 잡혀 `500 Unhandled exception`으로 응답되는 것을 확인함. 삭제된 사진 URL을 다시 요청해보는 수동 테스트 중 발견.

**수정**: `GlobalExceptionHandler`에 `@ExceptionHandler(NoResourceFoundException.class)` → `404`를 catch-all보다 먼저 오도록 추가.

같은 수동 테스트 과정에서 **두 번째 버그**도 함께 발견함: 업로드 API를 멀티파트가 아닌 요청(파일 파트 없이 호출)으로 부르면 `HttpMediaTypeNotSupportedException`이 발생하는데, 이것도 catch-all에 잡혀 500이 나고 있었음. `MissingServletRequestPartException`/`MissingServletRequestParameterException`을 처리하던 기존 핸들러에 `HttpMediaTypeNotSupportedException`을 추가해 `400 INVALID_INPUT`으로 통일함.

이 두 수정 모두 이번 기능(프로필 사진) 전용이 아니라 `GlobalExceptionHandler`(공통 컴포넌트)에 반영돼, 앞으로 정적 리소스를 다루거나 멀티파트 요청을 받는 다른 기능에도 함께 적용됨.

`mypage-test.html`의 비밀번호 재확인 게이트를 통해 실제 브라우저로 검증:
- 마이페이지 접속 시 프로필 수정 영역이 기본적으로 잠겨있고 게이트가 뜨는 것 확인
- 틀린 비밀번호 입력 → `401 INVALID_CREDENTIALS`, 수정 폼이 열리지 않음 확인
- **첫 실행 시 오탐**: 500ms만 기다리고 "필드가 여전히 숨겨져 있다"고 판단해 실패로 보고됐던 적이 있음 —
  원인은 버그가 아니라 Argon2 해싱 자체가 ~1~2초 걸리는 것(CLAUDE.md 참고), 대기 시간을 2500ms로 늘리자
  정상 통과. 실제 기능 자체는 처음부터 정상 동작하고 있었음.
- 맞는 비밀번호 입력 → 200 응답과 함께 수정 폼(닉네임/전화번호/프로필사진)이 열리는 것 확인
- 소셜 테스트 계정(`social: true`)으로는 게이트 자체가 뜨지 않고 곧바로 수정 불가 안내만 표시됨을 확인

검증에 쓴 테스트 회원은 확인 직후 정리함.
