## 2. 핵심 설계 결정
------------------------------------------------------------------------
### 2-1. "실시간 반경 검색"이 아니라 "동기화 후 우리 DB에서 검색"
001-01에서 확인한 대로, 공공데이터 API 자체에 위경도 반경 검색이 없다. 그래서:
1. 관리자가 `POST /api/admin/parking-lots/sync`를 트리거하면, 서버가 그 API를 페이지 단위로 순회하며
   시설정보(`PrkSttusInfo`)와 요금정보(`PrkOprInfo`)를 받아 `parking_lots` 테이블에 upsert
2. 실제 "근처 주차장 조회"(`GET /api/parking-lots/nearby`)는 외부 API를 전혀 호출하지 않고, 우리 DB에
   이미 동기화되어 있는 데이터에서 Haversine 공식으로 거리를 계산해 가까운 순으로 반환

이 정부 공개데이터는 07(카카오)과 달리 저장 자체가 재사용 목적에 맞는 정상적인 사용법이라, 매번 실시간
호출을 고집할 이유가 없다 — 오히려 매번 전체 목록을 페이지네이션으로 뒤져야 하는 이 API의 구조상, DB에
캐싱해두는 쪽이 훨씬 빠르고 합리적이다.

### 2-2. Haversine 공식 + bounding box 사전 필터
`ParkingLotRepository.findNearbyIds()`가 네이티브 SQL로 직선거리(m)를 계산한다:
```sql
6371000 * ACOS(COS(RADIANS(:lat)) * COS(RADIANS(latitude)) * COS(RADIANS(longitude) - RADIANS(:lng))
              + SIN(RADIANS(:lat)) * SIN(RADIANS(latitude)))
```
지구를 완전한 구로 근사하는 공식이라 아주 먼 거리(대륙 간)에서는 오차가 있지만, 이 기능이 다루는 반경
(수백m~5km)에서는 실용적으로 충분히 정확하다. `WHERE` 절에 위도/경도 대략 범위(bounding box)를 먼저
걸어서, MariaDB가 전체 행에 대해 매번 삼각함수를 계산하지 않도록 사전 필터링한다(정확한 거리는 그 다음
`HAVING`에서 다시 계산) — 데이터가 많아질 걸 대비한 최소한의 성능 고려.

id+거리만 네이티브 쿼리로 얻고, 실제 엔티티 데이터는 `findAllById()`로 다시 가져오는 2단계 방식을 쓴다 —
네이티브 쿼리에서 `SELECT *`로 엔티티 전체를 `Object[]`로 매핑하면 컬럼 순서에 의존하게 되어 스키마가
조금만 바뀌어도 깨지기 쉽기 때문(1단계로 합치는 것보다 쿼리 1번 더 도는 비용이 훨씬 안전함).

### 2-3. 요금 정보 → "무료/유료" 판단은 추정치
API가 "이 주차장은 무료입니다" 같은 명시적 필드를 주지 않는다(001-01 API 조사 결과). 그래서 운영정보의
기본요금(`parking_chrge_bs_chrge` — 실제 서비스키로 확인 후 정정된 필드명, `basic_info` 객체 안에 중첩되어
있음, 7장/001-03 3장 참고)이:
- 아예 없음(동기화 안 됨) → "정보없음"
- `0` → "무료"로 추정
- `0`보다 큼 → "유료"로 추정, 기본시간/기본요금/추가단위요금을 묶어 안내 문구 생성

**이 추정이 100% 정확하다는 보장은 없다** — 예: 어떤 주차장이 첫 30분 무료 이후 유료라면 "기본요금 0원"이
아니라 별도 필드(`opertn_bs_free_time`, 기본 무료 시간)로 표현될 수도 있는데, 이번 버전은 그 필드까지는
반영하지 않았다(8장 참고).

### 2-4. 요일별 운영시간은 이번에 파싱하지 않음
공공데이터 문서상 운영정보 응답에 "일~토 + 휴일" 8개 요일의 운영시작/종료시간이 있는데, 문서에 나열된
항목명이 요일별로 전부 `opertn_start_time`/`opertn_end_time`으로 **동일하게 표기**되어 있어(실제 JSON
필드명이 요일마다 어떻게 구분되는지 문서만으로는 확신할 수 없었음), 이번 버전은 이 값을 파싱하지 않고
요금 정보만 반영했다. 실제 서비스키로 살아있는 응답을 받아본 뒤, 정확한 필드명을 확인해서 추가하는 것을
권장(8장).

### 2-5. 음식점 상세 DTO를 확장하지 않고 별도 공개 API로 분리
`RestaurantDetailResponseDto`(07)는 이미 여러 곳에서 쓰이는 19개 인자짜리 생성자를 갖고 있다 — 여기에
주차장 목록 필드를 추가하면 그 생성자를 호출하는 모든 곳을 수정해야 해서 회귀 위험이 크다. 대신
`GET /api/parking-lots/nearby?latitude=&longitude=`를 완전히 별도의 공개 API로 분리했다 — 프론트가
음식점 상세를 받아온 뒤 그 좌표로 이 API를 한 번 더 호출하는 방식(마이페이지가 여러 API를 병렬 호출하는
것과 같은 조합형 패턴, `docs/11.마이페이지/001-02` 참고). 로그인 불필요(07의 검색/상세와 같은 공개 API 톤).

### 2-6. 동기화 — 관리자 수동 트리거(1차) → 자동 동기화(2차, 2026-07-23 후속 요청)
1차 구현은 `POST /api/admin/parking-lots/sync`(14.관리자-권한의 `SecurityConfig` `hasRole("ADMIN")` 재사용,
`maxPages` 파라미터로 한 번에 가져올 양 조절)만 있었다 — "관리자 페이지에서 수동으로 하지 말고 자동으로
되게 해달라"는 후속 요청으로 `ParkingSyncScheduler`를 추가했다:
- **서버 기동 직후 1회**: `ApplicationReadyEvent` 리스너로, `parking_lots`에 행이 하나도 없을 때만 실행
  (매번 재기동할 때마다 외부 API를 다시 부르면 개발 중 잦은 재시작 때 낭비이므로 — 이미 뭔가 동기화돼
  있으면 다음 정기 실행을 기다림)
- **매일 새벽 3시 정기 실행**: `@Scheduled(cron = "${parking-data.sync-cron:0 0 3 * * *}")` — 트래픽이
  적은 시간대. 05(회원정보수정)의 `member.cleanup.cron`과 같은 기존 스케줄러 패턴을 그대로 재사용(새
  스케줄링 인프라를 만들지 않음, `@EnableScheduling`은 이미 `Project2Application`에 있었음)
- 두 트리거 모두 서비스키가 없으면(`ParkingDataClient.isConfigured() == false`) **조용히 건너뛴다** —
  예외를 던져서 서버 기동을 막거나 스케줄러 자체를 죽이면 안 되므로(자동으로 도는 백그라운드 작업이라
  실패해도 앱 전체에 영향이 없어야 함)
- 관리자 수동 트리거(3-2장)는 **삭제하지 않고 그대로 유지** — "지금 당장 강제로 다시 동기화하고 싶을 때"
  쓰는 보조 수단으로 남긴다. 더 이상 "유일한 방법"이 아닐 뿐이다.

`maxPages`(관리자 수동, 기본 5)와 `sync-max-pages`(자동, 기본 50 — 정기 실행은 매일 한 번뿐이라 수동보다
넉넉하게 잡음)를 분리했다 — 자동 실행은 사람이 지켜보고 있지 않으므로 한 번에 더 많이 가져와도 안전하지만,
관리자가 즉석에서 누르는 수동 트리거는 응답을 기다리는 사람이 있으니 작게 잡아 빨리 끝나게 했다.

## 3. API 설계
------------------------------------------------------------------------
### 3-1. 근처 주차장 조회 (공개)
```
GET /api/parking-lots/nearby?latitude={lat}&longitude={lng}&radiusM={선택, 기본 1000, 최대 5000}
```
응답: `{ parkingLotId, name, address, latitude, longitude, distanceM, totalSpaces, feeType, feeSummary }[]`
(거리순 정렬, 최대 10건)

### 3-2. 주차장 정보 동기화 (관리자 전용)
```
POST /api/admin/parking-lots/sync?maxPages={선택, 기본 5}
```
응답: `{ success, message, facilitySynced, feeInfoSynced }`

## 7. 사전 조사 과정에서 확인한 것 (참고 기록)
------------------------------------------------------------------------
초기 조사에서는 정확한 API 엔드포인트를 문서만으로 확정하지 못해 사용자에게 직접 data.go.kr 활용신청
상세 페이지의 명세를 요청했다 — 그 결과 받은 정확한 스펙(요청 URL `http://apis.data.go.kr/B553881/Parking/
{PrkSttusInfo|PrkOprInfo|PrkRealtimeInfo}`, 요청 파라미터 `serviceKey`/`pageNo`/`numOfRows`/`format`,
필드명 `prk_center_id`/`prk_plce_nm`/`prk_plce_adres`/`prk_plce_entrc_la`/`prk_plce_entrc_lo`/
`prk_cmprt_co` 등)를 그대로 이 설계/구현에 반영했다. 다만 **응답 JSON의 정확한 봉투(envelope) 구조**
(최상위에 `items` 배열이 바로 있는지, `response.body.items.item`으로 감싸여 있는지)는 문서만으로 확정할
수 없어, 클라이언트가 두 형태를 모두 시도하도록 방어적으로 구현했다.

**(2026-07-26 갱신)** 실제 서비스키가 발급되어 라이브로 확인한 결과, 두 형태 다 아니고 **오퍼레이션 이름
자체가 최상위 키**인 세 번째 형태였다(예: `{"PrkSttusInfo": [...], "resultCode": "0", ...}`). 또한 요금
필드는 최상위가 아니라 `basic_info`/`fxamt_info` 객체 안에 중첩돼 있었고, 기본요금 필드명도
`parking_chrge_bs_chrg`가 아니라 `parking_chrge_bs_chrge`(e 포함)였다. 숫자로 보이는 필드(구획수/요금)도
전부 JSON 문자열로 내려온다(`format=2`). 세 가지 모두 `ParkingDataClient`에서 수정 완료, 상세 내용과 실제
동기화 검증 결과는 [001-03 3장](001-03.주차장-정보-구현-테스트.md) 참고.

## 9. 2차 전환 (2026-07-27) — 서울 열린데이터광장 기반 실시간 조회로 재설계
------------------------------------------------------------------------
001-01 10장에 정리된 이유(전국 176만여 건 규모+반경검색 불가+원인불명 `-999` 에러)로, data.go.kr 기반
"동기화 후 DB 조회"(2-1장) 구조를 **서울시 한정 실시간 조회**로 바꿨다.

### 9-1. 패키지 구조 변경
```
com.foodtrip.foodsearch.parking
 ├─ client
 │   ├─ ParkingDataClient       (기존, data.go.kr — 유지하되 미사용, 주석 처리된 코드만 참조)
 │   └─ SeoulParkingClient      (신규 — 서울 열린데이터광장 GetParkInfo)
 ├─ service
 │   ├─ ParkingLotServiceImpl   (전면 교체 — SeoulParkingClient + Haversine 직접 계산)
 │   ├─ ParkingSyncService/Impl (기존 — 유지하되 미사용)
 └─ scheduler
     └─ ParkingSyncScheduler    (기존 — @EventListener/@Scheduled 주석 처리로 비활성화)
```
`ParkingLotRepository`(Haversine 네이티브 SQL 쿼리)와 `parking_lots` 테이블은 그대로 남아있지만
`ParkingLotServiceImpl`이 더 이상 참조하지 않는다 — 삭제하지 않은 이유는 001-01 10장과 동일(전국 단위
필요해지면 되돌릴 수 있게).

### 9-2. 핵심 설계 — "동기화" 자체를 없앰
서울 열린데이터광장 API도 위경도를 요청 파라미터로 받지 않는 건 data.go.kr과 같다(`ADDR` 문자열 검색만
가능, 진짜 좌표 반경 검색 아님). 다른 점은 **전체 데이터가 2,189건뿐**이라는 것 — 한 페이지 최대 1000건
제한을 감안해도 3번 호출이면 전체를 다 가져올 수 있다. 그래서:
1. `GET /api/parking-lots/nearby` 요청이 오면 `SeoulParkingClient.fetchAll()`이 그 자리에서 3번(또는
   `list_total_count` 기준 필요한 만큼) 호출해 서울시 전체 목록을 받아온다
2. 위경도가 비어있는 행(약 1/3, 9-3장)은 거리 계산이 불가능하므로 이 시점에 제외
3. `ParkingLotServiceImpl`이 직접 구현한 Haversine 공식(기존 `ParkingLotRepository`의 네이티브 SQL과
   같은 공식, 이번엔 Java로)으로 거리를 계산하고, 반경 내로 걸러서 거리순 정렬 후 최대 10건 반환

DB 저장이 아예 없다 — 매 요청마다 실시간으로 계산한다(2026-07-27 실측 약 1.1초, 9-4장). 매번 검색마다
호출을 하기 때문에 서울 열린데이터광장의 일일 트래픽 한도는 별도로 확인해두는 것을 권장(9-5장 참고).

### 9-3. 위경도 결측치 처리
2026-07-27 실측 기준 전체 2,189건 중 1,456건(약 66%)만 `LAT`/`LOT`이 채워져 있다. 나머지는 `0.0` 또는
빈 값으로 내려온다 — 이런 행은 애초에 `SeoulParkingClient.toRecord()`에서 `null`로 필터링해 결과 목록에
아예 포함되지 않는다. 즉 "실제로는 근처에 주차장이 있지만 좌표가 없어서 안 나오는" 경우가 있을 수 있다는
한계는 남아있다.

### 9-4. 응답 시간
2026-07-27 실 서버 테스트: 강남역 좌표(37.4979, 127.0276)로 `radiusM=2000` 조회 시 **약 1.1초**(외부 API
3회 호출 + Haversine 계산 포함)에 응답 완료, 실제 주차장 2곳(양재역 공영주차장/반포천 공영주차장)이 거리순+
요금 정보와 함께 정상 반환됨을 확인.

### 9-5. 요금/무료 판단 — data.go.kr보다 신뢰도 높음
data.go.kr(2-3장)은 요금이 명시적으로 없어 기본요금 0원 여부로 "무료"를 추정해야 했는데, 서울 열린데이터
광장은 `CHGD_FREE_SE`(유무료구분, Y/N) 필드가 명시적으로 있어 추정이 아니라 실제 값으로 판단할 수 있다 —
2-3장의 "100% 정확하다는 보장 없음" 우려가 이번 전환으로 상당 부분 해소됨.

### 9-6. 개별 칸 단위 행 병합 (후속 수정)
서울 열린데이터광장은 노상 주차장을 "주차장 하나"가 아니라 **개별 주차 칸 하나하나를 별도 행**으로 준다
(실측: 같은 `PKLT_CD`를 가진 행이 38개, 각각 `TPKCT`(총 구획수)가 1). 그대로 반환하면 사용자에게 같은
이름의 주차장이 목록에 여러 번 중복으로 보인다 — `ParkingLotServiceImpl.mergeByCode()`에서 거리 계산
전에 같은 `PKLT_CD`끼리 먼저 하나로 합치고(대표 좌표는 그룹의 첫 행, 구획수는 합산) 처리한다.

### 9-7. 남은 작업
- 서울 열린데이터광장의 일일 트래픽 한도를 아직 확인하지 않음 — 검색마다 3회씩 호출되므로, 트래픽이
  많아지면 한도에 걸릴 수 있음(필요해지면 짧은 TTL 캐시 도입 검토)
- 위경도 결측 34%는 그대로 남음(9-3장) — "우리가 아는 것만" 보여준다는 걸 프론트에 안내할지는 미정
