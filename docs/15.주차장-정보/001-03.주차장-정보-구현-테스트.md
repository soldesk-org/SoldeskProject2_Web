## 1. 구현 결과 (2026-07-23)
------------------------------------------------------------------------
### 1-1. 실제 구현 파일
```
com.foodtrip.foodsearch.parking (신규 패키지)
 ├─ entity/ParkingLot
 ├─ repository/ParkingLotRepository (Haversine 네이티브 쿼리 + 프로젝션)
 ├─ dto/ParkingLotResponseDto, ParkingSyncResponseDto
 ├─ client/ParkingDataClient
 ├─ service/ParkingLotService, ParkingLotServiceImpl, ParkingSyncService, ParkingSyncServiceImpl
 └─ controller/ParkingLotController
```
`AdminController`(14.관리자-권한)에 `POST /api/admin/parking-lots/sync` 추가. `ErrorCode`에
`PARKING_DATA_SERVICE_UNAVAILABLE` 추가. `application.yml`/`.env.example`에 `parking-data.base-url`/
`parking-data.service-key` 추가.

### 1-2. API 구현 목록
| API | 인증 | 설명 |
|---|---|---|
| GET /api/parking-lots/nearby | 불필요 | 좌표 기준 반경 내 주차장 거리순 조회 |
| POST /api/admin/parking-lots/sync | ADMIN | 공공데이터 동기화 트리거 |

### 1-3. Jackson 3(Spring Boot 4) API 대응
`ParkingDataClient`가 외부 API의 JSON을 유연하게 파싱해야 해서(001-02 7장, 봉투 구조 불확실) `JsonNode`
트리 모델을 직접 썼는데, 이 프로젝트가 쓰는 Jackson 3(`tools.jackson`, 13/14 문서에서 이미 여러 번 확인된
Spring Boot 4의 패키지 변경)에서 다음을 확인하며 구현:
- `new ObjectMapper()` 같은 public 생성자가 없음 — `JsonMapper.builder().build()`로 생성
- `ObjectMapper.readTree(String)`이 던지는 예외가 Jackson 2의 체크 예외(`JsonProcessingException extends
  IOException`)가 아니라 **언체크 예외**(`tools.jackson.core.JacksonException extends RuntimeException`)로
  바뀜 — catch 절에 명시적으로 추가해야 잡힘
- `JsonNode.asString()`/`asText()` 둘 다 존재(문자열 추출은 아무거나 써도 됨, 이번엔 `asString()` 사용)

### 2-5. 2차 구현: 자동 동기화 (2026-07-23, 같은 날 후속)
"관리자 페이지에서 수동으로 하지 말고 자동으로" 요청으로 `ParkingSyncScheduler` 추가(001-02 2-6장 설계).

**구현**
- `@EventListener(ApplicationReadyEvent.class)` + `@Scheduled(cron = "${parking-data.sync-cron:0 0 3 * * *}")`
  두 트리거, 둘 다 서비스키 미설정 시 예외 없이 조용히 건너뜀
- `application.yml`에 `parking-data.sync-cron`/`parking-data.sync-max-pages`(기본 50) 추가,
  `.env.example`에 `PARKING_DATA_SYNC_CRON`/`PARKING_DATA_SYNC_MAX_PAGES` 추가

**검증**

서버 재기동 후 로그에서 확인:
```
Started Project2Application in 12.439 seconds ...
... ParkingSyncScheduler : 주차장 정보 서비스키(PARKING_DATA_SERVICE_KEY) 미설정 - 시작 시 자동 동기화 건너뜀
```
- `ApplicationReadyEvent` 리스너가 서버 기동 완료 직후 정확히 실행됨을 확인
- 서비스키가 없는 지금 상태에서 **예외 없이** 정상적으로 건너뛰고, 서버가 계속 정상 기동됨을 확인(스케줄러
  실패가 앱 전체에 영향을 주지 않는다는 001-02 2-6장 설계 검증)
- 재기동 후에도 `GET /api/parking-lots/nearby`가 기존 시드 데이터(2건)로 여전히 정상 응답하는 것 확인
  (스케줄러 추가가 기존 기능에 회귀를 일으키지 않음)
- 매일 새벽 3시 정기 실행 자체는 실시간으로 기다려서 확인하지는 않음(로직은 `syncOnStartupIfEmpty()`와
  같은 `runSyncSafely()`를 공유하므로 별도 검증 불필요로 판단) — 서비스키 승인 후 실제 동기화 결과와
  함께 재확인 필요(001-02 8장)

## 3. 실 서비스키로 첫 라이브 검증 (2026-07-26) — 파싱 버그 2건 발견 및 수정
------------------------------------------------------------------------
`PARKING_DATA_SERVICE_KEY` 활용신청이 승인되어, 2장에서 "최우선 남은 작업"으로 남겨뒀던 실제 동기화
라이브 검증을 처음으로 진행했다. 예상대로 001-02 7장에서 "실제 응답을 못 보고 추정으로 작성"이라고
명시했던 부분에서 진짜 버그가 나왔다.

### 3-1. 원본 응답 직접 확인 (curl로 raw 응답 먼저 확인)
서버를 거치지 않고 `curl`로 `http://apis.data.go.kr/B553881/Parking/PrkSttusInfo`를 직접 호출해서 실제
응답 형태부터 확인했다:
```json
{"PrkSttusInfo":[{"prk_center_id":"01016-11191-00001-00-1","prk_plce_nm":"아카데미주차장", "prk_cmprt_co":"71", ...}], "resultCode":"0", "resultMsg":"SUCCESS", ...}
```

### 3-2. 버그 1 — 응답 봉투(envelope) 구조가 세 번째 형태였음
`ParkingDataClient.extractItems()`는 두 가지 흔한 data.go.kr 형태(① 최상위 `items` 배열, ②
`response.body.items.item`)만 시도하도록 방어적으로 짜뒀는데, 실제로는 **오퍼레이션 이름 자체가 최상위
키**(`{"PrkSttusInfo": [...]}`)인 세 번째 형태였다. 두 형태 다 실패 → `PARKING_DATA_SERVICE_UNAVAILABLE`로
동기화 자체가 계속 실패하고 있었음(관리자 페이지에서 재현 확인). `extractItems()`에 오퍼레이션 이름 키를
가장 먼저 시도하는 분기를 추가해서 해결.

### 3-3. 버그 2 — 요금 필드가 중첩 객체 안에 있었고, 필드명도 추정과 달랐음
`PrkOprInfo` 응답의 요금 필드가 최상위가 아니라 `basic_info`/`fxamt_info` 객체 안에 중첩돼 있었다:
```json
{"prk_center_id":"...", "basic_info":{"parking_chrge_bs_time":"30","parking_chrge_bs_chrge":"1200", ...},
 "fxamt_info":{"parking_chrge_one_day_chrge":"10000","parking_chrge_mon_unit_chrge":"100000"}, ...}
```
기본요금 필드명도 처음 추정했던 `parking_chrge_bs_chrg`가 아니라 `parking_chrge_bs_chrge`(e가 붙음)였다.
`fetchOperationPage()`가 `basic_info`/`fxamt_info` 하위에서 읽도록 수정하고 필드명 오타도 고쳤다.

### 3-4. 버그 3 — 숫자 필드가 JSON 문자열로 내려옴
`prk_cmprt_co`(총 구획수), 요금 필드 전부 `"71"`처럼 **따옴표 붙은 JSON 문자열**로 내려오는데,
`intOrNull()`이 `value.isNumber()`로만 판별해서 전부 `null`로 빠지고 있었다(값 자체가 없어서가 아니라
타입 판별 방식이 틀려서). `decimalOrNull()`과 같은 방식(문자열이어도 파싱 시도)으로 통일해서 해결.

### 3-5. 수정 후 재검증
서버 재시작 → ADMIN 계정으로 `POST /api/admin/parking-lots/sync?maxPages=2` 재호출:
```json
{"success":true,"message":"주차장 시설정보 187건, 요금정보 200건 동기화 완료","facilitySynced":187,"feeInfoSynced":200}
```
DB에서 직접 확인한 결과 `source='DATA_GO_KR_B553881'` 181건이 정상 저장됐고(시설+요금 조인 후 최종
건수), 이름/주소/좌표/총구획수/기본요금/추가요금/일일요금/월정액요금 전부 `null` 없이 정상적으로 채워짐을
확인. `GET /api/parking-lots/nearby`도 이 실제 데이터로 거리순 정렬 + 요금 문구까지 정상 응답함을
확인(예: "기본 30분 1200원, 추가 10분당 0원").

## 4-1. 검증 후 정리 (data.go.kr 기반 시절)
------------------------------------------------------------------------
`source='TEST_SEED'`로 남겨둔 2건(55m/556m 거리)은 실제 서비스키가 승인되기 전까지 `tmp-map-test.html`에서
"인근 유료주차장" 기능이 눈으로 확인되도록 하기 위한 데모/검증용 데이터로 한동안 의도적으로 유지했다.
5.5km 밖에 있던 3번째 시드 행은 검증 직후 삭제함.

**(2026-07-27 최종 삭제)** 3장에서 실제 서비스키로 181건이 정상 동기화된 것까지 확인된 뒤, "예시로 넣어둔
데모 데이터는 지우고 실제 API 값만 보이게 해달라"는 요청으로 남아있던 `TEST_SEED` 2건도 완전히 삭제함
(`DELETE FROM parking_lots WHERE source='TEST_SEED'`). 이 직후 5장의 전환이 이어져, 이 삭제 자체는 큰
의미가 없어졌다(어차피 `parking_lots` 테이블 전체를 더 이상 조회하지 않음).

## 5. 2차 전환 (2026-07-27) — 서울 열린데이터광장 구현/검증
------------------------------------------------------------------------
설계는 [001-02 9장](001-02.주차장-정보-분석-설계.md) 참고. data.go.kr 기반 전체 재동기화가 대규모(17,000+
페이지) 시도에서 실 서비스키로도 계속 실패(`HttpTimeoutException`, 원인불명 `-999` 에러)하는 과정을 겪은
뒤, 사용자가 직접 찾은 서울 열린데이터광장 API로 전환했다.

### 5-1. 구현 파일
```
com.foodtrip.foodsearch.parking.client.SeoulParkingClient   (신규)
com.foodtrip.foodsearch.parking.service.ParkingLotServiceImpl  (전면 교체, 기존 코드는 블록 주석으로 하단에 보존)
com.foodtrip.foodsearch.parking.scheduler.ParkingSyncScheduler (@EventListener/@Scheduled 주석 처리로 비활성화)
```
`application.yml`에 `seoul-parking-data.base-url`/`seoul-parking-data.service-key` 추가, `.env`에
`SEOUL_PARKING_SERVICE_KEY` 추가(기존 `PARKING_DATA_SERVICE_KEY`는 남겨두되 미사용 표시).

### 5-2. 사전 확인 — 위경도 결측률
전환을 결정하기 전에 실제 데이터 품질부터 확인했다: 전체 2,189건을 3회 호출로 전부 받아서 `LAT`/`LOT`이
0이 아닌 행 개수를 세어봄 — **1,456건(약 66.5%)**이 실제 좌표를 갖고 있음을 확인(스크립트로 직접 카운트,
샘플 3건의 좌표값도 정상 범위인 것 확인). 이 수치를 근거로 "거리 계산이 실용적으로 가능하다"고 판단하고
구현을 진행했다.

### 5-3. 실 서버 라이브 검증
서버 재기동 후 `GET /api/parking-lots/nearby?latitude=37.4979&longitude=127.0276&radiusM=2000`(강남역)
호출:
```json
[
  {"parkingLotId":2877728,"name":"양재역 공영주차장(시)","address":"서초구 양재동 23-0",
   "distanceM":1707,"totalSpaces":885,"feeType":"유료","feeSummary":"기본 5분 400원, 추가 5분당 400원"},
  {"parkingLotId":3187200,"name":"반포천 공영주차장(파미에)(시)","address":"서초구 반포동 118-3",
   "distanceM":1885,"totalSpaces":1186,"feeType":"유료","feeSummary":"기본 5분 550원, 추가 5분당 550원"}
]
```
`time curl`로 측정한 실제 응답 시간은 **1.111초**(외부 API 3회 호출 + Haversine 계산 전부 포함) — DB
동기화 없이 매번 실시간으로도 실용적인 속도가 나옴을 확인. 이후 `parking_lots` 테이블을 직접 조회해서
행 수가 요청 전후로 변하지 않았음을 확인(더 이상 DB에 쓰지 않는다는 것의 실측 증거, 12,069건 그대로).

### 5-4. 후속 수정 — 같은 주차장이 여러 번 중복 표시되는 문제
사용자가 실제 화면에서 확인한 결과, 같은 이름의 주차장이 거리·요금 전부 동일하게 목록에 여러 번 반복
출력되는 걸 발견함. 원인 확인 결과 서울 열린데이터광장 API가 **노상 주차장을 개별 주차 칸 단위로 별도
행에 나눠서 준다**는 걸 알게 됨 — 예를 들어 "영동6교밑 공영주차장"은 같은 `PKLT_CD`(주차장 코드)
`1585237`을 가진 행이 38개 있었고, 각 행은 `TPKCT`(총 구획수)가 전부 `1`(칸 하나), 좌표만 몇 미터씩
다름. `mergeByCode()`를 `ParkingLotServiceImpl`에 추가해서 같은 코드끼리는 하나로 합치고(첫 번째 행의
이름/주소/좌표/요금을 대표값으로, 구획수는 전부 합산) 반환하도록 수정. 실 서버로 같은 위치(강남대로 인근)
재검색 → "영동6교밑 공영주차장(시)" 1건, 총 38면으로 정상 병합됨을 확인.
