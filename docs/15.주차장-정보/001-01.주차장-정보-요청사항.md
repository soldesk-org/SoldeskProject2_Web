## 배경 — 왜 "매장 전용 주차장 안내 문구"가 아니라 "인근 유료주차장"만 하는지
------------------------------------------------------------------------
사용자가 보여준 예시(부산집 종로점 등 카카오맵 매장 페이지의 "주차 가능 / 무료 / 매장 앞 전용 주차장에
주차 가능합니다..." 문구)는 **그 매장을 운영하는 사업자가 카카오맵에 직접 입력한 정보**다. 카카오 로컬
API(우리가 07에서 쓰는 그 API)의 공식 응답 필드(이름/주소/좌표/카테고리/전화/지도URL 등, 07 001-02 참고)에는
이 정보가 아예 없다 — 카카오맵 웹사이트 자체의 매장 상세페이지 렌더링에만 쓰이는 값이라, 우리가 그 API로는
가져올 방법이 없다.

대신 실제로 구현 가능한 두 갈래를 검토했다:
1. **"우리 매장 전용 주차장" 정보**: 카카오에서 못 가져오니, 사업자가 직접 입력해야 함(07의 `description`/
   `phone`처럼 사업자 등록 부가정보 패턴으로 가능은 하지만, 이번 요청 범위가 아님 — 8장 참고)
2. **"인근 유료주차장" 정보**: 공공데이터포털에 실제로 존재하는 정부 공개데이터(전국 주차장 위치/요금
   정보)로 가능. 사용자가 최종적으로 **이걸 넣기로 확정**함

## API 조사 결과 — 왜 "실시간 반경 검색"이 아니라 "동기화 후 우리 DB에서 검색"인지
------------------------------------------------------------------------
공공데이터포털에서 "한국교통안전공단_주차정보 제공 API"(서비스 `B553881/Parking`)를 확인했다:
- **주차장 시설정보**(`PrkSttusInfo`): 이름/주소/위도/경도/총 구획수
- **주차장 운영정보**(`PrkOprInfo`): 요일별 운영시간, 기본요금/추가요금/일주차권/월정기권 등 요금 정보
- **주차장 실시간 정보**(`PrkRealtimeInfo`): 실시간 주차 가능 면수(이번 범위 밖, 8장 참고)

이 API들은 **위도/경도로 "반경 몇 km 검색"하는 파라미터가 없다** — `pageNo`/`numOfRows`로 페이지 단위
전체 목록만 받을 수 있다. 그래서 07(음식점 검색)처럼 "매 요청마다 카카오를 실시간 호출"하는 방식이
아니라, **관리자가 트리거하는 배치 동기화로 우리 DB에 미리 받아두고, 그 안에서 우리가 직접 좌표 거리
계산을 하는 구조**로 설계했다. 이건 07이 카카오 데이터를 저장하지 않는 이유(카카오 ToS 위반)와는
무관하다 — 정부 공개데이터는 재사용에 그런 제약이 없다(오히려 공공데이터법상 재사용이 권장됨).

## 9. 후속 변경 (2026-07-23, 같은 날)
------------------------------------------------------------------------
1차 구현 직후 "관리자 페이지에서 안 하고 자동으로, 리뷰 쓰는 바 옆에 리스트로 보이게" 요청을 받음:
- **표시 위치**: 이미 1차부터 `tmp-map-test.html`의 음식점 상세 패널(리뷰 작성 영역 바로 위)에 "🅿️ 인근
  유료주차장" 섹션으로 구현되어 있어 추가 변경 없음
- **자동 동기화**: 관리자가 매번 버튼을 눌러야 했던 1차 방식 대신, 서버 기동 시 1회(데이터가 없을 때만) +
  매일 새벽 3시 정기 실행으로 전환(`ParkingSyncScheduler`). 관리자 수동 트리거는 즉시 강제 재동기화용
  보조 수단으로 남겨둠. 상세는 001-02 2-6장.

## 10. 2차 전환 — data.go.kr → 서울 열린데이터광장 (2026-07-27)
------------------------------------------------------------------------
실제 서비스키로 전국 단위 동기화를 시도하는 과정에서 세 가지 문제가 겹쳤다:
1. **규모가 예상보다 훨씬 큼**: `totalCount`가 약 176만여 건으로, 페이지가 17,000개를 넘음(같은 주차장이
   여러 번 중복 등록돼 있어 실제 고유 개수는 이보다 훨씬 적을 것으로 추정되지만, 원본 API 자체엔 중복
   제거 기능이 없음)
2. **반경/지역 필터가 API에 아예 없음**(001-02 2-1장에서 이미 알고 있던 제약) — "이 좌표 근처만" 요청할
   방법이 없어, 전국을 다 끌어와 DB에 쌓아두는 방식(001-02 2-1장 설계)이 유일한 선택지였음
3. **원인불명의 `-999` 에러**: 대량 동기화를 반복 시도하는 과정에서 API가 정상 JSON이 아닌 비표준 에러
   응답(`{ result_desc:'fail', result_code:'-999', ... }`)을 돌려주기 시작함 — 일일 트래픽 한도(10만 건)
   증설을 받은 뒤에도 동일하게 발생해, 단순 트래픽 초과가 아니라 게이트웨이/WAF 레벨의 요청 빈도 제한으로
   추정됨(확실한 원인은 미확인)

이 상황에서 사용자가 대안으로 **서울 열린데이터광장 "서울시 주차장 정보"(GetParkInfo)** API를 직접 찾아서
제시함 — 확인해보니:
- 서울시 한정이지만 전체 **2,189건**뿐(2026-07-27 실측) — data.go.kr과 비교가 안 될 정도로 작은 규모
- 한 번에 최대 1000건 요청 가능(`START_INDEX`~`END_INDEX`) → **딱 3번 호출로 전체를 다 가져올 수 있음**
- 응답에 위도/경도(`LAT`/`LOT`) 필드가 있음(1,456건/2,189건, 약 66%에 실제 값 채워져 있음 확인, 나머지는
  빈 값이라 거리 계산 대상에서 제외)

이 정도 규모면 "DB에 미리 동기화"가 아니라 **검색할 때마다 전체(3번 호출)를 실시간으로 가져와서 그 자리에서
거리 계산으로 거르는 방식**이 실용적으로 가능해진다 — 001-02 2-1장에서 "이 API 구조상 실시간 호출은
불가능하다"고 판단했던 전제가, 데이터 출처를 바꾸면서 뒤집힌 것. 범위를 **서울시로 좁히는 대신, DB 저장
없이 진짜 실시간 조회**로 전환하기로 확정. 상세 설계는 [001-02 9장](001-02.주차장-정보-분석-설계.md),
구현/검증은 [001-03 5장](001-03.주차장-정보-구현-테스트.md) 참고.

기존 data.go.kr 기반 코드(`ParkingDataClient`, `ParkingSyncService`, `ParkingSyncScheduler`, `parking_lots`
DB 테이블)는 삭제하지 않고 그대로 남겨뒀다(스케줄러 자동 트리거만 비활성화) — 나중에 전국 단위 데이터가
다시 필요해지면 참고해서 되돌릴 수 있다.
