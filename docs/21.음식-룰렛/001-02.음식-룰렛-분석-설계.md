## 2. 핵심 설계 결정
------------------------------------------------------------------------
### 2-1. 백엔드 없이 순수 프론트로 구현
이 프로젝트의 다른 모든 기능은 Spring Boot API + DB(또는 최소 Redis)를 거치지만, 이 기능은 "룰렛에 넣을
음식 목록"과 "당첨 결과"를 저장/공유할 필요가 없는 1회성 도구다. 굳이 API를 만들면 오히려 과한
설계("CLAUDE.md 2장 필요한 만큼만" 원칙)라 판단해서, 랜덤 선택 로직도 전부 브라우저 `Math.random()`으로
클라이언트에서 처리한다.

### 2-2. 칸 개수 = 선택한 카테고리 개수, 입력은 자유 텍스트 대신 아이콘 버튼으로
처음엔 "마라탕", "떡볶이"처럼 자유 텍스트를 하나씩 입력받는 방식으로 만들었는데, 사용자가 "이런 형식
말고 좀 더 좋게 해달라"고 요청해서(2026-07-26) 07(음식점-메뉴-검색)이 이미 쓰고 있는 **고정 카테고리
10개**(한식/양식/중식/일식/분식/패스트푸드/아시안/술집/뷔페/카페-디저트, `GET /api/restaurants/
categories` 응답)를 탭으로 선택하는 방식으로 바꿨다. 메인 지도(`tmp-map-test.html`)/AI 추천
(`recommend-test.html`)과 완전히 같은 카테고리 마커 이미지를 아이콘으로 재사용해서 시각적으로도 통일했다.

자유 텍스트를 없앤 데는 UX 개선 외에 실용적인 이유가 하나 더 있다 — "당첨된 메뉴 주변 음식점 추천"
(2-6장)을 구현하려면 당첨 결과가 우리 시스템이 인식하는 `categoryId`와 연결돼 있어야 하는데, "마라탕"
같은 자유 텍스트는 그 자체로는 어떤 카테고리인지 알 수 없다("마라탕"은 카테고리가 아니라 메뉴). 카테고리
버튼 선택으로 바꾸면서 이 문제가 자연스럽게 해결됐다. 칸 개수는 여전히 "선택한 카테고리 개수"로 자동
결정된다(최소 2개, 최대 12개 중 실제로는 10개가 상한).

### 2-3. 회전 각도 계산 - 결과를 먼저 정하고 그에 맞는 각도를 역산
"랜덤하게 도는 룰렛"을 자연스럽게 만들기 위해, 아래 순서로 계산한다:
1. `Math.random()`으로 당첨 칸의 인덱스를 먼저 결정
2. 그 칸의 중심 각도(12시 방향 포인터 기준, 시계방향)를 계산하고, 칸 폭의 ±35% 범위 안에서 무작위로
   살짝 벗어난 지점을 최종 목표 각도로 정함(항상 칸 정중앙에 딱 멈추면 부자연스러워 보여서)
3. 현재까지 누적된 회전각(`currentRotation`)에 6~8바퀴(2160~2880도)를 더하고, 그 목표 각도가 포인터
   위치(0도)에 오도록 나머지 보정각을 더해 최종 회전각을 구함
4. CSS `transition: transform 4.2s cubic-bezier(...)`로 캔버스 전체를 그 각도까지 회전시킴(감속하며
   멈추는 자연스러운 이징)

이 방식은 "결과를 미리 정해두고 그에 맞춰 도는 각도를 역산"하는 방식이라, 애니메이션이 끝났을 때
포인터가 가리키는 칸과 실제 당첨 결과가 항상 정확히 일치한다(랜덤 각도로 돌린 뒤 "그 지점의 칸이
당첨"이라고 사후에 계산하는 방식보다 결과 표시 타이밍이 깔끔함 - transitionend 이벤트에서 바로 결과를
보여줄 수 있음).

### 2-4. 반복 스핀 시 회전각이 계속 누적됨
CSS `transform: rotate(Ndeg)`는 절대값이라, 두 번째 스핀부터도 이전 회전각(`currentRotation`)에서 이어서
계산한다 — 매번 0도로 리셋하고 다시 돌리면 시각적으로 "덜컹"하는 부자연스러운 느낌이 나기 때문. "이건
빼고 다시 돌리기"(당첨 항목 제거 후 재시작)를 누를 때만 룰렛을 다시 그리면서 회전각도 0으로 리셋한다.

### 2-5. 실측 검증 - Playwright로 반복 스핀의 정확성 확인
회전각 계산이 삼각함수/모듈로 연산이 섞여 있어 실수하기 쉬운 부분이라, 실제 브라우저(Playwright
headless Chromium)로 5회 연속 스핀 + 결과 제거 후 재스핀까지 실행하며 매번 "포인터가 가리키는 칸"과
"모달에 표시된 당첨 텍스트"가 일치하는지 스크린샷으로 직접 확인했다(001-03 2장 참고) — 이 프로젝트가
과거 네이버 지도 마커에서 `scaledSize` 누락으로 시각적 버그를 겪었던 경험(19.오픈채팅 이전 세션 기록)
때문에, 캔버스/애니메이션처럼 코드만 봐서는 확신할 수 없는 부분은 항상 스크린샷으로 재확인하는 습관을
그대로 적용했다.

### 2-6. 당첨된 카테고리 주변 음식점 추천 - 07의 기존 API 재사용
"메뉴 정해졌으면 그 메뉴 내 위치 주변에 있는 그 음식을 판매하는 음식점도 추천해줘" 요청으로, 결과 모달에
"📍 내 주변 맛집 찾기" 버튼을 추가했다. 새 백엔드를 만들지 않고 07이 이미 만들어둔 두 API를 그대로 쓴다:

1. 브라우저 `navigator.geolocation.getCurrentPosition()`으로 현재 위치를 가져옴(거부/미지원 시 다른
   테스트 페이지들과 같은 기본 좌표인 강남역 인근으로 대체)
2. 그 좌표를 중심으로 ±0.015도(약 1.5km)짜리 bounding box를 만들어
   `GET /api/restaurants/filter?categoryId={당첨카테고리}&minLat=&maxLat=&minLng=&maxLng=&size=5` 호출
   (카카오 로컬 API를 실시간으로 호출하는 07의 기존 라이브 검색 - 새 DB 접근/저장 없음)
3. 응답의 상위 5곳을 이름/주소/평점/카카오맵 링크로 나열

`filter` API가 `minLat/maxLat/minLng/maxLng`를 요구하는 bounding box 방식이라(중심+반경 방식이 아님),
이 프로젝트의 다른 곳(15.주차장-정보 등)에서 쓰는 반경 검색과는 다르게 사각형 범위로 변환해서 넘긴다.

### 2-7. categoryId는 하드코딩하지 않음
`RestaurantController`의 기존 주석대로 "categoryId가 환경마다 달라질 수 있어 프론트가 API로 받아써야
함"이라, 룰렛도 페이지 로드 시 `GET /api/restaurants/categories`를 호출해서 실제 categoryId 값을 받아온
뒤 그 값을 그대로 룰렛 칸/필터 검색에 사용한다.

## 3. UI 구성
------------------------------------------------------------------------
1. 카테고리 아이콘 버튼 10개(탭해서 선택/해제, 선택된 카드는 보라색 테두리 + "✓ 선택됨" 표시)
2. "룰렛 만들기" 버튼(카테고리 2개 미만이면 비활성화) → 클릭 시 Canvas로 룰렛을 그리고 화면 아래로 스크롤
3. "START" 버튼 → 스핀 애니메이션(4.2초) → 당첨 결과 모달("오늘의 선택은... {카테고리명}")
4. 모달에서 "📍 내 주변 맛집 찾기"(2-6장), "이건 빼고 다시 돌리기"(당첨 항목을 후보에서 제거하고 룰렛을
   다시 그림), "닫기"(그대로 유지, 다시 START 가능) 중 선택
5. "처음부터 다시 만들기" — 선택/룰렛 전체 초기화

## 4. 확인이 필요한 사항 / 남은 작업
------------------------------------------------------------------------
- 사다리타기 방식은 미착수(001-01 참고) — 필요해지면 별도 기능으로 추가
- 결과 이력 저장/공유 기능 없음(의도된 설계, 2-1장)
- "내 주변 맛집 찾기" 결과 품질은 07의 기존 카테고리 분류 정확도에 그대로 의존한다 — 07 문서에 이미
  기록된 대로 카테고리 분류가 100% 정확하지는 않아서(예: 한식 식당이 카페/디저트로 분류되는 등의 오차),
  이번 기능에서 이 정확도를 더 손보지는 않았다(07의 소관)
