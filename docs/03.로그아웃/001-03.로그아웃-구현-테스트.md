## 1. 구현 결과 (2026-07-17)
------------------------------------------------------------------------
설계안(001-02) 그대로 구현함. 신규 엔티티/DB 테이블 없이 Redis만 사용, 기존 로그인 구현 자산에 파일만 추가.

### 1-1. 신규/수정 파일
```
com.foodtrip.foodsearch
 ├─ common
 │   ├─ exception    ErrorCode (NOT_LOGGED_IN 추가)
 │   └─ security      JwtProvider (jti 클레임 추가, generateAccessToken 반환 타입을
 │                                 IssuedAccessToken(token, jti) 레코드로 변경, parseClaims() 신규 추가,
 │                                 getExpirationMillis() 신규 추가)
 └─ member
     ├─ controller   MemberController          (POST /api/members/logout 추가)
     ├─ service      MemberService              (logout() 추가)
     │               MemberServiceImpl          (login()/refresh()에 access token 세션 등록 추가, logout() 신규 구현)
     │               AccessTokenSessionService  (신규, Redis 기반 — access:{jti} 등록/삭제)
     │               RefreshTokenService        (exists(memberId), revoke(memberId) 메서드 추가 — 로그아웃에서 사용)
     └─ dto          LogoutRequestDto  (신규)
                     LogoutResponseDto (신규)
```

### 1-2. JwtProvider 변경 상세
- `generateAccessToken()`이 `String` 대신 `IssuedAccessToken(String token, String jti)` 레코드를 반환하도록 변경
  → 발급 직후 `jti`를 바로 알아야 `access:{jti}` 키를 등록할 수 있어서, 토큰을 다시 파싱해서 jti를 꺼내는 것보다 발급 시점에 같이 반환하는 쪽을 선택
- `parseClaims(String token)` 신규 — 서명/형식/만료를 검증하고 `Claims` 반환, 실패 시 `io.jsonwebtoken.JwtException`(하위 타입 포함) 던짐
- `getExpirationMillis()` 신규 — access token TTL을 `AccessTokenSessionService.register()` 호출 시 그대로 넘겨주기 위함

이 변경으로 기존 `login()`/`refresh()` 호출부도 함께 수정됨(반환 타입이 바뀌었으므로).

### 1-3. 로그인/재발급 로직에 추가된 부분 (001-02 2장·9장에서 이미 계획했던 대로)
- `MemberServiceImpl.login()`: access token 발급 직후 `accessTokenSessionService.register(jti, memberId, jwtProvider.getExpirationMillis())` 호출 추가
- `MemberServiceImpl.refresh()`: 재발급된 새 access token에 대해서도 동일하게 등록 (재발급 시마다 새 `access:{jti}`가 생기고, 이전 access token의 키는 자연 TTL로 만료됨 — 별도로 무효화하지 않음. 001-02에서 명시적으로 다루지 않은 부분이라 이 문서 4장에 후속 검토사항으로 남김)

### 1-4. 로그아웃 로직 (MemberServiceImpl.logout, 설계 001-02 3-2장 그대로)
1. `accessToken`을 `jwtProvider.parseClaims()`로 검증 → 실패(서명 오류/형식 오류/만료) 시 `NOT_LOGGED_IN`
2. `claims.getSubject()`(memberId), `claims.getId()`(jti) 추출
3. `refreshTokenService.exists(memberId)` 확인 → 없으면(이미 로그아웃했거나 로그인 이력 없음) `NOT_LOGGED_IN`
4. `refreshTokenService.revoke(memberId)`(`refresh:{memberId}` 삭제) + `accessTokenSessionService.revoke(jti)`(`access:{jti}` 삭제)
5. `LogoutResponseDto(true, "로그아웃되었습니다.")` 반환

### 1-5. API 스펙 (실제 구현)
```
POST /api/members/logout
Request: { "accessToken": "eyJhbGciOi..." }

Response (성공, 200): { "success": true, "message": "로그아웃되었습니다." }
Response (실패, 401): { "success": false, "code": "NOT_LOGGED_IN", "message": "로그인 상태가 아닙니다." }
Response (입력값 오류, 400): { "success": false, "code": "INVALID_INPUT", "message": "accessToken: accessToken은 필수입니다." }
```
설계안과 100% 동일하게 구현됨 — 이번엔 구현 중에 설계를 바꾼 부분이 없었음.

## 2. Playwright 테스트
------------------------------------------------------------------------
- 위치: `Project2/e2e/tests/logout.spec.js`
- 테스트 방식: 기존 로그인 테스트와 동일하게 API request context로 직접 호출. 회원가입 → 로그인까지 실제 API로 거친 뒤 그 access token으로 로그아웃을 검증
- Redis 검증에는 기존 `redisHelper.js`를 확장해서 사용: `isAccessTokenActive(jti)`, `cleanupAccessKey(jti)` 신규 추가
- 실행 방법: `cd Project2/e2e && npx playwright test tests/logout.spec.js` (사전에 Spring Boot 앱이 8081 포트로 기동되어 있어야 함)

### 2-2. 회귀 확인 (기존 로그인/회원가입 테스트)
`JwtProvider.generateAccessToken()`의 반환 타입이 바뀌면서 `login()`/`refresh()` 호출부도 함께 수정되었기 때문에, 기존 로그인·재발급 테스트가 깨지지 않았는지 전체 스위트로 확인함. 기존 로그인 성공/재발급 테스트에는 이번에 새로 생긴 `access:{jti}` 키에 대한 정리(clean-up)가 없어서 처음 실행 후 Redis에 잔여 키 4개가 남는 것을 발견 → `login.spec.js`의 관련 테스트에 `cleanupAccessKey()` 호출을 추가해서 해결.

## 3. 설계 대비 확정한 사항 (001-02 10장 "확인이 필요한 사항" 답변)
------------------------------------------------------------------------
| 항목 | 확정 내용 |
|---|---|
| refresh token만 없고 access token만 유효한 경우 | 설계대로 `NOT_LOGGED_IN` 처리 (refresh token 존재 여부로 로그인 상태를 판단하므로) |
| 다중 기기 로그인 | 이번 구현에 포함하지 않음. 기존 로그인 설계(1인 1세션)를 그대로 따름 |
| 프론트의 로그아웃 실패 시 처리 | 백엔드 범위 밖. 001-04(연동 가이드) 작성 시 프론트에 안내 예정 |

## 4. 남은 작업 (Not Done)
------------------------------------------------------------------------
- **재발급(refresh)으로 새 access token을 받으면, 이전 access token의 `access:{jti}`가 즉시 삭제되지 않고 자연 TTL(최대 60분)로만 만료됨.** 즉 재발급 후에도 이전 access token이 이론적으로는 만료 전까지 "세션 등록소에 남아있는" 상태 — 다만 지금은 이 등록소를 검사하는 인가 필터 자체가 없어서 실질적 영향은 없음. 인가 필터를 만들 때 이 부분도 같이 정리(재발급 시 이전 jti도 revoke)할지 결정 필요
- 인가 필터(로그인 001-05 1번 항목) 자체는 이번에도 구현하지 않음 — `access:{jti}` 등록/삭제까지만 준비해두고, 실제로 이 값을 "검사"하는 필터는 보호할 API가 생길 때 만들기로 함(기존 방침 유지)
- 로그아웃 후 프론트 라우팅(메인 화면 이동)은 요구사항대로 이번 범위 제외 — 001-04(연동 가이드) 작성 시 프론트 쪽 처리 방법만 안내
