------------------------------------------------------------------------
## 1. 요구사항 정리
------------------------------------------------------------------------
- 현재 로그인 중인 경우에만 로그아웃이 동작해야 함
- 로그아웃 시 access token, refresh token 둘 다 삭제
- 로그아웃 후 메인 화면 이동 (프론트 화면 미개발이라 이번 범위 제외, 응답만 내려줌)

------------------------------------------------------------------------
## 2. 지금 상태에서 확인이 필요했던 부분과 확정한 방향
------------------------------------------------------------------------
요구사항 문서에 "로그인 중인 경우에만"이라고만 되어 있고 구체적인 판단 기준이 없어서, 기존 구현을 기준으로 아래와 같이 확정함.

| 항목 | 확정 내용 | 이유 |
|---|---|---|
| "로그인 중"의 판단 기준 | 요청으로 받은 access token이 **서명·형식상 유효**하고, 그 토큰의 `sub`(memberId)에 대응하는 **refresh token이 Redis(`refresh:{memberId}`)에 남아있으면** 로그인 중으로 판단 | 아직 인가 필터가 없어서(로그인 001-05 1번 항목) "이 요청이 인증된 사용자의 것"이라는 걸 확인할 다른 수단이 없음. refresh token 존재 여부가 "활성 세션이 있다"는 가장 현실적인 신호 |
| access token "삭제" | ~~블랙리스트에 등록~~ 대신, **refresh token과 똑같은 방식**으로 처리하기로 함: 로그인 시점에 access token도 Redis에 `access:{jti}` 키로 등록해두고(TTL = access token 만료시간과 동일), 로그아웃 시 그 키를 **`DEL`해서 즉시 만료**시킴. "블랙리스트에 추가"가 아니라 "로그인 때 만들어둔 걸 로그아웃 때 지운다"는 점에서 refresh token 처리와 완전히 대칭됨 | JWT는 서버가 상태를 안 들고 있어 토큰 자체를 지울 수는 없지만(stateless), "이 토큰이 아직 유효한 세션인가"를 Redis 쪽에서 별도로 관리하면 로그아웃 시 그 기록만 지우는 것으로 사실상 즉시 만료 처리가 됨. 새로 추가하는 개념(블랙리스트) 대신 이미 쓰고 있는 패턴(발급 시 등록 → 로그아웃 시 삭제)을 그대로 재사용 |
| refresh token 삭제 | Redis의 `refresh:{memberId}` 키를 `DEL` | 이미 있는 저장 방식과 그대로 대칭되는 처리 |
| 이 방식이 실제로 뭘 막아주는가 | 지금은 인가 필터 자체가 없어서, `access:{jti}`를 지워도 즉시 막히는 API는 없음(애초에 막을 API가 없음). 다만 **1) refresh token은 즉시 삭제되므로 재로그인 없이 새 access token을 받는 것은 확실히 막힘**, **2) 나중에 인가 필터를 만들 때 "`access:{jti}`가 Redis에 존재하는가"를 검사에 포함시키면 그 시점부터 남은 access token 수명 동안의 재사용도 막힘** (블랙리스트 방식이었어도 결과는 동일 — 검사 방향만 "블랙리스트에 없어야 통과"에서 "레지스트리에 있어야 통과"로 바뀌는 것) | 인가 필터가 없는 현재 상태에서 "완전한 즉시 무효화"까지는 안 되지만, 요구사항 범위(토큰 삭제) 안에서 할 수 있는 걸 다 함 |
| **로그인 로직도 같이 수정해야 함** | 이미 구현되어 있는 `MemberServiceImpl.login()`에서 access token을 발급하는 시점에 `access:{jti}` 키도 같이 등록해야 함(지금은 안 함) — 이번 로그아웃 작업이 로그인 코드에도 손을 대는 이유 | 로그아웃이 지우려면, 로그인이 먼저 등록해둬야 함(refresh token과 동일한 관계) |

------------------------------------------------------------------------
## 3. 전체 플로우
------------------------------------------------------------------------
### 3-1. 로그인 시점 (기존 로직에 추가되는 부분)
1. (기존과 동일) access token, refresh token 발급
2. (신규) access token의 `jti`로 `access:{jti}` 키를 Redis에 등록, TTL = access token 만료시간(기본 60분)

### 3-2. 로그아웃 시점
1. 클라이언트가 로그인 응답에서 받아 보관 중인 `accessToken`을 그대로 실어서 로그아웃 요청
2. 서버가 `accessToken`을 검증(서명/만료)
   - 서명이 틀렸거나 만료됐거나 형식이 이상하면 → "로그인 상태 아님"으로 처리, 에러 응답
3. 검증 성공 시 토큰에서 `sub`(memberId), `jti` 추출
4. `refresh:{memberId}` 키가 Redis에 있는지 확인
   - 없으면(이미 로그아웃했거나 원래 로그인 이력 없음) → "로그인 상태 아님"으로 처리, 에러 응답
5. 있으면:
   - `refresh:{memberId}` 삭제 (`DEL`) → refresh token 만료
   - `access:{jti}` 삭제 (`DEL`) → access token 만료 (자연 만료보다 앞당겨서 즉시 무효화)
6. 성공 응답 반환 (메인 화면 이동은 프론트 담당)

## 4. 패키지 구조 (제안)
------------------------------------------------------------------------
기존 로그인 구현 자산(`com.foodtrip.foodsearch`)에 파일만 추가하는 방식. 신규 엔티티/DB 테이블 없음(전부 Redis 처리).

```
com.foodtrip.foodsearch
 ├─ member
 │   ├─ controller   MemberController          (POST /api/members/logout 추가)
 │   ├─ service      MemberService              (logout() 추가)
 │   │               MemberServiceImpl          (login()에 access token 등록 로직 추가, logout() 신규 구현)
 │   │               AccessTokenSessionService  (신규, Redis 기반 — 로그인 시 등록 / 로그아웃 시 삭제)
 │   └─ dto          LogoutRequestDto  (신규)
 │                   LogoutResponseDto (신규)
 └─ common
     ├─ exception    ErrorCode (NOT_LOGGED_IN 추가)
     └─ security      JwtProvider (jti 클레임 추가, 토큰 파싱/검증 메서드 추가)
```

## 5. 데이터 모델 (Redis, 전부 로그인 단계에서 이미 쓰던 키 체계와 동일선상)
------------------------------------------------------------------------
| 키 | 값 | TTL | 비고 |
|---|---|---|---|
| `refresh:{memberId}` | refresh token 문자열 | (기존 그대로, 14일) | 로그아웃 시 `DEL` — 이미 로그인 단계에서 쓰던 키를 그대로 재사용 |
| `access:{jti}` | memberId (또는 아무 값, 존재 여부만 확인) | access token 만료시간과 동일(기본 60분) | 신규. **로그인 시점에 등록**, 로그아웃 시점에 `DEL`. `JwtProvider`에 `jti` 클레임 추가가 선행되어야 함 |

`access:{jti}`는 "블랙리스트"(로그아웃된 것만 모아두는 목록)가 아니라 **"현재 유효한 access token 등록소"**에 가깝다 — 로그인할 때마다 새로 생기고, 자연 만료(TTL)되거나 로그아웃으로 지워지면 없어진다. refresh token과 정확히 같은 생애주기.

------------------------------------------------------------------------
## 6. API 설계
------------------------------------------------------------------------
### 6-1. 로그아웃
```
POST /api/members/logout
Request:
{ "accessToken": "eyJhbGciOi..." }

Response (성공, 200):
{ "success": true, "message": "로그아웃되었습니다." }

Response (실패, 401):
{ "success": false, "code": "NOT_LOGGED_IN", "message": "로그인 상태가 아닙니다." }
```
처리:
- `accessToken`이 없거나 형식이 이상하면 400 `INVALID_INPUT` (`@NotBlank` 검증)
- `accessToken` 서명 검증 실패(위조/만료) → 401 `NOT_LOGGED_IN`
- 서명은 유효하나 `refresh:{memberId}`가 Redis에 없음(이미 로그아웃됨 등) → 401 `NOT_LOGGED_IN`
- 정상 케이스 → `refresh:{memberId}`, `access:{jti}` 둘 다 삭제 → 200 성공

------------------------------------------------------------------------
## 7. 검증 규칙
------------------------------------------------------------------------
- `accessToken`: `@NotBlank` (형식 자체는 JWT 파싱 과정에서 자연스럽게 걸러짐, 별도 정규식 검증은 불필요)

------------------------------------------------------------------------
## 8. 예외/에러 코드 설계
------------------------------------------------------------------------
| 코드 | 상황 | HTTP Status |
|---|---|---|
| INVALID_INPUT | accessToken 미입력 | 400 |
| NOT_LOGGED_IN | access token이 무효(서명 오류/만료)이거나, 유효하지만 대응하는 refresh token이 없어 로그인 상태로 볼 수 없음 | 401 |

두 가지 원인을 하나의 코드로 통일한 이유는 로그인 001-02에서 `INVALID_CREDENTIALS`를 여러 원인에 대해 하나로 통일했던 것과 같은 이유 — "정확히 왜 안 되는지"를 클라이언트에 노출할 실익이 없고, 프론트는 이 코드를 받으면 그냥 로그인 화면으로 보내면 됨.

------------------------------------------------------------------------
## 9. 기존 코드 변경 사항 (선행 작업)
------------------------------------------------------------------------
### JwtProvider
- `generateAccessToken()`에 `jti` 클레임(발급마다 랜덤 UUID) 추가 — 지금은 `sub`/`email`/`role`만 있고 `jti`가 없어서 `access:{jti}` 키를 만들 값이 없음
- 토큰을 파싱/검증하는 메서드 신규 추가 (예: `parseClaims(String token)` → 서명 검증 후 `Claims` 반환, 실패 시 예외)
  - 기존에는 발급(`generateAccessToken`)만 있고 검증 로직이 전혀 없었음(로그인 001-05 1번 항목 "인가 필터 없음"과 같은 맥락) — 로그아웃 구현에 필요한 최소한의 검증 로직만 우선 추가하고, 인가 필터 자체는 이번 범위에 포함하지 않음

### MemberServiceImpl.login() (이미 구현되어 있는 기존 로직 수정)
- access token 발급 직후 `AccessTokenSessionService.register(jti, memberId)` 호출 추가 — TTL은 access token 만료시간과 동일하게
- 기존 로그인 동작(응답 형태, 에러 처리 등)에는 영향 없음, Redis 등록 한 줄만 추가되는 것

------------------------------------------------------------------------
## 10. 확인이 필요한 사항
------------------------------------------------------------------------
- refresh token까지 만료/삭제된 상태에서 access token만 유효하게 남아있는 경우(예: refresh token 없이 access token만 오래 들고 있는 클라이언트)를 "로그인 중 아님"으로 처리하는 게 맞는지 — 이번 설계에서는 그렇게 정했지만, 실제 서비스 정책과 다를 수 있어 확인 필요
- 로그아웃을 여러 기기에서 동시에 하는 경우(다중 기기 로그인)는 현재 1인 1세션 가정(로그인 001-05 7-1번 항목)이라 고려하지 않음 — 나중에 다중 기기 지원이 필요해지면 재설계 필요
- 프론트가 로그아웃 실패(`NOT_LOGGED_IN`) 시에도 로컬에 저장된 토큰은 그냥 지우고 로그인 화면으로 보내는 게 맞는지 확인 필요 (서버 상태와 무관하게 클라이언트 쪽 정리는 항상 하는 게 일반적)

------------------------------------------------------------------------
## 11. 작업 순서 (제안)
------------------------------------------------------------------------
1. `JwtProvider`에 `jti` 클레임 추가, 토큰 파싱/검증 메서드 추가
2. `ErrorCode.NOT_LOGGED_IN` 추가
3. `AccessTokenSessionService`(Redis) 구현 — `register(jti, memberId, ttl)`, `revoke(jti)`, 필요 시 `isActive(jti)`(추후 인가 필터용으로 남겨둠, 이번 로그아웃 자체에는 조회가 필요 없음)
4. `MemberServiceImpl.login()`에 `AccessTokenSessionService.register()` 호출 추가 (기존 로그인 로직 수정)
5. `LogoutRequestDto`, `LogoutResponseDto` 작성
6. `MemberService`/`MemberServiceImpl.logout()` 구현 (토큰 검증 → refresh token 존재 확인 → `refresh:{memberId}`/`access:{jti}` 둘 다 삭제)
7. `MemberController`에 `POST /api/members/logout` 추가
8. Playwright로 성공/실패 케이스 테스트 (정상 로그아웃 후 Redis에서 두 키 모두 사라졌는지 확인, access token 위조/만료, 로그인 이력 없는 토큰, 이미 로그아웃한 토큰 재사용, 로그인 직후 `access:{jti}`가 등록되는지)

구현 결과 및 테스트 내용은 별도 구현/테스트 문서에 정리 (001-03.로그아웃-구현-테스트.md)
