### 1-2. API 구현 목록
| API | 인증 | 설명 |
|---|---|---|
| POST /api/reviews/{reviewId}/report | 로그인 필수 | 리뷰 신고 |
| GET /api/admin/reports?status= | ADMIN | 신고된 리뷰 목록(리뷰 단위로 집계, status로 PENDING/RESOLVED/REJECTED 필터, 2차 추가) |

| PATCH /api/admin/reports/{reviewId}/reject | ADMIN | 그 리뷰의 대기 중 신고 전체 반려/처리 불가(2차 추가) |

## 2. 검증 (2026-07-23, 실 서버 + 실 DB)
------------------------------------------------------------------------
Node `fetch` 스크립트로 실제 API를 순서대로 호출해 확인.

### 2-1. 컴파일
`./mvnw.cmd compile` 정상 통과.

### 2-2. 신고 등록 전체 흐름
- 일반 회원(ADMIN으로 승격되기 전 `test@naver.com`과는 별개로, 이 세션에서는 이미 ADMIN인 계정으로
  테스트 — 신고 API 자체는 role과 무관하게 로그인만 되어 있으면 누구나 호출 가능함을 코드로 확인) 토큰으로
  기존 리뷰 1건에 `POST /api/reviews/{id}/report`(`reasonCode: "SPAM"`) 호출 → `200`
- 같은 회원이 같은 리뷰를 다시 신고 → `409 REVIEW_ALREADY_REPORTED`(2-2장 유니크 제약이 애플리케이션
  레벨에서 먼저 걸림)
- 존재하지 않는 리뷰(`999999`) 신고 시도 → `404`(REVIEW_NOT_FOUND, 리뷰 존재 확인이 먼저 수행됨)

### 2-3. 관리자 신고 목록 + 처리
- `GET /api/admin/reports` → `200`, 방금 신고한 리뷰가 `reportCount: 1`, `latestReasonCode: "SPAM"`,
  작성자 닉네임/음식점명 스냅샷/별점/내용까지 정확히 채워진 한 줄로 정상 반환됨을 확인(2-4장 집계 로직 검증)
- `PATCH /api/admin/reports/{reviewId}/resolve` → `200`
- 같은 리뷰를 다시 resolve 시도(이제 `PENDING` 신고가 없음) → `404 REPORT_NOT_FOUND`(가드 정상 동작)

### 2-4. 14(관리자-권한) 대시보드와의 연동 확인
- 신고 등록 직후 `GET /api/admin/dashboard`의 `reviewReported`가 `0` → `1`로 증가하는 것을 확인
- `resolve` 처리 직후 다시 `0`으로 돌아오는 것을 확인(`AdminReportService.countPendingReportedReviews()`가
  `PENDING` 기준으로만 세므로, 처리 완료된 건 카운트에서 빠짐 — 001-02 2-4장/설계대로 동작)

### 2-5. 프론트 연동 확인 (1차)
- `admin-test.html`: "신고 관리(신고된 리뷰)" 카드에 목록/처리완료/리뷰삭제 버튼 정상 동작, "대시보드"
  카드의 신고된 리뷰 수 타일이 실시간으로 갱신되는 것 확인
- `tmp-map-test.html`: 리뷰 목록 각 항목에 "🚩 신고" 버튼 추가, 클릭 시 `prompt()`로 사유/상세를 받아
  신고 API를 호출하고 결과를 알림으로 표시하는 것까지 확인(검증용 최소 UI, 이후 2-6장에서 팝업 모달로 교체)

### 2-6. 신고 UI를 팝업 모달로 교체 (2026-07-23 2차, 001-01 후속 요청 1)
`tmp-map-test.html`의 `reportReview()`가 `prompt()` 대신 실제 모달(`#reportModalOverlay`/`#reportModal`)을
열도록 교체:
- 신고 사유 5종(2-1장)을 라디오 버튼으로 노출, 상세 내용은 textarea(최대 500자, 글자수 카운터 표시)
- "신고하기" 클릭 시 `submitReport()`가 선택된 사유+입력한 상세로 `POST /api/reviews/{id}/report` 호출
- 취소 버튼과 모달 바깥 클릭으로 닫기 지원
- 최초 배포 후 버튼이 화면에 안 보인다는 리포트가 있었으나, 원인은 코드 문제가 아니라 정적 리소스 캐싱
  이슈(파일 수정만으로는 서버가 반영 못 함 — 이 세션에서 반복 확인된 이슈, 전체 서버 재시작 필요)였고
  재시작 후 정상 노출 확인

### 2-7. 처리 완료/반려 구분 + 상태별 조회 (2026-07-23 2차, 001-01 후속 요청 2)
Node 스크립트로 실 서버/실 DB에 대해 순서대로 검증(스크립트는 검증 후 삭제):
- 리뷰 신고 등록 → `200`(신규 PENDING 신고 1건 생성, 기존 신고가 남아있어 409로 재사용된 케이스 포함해
  최종적으로 PENDING 신고 1건이 있는 상태로 정리)
- `GET /api/admin/reports`(status 생략, 기본 PENDING) → 방금 신고한 리뷰가 목록에 나타나고 `status:
  "PENDING"` 필드 포함 확인
- `PATCH /api/admin/reports/{reviewId}/reject` → `200`
- `GET /api/admin/reports`(기본 PENDING) → 방금 반려한 리뷰가 더 이상 나타나지 않음(PENDING 신고가 없어짐)
- `GET /api/admin/reports?status=REJECTED` → 방금 반려한 리뷰가 `status: "REJECTED"`로 정확히 나타남
- `GET /api/admin/reports?status=RESOLVED` → 이전(2-3장)에 resolve 처리했던 다른 리뷰가 `status:
  "RESOLVED"`로 정상 조회됨(상태별로 서로 섞이지 않음을 확인)
- 같은 리뷰를 다시 reject 시도(이제 PENDING 신고 없음) → `404 REPORT_NOT_FOUND`(resolve와 동일한 가드가
  reject에도 적용됨을 확인)
- `GET /api/admin/dashboard`의 `reviewReported`가 reject 후에도 `0`을 유지(2-4장과 동일 원리 — 카운트는
  PENDING 기준이므로 reject도 resolve와 마찬가지로 대시보드 카운트를 감소시킴)
- `admin-test.html`: 3개 탭 버튼(대기중/처리완료/반려)이 각각 올바른 목록을 보여주고, PENDING 탭에서만
  "처리 완료"/"처리 불가" 버튼이 노출되는 것 확인(RESOLVED/REJECTED 탭은 조회 전용, 액션 버튼 없음)
