## 2. 핵심 설계 결정
------------------------------------------------------------------------
### 2-1. 신고 사유는 고정 목록 — 10.리뷰의 태그 패턴 재사용
`ReportReasonCatalog`가 허용 목록의 유일한 출처(백엔드 검증) — `SPAM`/`ABUSE`/`FALSE_INFO`/`PRIVACY`/`ETC`
5종. 10(리뷰)의 `ReviewKeywordCatalog`(긍정/부정 태그 20개 고정 목록)와 완전히 같은 패턴이다 — 자유
텍스트로 사유를 받으면 관리자가 통계/필터링하기 어렵고, 스팸성 신고 문구가 그대로 쌓일 위험도 있다.
목록에 없는 값을 보내면 `400 REPORT_REASON_NOT_ALLOWED`.

### 2-2. 회원 1명당 리뷰 1개에 신고는 1번만
`review_reports`에 `UNIQUE(review_id, reporter_member_id)` 제약을 걸었다 — 같은 회원이 같은 리뷰를
여러 번 신고해서 신고 건수를 부풀리는 것을 막는다(악의적 신고 도배 방지). 중복 시도는
`409 REVIEW_ALREADY_REPORTED`로 명확히 거부한다(즐겨찾기처럼 "관대하게 무시"하지 않음 — 신고는 매번 다른
의도가 있을 수 있는 액션이라, 이미 신고했다는 사실을 사용자에게 명확히 알려주는 게 낫다고 판단).

### 2-3. "신고 처리 완료"와 "리뷰 삭제"는 별개 액션
관리자가 신고를 확인하고 `PATCH /api/admin/reports/{reviewId}/resolve`를 호출해도 **리뷰 자체는 지워지지
않는다** — 그 리뷰에 달린 모든 `PENDING` 신고를 `RESOLVED`로 바꿀 뿐이다. 신고가 근거 없다고 판단했으면
"확인만 하고 리뷰는 그대로 둔다"가 정상적인 결과이기 때문 — 신고=삭제라는 자동 연결을 만들지 않았다.
실제로 리뷰를 지우고 싶으면 14(관리자-권한)에 이미 있는 `DELETE /api/admin/reviews/{id}`를 그대로
호출하면 된다(새 삭제 API를 만들지 않음, "필요한 만큼만" 원칙).

### 2-4. 관리자 목록은 "신고 건수" 단위가 아니라 "신고된 리뷰" 단위로 묶어서 보여줌
한 리뷰에 여러 명이 신고할 수 있으므로, `review_reports` 원본 행을 그대로 나열하면 같은 리뷰가 여러 줄
반복돼서 관리하기 불편하다. `ReviewReportRepository.findReportedReviewSummaries()`가 `review_id`로
`GROUP BY`해서 신고 건수(`reportCount`)와 가장 최근 신고 시각을 함께 뽑고, `AdminReportServiceImpl`이
그 결과에 리뷰 정보(작성자 닉네임/음식점명 스냅샷/별점/내용)와 최근 신고 사유를 붙여 완성된 한 줄로
만든다 — `AdminServiceImpl.listReviews()`가 이미 쓰던 "배치로 회원 닉네임 조회 후 매핑" 패턴을 그대로
재사용.

### 2-5. "이미 삭제된 리뷰"에 대한 신고는 목록에서 자동 제외
어떤 리뷰가 신고된 뒤 다른 경로로(작성자 본인 삭제 또는 관리자 강제 삭제) 이미 삭제됐다면, 그 신고 내역은
관리자 목록에 굳이 보여줄 필요가 없다 — `AdminReportServiceImpl.toDto()`가 `reviewRepository.findAllById()`
결과에 없는(=삭제됐거나 존재하지 않는) `reviewId`는 조용히 걸러낸다. 별도 정리 배치 없이 조회 시점에
자연스럽게 걸러지는 방식을 택했다.

### 2-6. 처리 결과를 RESOLVED/REJECTED 두 가지로 구분 (2026-07-23 2차 추가)
"처리된 기록도 볼 수 있어야 하고, 처리 완료가 있으면 처리 불가도 있어야 하지 않냐"는 후속 요청으로,
애초에 `PENDING`→`RESOLVED` 한 방향뿐이던 처리 흐름에 `REJECTED`(반려/처리 불가)를 추가했다:
- **RESOLVED(처리 완료)**: 신고가 타당해서 실제 조치(예: 리뷰 삭제)를 했거나, 조치가 필요하다고 판단한 경우
- **REJECTED(반려/처리 불가)**: 신고를 검토했지만 근거가 없거나 조치할 필요가 없다고 판단한 경우

두 상태 모두 `PATCH .../resolve`와 `PATCH .../reject`로 그 리뷰의 `PENDING` 신고를 일괄 전환한다(2-2장에서
설명한 review 단위 일괄 처리와 동일한 방식). 두 상태를 하나의 "처리됨"으로 합치지 않은 이유는, 나중에
관리자가 이력을 되짚어볼 때 "그 신고가 실제로 타당했는지"를 구분할 수 있어야 하기 때문이다 — 전부 그냥
"RESOLVED"로 뭉뚱그리면, 근거 없는 신고와 실제 문제였던 신고를 나중에 구분할 방법이 없어진다.

`GET /api/admin/reports`에 `status` 파라미터(`PENDING`/`RESOLVED`/`REJECTED`, 기본 `PENDING`)를 추가해서
관리자가 대기중/처리완료/반려 세 목록을 각각 조회할 수 있게 했다 — 새 API를 추가하지 않고 기존 목록 API에
필터만 얹은 이유는 14(관리자-권한)의 `GET /api/admin/members?role=`(2-10장)과 완전히 같은 판단이다.

## 3. API 설계
------------------------------------------------------------------------
### 3-1. 리뷰 신고 (회원, 로그인 필수)
```
POST /api/reviews/{reviewId}/report
Authorization: Bearer {accessToken}
```
요청: `{ reasonCode, detail(선택, 최대 500자) }`

### 3-2. 신고된 리뷰 목록 (관리자 전용)
```
GET /api/admin/reports?status=PENDING
```
`status` 파라미터(선택, `PENDING`/`RESOLVED`/`REJECTED`, 생략 시 `PENDING`, 2-6장) — 대기중/처리완료/반려
세 목록을 각각 조회.

응답: `{ reviewId, authorNickname, restaurantName, rating, content, reportCount, latestReasonCode,
latestReportedAt, status }[]` — `status`는 요청한 필터 값 그대로(2026-07-23 2차 추가), 조회한 상태의
신고가 있는 리뷰만, 최근 신고순.

### 3-3. 신고 처리 완료 (관리자 전용)
```
PATCH /api/admin/reports/{reviewId}/resolve
```
그 리뷰에 달린 모든 `PENDING` 신고를 `RESOLVED`로 일괄 변경(2-3장 — 리뷰는 안 지워짐).

### 3-4. 신고 반려/처리 불가 (관리자 전용, 2026-07-23 2차 추가)
```
PATCH /api/admin/reports/{reviewId}/reject
```
그 리뷰에 달린 모든 `PENDING` 신고를 `REJECTED`로 일괄 변경(2-6장 — resolve와 동일한 구조, 상태값만 다름).
처리할 `PENDING` 신고가 없으면(이미 resolve/reject됐거나 애초에 없음) `404 REPORT_NOT_FOUND`.

## 4. 에러 코드
------------------------------------------------------------------------
| 코드 | 상황 | HTTP |
|---|---|---|
| NOT_LOGGED_IN(기존 재사용) | 신고 시 Authorization 헤더 없음/무효 | 401 |
| REVIEW_NOT_FOUND(10.리뷰 재사용) | 존재하지 않거나 이미 삭제된 리뷰를 신고 시도 | 404 |
| REPORT_REASON_NOT_ALLOWED(신규) | 고정 목록에 없는 사유 코드 | 400 |
| REVIEW_ALREADY_REPORTED(신규) | 같은 회원이 같은 리뷰를 다시 신고 시도 | 409 |
| REPORT_NOT_FOUND(신규) | 처리(resolve 또는 reject)할 `PENDING` 신고가 없는 리뷰 | 404 |
| ADMIN_ACCESS_DENIED / NOT_LOGGED_IN(14 재사용) | 관리자 API를 비관리자/미로그인으로 호출 | 403 / 401 |

## 7. 확인이 필요한 사항 / 남은 작업
------------------------------------------------------------------------
- **자동 처리 없음**(001-01 참고): 신고가 아무리 쌓여도 자동으로 숨겨지거나 삭제되지 않음 — 관리자가 매번
  수동으로 확인/처리해야 함. 필요해지면 "N건 이상 자동 비공개" 같은 정책 추가 검토
- **신고자 알림 없음**: 처리 결과를 신고자에게 알려주지 않음
- **본인 리뷰 신고 방지 로직 없음**: 본인이 쓴 리뷰를 본인이 신고하는 것을 막지 않았다(의미는 없지만
  막을 필요도 크지 않다고 판단, 필요해지면 추가)
- **신고 사유별 통계**: 지금은 "최근 사유"만 목록에 보여줌 — 사유별 집계(예: ABUSE가 몇 건인지)가
  필요해지면 관리자 API 확장 검토
- **독립된 자동화 회귀 테스트 스위트 없음**(ad-hoc 검증 수준, 다른 최근 기능들과 동일)
