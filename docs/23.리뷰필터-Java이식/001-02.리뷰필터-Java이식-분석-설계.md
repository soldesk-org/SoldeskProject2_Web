## 1. 기존 구조 vs 새 구조
------------------------------------------------------------------------
**기존(17.리뷰-필터링 당시)**:
```
ReviewServiceImpl / ChatMessageServiceImpl
   → ReviewFilterClient.containsProfanity(text)
        → RestClient(HTTP POST /check) → Python(FastAPI, review-filter) → korcen.check(text)
```
**새 구조(2026-07-30)**:
```
ReviewServiceImpl / ChatMessageServiceImpl
   → ReviewFilterClient.containsProfanity(text)
        → KorcenProfanityFilter.containsProfanity(text)  (같은 JVM 안, 순수 함수 호출)
```
`ReviewFilterClient`는 클래스명/메서드 시그니처를 그대로 유지해서 호출부 코드를 하나도 안 건드렸다 —
내부 구현만 HTTP 클라이언트에서 로컬 함수 호출로 바뀐 것.

## 2. korcen 원본 판정 알고리즘 (이식 대상 그대로)
------------------------------------------------------------------------
원본(`korcen/korcen.py`, 794줄)을 실제로 읽고 확인한 판정 흐름:

1. URL 제거(`https?://\S+|www\.\S+`)
2. 전처리(`preprocess_text`): 소문자화 → 유사 문자 정규화(수학 기호체/원문자/발음 구별 기호 등 유니코드
   변형을 표준 문자로 치환, `str.maketrans` 방식) → 다중 문자 치환(`_ㅣ_`→`ㅗ` 등) → 공백 제거 →
   카테고리별 추가 치환(예: minor는 `년`/`련`→`놈`, belittle은 `뇬`/`놈`/`넘`→`련`→다시 `년`으로 통일)
3. 오탐(false-positive) 문자열 제거 — 예: general 카테고리에서 "보지마"의 "보지"가 자칫 sexual로
   오판되지 않도록 sexual 카테고리엔 "보지마"류 오탐 목록이 별도로 있음
4. 허용 문자셋 필터링(카테고리별로 다름 — 한글 자모/음절만 허용하는 카테고리, 영문/숫자/일부 기호까지
   허용하는 카테고리로 나뉨). special 카테고리(이모지 등)는 이 단계를 건너뜀
5. 카테고리별 욕설 패턴(문자열 알고리즘 — 리터럴 문자열들의 정규식 알테네이션)과 매칭되면 그 카테고리는
   "욕설 있음"

`check(text)`는 general/minor/sexual/belittle/race/parent/special/politics 8개 카테고리 중 하나라도
걸리면 true. 이 프로젝트의 기존 Python 서버(`filter_api.py`)가 `korcen.check(text)`를 인자 없이(즉
`foreign=False`) 호출하고 있었으므로, english/japanese/chinese는 애초에 검사 대상이 아니었다 —
Java 이식도 이 8개 카테고리로 범위를 맞췄다.

## 3. Java 이식 시 실제로 겪은 문제 2가지
------------------------------------------------------------------------
### 3-1. 서로게이트 쌍(supplementary character) 처리 버그
Python 문자열은 코드포인트 단위로 다뤄지지만, Java `String`은 UTF-16 코드 유닛(`char`) 단위다. 원본의
단일 문자 정규화 맵에는 이모지(예: `🐦`→`새`, `🐕`→`개`, 특수기호 원문자 `🅧`→`x`)가 섞여 있는데, 이런
BMP 밖 문자(예: 🖕, 🏻)는 UTF-16에서 상위/하위 서로게이트 2개 `char`로 표현된다.

처음 작성한 `putAll(char target, String sources)` 헬퍼가 `sources.charAt(i)`로 **char 단위**로 순회하며
각 서로게이트 절반을 개별 키로 등록했는데, 여러 이모지가 같은 상위 서로게이트를 공유한다(예: 🖕와
🐦 계열 이모지가 전부 `U+D83D`로 시작). 그 결과 나중에 등록된 이모지 그룹이 먼저 등록된 그룹의
서로게이트 값을 덮어써서, `special` 카테고리 테스트(`"손가락 🖕🏻 그만"`)가 원래 잡혀야 하는데
안 잡히는 실제 버그로 나타났다(직접 만든 재현 테스트로 발견).

**수정**: `sources.codePoints()`로 코드포인트 단위 순회하고, BMP 밖(0xFFFF 초과) 코드포인트는 아예
건너뛰도록 변경(`Map<Character,Character>` 구조상 서로게이트 쌍 전체를 하나의 키로 담을 수 없어서
정규화 자체를 포기 — 대신 `translateSingleChars`가 맵에 없는 문자는 원본 그대로 통과시키므로, 실제
이모지 입력(예: 🖕🏻)은 정규화 없이도 원문 그대로 남아 `SPECIAL_PROFANITY` 패턴과 정상 매칭된다).

### 3-2. Windows 플랫폼 기본 인코딩(CP949)으로 이모지 리터럴이 컴파일 시점에 깨지는 문제
`pom.xml`에 `project.build.sourceEncoding`이 없어서 Maven이 OS 기본 인코딩(이 개발 환경 기준
`x-windows-949`)으로 `.java` 파일을 읽고 있었다. 순수 한글 텍스트는 CP949로도 표현 가능해서 지금까지
문제가 드러난 적이 없었지만, `SPECIAL_PROFANITY` 배열의 이모지 리터럴(CP949로 표현 불가능한 코드포인트)은
컴파일 중 깨질 위험이 있었다 — `<project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>`을
추가해서 해결(프로젝트 전체에 적용되는 안전한 변경, 기존 한글 텍스트 컴파일 결과는 동일).

## 4. 정확도 검증 방식
------------------------------------------------------------------------
원본 `korcen/korcen.py`의 `__main__` 데모 블록에 있는 실제 테스트 문장들을 그대로 가져와 Java
포트와 비교(자세한 결과는 [001-03](001-03.리뷰필터-Java이식-구현-테스트.md) 참고). 완전히 새로 만든
로직이 아니라 원본을 그대로 옮기는 작업이라, "원본과 동일하게 동작하는가"가 검증 기준이지 "얼마나
더 잘 잡는가"가 기준이 아니다.
