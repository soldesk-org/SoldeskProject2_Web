## 2. 핵심 설계 결정
------------------------------------------------------------------------
### 2-1. Spring Security는 `/api/admin/**`에만 건다 — 나머지는 그대로
가장 "정석적인" 방식은 모든 API를 Spring Security의 인증/인가 체계로 옮기는 것이다. 하지만 이 프로젝트는
이미 회원가입~마이페이지까지 13개 기능이 각자의 `resolveMemberId()`/`resolveMemberIdOrNull()` 패턴으로
완성되어 실사용 검증까지 끝난 상태다(예: 카카오 로그인 실사용자 검증 완료). 이걸 전부 Spring Security로
재작성하는 건:
- 이번 요청("관리자 권한 분리")의 범위를 크게 벗어나는 대규모 리팩터링이고
- 이미 잘 동작하는 코드를 건드리는 만큼 회귀 위험이 크며
- 지금 당장 필요한 건 "관리자만" 구분하는 것이지 "전체 인가 체계 재설계"가 아니다

그래서 `SecurityConfig`의 `authorizeHttpRequests`는 `/api/admin/**`만 `hasRole("ADMIN")`으로 제한하고,
`anyRequest()`는 `permitAll()`로 둔다 — Spring Security 레벨에서는 나머지 경로를 전혀 통제하지 않으며,
그 경로들은 지금까지와 똑같이 각 서비스의 자체 인증 로직이 그대로 담당한다. 두 인증 방식이 같은 앱 안에
공존하지만, 서로 다른 경로 대역을 담당하므로 충돌하지 않는다.

### 2-2. JwtAuthenticationFilter — 항상 통과시키고, 유효하면 SecurityContext만 채움
`JwtAuthenticationFilter`(`OncePerRequestFilter`)는 모든 요청에서 실행되지만, Authorization 헤더가
없거나 무효해도 요청을 막지 않는다 — 그냥 SecurityContext를 비운 채 다음 필터로 넘긴다. 유효한 토큰이면
`SecurityContext`에 `UsernamePasswordAuthenticationToken(memberId, null, [ROLE_{role}])`을 채운다.

- 기존 JWT에 이미 `role` 클레임이 들어있어서(`JwtProvider.generateAccessToken(memberId, email, role)`,
  02(로그인) 설계 때부터 있던 값) 이번에 토큰 발급 로직을 전혀 바꾸지 않고도 역할 정보를 그대로 재사용할
  수 있었다.
- `AccessTokenSessionService.isActive(jti)`도 그대로 재사용 — 로그아웃된/만료된 세션이면 Security
  Context를 채우지 않는다(다른 API들의 `resolveMemberId()`가 이미 하던 것과 동일한 검사).
- 이 필터가 SecurityContext를 채워도, `/api/admin/**`이 아닌 경로에서는 Spring Security가 그 정보를
  전혀 참조하지 않는다(2-1장) — 오직 `/api/admin/**`의 `hasRole("ADMIN")` 판단에만 쓰인다.

### 2-3. 커스텀 401/403 응답 — 이 프로젝트의 다른 API와 같은 JSON 형식으로
Spring Security 기본 동작은 401/403 응답 본문이 비어있거나 형식이 다르다. `SecurityConfig`에
`authenticationEntryPoint`(401, 미로그인 → `NOT_LOGGED_IN`)와 `accessDeniedHandler`(403, 로그인은
했지만 ADMIN이 아님 → 신규 `ADMIN_ACCESS_DENIED`)를 커스텀으로 등록해서, 기존 `ErrorResponse`
(`{success:false, code, message}`)와 동일한 형식으로 응답하도록 맞췄다 — 프론트 입장에서 관리자 API도
다른 API와 완전히 같은 방식으로 에러 처리를 할 수 있다.

### 2-4. 관리자 서비스는 자체 인증 코드가 없다
`AdminServiceImpl`은 다른 도메인 서비스와 달리 `Authorization` 헤더를 파싱하는 코드가 전혀 없다 —
컨트롤러에 도달했다는 것 자체가 이미 `SecurityConfig`의 `hasRole("ADMIN")`을 통과했다는 뜻이기 때문이다.
이게 이번에 Spring Security를 실제로 도입한 이유를 가장 직접적으로 보여주는 부분: 인가 로직이 한 곳
(필터체인 설정)에만 있고, 매 서비스 메서드가 그걸 각자 다시 구현할 필요가 없다.

### 2-5. 계정 정지 — 즉시 로그인 차단 + refresh token 무효화, 단 이미 발급된 accessToken은 예외
`suspend()`는 (1) `Member.status`를 `SUSPENDED`로 바꾸고 (2) `RefreshTokenService.revoke(memberId)`로
그 회원의 재발급 토큰을 즉시 무효화한다. 로그인 자체는 이미 `MemberServiceImpl`에 `ACCOUNT_SUSPENDED`
체크가 있어서(이전 세션에 소셜로그인/일반로그인 공용으로 이미 구현돼있던 로직, 새로 만들지 않음) 정지 즉시
재로그인이 막힌다.

**알려진 한계**: 정지 시점에 이미 발급되어 있던 accessToken은 `AccessTokenSessionService`가 jti 단위로만
관리되고(memberId로 전체 세션을 찾아 무효화하는 기능이 없음), 그 회원 본인이 로그아웃하거나 자연 만료
(`jwt.expiration-minutes`, 기본 60분)될 때까지 계속 유효하다. 이건 새로운 제약이 아니라 05(회원정보수정)
001-03 5장에서 이미 인지하고 있던 것과 같은 종류의 기존 구조적 한계다 — "정지된 회원이 만료 전
accessToken으로 계속 API를 호출하는 예외 상황은 범위 밖"이라고 이미 문서화되어 있었다. 이번에도 같은
전제를 그대로 따른다(8장 참고).

### 2-6. 정지 해제는 `SUSPENDED → ACTIVE`만 허용
`unsuspend()`는 현재 상태가 정확히 `SUSPENDED`일 때만 동작한다(아니면 `409 MEMBER_STATUS_INVALID`) —
`WITHDRAWN`(탈퇴) 회원을 이 API로 되살리는 건 별도 정책이 필요한 다른 문제라 이번 범위에 넣지 않았다
(001-01 "이번 범위에서 제외된 것"). 반대로 `suspend()`도 이미 `SUSPENDED`/`WITHDRAWN`인 회원에는 동작하지
않는다(같은 에러코드) — 상태 전이를 명확한 두 방향으로만 제한해서 예상 못한 상태 조합을 막았다.

### 2-7. ~~음식점 삭제~~ (2026-07-23 제거됨)
1차 구현에는 `DELETE /api/admin/restaurants/{id}`(음식점 부가정보 소프트 삭제, 카카오 ToS 구조상 실제로는
설명/사진/평점 캐시만 지워지고 리뷰는 남는다는 설계였음)가 있었으나, "필요없다"는 후속 지시로 컨트롤러/
서비스/`Restaurant.delete()` 엔티티 메서드/테스트 페이지 UI까지 전부 제거했다(9장). 이 절은 그 설계가
있었다는 기록만 남긴다 — 다시 필요해지면 git 이력에서 복구 가능.

### 2-8. 시스템 상태 실시간 모니터링 — 무엇을 "실제로" 확인하고 무엇을 "설정 여부만" 확인하는지
"현재 API 상태들 실시간으로 모니터링" 요청(001-01 9장)으로 `GET /api/admin/status`를 추가했다. 확인
대상을 두 종류로 나눴다:

- **실제 연결 확인(UP/DOWN)**: DB(MariaDB), Redis, business-verify Python 서버, recommendation Python
  서버. 전부 매 요청(관리자 페이지에서는 5초마다)마다 실제로 연결을 시도해서 결과를 즉시 반영한다 — 짧은
  타임아웃(2초)으로 응답이 늦어져도 전체 상태 조회가 오래 걸리지 않게 함.
- **설정 여부만 확인(CONFIGURED/NOT_CONFIGURED)**: 카카오 로컬/로그인 API, 메일(Daum SMTP), SMS(Ppurio).
  이 셋은 매 폴링마다 실제로 호출하면 (1) 카카오는 유료/쿼터가 있는 API라 그냥 상태 확인용으로 계속
  호출하면 쿼터를 낭비하고, (2) 메일/SMS는 "확인"이 곧 "실제 발송"이라 폴링할 때마다 진짜 메일/문자가
  나가버린다 — 그래서 이 셋은 환경변수(`.env`)에 값이 채워져 있는지만 확인하고, 실제로 그 값이 유효한지/
  그 서비스가 지금 응답하는지는 확인하지 않는다. 화면에도 이 차이를 명확히 표시해서, "CONFIGURED"가
  "지금 정상 동작 중"이라는 뜻이 아님을 오해하지 않도록 했다.

각 방식 모두 컨트롤러/서비스 계층에서 예외를 던지지 않는다 — DB가 죽어있어도 `/api/admin/status` 자체는
`200`으로 응답하고 그 항목만 `DOWN`으로 표시한다(상태 조회 API 자체가 그 대상 서비스 장애로 함께 죽으면
안 되므로, 각 체크를 개별 try/catch로 감쌈).

### 2-9. Python 서버 체크는 "그 포트에 뭔가 응답하는지"만 본다
business-verify/recommendation 둘 다 JDK `HttpClient`로 각자의 `base-url`에 단순 GET을 보내고, HTTP
상태 코드와 무관하게 **응답만 오면 UP**으로 판단한다(그 서버가 루트 경로에 정확히 뭘 두고 있는지는 관심
없음, 연결 자체가 되는지만 확인). **알려진 한계**: 두 서버 모두 기본 포트가 8000으로 같아서(07/08/12
연동 문서에서 이미 여러 번 언급된 제약 — 실제로는 한 번에 하나만 켜서 테스트하는 걸 전제), 만약 그 중
하나만 실제로 떠 있어도 그 포트에 응답이 오는 한 **둘 다 UP으로 표시될 수 있다**(포트를 분리해서 각각
따로 띄우지 않는 한 두 서버를 확실히 구분해서 확인할 수 없음, 8장 참고).

## 3. API 설계
------------------------------------------------------------------------
### 3-1. 회원 목록
```
GET /api/admin/members?role={선택, USER 또는 BUSINESS}
```
최신 가입순 최대 200명. 응답: `{ memberId, email, nickname, status, role, createdAt }[]`. `role` 파라미터
생략 시 전체(2-10장, 2026-07-23 3차 추가).

### 3-2. 회원 정지
```
PATCH /api/admin/members/{memberId}/suspend
```
`status`가 `ACTIVE`일 때만 성공(2-6장).

### 3-3. 회원 정지 해제
```
PATCH /api/admin/members/{memberId}/unsuspend
```
`status`가 `SUSPENDED`일 때만 성공(2-6장).

### 3-4. 리뷰 목록
```
GET /api/admin/reviews
```
최신순 최대 200건. 응답: `{ reviewId, memberId, nickname, restaurantId, restaurantName, rating, content, createdAt }[]`
(`restaurantName`은 리뷰 작성 시점 스냅샷, 11.마이페이지에서 추가된 필드 재사용)

### 3-5. 리뷰 강제 삭제
```
DELETE /api/admin/reviews/{reviewId}
```
작성자 본인이 아니어도 삭제 가능(10.리뷰의 `DELETE /api/reviews/{id}`는 본인만 가능한 것과 대비). 소프트
삭제 + 그 음식점의 평점 캐시 재계산까지 10.리뷰와 동일하게 처리.

## 4. 에러 코드
------------------------------------------------------------------------
| 코드 | 상황 | HTTP |
|---|---|---|
| NOT_LOGGED_IN | `/api/admin/**`에 Authorization 헤더 없음/무효 | 401 |
| ADMIN_ACCESS_DENIED(신규) | 로그인은 했으나 ADMIN이 아님 | 403 |
| MEMBER_NOT_FOUND(기존 재사용) | 존재하지 않는 memberId로 정지/해제 시도 | 400 |
| MEMBER_STATUS_INVALID(신규) | 이미 정지된 회원을 다시 정지, 정지 안 된 회원을 해제 등 잘못된 상태 전이 | 409 |
| REVIEW_NOT_FOUND(기존 재사용) | 존재하지 않는 리뷰 삭제 시도 | 404 |

`GET /api/admin/status`는 대상 서비스가 죽어있어도 이 API 자체는 에러를 던지지 않는다(2-8장) — 응답
본문의 각 항목 `status` 필드로 확인한다.

## 8. 확인이 필요한 사항 / 남은 작업
------------------------------------------------------------------------
- **정지 시점에 이미 발급된 accessToken이 즉시 무효화되지 않음**(2-5장) — memberId 기준으로 모든 활성
  jti를 한 번에 revoke하는 기능이 없어서 생기는 구조적 한계. 필요해지면 `access:{jti}` 대신
  `access:member:{memberId}` 형태의 별도 인덱스를 Redis에 추가로 유지해야 함(현재는 안 함)
- **관리자 활동 로그 없음**: 누가 언제 무엇을 정지/삭제했는지 기록이 안 남음 — 필요해지면 별도 감사 로그
  테이블/기능 검토
- **탈퇴(WITHDRAWN) 회원을 관리자가 되살리는 기능 없음**: 정지/해제만 지원(2-6장)
- **역할(role) 클레임의 신선도**: JWT에 로그인 시점의 role이 그대로 박혀있어서, 로그인 이후 관리자 권한을
  새로 부여/회수해도 그 회원이 재로그인하기 전까지는 이전 role로 계속 동작한다(accessToken 만료 시간,
  기본 60분 이내 자연 해소). 즉시 반영이 필요해지면 role 변경 시 그 회원의 세션을 강제 로그아웃시키는
  로직이 추가로 필요함
- **business-verify/recommendation 두 Python 서버를 포트로 구분 못 함**(2-9장): 기본 포트가 같아서 하나만
  떠 있어도 둘 다 UP으로 보일 수 있음 — 포트를 분리해서 기동하면 해결되지만 강제하지 않음
- **상태 조회가 진짜 실시간(push)은 아님**: 5초 폴링이라 그 사이의 짧은 장애는 놓칠 수 있음 — 더 즉각적인
  알림이 필요해지면 WebSocket/Server-Sent Events 등 검토(이번엔 이 프로젝트에 이미 있는 폴링 패턴으로
  충분하다고 판단)

### 2-10. 회원 관리 확장 — role 필터
`GET /api/admin/members`에 `role`(선택) 파라미터를 추가했다 — 값이 있으면
`MemberRepository.findAllByRoleOrderByCreatedAtDesc()`로, 없으면 기존 `findAllByOrderByCreatedAtDesc()`로
분기한다. 새 엔드포인트를 만들지 않고 기존 목록 API에 필터만 얹은 이유는, 응답 형식(`AdminMemberResponseDto`)
이 완전히 같고 "전체/일반/사업자"가 결국 같은 회원 목록의 부분집합이기 때문이다 — 별도 API로 쪼갤 이유가
없었다("필요한 만큼만" 원칙).

### 2-11. 관리자 대시보드 — 왜 새 서비스가 아니라 기존 AdminService에 얹었는지
`AdminDashboardResponseDto`(회원 수 3종 + 리뷰 수 2종)를 만드는 `getDashboard()`를 `AdminServiceImpl`에
추가했다. 이 메서드는 `MemberRepository.countByRole()`(신규), `ReviewRepository
.countByStatusAndDeletedAtIsNull()`(신규, 10.리뷰 쪽에 추가), 그리고 16(리뷰-신고)의
`AdminReportService.countPendingReportedReviews()`를 조합만 할 뿐 자체 로직이 없다 — 그래서 별도
"대시보드 서비스"를 새로 만들지 않고 `AdminServiceImpl`이 `AdminReportService`를 주입받아 그대로
호출하는 조합(composition) 방식을 택했다. 음식점 통계가 이 대시보드에 없는 이유는 001-01 10장 참고
("DB에 저장이 금지되기 때문에 구현 불가", 사용자가 직접 확인).

### 2-12. 신고 관리 엔드포인트는 이 문서가 아니라 16이 정본
`GET /api/admin/reports`/`PATCH /api/admin/reports/{reviewId}/resolve`가 `AdminController`(14 소관 파일)에
있지만, 실제 도메인 로직(`ReviewReport` 엔티티, 신고 사유 검증, 집계 쿼리 등)은 전부
`com.foodtrip.foodsearch.report` 패키지(16.리뷰-신고)에 있다 — 10(리뷰)의 리뷰 강제 삭제가
`AdminController`에서 `review` 패키지의 로직을 호출하는 것과 완전히 같은 패턴. 이 문서(14)에서는
"어떤 엔드포인트가 있는지"만 다루고, "왜 그렇게 설계했는지"는 16 문서를 따라갈 것.
