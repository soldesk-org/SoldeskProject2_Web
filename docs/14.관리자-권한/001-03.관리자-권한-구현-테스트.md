### 1-3. Spring Boot 4 / Spring Security 7의 패키지 변경 대응
컴파일 과정에서 두 가지가 예상과 달랐다(이 프로젝트가 최신 Spring Boot 4.0.7 기준이라 인터넷의 예전 자료와
패키지 경로가 다름, 13.HTTPS-전송암호화 때와 같은 종류의 문제):
1. `UsernamePasswordAuthenticationFilter`가 `org.springframework.security.authentication`이 아니라
   `org.springframework.security.web.authentication` 패키지에 있음
2. Jackson이 `com.fasterxml.jackson`이 아니라 `tools.jackson`(Jackson 3, Spring Boot 4가 채택)로 옮겨감
   — `SecurityConfig`에서 커스텀 401/403 JSON 응답을 만들 때 `ObjectMapper` import 경로를
   `tools.jackson.databind.ObjectMapper`로 맞춤

### 1-4. 2차 변경: 음식점 삭제 제거 + 시스템 상태 모니터링 추가 (같은 날 후속)
- **제거**: `AdminController.deleteRestaurant()`, `AdminService(Impl).deleteRestaurant()`,
  `Restaurant.delete()`, `admin-test.html`의 "음식점 삭제" 카드(검색+삭제 UI, 관련 JS 함수) 전부 삭제.
  `grep`으로 `deleteRestaurant`/`restaurantSearch` 잔여 참조가 없음을 확인.
- **추가**: `SystemStatusItemDto`/`SystemStatusService`/`SystemStatusServiceImpl` 신규,
  `AdminController`에 `GET /api/admin/status` 추가. DB는 `DataSource.getConnection().isValid()`,
  Redis는 `StringRedisTemplate` 커넥션의 `ping()`, business-verify/recommendation은 JDK `HttpClient`로
  각 `base-url`에 2초 타임아웃 GET(001-02 2-9장 — 상태 코드 무관, 응답만 오면 UP). 카카오/메일/SMS는
  `@Value`로 주입한 설정값의 공백 여부만 확인(001-02 2-8장).
- `admin-test.html`에 상태 보드 신규(`.status-grid`), `setInterval`로 5초마다 `GET /api/admin/status`
  폴링, "일시정지/재개" 토글 버튼 포함.

> 실제로 정상 동작했다는 사실 자체는 기록으로 남겨둔다. 2-8장이 2차 검증(제거 확인 + 상태 모니터링).

### 2-1. 관리자 테스트 계정 생성
DB에 직접 `role='ADMIN'`으로 `admin@test.com` 계정 생성(001-02 6장/001-04 참고), Argon2 해시로 비밀번호
저장 — 실제 로그인 API로 로그인까지 성공 확인.

### 2-2. 접근 제어 3단계 확인
- Authorization 헤더 없이 `GET /api/admin/members` → `401 NOT_LOGGED_IN`
- 일반 회원(`test@naver.com`, role=USER)으로 같은 API 호출 → `403 ADMIN_ACCESS_DENIED`
- **같은 일반 회원 토큰으로 `GET /api/members/me`(기존 API) 호출 → 여전히 `200` 정상** — Spring Security
  도입이 `/api/admin/**` 외의 기존 API에 회귀를 일으키지 않았음을 직접 확인(001-02 2-1장 설계의 핵심 검증
  포인트)
- ADMIN 계정으로 `GET /api/admin/members` → `200`, 회원 목록 정상 반환

### 2-3. 회원 정지/해제 전체 흐름
- ADMIN이 `test@naver.com`(memberId 2018) 정지 → `200`
- 정지된 계정으로 로그인 시도 → `401 ACCOUNT_SUSPENDED`(기존 로그인 로직이 그대로 작동, 001-02 2-5장
  설계대로 새로 만들 필요 없었음)
- 이미 정지된 회원을 다시 정지 시도 → `409 MEMBER_STATUS_INVALID`(상태 가드 확인)
- 정지 해제 → `200`
- 해제 후 재로그인 → 정상 성공

### 2-4. 리뷰 강제 삭제
- ADMIN(memberId 2031)이 다른 회원(memberId 2018) 소유 리뷰를 삭제 → `200`(본인 소유가 아니어도
  관리자는 삭제 가능함을 확인 — 10.리뷰의 일반 삭제 API였다면 `403 REVIEW_ACCESS_DENIED`가 났을 상황)
- 삭제 직후 그 음식점의 공개 리뷰 목록(`GET /api/restaurants/{id}/reviews`)을 재조회 → 삭제된 리뷰가
  더 이상 보이지 않음을 확인(소프트 삭제가 정상 반영됨)
- 일반 회원 토큰으로 리뷰 삭제 시도 → `403 ADMIN_ACCESS_DENIED`(SecurityConfig 단계에서 차단 — 컨트롤러/
  서비스 코드까지 도달하지 않고 필터에서 막힘)

### 2-5. 음식점 삭제 (1차 구현 당시 기록 — 이후 기능 자체가 제거됨, 위 안내 참고)

### 2-8. 2차 검증: 제거/추가 사항 (2026-07-23, 같은 날 재기동 후)
- 서버 재컴파일 → 정상 컴파일 확인(음식점 삭제 관련 코드 제거로 인한 참조 깨짐 없음)
- `DELETE /api/admin/restaurants/16421356` 호출 → **`404`(라우트 자체가 없어져서 Spring이 매핑을 못

- ADMIN 계정으로 `GET /api/admin/status` 호출 → `200`, 7개 항목(DB/Redis/business-verify/recommendation/

  - DB `UP`, 5ms / Redis `UP`, 5ms — 둘 다 실제 연결 확인 정상(HikariCP/Lettuce 커넥션 풀이 이미 연결을

    구분되지 않고 둘 다 UP으로 나옴(같은 포트를 보고 있으므로 당연한 결과 — 결함 아님)
  - 카카오/메일/SMS 셋 다 `CONFIGURED`(`.env`에 값이 있음을 정상 반영, 실제 연결 확인은 설계대로 안 함)
- `admin-test.html`을 브라우저로 열어 상태 보드가 5초마다 자동 갱신되는 것, "일시정지" 버튼을 누르면
  갱신이 멈추고 "재개"로 다시 시작하는 것 확인

### 2-9. 3차 구현/검증: 회원 관리 확장 + 대시보드 + 신고 관리 연동 (2026-07-23, 같은 날)

### 2-10. 4차 구현/검증: 신고 처리 완료/반려 구분 + 상태별 조회 (2026-07-23, 같은 날)
