## 배경 — 지금까지 이 프로젝트에 Spring Security가 없었던 이유와, 지금 도입하는 이유
------------------------------------------------------------------------
CLAUDE.md 2장 "필요할 때만 인프라를 만든다" 원칙에 따라, 이 프로젝트는 지금까지 Spring Security 필터체인을
전혀 쓰지 않고 있었다. 대신 각 도메인 서비스가 `resolveMemberId(authorizationHeader)`라는 작은 private
헬퍼를 각자 복제해서 Authorization 헤더의 JWT를 직접 파싱하는 방식으로 "로그인 여부"만 확인해왔다(로그아웃
기능을 만들 때 "그때 가서 두 번째 보호된 엔드포인트가 필요해지면 만들자"고 합의했던 것, 06/05/07/10/11 등
전부 이 패턴을 그대로 복제해서 씀).

이 방식은 "로그인했는지 여부"만 구분하면 충분했던 지금까지는 문제가 없었다 — 하지만 이번 요청은
**"로그인한 사람 중에서도 관리자만" 구분**해야 한다. 이건 단순 인증(Authentication)이 아니라 인가
(Authorization) 문제이고, 이걸 기존 패턴(각 서비스에 `if (!"ADMIN".equals(role)) throw ...` 코드를 또
복제)으로 풀면 앞으로 관리자 전용 엔드포인트가 늘어날 때마다 실수로 그 검사를 빠뜨릴 위험이 계속 쌓인다.
그래서 "필요할 때만 인프라를 만든다" 원칙의 다음 단계로, 이번에 실제로 Spring Security를 도입했다 — CLAUDE.md
2장에서 이미 "다음에 정말 필요해지면 이야기하겠다"고 명시해뒀던 바로 그 시점이 이번이라고 판단함.

## 이번 범위에서 제외된 것
------------------------------------------------------------------------
- 관리자 계정을 스스로 만드는 API(회원가입 화면에서 "관리자로 가입" 같은 것) — 보안상 자기 자신을 관리자로
  격상시킬 수 있는 API를 만들면 안 되므로, 관리자 계정은 DB에 직접 심는 방식으로만 만든다(001-04 참고)
- 관리자 활동 로그(누가 언제 무엇을 정지/삭제했는지 기록) — 이번엔 즉시 처리만 하고 감사(audit) 로그는
  남기지 않음
- 사업자(BUSINESS) 권한과의 세분화된 관계 정리 — 이번엔 ADMIN 여부만 구분(BUSINESS는 기존 그대로)
- 기존 API 전체를 Spring Security로 옮기는 마이그레이션 — 001-02 2-1장 참고, 의도적으로 안 함

상세 설계는 [001-02.관리자-권한-분석-설계.md](001-02.관리자-권한-분석-설계.md) 참고.

## 9. 후속 변경 (2026-07-23, 같은 날)
------------------------------------------------------------------------
1차 구현 직후 두 가지 후속 지시가 있었다:
- **음식점 삭제 기능 제거**: 1차 구현에 있던 `DELETE /api/admin/restaurants/{id}`(음식점 부가정보 소프트
  삭제)를 "필요없다"는 지시로 컨트롤러/서비스/엔티티 메서드/테스트 페이지 UI까지 전부 제거함. `Restaurant`
  엔티티에 추가했던 `delete()` 메서드도 함께 되돌림(사용하는 곳이 없어짐).
- **시스템 상태 실시간 모니터링 추가**: "현재 API 상태들 실시간으로 나와서 모니터링" 요청으로
  `GET /api/admin/status` 신규 — DB/Redis/Python 서버(사업자·영수증 OCR, AI 추천)는 실제 연결을 시도해
  UP/DOWN을 확인하고, 카카오/메일/SMS는 매 폴링(5초)마다 실제로 호출하면 API 쿼터 소모/실제 발송이
  일어나므로 설정값 존재 여부만 확인(CONFIGURED/NOT_CONFIGURED). `admin-test.html`이 5초 간격으로
  폴링해서 화면을 자동 갱신(진짜 서버 push는 아니고, 이 프로젝트의 기존 패턴과 같은 폴링 방식).

## 10. 3차 후속: 회원 관리 확장 + 대시보드 + 신고 관리 연동 (2026-07-23, 같은 날)
------------------------------------------------------------------------
사용자가 원래 그리던 관리자 페이지 전체 그림("회원 관리 - 전체 회원 수/일반 회원 관리/사업자 회원 관리,
음식점 관리, 신고 관리 - 신고된 리뷰 관리, 리뷰 관리 - 작성된 리뷰 수/신고된 리뷰 수")을 구체적으로 받고
그대로 반영:

- **회원 관리**: `GET /api/admin/members`에 `role` 필터(`USER`/`BUSINESS`) 추가 — "일반 회원 관리"/"사업자
  회원 관리" 화면을 이걸로 분리 가능
- **음식점 관리**: **"DB에 저장이 금지되기 때문에 구현 불가"** — 사용자가 직접 확인한 내용을 그대로 반영,
  코드 변경 없음(9장의 음식점 삭제 기능 제거 결정과 같은 맥락 — 이미 한 번 같은 결론에 도달했던 부분을
  사용자도 독립적으로 재확인한 셈)
- **신고 관리**: 그 전제 기능인 "리뷰 신고" 자체가 없어서, 완전히 새로운 도메인
  [`docs/16.리뷰-신고`](../16.리뷰-신고/001-01.리뷰-신고-요청사항.md)로 분리 개발. 이 문서(14)는
  `GET /api/admin/reports`/`PATCH /api/admin/reports/{reviewId}/resolve` 엔드포인트만 (16이 만든
  서비스를 그대로 호출해서) 제공할 뿐, 신고 도메인 자체의 설계/구현/테스트/가이드는 16 문서가 정본이다
- **리뷰 관리 통계 + 대시보드**: `GET /api/admin/dashboard` 신규 — 전체/일반/사업자/관리자 회원 수, 작성된
  리뷰 수, 신고된 리뷰 수를 한 번에 반환. 음식점 통계가 없는 이유는 위 "음식점 관리" 항목과 동일

상세는 001-02 2-10~2-11장(신설), 001-03 3장(신설) 참고.
