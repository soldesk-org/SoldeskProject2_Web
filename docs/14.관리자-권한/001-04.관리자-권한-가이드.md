## 1. 서버 접속 정보
------------------------------------------------------------------------
- 로컬 개발 서버: `http://localhost:8081` (HTTPS를 켰다면 `https://localhost:8443`도 동일하게 동작,
  `docs/13.HTTPS-전송암호화` 참고)
- 이 문서의 API는 전부 **로그인 + ADMIN 권한 필수**. `Authorization: Bearer {accessToken}` 헤더 필수.
- 로그인은 안 했거나 무효 토큰이면 `401 NOT_LOGGED_IN`, 로그인은 했지만 ADMIN이 아니면 `403
  ADMIN_ACCESS_DENIED` — 둘 다 이 프로젝트의 다른 API와 같은 형식(`{success:false, code, message}`).

## 2. 관리자 계정 만들기 (DB 직접 조작 — API로는 불가능)
------------------------------------------------------------------------
자기 자신을 관리자로 만드는 API는 의도적으로 없다(001-02 6장). 두 가지 방법:

**(A) 이미 있는 회원을 관리자로 승격**
```sql
UPDATE members SET role = 'ADMIN' WHERE email = '{승격할 이메일}';
```
그 회원은 **재로그인해야** 새 role이 반영된 accessToken을 받는다(001-02 8장 — JWT에 role이 로그인
시점에 박히기 때문에, 이미 로그인된 상태라면 재로그인 전까지 예전 권한으로 동작함).

**(B) 테스트 전용 관리자 계정을 새로 생성** (이번 검증에 실제로 쓴 방법)
```js
// Node.js + mysql2, 프로젝트 .env의 DB 접속 정보 재사용
const mysql = require('mysql2/promise');
// Argon2 해시는 Project2 클래스패스로 아래 작은 유틸을 컴파일해서 생성(05 등 이전 세션에서도 쓴 방법)
// Argon2PasswordEncoder(16, 32, 1, 65536, 3).encode("원하는비밀번호")
const conn = await mysql.createConnection({ host, user, password, database });
const [r] = await conn.query(
  "INSERT INTO members (email, nickname, status, role, created_at, updated_at) VALUES (?, ?, 'ACTIVE', 'ADMIN', NOW(), NOW())",
  [email, nickname]);
await conn.query(
  "INSERT INTO member_credentials (member_id, password_hash, created_at, updated_at) VALUES (?, ?, NOW(), NOW())",
  [r.insertId, argon2Hash]);
```

## 3. 기능별 호출 흐름
------------------------------------------------------------------------
### 3-1. 관리자 페이지 진입
1. 로그인(`POST /api/members/login`)
2. `GET /api/admin/members` 호출 — `200`이 오면 ADMIN 확인된 것, `403`이 오면 이 계정은 ADMIN이 아니라는
   뜻이므로 화면 자체를 접근 거부 처리할 것(참고 구현: `admin-test.html`의 `checkAdminAccess()`가 이
   API 호출 하나로 401/403/200 세 가지 상태를 전부 화면 분기에 씀)
3. ADMIN 확인되면 `GET /api/admin/dashboard`로 홈 화면 통계(3-1-1장)를 함께 불러올 것을 권장

### 3-1-1. 대시보드 (2026-07-23 3차 추가)
1. `GET /api/admin/dashboard` — 회원 3종(전체/일반/사업자, `memberAdmin`도 있지만 화면에 꼭 안 보여줘도
   됨) + 리뷰 2종(작성됨/신고됨) 통계를 한 번에 받는다
2. `reviewReported > 0`이면 눈에 띄게 강조 표시(예: 빨간 배지)해서 관리자가 신고 관리 카드로 유도할 것을
   권장(참고 구현: 0보다 크면 카드에 경고색 테두리)
3. 회원 정지/해제, 리뷰 삭제, 신고 처리 등 이 문서의 다른 액션을 수행한 뒤에는 대시보드도 함께 재조회해서
   숫자를 최신 상태로 유지할 것

### 3-2. 회원 정지/해제/필터
1. `GET /api/admin/members`로 목록 표시, `status` 값에 따라 정지/해제 버튼을 다르게 보여줄 것
   (`ACTIVE`면 정지 버튼만, `SUSPENDED`면 해제 버튼만 — 둘 다 표시하지 말 것, 5장 에러 참고)
2. **(2026-07-23 3차 추가)** "일반 회원 관리"/"사업자 회원 관리"를 탭이나 버튼으로 분리하고 싶으면
   `GET /api/admin/members?role=USER` / `?role=BUSINESS`를 각각 호출할 것 — 응답 형식은 필터 없을 때와
   완전히 동일
3. 정지: `PATCH /api/admin/members/{id}/suspend`
4. 해제: `PATCH /api/admin/members/{id}/unsuspend`
5. 성공하면 목록 재조회해서 상태 배지 갱신(그리고 3-1-1장의 대시보드도 재조회하면 좋음 — 단, 정지/해제는
   대시보드 숫자에 영향 없음, 회원 수는 안 바뀌므로)

### 3-3. 리뷰 강제 삭제
1. `GET /api/admin/reviews`로 목록 표시(작성자 닉네임/음식점명/별점/내용/선택한 태그 목록 포함,
   `keywords` 필드는 2026-07-23 추가)
2. `DELETE /api/admin/reviews/{id}` — 확인창 권장(되돌릴 수 없음)

### 3-5. 시스템 상태 모니터링 (2026-07-23 추가)
1. `GET /api/admin/status`를 주기적으로(참고 구현은 5초 간격) 폴링해서 상태 보드를 갱신할 것 — 진짜
   서버 push는 아니고 폴링 방식이다(001-02 2-8/2-9장)
2. 응답 배열의 각 항목을 `status` 값에 따라 다르게 표시:
   - `UP`/`CONFIGURED` → 정상(녹색 등)
   - `DOWN`/`NOT_CONFIGURED` → 문제(빨간색 등)
3. **`CONFIGURED`는 "설정값이 있다"는 뜻이지 "지금 정상 동작 중"이라는 뜻이 아니다** — 카카오/메일/SMS는
   실제 연결을 확인하지 않는다(001-02 2-8장 이유). 화면에도 이 차이를 명확히 안내할 것(참고 구현은
   카드 상단에 안내 문구를 고정 표시함).
4. 화면을 떠나 있을 때도 계속 폴링하면 불필요한 서버 부하가 되므로, 탭이 백그라운드거나 사용자가 잠깐
   안 볼 때 멈출 수 있는 토글을 두는 것을 권장(참고 구현: "일시정지"/"재개" 버튼).

### 3-6. 신고 관리 (2026-07-23 3차 추가)
`GET /api/admin/reports`/`PATCH /api/admin/reports/{reviewId}/resolve`의 상세 사용법은 이 문서가 아니라
[`docs/16.리뷰-신고/001-04`](../16.리뷰-신고/001-04.리뷰-신고-가이드.md)를 따를 것 — 인증 방식만 이
문서(14)와 동일(ADMIN 권한 필수)하고, 나머지 흐름/에러코드는 16이 정본이다.

## 4. API 상세
------------------------------------------------------------------------
### 4-1. 회원 목록
```
GET http://localhost:8081/api/admin/members?role=USER
Authorization: Bearer {accessToken}
```
`role`(선택, `USER`/`BUSINESS`) 생략 시 전체. 응답(200):
```json
[
  { "memberId": 2018, "email": "test@naver.com", "nickname": "test_user",
    "status": "ACTIVE", "role": "USER", "createdAt": "2026-07-22T07:10:26" }
]
```

### 4-2. 회원 정지
```
PATCH http://localhost:8081/api/admin/members/2018/suspend
Authorization: Bearer {accessToken}
```
성공(200): `{ "success": true, "message": "회원을 정지했습니다." }`
실패(409, 이미 정지/탈퇴 상태): `{ "success": false, "code": "MEMBER_STATUS_INVALID", "message": "..." }`
실패(400, 존재하지 않는 회원): `{ "success": false, "code": "MEMBER_NOT_FOUND", "message": "..." }`

### 4-3. 회원 정지 해제
```
PATCH http://localhost:8081/api/admin/members/2018/unsuspend
Authorization: Bearer {accessToken}
```
성공(200): `{ "success": true, "message": "회원 정지를 해제했습니다." }`
실패(409, SUSPENDED가 아닌 상태): `MEMBER_STATUS_INVALID`

### 4-4. 리뷰 목록
```
GET http://localhost:8081/api/admin/reviews
Authorization: Bearer {accessToken}
```
응답(200):
```json
[
  { "reviewId": 10, "memberId": 2018, "nickname": "test_user", "restaurantId": "16421356",
    "restaurantName": "농민백암순대 강남직영점", "rating": 5, "content": "...",
    "keywords": ["맛있어요", "친절해요"],
    "createdAt": "2026-07-22T14:00:00" }
]
```
`keywords`는 2026-07-23 추가 — 회원이 리뷰 작성 시 선택한 태그(10.리뷰 001-02 2-4장 고정 목록 중)를
관리자도 볼 수 있게 함. 태그가 하나도 없는 리뷰(텍스트만 쓴 경우)는 빈 배열.

### 4-5. 리뷰 강제 삭제
```
DELETE http://localhost:8081/api/admin/reviews/10
Authorization: Bearer {accessToken}
```
성공(200): `{ "success": true, "message": "리뷰를 삭제했습니다." }`
실패(404): `REVIEW_NOT_FOUND`

## 5. 에러 코드
------------------------------------------------------------------------
| code | 상황 | HTTP |
|---|---|---|
| NOT_LOGGED_IN | Authorization 헤더 없음/무효 | 401 |
| ADMIN_ACCESS_DENIED | 로그인은 했으나 ADMIN이 아님 | 403 |
| MEMBER_NOT_FOUND | 존재하지 않는 memberId | 400 |
| MEMBER_STATUS_INVALID | 잘못된 상태 전이(이미 정지된 회원 재정지 등) | 409 |
| REVIEW_NOT_FOUND | 존재하지 않는 리뷰 | 404 |
