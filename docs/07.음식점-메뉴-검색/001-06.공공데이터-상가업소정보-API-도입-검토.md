# 공공데이터포털 "소상공인시장진흥공단_상가(상권)정보_API" 도입 검토
------------------------------------------------------------------------
001-05에서 확인한 대로, 네이버가 공식적으로 공개한 API만으로는 "지금 보고 있는 지도 범위 안에서 검색"이
원천적으로 불가능하다(위치를 좁히는 파라미터 자체가 없음). 그 대안으로 사용자가 제시한 공공데이터포털의
상가업소(상권)정보 API를 조사한 결과를 정리한다.

> **⚠️ 2026-07-22 대체 공지**: 이 문서에서 도입을 결정했던 공공데이터(상가업소정보) API는 이후 실사용 중
> **오래되거나 카테고리가 부정확한 데이터** 문제가 드러나 완전히 폐기되고, 카카오 로컬 API로 교체됨(그 과정에서
> DB 캐싱 자체도 ToS 문제로 없앰). 최종 결정은
> [001-07.카카오-로컬-API-전환-및-리뷰-기능-구현.md](001-07.카카오-로컬-API-전환-및-리뷰-기능-구현.md) 참고.
> 이 문서는 도입 검토 당시의 판단 근거 기록으로만 남겨둠.

## 1. 결론
------------------------------------------------------------------------
**도입 가능하고, 001-05에서 막혔던 "지도 범위 기준 검색"을 정확히 해결해준다.** 다만 이 데이터에는 메뉴/평점/
리뷰/사진 정보가 없어서, "메뉴명으로도 검색되는" 지금 기능(`RestaurantRepository.searchByKeyword` — 상호명
OR 메뉴명)을 그대로 유지하려면 별도 보완이 필요하다(4장).

------------------------------------------------------------------------
## 2. API 개요
------------------------------------------------------------------------
- 이름: 소상공인시장진흥공단_상가(상권)정보_API
- 제공 데이터: 상가업소번호, 상호명, 주소(지번/도로명), 상권업종명(대/중/소분류), 표준산업분류명, 경도, 위도 등
- 데이터 출처: 국세청/카드사 기반, 분기별 갱신
- 인증: REST, JSON/XML, 서비스키 발급 필요(data.go.kr 활용신청, 자동승인)
- 요금: 무료(개발계정 트래픽 10,000건/일, 운영계정은 활용사례 등록 시 증량 가능)

------------------------------------------------------------------------
## 3. 위치 기반 조회 — 001-05의 문제를 정확히 해결함
------------------------------------------------------------------------
공식 API가 제공하는 조회 방식 중 이 프로젝트에 필요한 2가지:

| 조회 방식 | 파라미터 | 용도 |
|---|---|---|
| 반경조회 | `cx`, `cy`(중심 좌표), `radius`(미터) | 특정 좌표 기준 반경 안의 상가 전부 조회 |
| 사각형(영역)조회 | `minx`, `miny`, `maxx`, `maxy` | 사각형 범위 안의 상가 전부 조회 |

**핵심**: 사각형조회의 4개 파라미터가 지도 화면이 지금 보여주고 있는 뷰포트(왼쪽아래~오른쪽위 좌표)와 정확히
대응된다. 즉 지도를 옮길 때마다 바뀐 화면 좌표를 그대로 넣어 재호출하면 "이 지역에서 검색" 버튼이 요구하는
동작이 그대로 나온다 — 네이버 지역 검색 API에는 애초에 없던 파라미터(001-05 2-1장)가 여기엔 있다.

이 조회는 **키워드 없이 그 범위의 상가를 전부** 돌려준다(네이버처럼 검색어 관련도 기준 최대 5건이 아니라, 그
지역에 실제로 존재하는 상가 전체). 그래서 "사용자가 안 가본 동네라 DB에 데이터가 없다"는 문제(001-03 4-3장에서
남겨둔 이슈)가 근본적으로 해결된다 — 지역명 조합으로 여러 번 키워드 검색을 돌릴 필요 없이, 좌표 범위 하나로
그 지역 상가 전체를 한 번에 가져와 DB에 채울 수 있다.

------------------------------------------------------------------------
## 4. 한계 — 메뉴/평점/리뷰/사진 정보 없음, 보완 전략
------------------------------------------------------------------------
이 API는 상호명/주소/업종/좌표만 제공한다. 업종 분류도 상권업종분류 소분류(247개, 예: "카페", "제과점",
"분식") 수준까지만 있고, "빙수" 같은 메뉴 단위 정보는 없다(이걸 보완해주는 별도 공식 데이터도 확인되지 않음).
그래서 "빙수"로 검색했을 때 **상호명에 "빙수"가 들어간 곳만** 잡히고, 상호명은 "OO카페"인데 실제로 빙수를
파는 집은 이 데이터만으로는 못 찾는다.

**3단계 보완안**:
1. **1차(대량 채우기)**: 사각형조회로 그 지역 상가 전체를 DB에 upsert(상호명/주소/좌표/업종만). 001-03의
   네이버 동기화(`RestaurantSyncServiceImpl`)와 같은 upsert 패턴을 재사용.
2. **2차(자동 보강, 별도 작업 불필요)**: `RestaurantRepository.searchByKeyword()`가 이미 상호명 OR
   `menus.menu_name`으로 검색한다(001-02 5-3장). 사업자가 001-03 4장에서 만든 메뉴 등록 API로 메뉴를
   직접 등록할수록, 상호명에 없는 메뉴 키워드 검색도 자연히 커버된다 — 이미 있는 기능을 그대로 활용.
3. **3차(즉시 보강, 선택적)**: DB 검색 결과가 부족하면 그 자리에서 네이버 지역 검색 API를 키워드로 한 번 더
   호출 — 네이버는 자체 내부 태그/카테고리로 "이름에 없어도" 매칭해주므로, 반환된 상호명을 주소/좌표 기준으로
   우리 DB 레코드와 매칭시켜(001-03 4-1장의 "정규화 후 부분 문자열 포함" 패턴 재사용) 결과에 끼워넣을 수 있다.

### 4-1. 3차 보강("이름에 없어도 매칭")의 근거
"네이버 지역 검색이 상호명 문자열 일치만 본다"고 단정할 수 없는 근거 두 가지를 확인함.

- **API 자체가 상호명 외에 `category`/`description` 필드를 함께 응답으로 준다** — 검색 결과 매칭이 상호명
  하나만 보고 이뤄지는 게 아니라 업체 분류(`category`, 예: "음식점>카페,디저트")와 설명(`description`)까지
  포함한 인덱스를 기준으로 한다는 뜻(네이버 개발자 문서 기준, 9장 참고).
- **이 프로젝트에서 실제로 검증한 사례가 있음**: 앞서 시도했다가 지금은 코드/문서에서 제외한 AI 자연어 검색
  기능 테스트 당시, `"강남 파스타"`로 지역 검색을 호출했을 때 상호명에 "파스타"가 전혀 들어가지 않는
  "나폴리회관 강남역점", "이비티 스타필드 코엑스점", "로마옥 도곡" 같은 곳들도 실제로 결과에 포함되어
  돌아온 것을 직접 확인했음 — 상호명 리터럴 매칭만으로는 설명이 안 되는 결과로, 네이버가 카테고리/업체
  등록 정보(사업자가 네이버플레이스에 직접 등록하는 대표메뉴·키워드 태그 등)를 검색에 반영하고 있다는
  간접 증거로 볼 수 있음.

다만 이 매칭 기준(정확히 뭘 근거로 관련도를 매기는지)이 네이버 쪽에 공개된 사양은 아니라서, "완전히 신뢰할
수 있는 메뉴 검색"으로 보긴 어렵고 어디까지나 "상호명 매칭보다 넓게 잡아주는 보조 수단" 정도로 취급하는 게
안전함.

## 7. 구현 완료 (2026-07-21)
------------------------------------------------------------------------
### 7-1. 구현 범위 — 4장 3단계 보완안 중 1차/2차
- **1차(대량 채우기)**: `SmbizStoreClient`(신규, `restaurant/client`)가 사각형조회(`storeListInRectangle`)를
  호출해 그 범위의 상가 목록을 받아오고, 응답에서 대분류명(`indsLclsNm`)에 "음식"이 포함된 것만 걸러낸다.
  `RestaurantAreaSyncService`/`Impl`(신규)이 `bizesId`(상가업소번호, 원본 자연키라 네이버 동기화처럼 해시를
  만들 필요 없이 그대로 `external_place_id`로 사용)를 기준으로 upsert한다. `POST /api/restaurants/sync-area
  ?minX=&minY=&maxX=&maxY=`로 트리거(001-02 4-3장 `/sync`와 같은 성격 — 아직 관리자 인증 없음).
- **2차(자동 보강)**: 별도 구현 불필요 — 기존 `RestaurantRepository.searchByKeyword()`가 이미 상호명 OR
  `menus.menu_name`을 본다. 사업자가 메뉴를 등록할수록 자연히 커버됨(001-03 4장에서 이미 완료한 기능).
- **3차(네이버 실시간 보강)**: **(2026-07-21 구현 완료, 7-5장)** `RestaurantServiceImpl.search()`가 우리
  DB 검색이 0건일 때 그 키워드로 네이버 지역 검색 API를 실시간 호출해 upsert하고, 그 upsert된 결과 자체를
  그대로 응답으로 씀(우리 LIKE 쿼리로 다시 거르지 않음 — 이유는 7-5장).

### 7-2. 지도 뷰포트 검색("이 지역에서 검색") 반영
`GET /api/restaurants/search`에 `minLat`/`maxLat`/`minLng`/`maxLng` 4개를 선택 파라미터로 추가했다
(`RestaurantRepository.searchByKeywordInBoundingBox`, 넷 다 없으면 기존과 동일하게 전체 범위 대상).
프론트는 지도를 옮길 때마다 바뀐 뷰포트 좌표를 그대로 이 4개 파라미터에 넣어 재호출하면 된다 — 새 엔드포인트를
만들지 않고 기존 검색 API를 확장하는 쪽을 택함(엔드포인트 난립 방지).

### 7-3. 카테고리 매칭 로직 공유화(리팩터링)
네이버 동기화(`RestaurantSyncServiceImpl`)에 있던 "정규화 후 부분 문자열 포함" 카테고리 매칭 로직을
`RestaurantCategoryMatchingService`(신규)로 뽑아내 공공데이터 동기화(`RestaurantAreaSyncServiceImpl`)와
공유한다 — 두 동기화 소스가 완전히 같은 매칭 규칙을 쓰므로 중복보다 공유가 맞다고 판단(001-02 3장 원칙과
달리 이번엔 "진짜 같은 로직"이라 추출).

### 7-4. 실데이터 검증 완료 (2026-07-21)
서비스키를 발급받아 실제로 검증함.

- **API 직접 호출**: `storeListInRectangle`에 서초/강남 인근 사각형(minx=127.025~maxx=127.030,
  miny=37.495~maxy=37.500)으로 호출 → 실제 상가 데이터 수신 확인. 응답 필드명(`bizesId`/`bizesNm`/
  `indsLclsNm`/`indsMclsNm`/`indsSclsNm`/`lnoAdr`/`rdnmAdr`/`lon`/`lat`)이 `SmbizStoreClient`에 작성한
  것과 **정확히 일치**함(오픈소스 라이브러리 기준 추정이 맞았음). `indsLclsNm`이 실제로 `"음식"`(예: 김밥/만두/
  분식 업종의 대분류)로 오는 것도 확인 — 대분류 필터링 로직 그대로 동작.
- **`/api/restaurants/sync-area` 종단 간 테스트**: 같은 범위로 호출 → `fetchedCount:101, createdCount:101`
  로 실제 DB에 101건 저장됨(`success:true`). 같은 범위로 재호출 시 `createdCount:0, updatedCount:101`로
  upsert가 의도대로 멱등하게 동작함을 확인.
- **`GET /api/restaurants/search`의 bbox 파라미터**: 위 101건이 저장된 범위로 `minLat/maxLat/minLng/maxLng`
  없이 검색하면 전체(기존 동작 유지), 넣으면 그 범위로 좁혀짐, 범위 밖 좌표로는 0건 — 전부 기대대로 동작.
  `keyword`+bbox 조합도 정상(예: "타코" 키워드 + 범위 → 그 범위 안의 "낙원타코" 1건만 반환). bbox 파라미터
  4개 중 일부만 넘기면 400 INVALID_INPUT도 확인.
- **`restaurants.address` NOT NULL 우려**: 이번 101건 전부 `lnoAdr`이 채워져 있어 저장 실패 없었음 — 다만
  전국 모든 지역에서 항상 그런지는 이번 표본만으로 단정 못 함(잠재 이슈로 계속 인지).
- 검증에 쓴 101건은 실제 서비스 데이터가 아니라 테스트 목적이라 검증 직후 DB에서 삭제함(연관 테이블 포함).
- Playwright 자동화 테스트는 추가하지 않음 — 서비스키(과금/트래픽 한도 있는 외부 자격증명)에 의존적이라
  001-03의 네이버 `/sync`와 같은 이유로 수동 검증 대상으로 유지.

### 7-5. 3차(네이버 실시간) 보강 구현 및 실데이터 검증 (2026-07-21, 테스트 페이지로 발견/수정)
임시 지도 테스트 페이지(`tmp-map-test.html`, 아래 8장)로 "빙수" 키워드를 실제로 검색해보다가 두 가지를
발견해서 수정함.

**1차 시도(버그)**: 처음엔 DB 검색 0건일 때 `RestaurantSyncService.syncFromNaver()`로 네이버를 호출해
upsert한 뒤, 그 자리에서 **우리 LIKE 쿼리로 다시 한번** 걸러서 응답했다. 그런데 "빙수" 검색 시 네이버가
실제로 "설빙" 같은 곳을 찾아줘도(4-1장 근거 그대로) 그 상호명 자체엔 "빙수"라는 글자가 없어서, 방금 막
upsert한 데이터를 우리 LIKE 쿼리가 스스로 걸러내 버려 결국 0건으로 남는 문제를 실제로 재현함.

**수정**: `RestaurantSyncService`에 `syncFromNaverAndGetRestaurants()`(신규, 예전 AI 검색 기능에서 쓰다가
지웠던 것과 같은 형태 — upsert 핵심 로직은 `syncFromNaver()`와 공유하되 반환 형태만 다름)를 다시 추가하고,
`RestaurantServiceImpl.search()`가 네이버 upsert 결과 목록 자체를 그대로 응답으로 씀(LIKE 재필터링 없음).
bbox가 있으면 그 범위 안의 것만 자바 쪽에서 좌표 비교로 거른다(`isWithinBoundingBox()`).

**실데이터 검증**:
- `keyword=빙수`(bbox 없음) → **5건 정상 반환**: "먹쿠슬낭카페"(제주), "마시랑게"(전주), "공간갑"(서울 중구),
  "카페이르리"(전주), "티노마드"(서울 마포) — 전부 상호명에 "빙수"가 없는데도 네이버가 관련 있다고 판단해
  준 곳들. 3차 보강이 의도대로 동작함을 실증.
- `keyword=빙수` + 반포~강남역 bbox → **0건**(버그 아님): 위 5건이 전부 그 좁은 범위 밖(제주/전주/중구/마포)에
  있어서 필터링 후 남는 게 없었을 뿐 — 네이버 지역 검색 API 자체가 위치 파라미터 없이 "전국 상위 5건"만
  주는 근본 한계(001-05) 때문에 생기는 당연한 결과. bbox를 좁게 걸수록 이 3차 보강이 실제로 도움될 확률은
  낮아짐(전국 상위 5건 중 하필 그 좁은 범위 안에 있어야 하므로) — 넓은 범위나 bbox 없는 검색에서 더 유용함.

## 8. 임시 지도 테스트 페이지 (2026-07-21, 검증 끝나면 삭제 예정)
------------------------------------------------------------------------
프론트엔드는 별도 팀원이 작업 중이라, 이 기능(지도 뷰포트 검색)만 독립적으로 눈으로 확인할 목적의 임시
정적 페이지를 만들었다 — `Project2/src/main/resources/static/tmp-map-test.html`, 백엔드 서버(8081)와
같은 오리진에서 정적 리소스로 서빙되어 CORS 설정 없이 바로 동작한다.

- 네이버 지도(NCP Maps JS SDK v3, `ncpKeyId=i99edc9due`)로 실제 지도 렌더링, 키워드 검색창, 지도를 옮기면
  뜨는 "이 지역에서 검색" 버튼, "이 지역 동기화(공공데이터)" 버튼(그 자리에서 `/sync-area` 트리거) 포함.
- **버그 1(지도 안 뜸)**: 네이버 지도 SDK가 초기화 시 컨테이너 div의 inline style에 `position: relative`를
  강제로 덮어써서, `position: absolute` + `top/bottom:0`으로 사이징하던 기존 CSS가 무력화되어 지도 영역
  높이가 0이 됨(Playwright로 `getBoundingClientRect()` 실측해서 원인 특정). 별도 래퍼 div(`#mapWrap`)가
  절대 위치/크기를 담당하고, 지도 컨테이너 자신은 `width/height:100%`만 갖도록 구조를 분리해서 해결.
  Static 리소스 변경이 실행 중인 `spring-boot:run` 서버에 즉시 반영되지 않아(클래스패스 캐시), 서버 재기동이
  필요했다는 것도 확인.
- **버그 2**: 위 7-5장의 3차 보강 LIKE 재필터링 버그 — 이 페이지로 직접 "빙수" 검색해보다가 발견함.
