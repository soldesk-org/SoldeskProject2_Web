## 1. 전환 배경: 카카오 로컬 API 이용약관(ToS) 준수 이슈
------------------------------------------------------------------------
### 1-1. 발단
기존 설계(001-02/001-03)는 네이버 지역 검색 API와 공공데이터포털 상가업소정보 API를 **주기적으로 호출해
`restaurants` 테이블에 저장(upsert)해두고, 이후 조회는 전부 우리 DB만 보는 방식**이었다. 그런데 001-06 문서
검토 중, 공공데이터 API가 실제로는 오래되거나 카테고리가 부정확한 데이터를 갖고 있다는 문제가 드러나서
대안으로 **카카오 로컬 API**(좌표/반경 기반 카테고리·키워드 검색을 공식 지원 — 001-05에서 확인된 네이버 API의
"위치 기반 검색 불가" 한계를 카카오는 갖고 있지 않음)로 데이터 소스를 교체하기로 결정했다.

### 1-2. 카카오 개발자 공식 답변 발견 → 설계 전면 재검토
카카오 로컬 API로 교체하는 과정에서, 지도 렌더링은 네이버 지도를 계속 쓰고(마커/타일 표시) 검색 데이터만
카카오에서 가져오는 것이 약관상 문제가 없는지 확인하기 위해 카카오 데브톡(공식 개발자 포럼)을 조사했다.
카카오 스태프의 공식 답변(원문 그대로 인용):

> "타사 지도SDK와 혼용하여 사용하셔도 약관 상 이슈는 없습니다... 실시간 호출 기반의 사용만 가능하며,
> 데이터 저장 등의 목적으로는 호출이 불가한 점 참고해 주세요."

이 한 문장이 결정적이었다:
- **(허용)** 네이버 지도를 렌더링 SDK로 쓰면서 데이터는 카카오 API에서 가져오는 것 → 문제 없음
- **(금지)** 카카오 API가 응답한 장소 정보(상호명/주소/좌표/전화번호 등)를 DB에 저장해두고 재사용하는 것
  → **명시적으로 금지**. 데브톡에는 이 조항 위반으로 실제 개발자 계정이 정지된 사례도 보고되어 있음(조사 중 확인)

기존 설계(001-02 4-3장/5-9장)는 정확히 이 "저장 후 재사용" 방식이었으므로, **001-02/001-03에 이미 구현되어
있던 네이버/공공데이터 동기화(`/sync`, `/sync-area`) 아키텍처 전체가 이용약관 위반 소지가 있다는 결론**에
도달했다. 가벼운 우회(예: 캐시 TTL을 짧게 두는 것)로는 "저장 목적 호출 금지" 조항을 피할 수 없다고 판단해,
**DB 캐싱을 완전히 없애는 아키텍처 재설계**를 진행했다.

### 1-3. 사용자 확정 지시
"그럼 테이블에 저장하지 않고 해야 할거 같아 그렇게 해줘 리뷰나 그런거만 하던가" — 검색/조회 자체를 카카오
실시간 호출로 완전히 전환하고, DB에는 리뷰처럼 우리 서비스 고유 데이터만 남기기로 확정. 뒤이은 확인 질문에
대한 답변으로 **"카카오 place id를 restaurant_id로 그대로 쓰고, 부가정보(리뷰/메뉴/사업자)만 최소 DB에
보관"** 방식이 최종 채택되었다(2-1장).

### 1-4. 남은 그레이존(카카오 문의 예정)
장소 `id` 값 하나만 리뷰 테이블의 외래키로 저장하는 것(상호명/주소 등 실제 장소 정보는 저장하지 않음)까지도
"데이터 저장 등의 목적"에 해당해 금지되는지는 데브톡 답변에 명시적으로 확인되지 않은 부분 — 이 방식 자체는
핵심 조항(실시간 호출, 실질 장소 정보 미저장)을 지키는 방어 가능한(defensible) 설계로 판단해 우선 이대로
구현했고, 별도로 카카오 데브톡에 문의 글을 작성해두었다(사용자가 직접 게시 예정, 4장 참고).

## 2. 최종 아키텍처: "부가정보(extras)만 저장" 패턴
------------------------------------------------------------------------
### 2-1. 핵심 설계
- **`Restaurant` 엔티티의 PK가 카카오 장소 `id`(String)** — 더 이상 자동 증가 `Long`이 아니고, 우리가 새로
  만드는 값도 아니다. 카카오가 응답하는 `id`를 그대로 사용한다.
- `Restaurant`이 저장하는 필드는 **오직 우리 서비스가 직접 생성한 데이터**뿐: `description`(사업자 소개글),
  `phone`(사업자가 직접 입력한 전화번호), `imageUrl`, `managementStatus`, `businessStatus`, `avgRating`/
  `reviewCount`(캐시). **상호명/주소/좌표/카카오가 제공하는 전화번호 등은 절대 저장하지 않는다.**
- `Restaurant` 행은 **평소 검색/조회로는 절대 생기지 않는다** — 리뷰 작성, 즐겨찾기, 사업자 소유권 신청처럼
  사용자가 그 장소와 실제로 상호작용할 때만 `Restaurant.createExtras(kakaoPlaceId)`로 지연 생성(lazy create)된다.

### 2-2. 캐싱 없는 실시간 검색
- `list()`/`search()`/`filter()`/`nearby()` 전부 매 요청마다 `KakaoLocalSearchClient`를 실시간 호출한다.
  응답을 우리 DB의 "부가정보(extras)"와 인메모리로 병합해서 응답을 만들 뿐, 어떤 것도 저장하지 않는다.
- `filter()`는 이제 **좌표 사각형(bounding box)이 필수**다(없으면 `INVALID_INPUT`) — 카카오 API 자체가
  좌표 기반 검색만 지원하기 때문에, 001-02 5-4장의 "bbox 선택적" 설계는 더 이상 유효하지 않다.

### 2-3. 상세 조회에 "재조회 불가" 문제와 그 해결
카카오 로컬 API에는 **"장소 id로 단건 상세를 다시 조회하는 API가 없다**(직접 curl로 확인, category/keyword
검색만 존재). 따라서 `restaurantId`만으로는 그 장소의 이름/주소/좌표를 나중에 다시 알아낼 방법이 없다.

해결책: `GET /api/restaurants/{restaurantId}`가 `name`/`address`/`roadAddress`/`latitude`/`longitude`를
**선택적 쿼리 파라미터**로 추가로 받는다. 프론트가 검색 결과 카드/마커를 클릭할 때 **이미 갖고 있던 데이터**를
그대로 실어 보내면, 백엔드는 그 값을 그대로 응답에 채워 반환할 뿐 서버에 저장하지 않는다(순수 pass-through).

### 2-4. 카테고리 분류도 실시간 재계산
`RestaurantCategoryMatchingService.classify()`가 DB에 쓰지 않는 순수 함수로 재작성됨 — 매 검색/상세 요청마다
카카오가 준 상호명 + 우리 자체 메뉴 키워드 마스터(`MenuKeyword`)로 그 자리에서 분류를 다시 계산한다.

### 2-5. 삭제된 것 / 새로 생긴 것
| 구분 | 내용 |
|---|---|
| **삭제** | `NaverLocalSearchClient`, `SmbizStoreClient` 및 관련 DTO, `RestaurantSyncService`/`Impl`, `RestaurantAreaSyncService`/`Impl`, `POST /api/restaurants/sync`, `POST /api/restaurants/sync-area`, `ErrorCode.SMBIZ_STORE_API_FAILED`/`NAVER_LOCAL_SEARCH_FAILED` |
| **신규** | `KakaoLocalSearchClient`(2-6장), `ErrorCode.KAKAO_LOCAL_SEARCH_FAILED`, `Restaurant.createExtras()` 팩토리 |
| **변경** | `Restaurant`/`Menu`/`RestaurantBusinessHour`/`RestaurantManager`/`Favorite`/`RestaurantTag`/`Review`/`Receipt` 등 `restaurantId` 참조 필드 전부 `Long → String` 타입 변경(카카오 place id를 그대로 저장) |

### 2-6. `KakaoLocalSearchClient` 상세
- `searchByBoundingBox(minX,minY,maxX,maxY)` — 카테고리 검색(`FD6` 음식점 + `CE7` 카페), 페이지 3장까지 순회
- `searchByKeyword(query)` — 전국 대상 키워드 검색(좌표 모를 때 사용, 리뷰 등록 시 3차 보강 등)
- `searchByKeywordInBoundingBox(query,minX,minY,maxX,maxY)` — 좌표(x/y/radius) 편향 키워드 검색(3장)
- `isActualFoodOrCafe(item)` — `category_name`이 `"음식점"`으로 시작하는 것만 통과. **버그 수정**: 카카오의
  `CE7`(카페) 카테고리 그룹 코드로 검색하면 보드게임카페/만화카페/스터디카페/영화관처럼 최상위 분류가
  `"음식점"`이 아닌 곳(`"가정,생활 > 여가시설 > ..."`)까지 섞여 나오는 걸 실제 curl 테스트로 확인 → 이 필터로 제거
- `matchesQuery(item, query)`/`normalize(value)` — 키워드 검색 관련성 버그 수정(3-2장)

## 3. 검색 기능 고도화 (프론트 요청사항 추가 반영)
------------------------------------------------------------------------
### 3-1. 가게명 검색 + 위치 편향
"검색 기능도 넣자... '써브웨이' 검색 시 지금 보고 있는 지도 주변의 써브웨이들 다 보이게" 요청에 따라 지도
테스트 페이지에 검색창을 추가했다. 카카오 `keyword.json`이 지원하는 `x`/`y`/`radius` 파라미터를 활용해
현재 지도 뷰포트 중심으로 편향된 결과를 받도록 `searchByKeywordInBoundingBox`를 신규 작성.

### 3-2. 키워드 검색 관련성 버그
`category_group_code`로 제한해도 카카오 키워드 검색이 무관한 결과를 섞어 반환하는 문제 발견(예: "은행" 검색 시
"노가리"/"호프" 등 24건의 무관한 결과가 함께 옴 — `x`/`y` 편향이 걸리면 카테고리 그룹 내 "근처" 결과로
느슨하게 대체되는 것으로 추정). **앱 단에서 `matchesQuery()` 필터를 추가**해, 정규화(공백 제거+소문자화)한
장소명이 정규화한 검색어를 문자열로 포함할 때만 결과에 포함시키도록 수정.

### 3-3. 음식(메뉴) 이름 검색
"음식 검색도 가능하게 해줘 가게의 음식 리스트에서 있는 그 음식을 판매하는 가게를 검색" 요청 반영. 메뉴는
카카오 데이터가 아니라 **사업자가 직접 등록한 우리 자체 데이터**이므로, DB에서 바로 `LIKE` 검색해도 ToS
문제가 없다(`MenuRepository.findRestaurantIdsByMenuNameContaining`). 다만 카카오 재조회가 안 되는 한계 때문에
매칭된 `restaurantId` 목록을 **현재 지도 범위의 카카오 실시간 카테고리 검색 결과와 교집합**시켜 좌표를 얻어야
마커로 표시할 수 있다(2-3장의 "단건 재조회 불가" 문제의 연장선) — `RestaurantServiceImpl.search()`가 가게명
매칭(카카오 키워드 검색)과 메뉴명 매칭(DB LIKE + bbox 카테고리 검색 교집합)을 하나의 응답으로 병합해서 반환.

### 3-4. 초기 로드도 무조건 카카오 실시간 호출
"카카오 원래 빨리 불러와지는데 왜 이렇게 딜레이가 있냐? 처음 들어왔을때 보여지는거도 카카오쪽으로 무조건
가야 해" — 페이지 최초 진입 시에도 캐시 확인 로직 없이 곧바로 `researchThisArea()`(실시간 카카오 호출)를
호출하도록 변경. 예전에 있던 "동기화 여부 확인 후 필요할 때만 갱신"(`autoSyncCurrentArea`, `lastSyncedBoundsList`
등)은 애초에 캐싱 아키텍처 전제였던 코드라 전부 삭제.

### 3-5. 지도 테스트 페이지 UI 변경 요약
- 별도였던 "카카오 테스트" 버튼(검증용 임시 버튼)을 제거하고, 기존 "이 지역에서 검색" 버튼이 동일한 카카오
  실시간 갱신 동작을 하도록 통합
- 검색창(`#searchRow`) 추가 — 가게명/메뉴명 통합 검색, 카테고리 필터와 상호 배타(하나를 쓰면 다른 쪽 초기화)

### 3-6. 카테고리별 마커 아이콘 (2026-07-23 추가, 같은 날 사용자 제공 이미지로 교체)
"지도 마커 저거 카테고리마다 저 마커로 표시되게 해줘"라는 요청으로, `tmp-map-test.html`의
`renderRestaurants()`가 모든 가게에 같은 기본 마커를 쓰던 것을 그만두고, `RestaurantSummaryResponseDto.category`
(카카오 원본 카테고리가 아니라 `restaurantCategoryMatchingService.classify()`가 이미 분류해둔, 2-4장의
공식 11개 한글 카테고리명 중 하나)를 키로 카테고리별로 다른 핀 마커를 붙였다.

**1차(직접 제작 SVG) → 2차(사용자 제공 이미지로 전면 교체)**: 처음엔 색/아이콘을 인라인 SVG로 직접
그려서 붙였는데, "내가 준 이미지 파일 그거로 마커 무조건 해줘 니가 만들지 말고"라는 명확한 지적으로
전량 교체했다 — 사용자가 채팅에 첨부한 10개 PNG(카테고리별 색깔 핀, 320×416px)를
`Project2/src/main/resources/static/img/markers/marker-{korean|western|chinese|japanese|snack|fastfood|
asian|bar|buffet|cafe}.png`로 저장하고, `CATEGORY_MARKER_ICONS`(프론트 JS 상수)가 카테고리 한글명 →
이 이미지 경로로 매핑한다. `naver.maps.Marker`의 `icon.url`에 이 경로를 그대로 넣고, 원본 비율(320:416)을
유지한 채 40×52px로 축소해서 표시(`anchor`는 핀 뾰족한 끝인 (20,52)).

- 사용자가 이미지를 준 10개 카테고리(한식/양식/중식/일식/분식/패스트푸드/아시안/술집/뷔페/카페-디저트)만
  이 이미지를 쓴다 — "그 외"는 대응 이미지가 없어서 별도로 만들지 않고 네이버 지도 기본 마커를 그대로 둠
- 카테고리 분류가 안 된 가게(`category`가 `null`)도 마찬가지로 기본 마커
- "전체"(카테고리 필터 미적용) 보기에서는 이 마커들이 그냥 각자 카테고리 이미지로 섞여서 보이면 된다는
  요청대로, 별도의 "전체 보기 전용 마커"는 만들지 않음 — 필터 여부와 무관하게 항상 `r.category` 기준으로
  마커 아이콘이 정해진다
- 이미지 파일들은 사용자가 어디서 첨부했는지 대화창에서 바로 확인할 수 없어서(클립보드 붙여넣기), 실제
  저장 위치(`~/Downloads/marker-*.png`)를 파일 시스템에서 타임스탬프 기준으로 찾아서 복사해왔다

### 3-7. 카테고리 분류 커버리지 개선: 카카오 원본 카테고리로 2차 분류 (2026-07-23 추가)
이미지 교체 직후 실제 화면에서 확인해보니, 강남역 인근 72곳 중 겨우 29곳(40%)만 카테고리가 분류되고
나머지는 전부 기본 마커로 나왔다 — 원인은 `RestaurantCategoryMatchingService.classify()`가 **상호명에
우리 메뉴 키워드 마스터(`menu_keywords`)의 단어가 실제로 포함될 때만** 분류하기 때문("땀땀 본점", "강남진
해장"처럼 상호명만 봐서는 음식 종류를 알 수 없는 가게가 대부분 분류 실패로 남음). "전체인 경우 일반 그
마커 말고 전체 다 섞여도 좋으니 자기들 그 이미지 쓰게 해줘"라는 후속 요청으로 커버리지를 크게 높였다.

**해결**: 카카오 로컬 API가 검색 결과마다 이미 내려주는 원본 카테고리 문자열(`KakaoLocalSearchItem.categoryName`,
예: `"음식점 > 한식 > 육류,고기"`)을 2차 신호로 추가 활용 — 1차(상호명+메뉴명 키워드 매칭)가 실패했을
때만 이 문자열에서 "한식"/"일식"/"카페"/"술집" 같은 뻔한 단어를 찾아 우리 11개 공식 카테고리 중 하나로
매핑한다(`RestaurantCategoryMatchingService.classifyByKakaoCategoryName()`, 신규). 1차 분류가 항상
우선이라는 원칙은 그대로 유지 — 이건 어디까지나 1차가 실패했을 때의 보조 수단이다. `RestaurantServiceImpl
.classifyItem()`(목록/검색/주변조회 공용)에만 적용했고, 상세 조회(`getDetail()`)는 카카오 원본 카테고리를
애초에 안 받는 구조라(001-05, 단건 재조회 불가) 이번 변경 대상에서 제외.

**효과**: 같은 72곳 재조회 기준 71/72(99%)로 분류 성공 — 남은 1곳("하이디라오 서초점", 중국 훠궈 전문점)은
카카오 원본 카테고리 문자열에도 "중식" 같은 명시적 단어가 없는 예외적 케이스라 여전히 기본 마커로 남는다
(허용 가능한 잔여 미분류로 판단, 별도 조치 안 함).

### 3-8. 진짜 원인: `scaledSize` 누락으로 마커 이미지가 안 보이던 버그 (2026-07-23, Playwright로 직접 검증)
분류 커버리지를 99%로 올린 뒤에도 "여전히 마커가 안 됨"이라는 재확인 요청이 들어와서, 추측 대신
Playwright(`e2e/playwright.config.ts`가 이미 설정돼 있어 그대로 재사용, 신규 ad-hoc 스크립트로 실행 후
삭제)로 headless 브라우저를 직접 띄워 원인을 찾았다:

1. `markers` 배열/네이버 마커 객체 상태 확인 → 72개 전부 `getMap()`이 살아있고 `getVisible()`도 `true`,
   아이콘 URL도 `img/markers/marker-*.png`로 정확히 채워짐 — **JS 로직 자체는 정상**
2. 네트워크 탭 확인 → 8종 마커 이미지 전부 `200`으로 정상 로드됨 — **이미지 파일/경로도 문제 없음**
3. DOM에서 실제 `<img>` 엘리먼트의 `getBoundingClientRect()`를 찍어보니 **`320×416`(원본 그대로)**로
   렌더링되고 있었다 — 부모 wrapper `div`는 네이버가 `40×52`(`overflow:hidden`)로 잘라주지만, `<img>` 자체는
   축소되지 않은 원본 크기 그대로였던 것. 핀 그림이 이미지 가운데 있다 보니, 40×52로 잘린 부분(이미지의
   왼쪽 위 모서리)은 투명한 여백뿐이라 **화면에는 아무것도 안 보이는 상태**였다.
4. 원인: `icon` 옵션에 `size`만 주고 **`scaledSize`를 빠뜨림** — 네이버 지도(구글 지도와 동일한 API 관례)에서
   `size`는 스프라이트 클리핑 기준일 뿐이고, 원본 이미지를 실제로 리사이즈하려면 `scaledSize`를 반드시
   같이 줘야 한다. `currentLocationMarker`(기존 코드, 파란 점)는 SVG 자체를 24×24로 그려서 `size`와 원본
   크기가 우연히 같았기 때문에 이 버그가 드러나지 않았었다.
5. 수정: `markerOptions.icon`에 `scaledSize: new naver.maps.Size(40, 52)` 추가(`size`와 동일한 값).

**재검증(Playwright, 같은 스크립트로)**: 서버 재기동 후 다시 headless로 접속해 스크린샷을 찍어 육안으로
확인 — 강남/서초 지역 72개 마커가 카테고리별 색(빨강 한식/갈색 카페-디저트/청록 일식/보라 술집 등)이 뚜렷하게
구분되는 작은 핀으로 정상 렌더링됨을 확인. 검증에 쓴 스크립트/스크린샷 파일은 확인 직후 삭제.

## 4. 리뷰 기능 신규 구현 (별도 설계 문서 없이 진행 — 이 문서에 최초 기록)
------------------------------------------------------------------------
음식점-메뉴-검색(07) 기능과 영수증OCR(08) 기능 사이에서 진행된 리뷰 작성/조회 기능. 별도 분석·설계 문서 없이
바로 구현되어, 이 문서가 최초의 공식 기록이다. 새 도메인 패키지 `com.foodtrip.foodsearch.review`.

### 4-1. 기능 범위
- `POST /api/reviews` — 리뷰 작성(별점 + 키워드 칩 + 자유 텍스트, `receiptId` 선택 — 영수증 인증 연결, 08장)
- `GET /api/restaurants/{restaurantId}/reviews` — 그 음식점의 리뷰 목록 조회(공개 API)

### 4-2. 로그인 필수 여부 (2026-07-22 확인)
`POST /api/reviews`는 **로그인한 회원만 가능** — `Authorization` 헤더 없이/무효 토큰으로 호출 시 `401
NOT_LOGGED_IN`. 조회(`GET .../reviews`)는 그대로 공개. (목록/상세 조회의 "선택적 인증"과는 다르게, 쓰기 API는
사업자 등록 API(001-02 5-8장)와 같은 "로그인 필수" 패턴을 따름 — CLAUDE.md 2장의 필터 없는 인라인 토큰
검증 패턴 재사용, `resolveMemberId()`.)

### 4-3. 부가정보 지연 생성과의 연결
`ReviewServiceImpl.create()`는 `restaurantRepository.findByRestaurantIdAndDeletedAtIsNull(id)
.orElseGet(() -> restaurantRepository.save(Restaurant.createExtras(id)))` 패턴으로, **리뷰가 그 음식점에
대한 첫 상호작용이면 이 시점에 비로소 `Restaurant` 행이 생긴다**(2-1장). 이전 설계(001-02)의
`RESTAURANT_NOT_FOUND` 에러는 이 기능에서는 발생하지 않음 — "음식점을 못 찾아서 실패"가 아니라 "처음
상호작용하는 음식점이라 지금 부가정보 행을 만든다"는 개념으로 바뀌었기 때문.

### 4-4. 키워드 칩 저장 방식
백엔드 `CreateReviewRequestDto`에 키워드 전용 컬럼이 없어, 프론트가 선택한 키워드를 `#키워드` 형태로 자유
텍스트(`content`) 앞에 이어붙여 하나의 문자열로 저장(예: `"#음식이 맛있어요 #친절해요\n정말 맛있었어요"`).
별도 스키마 변경 없이 참고 화면(네이버맵 리뷰 UI)의 키워드 선택 UX를 최소 변경으로 재현.

### 4-5. 리뷰 임시저장(초안 자동저장) 기능 (2026-07-22 신규)
"리뷰 작성 시 리뷰 적다가 잠시 나갔다 올 때 임시저장도 가능하게 해줘" 요청으로 추가. **순수 프론트엔드
기능**(백엔드 변경 없음) — `tmp-map-test.html`에 `localStorage` 기반으로 구현.

- **저장 키**: `tmp_review_draft_{restaurantId}` (음식점별로 별도 보관)
- **저장 트리거**: 별점 클릭, 키워드 칩 선택/해제, 리뷰 내용 `input` 이벤트, 상세 패널 닫기(`closeDetailPanel`)
  — 총 4곳에서 `saveReviewDraft()` 호출
- **저장 안 함(정리)**: 별점 5(기본값) + 키워드 미선택 + 빈 텍스트인 "완전 기본 상태"면 오히려
  `localStorage.removeItem()`으로 지워서, 실제로 아무것도 안 쓴 초안이 계속 쌓이는 걸 방지
- **복원**: `openDetailPanel(r)`이 열릴 때 `loadReviewDraft(r.restaurantId)`로 저장된 초안이 있으면 별점/
  키워드/텍스트를 그 값으로 채우고, "작성 중이던 리뷰 임시저장이 복원되었습니다." 안내 문구를 표시
- **정리**: `submitReview()`가 성공하면 `clearReviewDraft(currentDetailRestaurantId)`로 그 음식점의 초안을
  삭제 — 제출 성공 후 다시 들어가도 빈 폼으로 시작
- **검증**: Playwright로 (1) 입력 중 자동저장 → 패널 닫기 → 재오픈 시 별점/키워드/텍스트 및 안내 문구 복원
  확인, (2) 로그인 상태로 실제 제출 → 초안이 `localStorage`에서 삭제되고 재오픈 시 빈 폼임을 확인. 둘 다
  통과(검증에 사용한 테스트 회원/스크립트는 검증 직후 삭제).

## 5. DB 마이그레이션
------------------------------------------------------------------------
### 5-1. 타입 변경 (`restaurant_id` `BIGINT` → `VARCHAR`)
`ddl-auto=update`는 기존 컬럼의 타입을 안전하게 바꾸지 못한다(기존에 확인된 제약) — 영향받는 9개 테이블
(`restaurants`, `menus`, `restaurant_business_hours`, `restaurant_managers`, `favorites`, `reviews`,
`receipts`, `receipt_items`, `ocr_processing_logs` — 전부 빈 테이블임을 먼저 확인)을 수동으로 `DROP`하고
Hibernate가 재부팅 시 새 스키마로 다시 생성하도록 함.

### 5-2. FK 제약 충돌
`restaurants` 재생성 시 `Can't create table restaurants (errno: 150)` 발생 — 원인은 이번 기능과 무관한
**레거시 테이블 5개**(`restaurant_nearby_places`, `restaurant_tags`, `recommendation_results`,
`restaurant_category_mappings`, `navigation_histories` — AI 추천/내비게이션 등 아직 안 만든 기능을 위해 프로젝트
초기 DB 설계 당시 미리 만들어뒀던 것)가 옛 `BIGINT restaurants.restaurant_id`를 참조하는 실제 FK 제약을 여전히
갖고 있었기 때문. `information_schema.KEY_COLUMN_USAGE`로 원인 특정 후, 테이블 자체는 남기고 `ALTER TABLE ...
DROP FOREIGN KEY`로 제약 5개만 제거해서 해결.

### 5-3. 레거시 데이터 정리
과거(이번 세션 이전) 공공데이터/소상공인 방식으로 동기화됐던 옛 형식 데이터(`external_place_id`가
`MA0101202306A0099473` 같은 형식) 1417건이 남아있어 "여전히 옛날 데이터가 보인다"는 혼선이 있었음 — 실제로는
코드 버그가 아니라 이번 리아키텍처 이전의 잔존 데이터였고, 사용자 확인 후 전량 삭제.
