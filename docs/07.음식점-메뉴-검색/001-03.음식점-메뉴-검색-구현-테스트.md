### 1-3. 설계 대비 실제 구현 확정 사항
- **주변조회 쿼리**: 설계(001-02 4-1장)대로 바운딩 박스(위도 1도≈111km 근사) → Haversine 공식 순으로 native SQL(`RestaurantRepository.findNearby`)로 구현. 엔티티 전체를 매핑하는 대신 `restaurant_id`+`distanceKm` 프로젝션만 뽑고, 서비스에서 `findAllById()`로 본체를 가져와 순서를 유지한 채 재조합하는 방식을 택함(네이티브 쿼리로 엔티티 전체를 매핑하는 것보다 단순).
- **검색/필터 쿼리 (2026-07-20 분리)**: `searchByKeyword()`는 JPQL `EXISTS` 서브쿼리로 키워드(음식점명 OR 메뉴명)만 처리, `filterByCategoryAndAveragePrice()`는 카테고리 + 메뉴 평균가(`AVG(price)` 상관 서브쿼리)를 처리. 둘 다 `Page<Restaurant>` + 별도 `countQuery`로 페이징까지 한 번에 처리(1-6장 참고).
- **favorite 필드의 선택적 인증**: 001-02 8장에서 열어뒀던 "헤더가 있는데 토큰이 무효하면 에러로 처리할지"를 실제로 결정함 — **에러를 던지지 않고 비로그인(favorite=false)으로 취급**하기로 함. 이 5개 API는 로그인 여부와 무관하게 항상 공개로 동작해야 한다고 판단했고, 위조/만료된 토큰 하나 때문에 공개 조회 자체가 401이 되는 건 이상하기 때문. `RestaurantServiceImpl.resolveMemberIdOrNull()`이 `JwtException`/`IllegalArgumentException`을 전부 잡아 null(비로그인)로 처리.
- **N+1 방지**: 목록/검색/주변조회 응답의 `category`(단일)/`favorite` 필드는 음식점별로 한 번씩 조회하면 N+1이 발생하므로, `restaurantIds` 리스트를 받아 한 번에 배치 조회하는 `findFirstCategoryNamesByRestaurantIds()`/`findFavoritedRestaurantIds()`를 각각 추가해서 페이지당 쿼리 수를 고정시킴.
- **즐겨찾기(Favorite) 엔티티**: 즐겨찾기 등록/해제 자체는 이번 기능 범위가 아니지만(001-01 1-0장), `favorite` 응답 필드를 채우려면 조회가 필요해서 `favorites` 테이블에 읽기 전용(생성자 없음, getter만) 엔티티를 매핑함. 등록/해제 API는 만들지 않음 — 향후 즐겨찾기 기능이 별도로 구현될 때 같은 테이블에 쓰기 로직만 추가하면 됨.

### 1-5. 네이버 지역 검색 API 연동 — 최초엔 실패, 2026-07-20 재검증으로 실제 데이터 수신 성공
`NaverLocalSearchClient`는 공식 문서(https://developers.naver.com/docs/serviceapi/search/local/local.md ) 기준으로 구현했고, 소셜로그인(006)에서 이미 쓰고 있는 네이버 OAuth 앱의 Client-ID/Secret(`oauth.naver.client-id/secret`)을 그대로 재사용하도록(별도로 `naver.search.client-id/secret`을 앞세우되 없으면 fallback) 만들었다.

**최초 시도(같은 날) 실패**: 그 값으로 바로 호출해보면 `{"errorMessage":"Scopes are Empty : Authentication failed.","errorCode":"024"}` — 팀의 네이버 개발자 앱이 "로그인" API만 등록돼 있고 "검색" API 사용 설정이 꺼져 있었음. 사용자가 네이버 개발자 콘솔에서 **"검색" API 사용 설정 + "비로그인 오픈 API 서비스 환경"(서비스 URL 등록)**을 켠 뒤 재시도.

**두 번째 시도(같은 날) — 여전히 실패, 이번엔 우리 쪽 버그**: `errorCode: 024`는 사라졌지만(인증은 통과) `POST /api/restaurants/sync`가 `success:true`/`fetchedCount:0`으로 빈 응답을 줌 — 에러가 안 나서 원인 파악이 까다로웠음. 네이버 API를 `curl`로 직접 호출하면 데이터가 정상으로 오는데, 우리 서버를 거치면 0건이 나오는 걸 보고 클라이언트 코드 문제로 좁혀서 원인을 찾음: `NaverLocalSearchClient.search()`가 `UriComponentsBuilder.toUriString()`으로 **이미 퍼센트 인코딩된 URL 문자열**을 만든 다음, 그 문자열을 `RestClient.uri(String)`에 그대로 넘기고 있었음 — `RestClient.uri(String)`은 받은 문자열을 "인코딩 안 된 템플릿"으로 취급해서 다시 인코딩하기 때문에, 공백(`%20`)이 `%2520`으로 **이중 인코딩**됨. 이중 인코딩된 검색어를 네이버가 "검색어 없음"과 동일하게 처리해서 `items: []`(빈 배열)를 정상 응답(200)으로 돌려준 것 — 우리 쪽은 그걸 "검색 결과 0건"으로 그냥 받아들여서 에러조차 나지 않았음.

**수정**: `UriComponentsBuilder...encode().build().toUri()`로 `java.net.URI` 객체를 만들어 `RestClient.uri(URI)`에 넘기도록 변경(문자열이 아니라 이미 만들어진 `URI` 객체를 넘기면 재인코딩되지 않음).

**최종 재검증 성공**: `POST /api/restaurants/sync?query=강남역 음식점` → `{"fetchedCount":5,"createdCount":5,"updatedCount":0,"success":true}`. `GET /api/restaurants`/`GET /api/restaurants/{id}`로 실제 음식점 5건(이름/도로명주소/지번주소/좌표/네이버링크)이 정상 저장·조회되는 것까지 확인함 — 좌표 변환(mapx/mapy ÷ 10^7)도 실제 응답값으로 정확히 일치하는 것을 확인(예: "주도락 강남점" mapx=1270284715/mapy=374999331 → longitude 127.0284715/latitude 37.4999331). `category`는 전부 `null`로 나오는데, 이는 버그가 아니라 4-3-4장에서 확정한 "유사 카테고리 없으면 자동 생성하지 않고 건너뜀" 설계대로 동작한 것(`restaurant_categories`가 아직 팀 대분류로 채워지지 않은 빈 테이블이라 매칭될 게 없음).
전체 회귀 테스트도 재실행해 130/130 통과 확인(이 수정이 다른 기능에 영향 없음).

### 1-6. 2차 구현 (2026-07-20): 001-02 8장 답변 3가지 코드 반영
001-02 설계 문서에 사용자가 직접 답변한 8장 항목 중, 최초 구현(1~5장)과 실제로 어긋나 있던 3가지를 코드에 반영함(사용자가 처음엔 "문서만 먼저 수정"을 선택했다가, 이번에 "001-03대로 다시 코드 짜줘"로 진행 요청).

1. **검색/필터 API 분리(1-1장)**: 기존 `GET /api/restaurants/search`가 keyword/categoryId/minPrice/maxPrice를 전부 받던 것을, `GET /api/restaurants/search`(keyword 전용)와 `GET /api/restaurants/filter`(categoryId/minPrice/maxPrice 전용) 2개로 쪼갬. `RestaurantRepository.search()` 하나였던 걸 `searchByKeyword()`/`filterByCategoryAndAveragePrice()` 2개로, `RestaurantService.search()`도 시그니처를 나눠 `search()`/`filter()` 2개로 분리. 컨트롤러 엔드포인트도 6개→7개로 늘어남.
2. **가격대 필터의 평균가 기준 전환(2-4장)**: "메뉴 하나라도 그 가격대에 있으면 매칭"에서 "그 음식점의 메뉴 평균가(`AVG(menus.price)`)가 범위 안에 있으면 매칭"으로 변경. JPQL 상관 서브쿼리(`(SELECT AVG(m.price) FROM Menu m WHERE m.restaurantId = r.restaurantId AND m.deletedAt IS NULL) >= :minPrice`)로 구현 — 메뉴가 하나도 없는 음식점은 `AVG`가 `NULL`이라 비교 자체가 성립하지 않아(SQL NULL 비교 규칙) 자연스럽게 필터 결과에서 제외됨(별도 분기 코드 없이 SQL 특성만으로 원하는 동작이 나옴).
3. **네이버 카테고리 매핑을 자동생성 대신 유사매칭으로 전환(4-3-4장)**: `RestaurantSyncServiceImpl.mapCategory()`가 기존엔 못 찾으면 `RestaurantCategory.create()`로 새로 만들었는데, 이제는 기존 카테고리 전체를 조회해(`findAll()`, 카테고리 테이블이 작아서 괜찮다고 판단) 공백 제거 후 부분 문자열 포함 관계(양방향)로 "비슷한" 카테고리를 찾고, 있으면 그쪽에 매핑, 없으면 매핑을 건너뛰고 `log.warn()`만 남김(새로 생성하지 않음). "비슷하다"의 정확한 판단 기준과 팀의 대분류 카테고리 목록 자체가 아직 없어서, 이 로직은 실데이터로 검증하지 못했다(3장 남은 작업 참고) — 단순 부분 문자열 매칭은 팀이 실제 대분류를 만들면 재검토가 필요한 잠정 구현.

새 코드에 맞춰 `e2e/tests/restaurant.spec.js`도 갱신: 카테고리/가격대 테스트를 `/api/restaurants/filter`로 옮기고, 가격대 테스트는 "개별 메뉴는 범위 밖이지만 평균은 범위 안"인 케이스로 다시 짜서 평균가 로직임을 실제로 검증하도록 함(2-2장 참고).
