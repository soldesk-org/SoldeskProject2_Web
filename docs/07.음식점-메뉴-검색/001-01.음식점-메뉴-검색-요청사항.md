## 기능 정리하기
------------------------------------------------------------------------
현재 해당 기능은 프론트 연결하지 않고 개발만 하기

회원(가입/로그인/정보수정/탈퇴/소셜로그인) 파트는 끝났으니, 다음 단계로 음식점 파트로 넘어감.

팀 역할 분담:
- 준혁: AI로 자연어 분석 담당. 예를 들어 사용자가 "나 오늘 이거 먹고 싶은데 분위기 좋은 거 추천해줘"라고 말하면, 그 문장을 분석해서 검색어/조건으로 뽑아내는 역할
- 윤지: 태그에 들어갈 카테고리 정리 담당. 1만원 이하, 한식, 일식처럼 가격대/음식종류 등으로 카테고리를 나눔
- 주혁(나, 백엔드 총괄): 정보를 가져와 수신하는 역할. 준혁이 분석한 검색어와, 윤지가 정리한 태그 조건(가격대/음식종류 등 카테고리)을 받아서, 그 조건에 맞는 음식점·메뉴만 DB에서 조회해서 돌려주는 기능을 만들면 됨

즉 이번 기능 범위:
- 음식점·메뉴 DB 조회
- 검색어와 필터 조건(태그 카테고리 — 가격대, 한식/일식 등 음식종류 등)을 받아서 조건에 맞는 결과만 가져오기

AI 자연어 분석 자체(준혁 담당)나 태그/카테고리 값을 직접 정하는 것(윤지 담당)은 이번 범위가 아니고, 그 결과물(검색어, 필터 조건)을 받아서 DB 조회하는 부분만 담당함.

### 데이터 출처 3단 구조 (2026-07-20 요구사항 추가)
네이버 개발자 API 중 지역 검색 API(https://developers.naver.com/docs/serviceapi/search/local/local.md )에서
음식점의 이름, 카테고리, 주소, 좌표 정도는 가져올 수 있음. 근데 우리가 기획했던 메뉴, 영업시간, 리뷰 같은 건
개인정보라 그런지 API에서 제공을 안 해줘서, 이런 건 전부 사업자 쪽에서 직접 등록할 수 있게 해줘야 함.

정리하면 데이터 출처가 3단 구조임:
1. **네이버 지역 검색 API에서 가져오는 것**: 이름, 카테고리, 주소, 좌표 목록 — 처음에 가져올 API가 이거
2. **지도/마커 표시**: 윤지가 프론트 화면에서 보여줄 지도랑 마커를 표시할 지도 API(참고 문서 섹션의 네이버 지도 API)
3. **주혁(나)이 직접 만들 것**: 리뷰, 즐겨찾기, 태그, 추천 결과를 표시할 고유 정보를 저장할 DB

(메뉴/영업시간은 사업자가 직접 등록하는 부분이라 이 기능 범위인지 별도 기능인지는 아직 확정 안 함 — 일단 이렇게 생각하고 있음)

## 응답 데이터 / 작업 순서 (2026-07-20 추가)
------------------------------------------------------------------------
목록/상세 조회 응답에 아래 항목들을 담아서 넘기면 될 것 같음(리뷰·즐겨찾기·지도·위도·경도는 이 기능 담당이 아니라 다른 팀원들이 그대로 가져다 써야 하는 값이라 포함시켜야 함):

| 항목 | 설명 |
|---|---|
| restaurantId | 우리 DB 음식점 번호 |
| name | 음식점명 |
| category | 음식점 카테고리 |
| description | 간단한 설명 |
| roadAddress | 도로명 주소 |
| address | 지번 주소 |
| latitude | 지도 표시용 위도 |
| longitude | 지도 표시용 경도 |
| naverPlaceUrl | 네이버에서 보기 주소 |
| averageRating | 우리 사이트 평균 평점 |
| reviewCount | 우리 사이트 리뷰 수 |
| favorite | 현재 회원의 즐겨찾기 여부 |

작업 순서(결론):
1. 네이버 지역 검색 API 연결
2. 응답 데이터 정리
3. 우리 DB 음식점과 연결
4. 음식점 목록 API
5. 음식점 상세 API
6. 오류·예외 처리
7. Swagger·Postman 정리
8. 프론트 인수인계

정보 없음 표시: 메뉴가 없으면 "메뉴가 없습니다.", 리뷰가 없으면 "리뷰가 없습니다." 처럼, 항목별로 어떤 정보가 부족하거나 없는지 구분해서 알 수 있게 표시해줬으면 함

## 설계 확인사항 답변 (2026-07-20)
------------------------------------------------------------------------
분석-설계 문서(001-02) 8장에서 확인이 필요했던 항목들에 대한 답변.

1. **지도 마커 표시**: 있는 음식점은 전부 마커로 표시하고 그 주변에 이름을 표기, 클릭하면 상세 내용이 나오는 방식으로 생각 중(프론트가 목록/주변조회 응답의 이름·좌표로 마커+라벨을 그리고, 클릭 시 상세 조회 API를 호출하는 흐름).
2. **검색과 필터는 별개**임 — 하나의 API로 합치지 않음.
3. (로그인 상태 유지 관련 질문은 이미 만들어져 있는 기능(rememberMe)이라 이번 문서와 무관 — 패스)
4. **가격대 필터**는 그 음식점의 **평균 가격대**가 필터 범위 안에 있을 때로 함(메뉴 하나라도 걸리면 매칭되는 방식 아님).
5. 정렬 기준/페이지네이션/기본 반경 관련 세부값: 프론트야(백엔드는 잠정값 유지, 필요하면 프론트에서 조정).
6. 태그 데이터 시딩 시점: 프론트야(백엔드가 결정할 사항 아님).
7. **닫힌 음식점**은 목록/검색에서 숨기지 않고 "영업 휴무"라고 표기함.
8. 네이버 API 동기화는 **일단 수동을 베이스**로 두되, 자동화(스케줄러)는 나중에 검토해보기로 함.
9. **카테고리 매핑**: 팀이 큰 카테고리(대분류)를 나눠둘 예정이라, 네이버 API가 준 카테고리와 비슷한 카테고리열이 이미 있으면 그쪽으로 자동으로 종속시킴 — 새 카테고리를 자동으로 만들지는 않음.
10. **네이버 API 호출량 한도**: 한 달 600만 회 한도라, 안전하게 일일 호출 한도를 20만 회로 지정하기로 함.
11. **리뷰 표시**: 리뷰 목록 자체는 클릭해서 들어가는 화면(리뷰창)이 따로 있고, 그 화면에 들어갔을 때 리뷰 개수가 0이면 "리뷰가 없습니다"라는 문구가 나오게 함.
