## 1. 요구사항 정리
------------------------------------------------------------------------
- 팀 역할 분담(요청사항 원문): 준혁(AI 자연어 분석) → 검색어/조건 추출, 윤지(태그/카테고리 정리), **주혁=이 기능(백엔드)**: 검색어 + 필터 조건(태그 카테고리)을 받아 조건에 맞는 음식점·메뉴만 DB에서 조회해 반환
- **이번 범위에 포함**: 음식점·메뉴 DB 조회, 검색어/필터 조건 처리
- **이번 범위에서 제외**: AI 자연어 분석 자체(준혁 담당), 태그/카테고리 값을 정하는 것(윤지 담당) — 이 기능은 그 결과물(검색어, 필터 조건)을 "입력"으로만 받음
- 세부 기능(요청사항 원문 그대로):
  1) 음식점 목록·상세 조회
  2) 음식점명·메뉴명 검색
  3) 카테고리·가격대 필터
  4) 메뉴 조회
  5) 현재 위치 주변 음식점 조회
  6) 지도에서 선택한 음식점 조회
- 프론트 연결 없음 → REST API + Postman/테스트 코드로 검증

### 1-0. 데이터 출처 3단 구조 (2026-07-20 요구사항 추가)
요청사항 원문에 새로 추가된 내용을 그대로 반영: 이번 기능이 다루는 데이터는 출처가 다른 3단 구조다.
1) **네이버 지역 검색 API**(https://developers.naver.com/docs/serviceapi/search/local/local.md )에서 가져오는 것: 음식점 **이름/카테고리/주소/좌표**. 이번 기능이 최초로 붙는 외부 API이자, `restaurants`/`restaurant_categories` 데이터의 1차 출처가 됨(4-3장, 신규)
2) **지도/마커 표시**: 윤지가 프론트에서 쓸 네이버 지도 API — 이번 백엔드 설계와는 직접 관련 없음(참고만)
3) **주혁(이 기능)이 DB로 직접 구축하는 것**: 리뷰/즐겨찾기/태그/추천결과 등 우리 서비스 고유 정보

이 구조가 바뀌는 지점: **메뉴/영업시간/리뷰는 네이버 API에서 제공하지 않음**(비공개 데이터로 추정) → 전부 사업자가 직접 등록해야 채워지는 값. 즉 기존 2-2장/2-4장/5-2장/5-4장에서 "당연히 있는 값"처럼 다뤘던 메뉴/영업시간은 **사업자가 아직 등록하지 않았다면 비어있을 수 있는 값**으로 다시 봐야 한다(아래 각 장에 반영). 사업자가 메뉴/영업시간을 "등록"하는 기능 자체(관리자 인증, 등록 API 등)가 이번 07 기능 범위에 포함되는지, 별도 기능(예: 08.사업자-음식점관리)으로 분리할지는 아직 미확정 — 8장에 새 항목으로 남김.

### 1-1. "검색"과 "필터"는 별개 API (2026-07-20 확정)
요청사항에는 "음식점명·메뉴명 검색"(2번)과 "카테고리·가격대 필터"(3번)가 별개 항목으로 나열돼 있었는데, 처음에는 사용 편의를 위해 하나의 통합 API로 합쳐서 설계했었다. 그런데 사용자가 명시적으로 "검색과 필터는 별개"라고 확인해줘서, **검색 API**(`GET /api/restaurants/search`, keyword 전용)와 **필터 API**(`GET /api/restaurants/filter`, categoryId/minPrice/maxPrice 전용)를 **분리**하는 것으로 최종 확정한다(2-3장/2-4장, 5-3장/5-4장).

### 1-2. "지도에서 선택한 음식점 조회"의 해석 (2026-07-20 확정)
사용자가 확인해준 내용: "있는 음식점은 전부 마커로 표시하고 그 주변에 이름을 표기, 클릭하면 상세 내용이 나옴." 즉:
- 지도 위에 보이는 모든 음식점을 마커+이름으로 표시하는 것 자체는 **프론트가 목록 조회(5-1장)/주변 조회(5-6장) 응답에 이미 포함된 이름·좌표로 그리는 것**이라 백엔드에 별도 API가 필요 없음
- 마커를 **클릭**했을 때는 그 음식점 하나의 상세 정보를 보여주는 것이므로, 별도 API 없이 5-2장(상세 조회)을 그대로 재사용하는 기존 설계가 맞았음 — 확정, 2-7장

## 2. 전체 플로우
------------------------------------------------------------------------
### 2-1. 음식점 목록 조회
1) 클라이언트가 `GET /api/restaurants` 호출(페이지 번호/크기 선택적)
2) 소프트 삭제(`deleted_at IS NULL`)되지 않은 음식점을 정렬 기준(6장)에 따라 페이징 조회
3) 카테고리/태그/영업시간까지는 포함하지 않고, 목록 화면에 필요한 최소 정보(이름/주소/평점/리뷰수/대표 이미지 등)만 반환 — 상세 정보는 2-2장에서 별도 조회

### 2-2. 음식점 상세 조회
1) 클라이언트가 `GET /api/restaurants/{restaurantId}` 호출
2) 음식점 기본정보 + 카테고리 목록 + 태그 목록 + 영업시간 + 대표 메뉴(또는 전체 메뉴, 6장 참고)를 함께 조회해 반환
3) 존재하지 않거나 소프트 삭제된 음식점이면 `RESTAURANT_NOT_FOUND`
4) **(1-0장 반영)** `businessHours`/`menus`는 사업자가 등록하기 전까지는 비어있을 수 있음 — 조회 자체는 실패로 취급하지 않고 빈 배열(`[]`)로 반환(5-2장 응답 형식에 반영)

### 2-3. 음식점명·메뉴명 검색 (1-1장, 2026-07-20 필터와 분리 확정)
1) 클라이언트가 `GET /api/restaurants/search?keyword=...`를 호출(키워드 전용, 필터 조건 없음)
2) `restaurants.name` **또는** `menus.menu_name`에 부분일치(`LIKE %keyword%`)하는 음식점을 찾음(메뉴명으로 검색해도 그 메뉴를 파는 "음식점"이 결과에 나옴 — 메뉴 단건이 아니라 음식점 목록을 반환하는 게 요청사항의 취지로 판단)
3) `keyword`가 없으면 2-1장의 전체 목록과 동일하게 동작
4) 검색에 사용된 키워드를 `search_histories`에 기록할지는 이번 범위에서 결정하지 않음(8장 참고 — 그 테이블은 `member_id NOT NULL`이라 비로그인 사용자의 검색은 애초에 기록할 수 없는 구조)

### 2-4. 카테고리·가격대 필터 (1-1장, 2026-07-20 신규 — 검색과 분리된 별도 API)
1) 클라이언트가 `GET /api/restaurants/filter?categoryId=...&minPrice=...&maxPrice=...`를 카테고리/가격대 중 있는 것만 골라 호출
2) `categoryId`가 있으면 `restaurant_category_mappings`로 그 카테고리에 속한 음식점만 필터
3) `minPrice`/`maxPrice`가 있으면 **그 음식점이 파는 메뉴들의 평균 가격**(`AVG(menus.price)`)이 그 범위 안에 있는 음식점만 필터(2026-07-20 확정 — 메뉴 하나라도 걸리면 매칭되는 방식이 아니라 음식점 단위 평균가 기준. 기존 001-03 구현은 "메뉴 중 하나라도 그 가격대에 있으면 매칭"이었는데, 이 결정으로 로직 변경이 필요함 — 001-03에 반영 필요, 아직 미반영)
4) 조건이 하나도 없으면 2-1장의 전체 목록과 동일하게 동작

### 2-5. 메뉴 조회
1) 클라이언트가 `GET /api/restaurants/{restaurantId}/menus` 호출
2) 그 음식점의 판매 중(`is_available=1`)이고 소프트 삭제되지 않은 메뉴 목록을 반환(대표 메뉴가 먼저 오도록 정렬, 6장)
3) 음식점 상세 조회(2-2장)에도 메뉴가 포함되므로, 이 API는 메뉴 목록만 별도로 다시 불러오고 싶은 화면(예: "메뉴 더보기")을 위한 보조 API
4) **(1-0장 반영)** 사업자가 메뉴를 등록하지 않은 음식점이면 빈 배열(`[]`)을 그대로 반환 — `RESTAURANT_NOT_FOUND`와는 구분(음식점은 존재하되 메뉴가 없는 정상 상태)

### 2-6. 현재 위치 주변 음식점 조회
1) 클라이언트가 현재 위치의 위도/경도를 담아 `GET /api/restaurants/nearby?latitude=...&longitude=...&radiusKm=...` 호출
2) `restaurants.latitude`/`longitude`(이미 `INDEX(latitude, longitude)` 있음)로 위경도 사각형(bounding box) 범위를 먼저 걸러낸 뒤, Haversine 공식으로 실제 직선거리(km)를 계산해 `radiusKm` 이내만, 거리가 가까운 순으로 반환(4-1장 참고)
3) `radiusKm` 생략 시 기본값 적용(6장)

### 2-7. 지도에서 선택한 음식점 조회 (1-2장, 2026-07-20 확정)
지도 위 마커+이름 표시 자체는 2-1장(목록)/2-6장(주변조회) 응답을 프론트가 그대로 그리는 것이라 별도 API 불필요. 마커를 **클릭**했을 때만 별도 신규 로직 없이 2-2장(상세 조회)을 그대로 사용.

## 4. 데이터 모델
------------------------------------------------------------------------

| 테이블 | 이번 기능에서의 역할 |
|---|---|
| restaurants | 음식점 기본정보(이름/주소/좌표/전화/영업상태/평점·리뷰수 캐시). `deleted_at`으로 소프트 삭제 필터 |

| restaurant_category_mappings | 음식점-카테고리 N:M |
| menus | 메뉴(이름/가격/설명/이미지/대표메뉴 여부/판매 여부). `deleted_at`으로 소프트 삭제 필터 |
| tags | 공용 태그(`tag_type`: GENERAL/MOOD/MENU_TYPE/PREFERENCE — 윤지가 정리하는 카테고리가 여기 들어올 것으로 예상) |
| restaurant_tags | 음식점-태그 N:M |
| restaurant_business_hours | 요일별 영업시간(상세 조회에 포함) |
| restaurant_managers (2026-07-20 추가) | 사업자 회원-음식점 소유 연결, 5-8장 쓰기 API 권한 확인에 사용(이번에 처음 실사용, `Favorite`처럼 이 기능 이전엔 코드가 없던 테이블) |

### 4-1. 위치 기반 조회(2-5장) 쿼리 설계
`restaurants` 테이블은 `latitude`/`longitude`가 일반 `DECIMAL` 컬럼이고 공간(spatial) 타입이 아니라서, MariaDB의 `ST_Distance_Sphere` 같은 지오메트리 함수를 바로 쓸 수 없다. 대신 업계에서 흔히 쓰는 2단계 방식을 그대로 적용한다:
1) **바운딩 박스 사전 필터**: 위도 1도 ≈ 111km라는 근사치로 `radiusKm`를 위경도 범위로 환산해 `WHERE latitude BETWEEN ? AND ? AND longitude BETWEEN ? AND ?`로 1차로 후보를 크게 줄임 — 기존 `INDEX(latitude, longitude)`가 여기서 실제로 활용됨
2) **Haversine 공식으로 정확한 거리 계산**: 1차로 줄어든 후보들에 대해서만 `SELECT` 절에 Haversine 공식(구면 삼각법)을 적용해 실제 직선거리(km)를 계산하고, `HAVING distance <= radiusKm ORDER BY distance`로 최종 필터/정렬
3) `RestaurantRepository`에 이 로직을 native SQL `@Query`로 구현(신규 지오메트리 라이브러리/의존성 도입 없이 순수 SQL로 해결 — "필요한 만큼만" 원칙)

### 4-2. 카테고리/태그 초기 데이터
`tags`는 이번 기능에서 **읽기만** 하고 채워 넣지 않는다 — 필터용 태그(1만원 이하, 분위기좋음 등)를 정하는 건 윤지 담당(요청사항 원문)이라 이번 범위 밖. 다만 `restaurant_categories`는 아래 4-3장대로 네이버 API에서 음식점 데이터를 가져올 때 그 안의 카테고리 문자열로부터 채워지는 경로가 새로 생김 — 그래서 카테고리와 태그의 채워지는 방식이 서로 달라졌다는 점에 유의(카테고리=API 동기화, 태그=윤지가 별도 정리).

### 4-3. 네이버 지역 검색 API 연동 설계 (1-0장, 2026-07-20 요구사항 추가)
`restaurants` 테이블에는 이미 `external_place_id UNIQUE`(외부 API의 장소 ID를 저장하는 용도)가 정의돼 있어 — 이번 요구사항 추가 이전부터 정확히 이 시나리오를 염두에 두고 만들어진 컬럼으로 보임 — 그대로 활용한다.

1) **연동 방식**: 네이버 지역 검색 API(`GET https://openapi.naver.com/v1/search/local.xml`, `Client-ID`/`Client-Secret` 헤더 인증)를 호출하는 `NaverLocalSearchClient`(가칭, `RestTemplate` 또는 `WebClient`)를 신규 작성. 검색어(예: 지역명+"음식점")를 파라미터로 호출하면 이름/카테고리/주소/좌표/`link`(고유 URL, `external_place_id`로 활용 가능)를 응답으로 받음
2) **동기화 트리거 (2026-07-20 확정)**: 매 요청마다 실시간 호출하는 게 아니라, **미리 가져와서 우리 DB(`restaurants`)에 저장**해두고 이후 목록/검색/필터/상세/주변조회는 전부 우리 DB만 조회하는 방식으로 설계(이유: 응답속도, 네이버 API 호출 한도, 우리 쪽 리뷰/즐겨찾기/태그를 그 음식점에 연결하려면 어차피 우리 DB에 행이 있어야 함). **일단 수동 트리거(관리자 API `POST /api/restaurants/sync?query=...`)를 베이스로 확정** — 스케줄러(`@Scheduled`) 자동화는 나중에 한 번 검토해보기로 함(수동으로 어느 정도 운영해보고 판단)
3) **Upsert 로직**: 응답의 장소 식별자를 `restaurants.external_place_id`로 매칭 — 이미 있으면 이름/주소/좌표 갱신(UPDATE), 없으면 신규 INSERT. 이렇게 하면 같은 음식점을 중복 저장하지 않고 재동기화 시 최신 정보로 갱신됨
4) **카테고리 매핑 (2026-07-20 확정)**: 네이버 API의 `category`는 `"음식점>한식>육류,고기"`처럼 계층이 한 문자열에 `>`로 이어진 자유 텍스트라, 우리 `restaurant_categories`(PK 기반 계층 테이블)와 형식이 다름. **팀이 큰 카테고리(대분류)를 먼저 나눠서 `restaurant_categories`에 미리 만들어두고, 네이버 응답의 카테고리와 비슷한 카테고리가 이미 있으면 그쪽으로 자동 종속시킨다 — 신규 카테고리를 자동으로 새로 만들지는 않는다**(기존 001-03 구현은 못 찾으면 자동 생성하는 방식이었는데, 이 결정으로 바뀜 — 001-03에 반영 필요, 아직 미반영). 다만 "비슷하다"의 정확한 판단 기준(부분일치? 자모 유사도?)과, 비슷한 카테고리가 하나도 없을 때 어떻게 할지(미분류로 둘지, 관리자 검수 큐에 쌓을지)는 여전히 미정 — 8장 참고
5) **메뉴/영업시간/리뷰는 이 동기화 대상이 아님**(1-0장) — 동기화로 채워지는 건 `restaurants` 기본정보 + `restaurant_categories`/`restaurant_category_mappings`뿐
6) **API 호출량 한도 (2026-07-20 확정)**: 네이버 지역 검색 API가 한 달 600만 회 한도라, 안전하게 우리 쪽 자체 일일 호출 한도를 20만 회로 지정하기로 함 — 실제 카운팅/차단 로직(예: `LoginAttemptService`와 같은 Redis 카운터 패턴)은 아직 구현 안 됨, 001-03에 반영 필요

### 5-0-1. "정보 없음" 표시 설계 (요청사항 원문: 메뉴/리뷰 등 없으면 구분되게 표시)
백엔드는 값이 없다고 필드를 생략하지 않고, 항상 필드를 포함하되 데이터가 없으면 명확히 구분 가능한 값을 내려준다:
- **목록형 필드**(`menus`, `businessHours`, `categories`, `tags`): 데이터가 없으면 빈 배열 `[]`(이미 2-2-4/2-5-4장에서 결정) — "메뉴가 없습니다." 같은 안내 문구 자체는 프론트가 빈 배열을 보고 표시(백엔드가 문자열 메시지를 내려주지 않음, 다국어/문구 변경에 유연하도록)
- **리뷰 (2026-07-20 UX 확정, 범위는 미정)**: 사용자가 확인해준 흐름은 "리뷰 목록 자체는 클릭해서 들어가는 화면이 따로 있고, 그 화면에서 리뷰 개수가 0이면 '리뷰가 없습니다'라는 문구가 나오는 것" — 즉 리뷰 원문 목록을 보여주는 화면 자체는 존재를 전제로 함. 다만 그 리뷰 목록 API를 **이번 07 기능이 만드는지, 별도 리뷰 도메인 기능이 만드는지는 여전히 미정**(1-0장 3번 — 리뷰는 주혁이 별도로 만들 도메인으로 분류했던 부분과 상충 가능성 있음, 8장 참고). 이번 상세 API는 일단 `averageRating`/`reviewCount`(캐시값)만 포함하고, `reviewCount=0`이면 프론트가 리뷰 화면 진입 시 "리뷰가 없습니다."를 표시하는 것으로 설계 유지
- **단일 값 필드**(`description`/`phone` 등): 없으면 `null` — 있음/없음이 명확히 구분됨. 프론트가 `phone === null`이면 "전화번호 없음", `businessHours.length === 0`이면 "등록된 영업시간 없음" 식으로 표시하는 건 프론트 책임(2026-07-20 확인 — 백엔드는 null/빈 배열만 정확히 내려주면 됨)
- **음식점 이미지 (2026-07-20 확정)**: 위 목록형/단일값 필드와 달리 예외적으로 "없으면 null"이 아니라 **없으면 고정 기본 이미지로 대체**해서 내려줌(`imageUrl`, 위 표 참고) — 사업자가 등록하기 전까지도 화면에 항상 뭔가는 보여야 한다는 요구사항이라, 다른 필드들과 다르게 백엔드가 폴백값을 채워서 내려주는 유일한 케이스

### 5-7. 검색+필터를 지도 마커 표시용으로 동시에 걸 때 (2026-07-20 확정)
"빙수" 검색 + 카테고리/가격대를 동시에 지정해서 지도에 마커를 표시하고 싶은 경우, 5-3(검색)/5-4(필터)를 하나로 합치는 것이 아니라 **프론트가 둘 다 각각 호출해서 교집합을 계산**하는 것으로 확정함(1-1장에서 검색/필터를 별개 API로 분리하기로 했던 결정과 일관됨). 백엔드 변경 없음 — `GET /api/restaurants/search?keyword=빙수`와 `GET /api/restaurants/filter?categoryId=...&minPrice=...&maxPrice=...`를 각각 호출해서 두 결과 모두에 있는 `restaurantId`만 프론트에서 추려 마커로 표시.

### 5-8. 사업자 등록 (전화/영업시간/메뉴/사진 쓰기 API) — 2026-07-20 요구사항 추가, 001-02 8장에서 열어뒀던 범위 질문 해결
"사업자가 자기 가게 정보를 직접 등록"하는 기능을 실제로 만들기로 확정(01(회원가입) 8-4장의 사업장 주소 자동귀속과 세트). 지금까지 조회 전용이던 `restaurants`/`restaurant_business_hours`/`menus`에 처음으로 **쓰기(Create/Update/Delete)** 가 생김.

**권한 모델**: `restaurant_managers`(DB-테이블설계.md 3-5장, 이번에 처음 실제 사용)로 "이 회원이 이 음식점의 ACTIVE 관리자인가"를 확인 — 목록/상세 조회처럼 "헤더 있으면 검증, 없으면 익명"이 아니라, **로그인 필수 + 소유 확인**(안 하면 아예 호출할 이유가 없는 쓰기 API라서). `resolveMemberId()`(2장 원칙)와 비슷하지만 이번엔 "무효 토큰=비로그인 취급"이 아니라 "무효 토큰=바로 401" — 조회 API의 선택적 인증(5-0장)과는 성격이 다름.

**어떻게 그 음식점의 관리자가 되는가**: 지금 이 문서 시점 기준으로는 사업자 회원가입 시 사업장 주소 자동귀속(01 8-4장)이 유일한 경로 — 수동으로 "이 가게 제 겁니다" 신청하는 별도 화면/API는 이번 범위에 포함하지 않음(자동귀속이 실패하면 그냥 등록 불가 상태로 남음, 8장 참고).

**엔드포인트**:
| API | 설명 |
|---|---|
| `PATCH /api/restaurants/{id}/phone` | 전화번호 수정 |
| `PUT /api/restaurants/{id}/business-hours` | 영업시간 전체 교체(요일별 개별 API 없음 — delete-then-insert로 7일치를 통째로 갈아끼움) |
| `POST /api/restaurants/{id}/menus` | 메뉴 신규 등록 |
| `PATCH /api/restaurants/{id}/menus/{menuId}` | 메뉴 수정(판매중지도 `isAvailable=false`로 이걸로 처리) |
| `DELETE /api/restaurants/{id}/menus/{menuId}` | 메뉴 삭제(소프트 삭제, `deleted_at`) |
| `POST /api/restaurants/{id}/image` | 음식점 사진 업로드(`multipart/form-data`, 005(회원정보수정) 프로필 사진과 동일한 로컬 디스크 저장 패턴) |
| `DELETE /api/restaurants/{id}/image` | 음식점 사진 삭제(기본 이미지로 되돌아감, 5-0장) |

모든 엔드포인트가 성공 시 갱신된 `RestaurantDetailResponseDto`(5-2장과 동일 형식)를 그대로 반환 — 별도 응답 DTO를 만들지 않고 "수정 후 최신 상세 정보"를 바로 보여주는 쪽이 프론트에서 다루기 단순하다고 판단.

**메뉴 소유권 교차 검증**: `menuId`가 URL의 `restaurantId` 소속이 맞는지(`findByMenuIdAndRestaurantIdAndDeletedAtIsNull`)까지 확인 — 다른 음식점 관리자가 자기 `restaurantId`로는 권한이 있다는 걸 이용해 남의 메뉴 ID를 넣어 수정 시도하는 것을 막는다.

### 5-9. 공공데이터(상가업소정보) 사각형 영역 동기화 (2026-07-21 추가, 001-06장)

2. **[응답 데이터 정리]** 네이버 API 응답 파싱 + 5-0장 필드로 매핑, 카테고리 문자열 매핑 로직 구현(4-3-4장, 8장의 매핑 규칙 확정 후 진행)
3. **[우리 DB 음식점과 연결]** `Restaurant`/`RestaurantCategory`/`RestaurantCategoryMapping`/`Menu`/`Tag`/`RestaurantTag`/`RestaurantBusinessHour` 엔티티 + `Repository` 작성(기존 테이블 매핑, 스키마 변경 없음), `external_place_id` 기준 upsert 로직 구현
4. **[음식점 목록/검색/필터 API]** `RestaurantSummaryResponseDto`(5-0장 필드) + `RestaurantService`/`RestaurantServiceImpl` 목록/검색(키워드)/필터(카테고리·평균가)/주변조회 로직 + `RestaurantController` 엔드포인트(검색/필터/주변조회는 별개 API, 1-1장) — 필터의 평균가 계산과 주변조회는 native `@Query` 사용
5. **[음식점 상세 API]** `RestaurantDetailResponseDto` + 상세/메뉴 조회 로직·엔드포인트(`favorite` 선택적 인증 포함, 5-0장)
6. **[오류·예외 처리]** `ErrorCode`에 `RESTAURANT_NOT_FOUND` 추가, `INVALID_INPUT` 검증 규칙(6장) 적용
7. **[Swagger·Postman 정리]** 6개 공개 엔드포인트(목록/검색/필터/상세/메뉴/주변조회) 문서화, 테스트용 태그/메뉴 시딩 데이터 준비(음식점/카테고리 기본정보는 1~3번 동기화로 확보, 메뉴/영업시간은 사업자 등록 전이라 직접 시딩 필요 — 4-2장)
8. **[프론트 인수인계]** Postman/Playwright로 목록/상세(메뉴·영업시간 없는 케이스, `favorite` 유/무 로그인 케이스 포함)/검색/메뉴(빈 배열 케이스 포함)/주변조회(반경 안/밖 경계 케이스)/존재하지 않는 restaurantId 테스트 후, 001-04 연동 가이드 작성 시점에 프론트에 전달
