## 2. 검증 (2026-07-24, 실 서버 + 실 DB + 실제 WebSocket 연결)
------------------------------------------------------------------------
서버를 재기동(새 의존성 반영 필요)하고, throwaway 회원 3명(host/guest/admin, `e2e/dbHelper`로 시딩) +
`e2e/jwtHelper`(토큰 발급) + `e2e/redisHelper`(access 세션 활성화) + `@stomp/stompjs`(Node에 임시 설치,
검증 후 제거) + Node 24 네이티브 `WebSocket`으로 REST와 WebSocket을 모두 실제로 호출해 확인.

### 2-1. `ddl-auto=update`로 테이블 4개가 실제로 생성됐는지 확인
```sql
SHOW TABLES LIKE 'chat_%'
```
`chat_messages`, `chat_reports`, `chat_room_members`, `chat_rooms` 4개 모두 정상 생성 확인.

### 2-2. 방 생성 → 참가코드로 입장
- host가 방 생성 → `200`, `joinCode` 8자리(영문 대문자+숫자) 확인, `memberCount: 1`
- guest가 그 참가코드로 입장 → `200`, `memberCount: 2`
- 존재하지 않는 참가코드(`ZZZZZZZZ`)로 입장 시도 → `404 CHAT_ROOM_NOT_FOUND` 정상 거부

### 2-3. 실시간 메시지 (WebSocket)
- host, guest 둘 다 `/ws-chat`에 STOMP CONNECT(각자 accessToken을 Authorization 헤더로) → 정상 연결
- guest가 `/app/rooms/{roomId}/send`로 "여기 파스타 맛있어요!" 전송 → host가 `/topic/rooms/{roomId}`
  구독으로 실시간 수신 확인(닉네임 `chat19Guest`, 내용 정확히 일치)

### 2-4. 클린봇 (korcen, review-filter 서버 실제 기동 상태에서 검증)
- guest가 "병신같은 사장님" 전송 → host는 아무것도 받지 않음(브로드캐스트 안 됨) 확인, guest 본인만
  `/user/queue/errors`로 `{ code: "CHAT_MESSAGE_PROFANITY", message: "메시지에 부적절한 표현이 포함되어
  있습니다." }` 수신 확인 — 17(리뷰-필터링)에서 검증한 korcen 판정과 동일한 라이브러리를 그대로 재사용
  했음을 실측으로 재확인

### 2-5. 신고 (메시지/방 둘 다)
- host가 방금 온 메시지를 `ABUSE` 사유로 신고 → `200` 성공
- 같은 메시지를 같은 회원이 다시 신고 → `409 CHAT_ALREADY_REPORTED` 정상 거부
- guest가 방 전체를 `SPAM` 사유로 신고 → `200` 성공

### 2-6. 관리자 - 신고 목록/처리
- 회원 role을 `ADMIN`으로 직접 시딩한 뒤 `GET /api/admin/chat-reports?status=PENDING` 호출 → 방금
  등록한 방 신고 1건(`targetType: ROOM`) + 메시지 신고 1건(`targetType: MESSAGE`,
  `contentSnapshot: "여기 파스타 맛있어요!"`) 정확히 조회됨 확인 — 메시지 스냅샷이 신고 시점 내용을
  정확히 담고 있음도 함께 확인
- 메시지 신고를 `PATCH .../resolve` → `200` 처리 완료
- 방 신고를 `PATCH .../reject` → `200` 반려
- `GET .../chat-reports?status=RESOLVED` → 방금 처리한 1건이 정확히 조회됨 확인(상태별 목록 분리 정상)

### 2-7. 방 폭파 (host만 가능)
- guest(방장 아님)가 `DELETE /api/chat/rooms/{roomId}` 시도 → `403 CHAT_ROOM_ACCESS_DENIED` 정상 거부
- host가 같은 API 호출 → `200` 성공, 접속 중이던 host의 WebSocket 세션이 `/topic/rooms/{roomId}`로
  `{ type: "SYSTEM", content: "방장이 채팅방을 폭파했습니다." }`를 실시간 수신함을 확인
- 폭파 직후 `chat_messages` 테이블에서 해당 방 행 개수 확인 → `0`(물리 삭제 정상 동작)
- 폭파된 방에 guest가 메시지 전송 시도 → 브로드캐스트되지 않고 guest에게
  `{ code: "CHAT_ROOM_NOT_FOUND" }` 에러가 옴을 확인(폭파된 방은 더 이상 메시지를 받지 않음)

검증에 쓴 회원 3명/채팅방/메시지/신고 행은 확인 직후 DB에서 직접 삭제해 정리함. 검증 스크립트(Node
`e2e/verify19.js`)와 임시 설치한 `@stomp/stompjs` 패키지도 확인 완료 후 삭제.

### 검증 (실 서버 + 실 DB)
서버 재기동 시 `ddl-auto=update`가 기존 채팅방 2건(사용자가 이미 만들어둔 실제 데이터)에도 `max_members`를
`columnDefinition`의 DB 기본값(5)으로 정상 backfill함을 `SELECT`로 확인(만약 컬럼에 기본값을 안 줬다면
기존 행이 있는 테이블에 NOT NULL 컬럼을 추가하는 `ALTER TABLE`이 실패했을 것). throwaway 회원 4명으로:
최대 2명 방 생성 → 2번째 회원 입장(성공, 2/2 꽉 참) → 3번째 회원 입장 시도(`409 CHAT_ROOM_FULL` 정상 거부)
→ 이미 활성 참가자인 1번째 회원이 다시 `join` 호출(정원 체크 없이 성공 확인) → 2번째 회원이 나간 뒤 3번째
회원 입장 시도(자리가 열려 성공) 까지 순서대로 라이브 검증 완료. 검증 스크립트/데이터는 확인 후 삭제.
