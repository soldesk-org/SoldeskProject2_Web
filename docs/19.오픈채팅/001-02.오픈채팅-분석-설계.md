# 오픈채팅 - 분석 및 설계
------------------------------------------------------------------------
[001-01.오픈채팅-요청사항.md](001-01.오픈채팅-요청사항.md) 기반 분석/설계 문서
작업 영역: Back-end (Spring Boot, WebSocket/STOMP 최초 도입)

------------------------------------------------------------------------
## 1. 아키텍처
------------------------------------------------------------------------
```
com.foodtrip.foodsearch.chat
 ├─ entity       ChatRoom, ChatRoomMember, ChatMessage, ChatReport
 ├─ repository   ChatRoomRepository, ChatRoomMemberRepository, ChatMessageRepository, ChatReportRepository
 ├─ service      ChatRoomService(방 생성/참가/목록/나가기/폭파), ChatMessageService(메시지 검증/저장),
 │               ChatReportService(신고), AdminChatService(관리자용), JoinCodeGenerator
 ├─ controller   ChatRoomController(REST), ChatMessageController(STOMP), ChatReportController(REST)
 ├─ config       ChatWebSocketConfig (STOMP 엔드포인트/브로커 설정)
 └─ security     ChatStompAuthInterceptor, StompPrincipal
```
방 생성/참가/목록/신고 같은 "상태를 바꾸는 액션"은 기존과 동일하게 REST로, 실시간 메시지 송수신만 STOMP로
분리했다 — 이 프로젝트의 다른 기능들과 최대한 같은 모양(REST + JSON + Authorization 헤더)을 유지하면서,
정말로 실시간이 필요한 부분(메시지 브로드캐스트)에만 WebSocket을 쓰는 구조.

관리자 기능은 별도 `AdminChatService`로 분리했지만 `AdminController`가 기존 `AdminReportService`와
나란히 주입받아 같은 컨트롤러/같은 "신고 관리" 화면 영역에서 노출한다(001-01 "신고 리스트에 저거들도
들어가게 나눠놔야" 요청 반영).

## 2. 핵심 설계 결정
------------------------------------------------------------------------
### 2-1. WebSocket을 이 프로젝트 최초로 도입 (오픈채팅 전용)
지금까지 이 프로젝트는 순수 REST API만 있었다. 실시간 메시지 브로드캐스트는 REST 폴링으로 흉내 낼 수도
있지만 "실시간 채팅 (Socket)"이 명시적 요청이라 WebSocket(STOMP)을 새로 도입했다. `spring-boot-starter-
websocket` 의존성을 추가하고, `/ws-chat` 엔드포인트 하나만 등록했다(다른 기능이 실시간 통신을 아직 쓸 일이
없어 이 기능 전용으로만 - CLAUDE.md 2장 "필요한 만큼만" 원칙을 인프라 도입에도 그대로 적용).

### 2-2. 참가코드 설계
"6자리 또는 8자리(영문 숫자 섞인), 랜덤" 요청을 그대로 반영 — `JoinCodeGenerator`가 영문 대문자+숫자
알파벳(`ABCDEFGHJKMNPQRSTUVWXYZ23456789`, 32자)에서 무작위로 뽑아 만든다. `0/O`, `1/I/L`처럼 사람이 직접
타이핑할 때 헷갈리기 쉬운 문자는 후보에서 아예 뺐다(카카오톡 오픈채팅 초대코드도 이런 방식을 씀). 기본
길이는 8자리(32^8 ≈ 1조 가지, 6자리보다 엔트로피가 커서 기본값으로 선택)로 하되 6자리도 지원하도록
`generateUnique(int length)`를 열어뒀다(REST API 자체는 기본값만 사용, 나중에 길이를 선택하게 하려면
DTO에 파라미터만 추가하면 됨). DB에 이미 있는 코드와 우연히 겹치면 최대 10번 재시도한다.

### 2-3. STOMP 인증 - REST의 resolveMemberId와 다른 방식이 필요했음
REST API들은 매 요청마다 `Authorization` 헤더를 각 서비스가 직접 파싱하는 `resolveMemberId()` 패턴을
복제해서 써왔다(CLAUDE.md 2장). WebSocket은 세션 하나가 여러 메시지를 주고받으므로 매번 인증할 필요가
없다 — 대신 최초 STOMP `CONNECT` 프레임 한 번만 인증하고, 세션에 `Principal`(memberId)을 심어서 이후
`@MessageMapping` 메서드들이 그대로 꺼내 쓰게 했다. `ChatStompAuthInterceptor`(`ChannelInterceptor`)가
CONNECT 프레임의 커스텀 헤더 `Authorization`(REST와 같은 `Bearer {accessToken}` 형식)을 검증하고,
무효하면 연결 자체를 거부한다. REST의 `resolveMemberIdOrNull`처럼 "익명 허용"은 채팅에는 의미가 없어서
만들지 않았다 — 오픈채팅은 항상 로그인이 필요하다.

### 2-4. 방 폭파 - 상태 전환 + 메시지 물리 삭제 + 실시간 알림
"채팅방 방 폭파" 요청을 카카오톡의 "채팅방 나가기"보다 강한 의미(대화 내용 자체가 사라짐)로 해석해서,
`ChatRoom.explode()`가 상태를 CLOSED로 바꾸는 동시에 `chatMessageRepository.deleteByChatRoomId()`로 그
방의 메시지를 전부 물리 삭제한다. 방장(host)만 가능(`CHAT_ROOM_ACCESS_DENIED` 403). 방 자체(row)는 남겨서
신고 이력이 참조하는 `chat_room_id`가 계속 유효하게 하고, 폭파 시 `SimpMessagingTemplate`로
`/topic/rooms/{roomId}`에 `SYSTEM` 타입 메시지("방장이 채팅방을 폭파했습니다")를 브로드캐스트해서 접속
중인 클라이언트들이 즉시 알 수 있게 했다. 신고된 메시지의 증거는 `ChatReport.reportedContentSnapshot`에
신고 시점 내용을 복사해두므로, 나중에 방이 폭파돼도 남는다(2-9장).

관리자도 같은 이유(신고된 방을 강제로 폭파)로 `AdminChatService.explodeRoom()`을 통해 같은 로직을 호출할
수 있다 — `ChatRoomService.adminExplodeRoom()`이 방장 소유권 체크만 건너뛰고 나머지(메시지 삭제, 시스템
알림)는 동일하게 재사용한다.

### 2-5. 클린봇 - 17(리뷰-필터링)의 ReviewFilterClient 재사용
"korcen도 해서 검열도 하고"라는 요청에, 새 Python 서버나 새 Java 클라이언트를 만드는 대신 17에서 이미
만든 `com.foodtrip.foodsearch.reviewfilter.client.ReviewFilterClient`를 그대로 채팅 메시지 검사에도
재사용했다 — 그 클라이언트는 "텍스트 하나 → 욕설 여부(bool)"라는 범용 동작이라 리뷰 도메인에 묶여있지
않고, 패키지 이름(`reviewfilter`)과 무관하게 재사용 가능하다고 판단(억지로 `chatfilter`라는 이름의 거의
동일한 클라이언트를 새로 만드는 것보다 중복을 피하는 쪽을 선택). 17과 동일하게 fail-open — 필터
Python 서버(`review-filter`, 포트 8002)가 꺼져 있으면 검사를 건너뛰고 메시지를 통과시킨다(핵심 기능인
채팅 자체가 부가 기능 장애로 막히면 안 된다는 같은 원칙).

### 2-6. STOMP 예외 처리 - GlobalExceptionHandler를 못 타므로 컨트롤러가 직접 처리
REST는 `@RestControllerAdvice`(`GlobalExceptionHandler`)가 `CustomException`을 표준 JSON 에러로 자동
변환해주지만, STOMP `@MessageMapping`은 이 흐름을 타지 않는다. 그래서 `ChatMessageController.send()`가
`ChatMessageService.sendMessage()`가 던지는 `CustomException`을 직접 잡아서, 방 전체가 아니라 **보낸
사람에게만** `/user/queue/errors`로 에러를 돌려준다(`SimpMessagingTemplate.convertAndSendToUser`) — 다른
참가자들은 실패한 메시지 자체를 아예 모른다(클린봇에 걸린 메시지가 다른 사람에게 잠깐이라도 보이지
않도록 하는 것이 목적).

### 2-7. 메시지 조회 범위 - 최근 50건, 페이지네이션 없음
방에 입장할 때(`GET /api/chat/rooms/{roomId}/messages`)는 최근 50건만 오래된 순으로 반환한다. 오픈채팅은
"지금 여기서 대화"가 핵심이라, 과거 전체 이력을 무한 스크롤로 불러오는 기능까지는 이번 범위에 넣지
않았다(001-01 "이번 범위에서 제외된 것" 참고) — 필요해지면 나중에 `createdAt` 기준 커서 페이지네이션을
추가할 수 있는 구조(리포지토리 메서드 하나만 바뀌면 됨).

### 2-8. 시스템 메시지 타입 (SYSTEM)
`ChatMessageResponseDto`에 `type` 필드(`MESSAGE`/`SYSTEM`)를 둬서, 방 폭파 같은 서버 발 공지와 실제 회원이
보낸 메시지를 프론트가 구분해서 다르게 렌더링할 수 있게 했다(`chat-test.html`에서는 SYSTEM을 화면
가운데 빨간 안내 문구로 표시). SYSTEM 메시지는 DB에 저장되지 않는다(휘발성 알림일 뿐, 대화 기록이
아니라고 판단).

### 2-9. 신고 데이터 모델 - 방/메시지 통합 엔티티, 그룹핑 없음 (16.리뷰-신고와의 차이)
"그 채팅 또는 그 채팅방 둘 다 신고 가능하게" 요청을 하나의 `ChatReport` 엔티티로 처리한다 —
`targetType`(ROOM/MESSAGE)으로 구분하고, `chatMessageId`는 방 신고일 땐 null이다. `chatRoomId`는 메시지
신고여도 항상 채워서(그 메시지가 속한 방) 관리자 화면에서 방 제목을 같이 보여줄 수 있게 했다. DB UNIQUE
제약으로 중복 신고를 막고 싶었지만 `chat_message_id`가 null일 수 있어(MariaDB는 NULL을 서로 다른 값으로
취급해 UNIQUE가 안 먹음) 애플리케이션 레벨에서 직접 중복 여부를 확인한다(`existsBy...`).

16(리뷰-신고)은 관리자 목록을 "신고 대상별로 묶어서"(리뷰 1개 = 신고 여러 건을 합쳐 1행) 보여주지만,
이번엔 그렇게 하지 않고 **신고 1건 = 1행**으로 그대로 노출한다 — 오픈채팅은 아직 신고 볼륨이 낮을 것으로
예상되고, 굳이 리뷰처럼 그룹핑 로직을 만들 필요가 없다고 판단했다(필요해지면 나중에 리뷰와 같은 방식으로
바꿀 수 있음, 001-04에도 명시).

### 2-10. 신고 사유는 16의 ReportReasonCatalog를 그대로 재사용
채팅용 신고 사유를 새로 만들지 않고 `com.foodtrip.foodsearch.report.service.ReportReasonCatalog`(SPAM/
ABUSE/FALSE_INFO/PRIVACY/ETC)와 `CreateReportRequestDto`를 그대로 재사용했다 — 신고 사유는 도메인(리뷰냐
채팅이냐)과 무관하게 보편적인 목록이라 판단.

### 2-11. 후속 추가(2026-07-24, 같은 날) — 신고 사유 한글 표시 + 관리자 삭제의 실시간 반영
두 가지를 추가로 요청받아 구현:

**신고 사유 한글 라벨링**: `admin-test.html`의 신고 관리 화면(리뷰 신고 + 채팅 신고 둘 다)이 `reasonCode`
값(`SPAM`, `ABUSE` 등 영문 상수)을 그대로 화면에 노출하고 있어서, 회원이 보기 불편하다는 지적으로
한글 라벨로 바꿨다. 백엔드 `reasonCode` 자체(API 요청/저장/코드 로직)는 계속 영문 상수 그대로 두고,
`admin-test.html`에 `REASON_LABELS` 매핑(순수 표시용 JS 객체)만 추가해서 화면에 보여줄 때만 한글로
바꾼다 — 데이터 모델은 안 건드리고 프레젠테이션 레이어에서만 처리(다국어 지원이 필요해지면 이 매핑 하나만
확장하면 됨).

**관리자 메시지 삭제의 실시간 반영**: 기존엔 관리자가 `DELETE /api/admin/chat-messages/{id}`로 메시지를
지워도 DB에서만 사라질 뿐, 그 방을 보고 있는 다른 참가자의 화면에는 실시간으로 반영되지 않았다(새로고침
해야만 사라짐 - 사실상 놓치기 쉬운 허점이었음, 사용자가 실제로 신고→관리자 삭제를 해보고 지적해서 발견).
`ChatMessageResponseDto`에 `DELETED` 타입을 추가하고(`chatMessageId`만 채워서 보냄), `AdminChatServiceImpl.
deleteMessage()`가 DB 삭제 직후 `/topic/rooms/{roomId}`에 이 이벤트를 브로드캐스트하도록 수정했다 — 방
폭파 시 이미 쓰고 있던 `SimpMessagingTemplate` 브로드캐스트(2-4장)와 같은 패턴을 재사용. 접속 중인
클라이언트(`chat-test.html`)는 이 이벤트를 받으면 새 말풍선을 추가하는 대신, 이미 그려져 있는 그
`chatMessageId`의 말풍선을 찾아 "(관리자에 의해 삭제된 메시지입니다)"로 바꾼다(완전히 지우지 않고
삭제됐다는 사실 자체는 남겨서 대화 흐름이 끊기지 않게 함 - 카카오톡이 "삭제된 메시지입니다"를 남기는
방식과 같은 톤).

방 폭파(explode)는 이미 2-4장에서 시스템 메시지 브로드캐스트로 실시간 반영이 되고 있었으므로 이번엔
손대지 않음 - 이번 수정은 단일 메시지 삭제 경로에만 있던 공백을 메운 것.

### 2-12. 후속 추가 3(2026-07-24, 같은 날) — 방 폭파 시 목록에서 숨기기 + 접속자 강제 퇴장
기존 2-4장 설계는 방을 폭파해도 "이력 조회 목적"으로 `GET /api/chat/rooms/my` 목록에 "폭파됨" 배지를 달고
계속 남겨뒀고, 접속 중인 클라이언트는 시스템 메시지(`SYSTEM` 타입)로 안내만 받을 뿐 방에 계속 머물러
있었다. 사용자가 "방 폭파 된건 내 채팅방에서 안보이게, 실시간 방 폭파 그거 소켓으로 하는건 그 사람들
거기서 튕겨져서 메인 화면으로 나가지게 해줘야 해"로 두 가지를 명확히 요구해서 반영:

**목록에서 완전히 숨김**: `ChatRoomServiceImpl.listMyRooms()`에 `.filter(ChatRoom::isOpen)`을 추가해
CLOSED 상태 방은 아예 응답에서 빠진다 — "이력 조회" 용도는 이번 요청으로 폐기, 단순하게 "지금 참가 중인
열린 방만" 보여주는 목록으로 바뀌었다.

**실시간 강제 퇴장**: 기존 `TYPE_SYSTEM`(범용 안내, 안내만 하고 클라이언트가 그 방에 남아있어도 되는
타입)과 "이 방은 폭파됐으니 무조건 나가야 한다"는 의미가 섞여 있던 게 문제였다 - 방 폭파 전용
`TYPE_ROOM_CLOSED`를 새로 분리해서 `doExplode()`(방장 폭파/관리자 강제 폭파 공통 경로, 2-4장)가 이 타입으로
브로드캐스트하도록 바꿨다. 클라이언트(`chat-test.html`)는 `ROOM_CLOSED`를 받으면 안내(alert) 후 즉시
`leaveActiveRoomView()`(구독 해제 + 메인 빈 화면 전환)를 호출하고 방 목록을 다시 불러온다(방금 필터가
추가됐으니 자연스럽게 목록에서 사라짐) — 방장이 직접 폭파를 눌렀을 때도 방장 자신의 클라이언트가 그 방을
구독 중이므로 같은 소켓 이벤트로 정리되고, REST 응답 콜백에서 별도로 화면을 정리하지 않는다(소켓 이벤트
하나로 방장/참가자 모두 동일하게 처리 - 단일 경로 유지).

### 2-13. 후속 추가 4(2026-07-24, 같은 날) — 방 최대 인원 제한
"최대 인원이 들어갈 수 있는 수를 우리가 임의로 정하도록 해주게 해줘 5명으로 최대" 요청 — 카카오톡
오픈채팅처럼 방마다 인원 제한을 걸 수 있게 했다. `ChatRoom.maxMembers`(신규 컬럼) 추가, 방 생성 API에
선택적 `maxMembers` 파라미터(2~50명 범위 검증)를 받아 지정하지 않으면 `ChatRoom.DEFAULT_MAX_MEMBERS`(5명)가
적용된다 - "우리가 임의로 정하도록"을 "방 만들 때 원하는 값을 넣을 수 있게, 기본은 5명"으로 해석했다.

`joinRoom()`에서 이미 활성 참가자(재입장/중복 호출)는 새 자리를 차지하는 게 아니므로 정원 체크를
건너뛰고, 그 외의 경우에만 현재 활성 인원(`countByChatRoomIdAndLeftAtIsNull`)이 `maxMembers` 이상이면
`409 CHAT_ROOM_FULL`로 거부한다. 누군가 나가면(`leaveRoom()`) 자리가 다시 열려서 다음 사람이 들어올 수
있다.

기존 데이터(이미 있던 채팅방들) 때문에 `ALTER TABLE`이 실패하지 않도록, JPA 컬럼에
`columnDefinition = "INT DEFAULT 5"`를 직접 지정해 기존 행도 5명으로 자동 채워지게 했다(`ddl-auto=update`가
NOT NULL 컬럼을 기본값 없이 추가하려 하면 이미 데이터가 있는 테이블에서 실패하기 때문).

## 3. API 설계
------------------------------------------------------------------------
### 3-1. 채팅방 REST API
```
POST   /api/chat/rooms                    방 생성 (title, maxMembers 선택 - 기본 5명)
POST   /api/chat/rooms/join               참가코드로 입장 (joinCode)
GET    /api/chat/rooms/my                 내 채팅방 목록
GET    /api/chat/rooms/{roomId}/messages  최근 메시지 50건(오래된 순)
POST   /api/chat/rooms/{roomId}/leave     나가기
DELETE /api/chat/rooms/{roomId}           방 폭파 (방장만)
```
전부 `Authorization: Bearer {accessToken}` 필수.

### 3-2. 신고 REST API
```
POST /api/chat/rooms/{roomId}/report      채팅방 신고 (reasonCode, detail)
POST /api/chat/messages/{messageId}/report 메시지 신고 (reasonCode, detail)
```

### 3-3. 실시간 메시지 (STOMP over WebSocket)
```
접속:     ws://localhost:8081/ws-chat
CONNECT 헤더: Authorization: Bearer {accessToken}   (필수, 없으면 연결 거부)

전송(publish): /app/rooms/{roomId}/send   { "content": "..." }
구독(subscribe): /topic/rooms/{roomId}     방 전체 브로드캐스트(메시지 + 시스템 알림)
구독(subscribe): /user/queue/errors        본인에게만 오는 에러(클린봇에 걸림, 방에 없음 등)
```

### 3-4. 관리자 API (신규, `/api/admin/**` - 14의 ADMIN 권한 그대로 적용)
```
GET    /api/admin/chat-reports?status=PENDING   채팅 신고 목록(기본 PENDING)
PATCH  /api/admin/chat-reports/{id}/resolve     처리 완료
PATCH  /api/admin/chat-reports/{id}/reject      반려
DELETE /api/admin/chat-messages/{messageId}     메시지 강제 삭제
DELETE /api/admin/chat-rooms/{roomId}           방 강제 폭파
```
