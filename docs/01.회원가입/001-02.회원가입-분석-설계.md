## 1. 요구사항 정리
------------------------------------------------------------------------
- 입력값: 이메일, 비밀번호, 닉네임, 전화번호
- 비밀번호 등 민감정보는 Argon2 단방향 해시로 저장 (복호화 불가)
- **전화번호는 나중에 다시 사용할 일이 있어(예: 이메일/아이디 찾기) 단방향이 아니라 AES-256-GCM 양방향 암호화로 저장** (2026-07-18 요구사항 문서 갱신, 7-1장 참고)
- 이메일 인증 절차 필요, 인증번호 유효기간 5분
- 인증번호 발송은 Naver Mail(SMTP)로 발송
- **전화번호도 SMS 인증번호로 본인 소유 확인 절차 추가** (2026-07-18 요구사항 문서 갱신, 8-1장 참고) — 뿌리오(Ppurio) 연동, 이메일 인증과 동일하게 최종 가입 전에 인증을 완료해야 함
- **비밀번호는 "비밀번호"/"비밀번호 확인" 두 값을 입력받아 서로 일치하는지 검증** (2026-07-19 코드 리뷰로 발견된 누락 항목 반영, 8-2장 참고) — 회원가입 화면에 비밀번호 재입력 칸이 있는 것을 전제로 함
- **일반 회원가입과 별개로 사업자 회원가입을 분리** (2026-07-19 요구사항 추가, 13장 참고) — 입력값은 일반 회원과 동일 + 사업자등록증명원 파일 업로드가 추가되고, 별도 Python(FastAPI) 서버로 OCR+원본확인+진위확인까지 통과해야 가입이 완료됨. 이메일/전화번호 인증, 비밀번호 암호화는 일반 회원가입과 완전히 동일한 절차 재사용. 로그인은 일반 회원과 동일한 API를 그대로 쓰되, 발급되는 JWT의 `role` 클레임으로 구분됨(로그인 자체의 코드 변경 없음)
- 프론트 연결 없음 → REST API + Postman/테스트 코드로 검증

## 2. 전체 플로우
------------------------------------------------------------------------
※ [DB-테이블설계.md](../00.공통/DB-테이블설계.md)의 `email_verifications.member_id`가 NOT NULL FK이므로,
   인증번호를 발급하는 시점에 members row가 먼저 존재해야 함 → 아래와 같이 순서 조정

1) 이메일 인증번호 요청
   - 클라이언트가 이메일 입력
   - 해당 이메일로 이미 가입된 members가 있으면 DUPLICATE_EMAIL 에러
   - members row를 우선 생성(email만 확정, nickname/phone은 임시값 또는 이후 단계에서 채움, status='ACTIVE')
   - 6자리 인증번호 생성 → email_verifications에 member_id/email/verification_code/expired_at(5분 후) 저장
   - Naver SMTP로 메일 발송
2) 이메일 인증번호 확인
   - 클라이언트가 이메일 + 인증번호 입력
   - email_verifications에서 해당 member_id의 최신 레코드 조회 → 일치/만료 여부 검증
   - 검증 성공 시 is_verified=1, verified_at=now() 처리
3) 전화번호 SMS 인증번호 요청 (2026-07-18 요구사항 추가, 8-1장 참고)
   - 클라이언트가 이메일(1번에서 인증 완료된 이메일) + 전화번호 입력
   - 이메일로 members 조회, 해당 member의 email_verifications가 is_verified=1인지 확인(미인증이면 거부)
   - 6자리 인증번호 생성 → phone_verifications에 member_id/phone/verification_code/purpose='SIGNUP'/expired_at(5분 후) 저장
   - Ppurio SMS API로 발송
4) 전화번호 SMS 인증번호 확인
   - 클라이언트가 이메일 + 전화번호 + 인증번호 입력
   - 해당 member_id의 phone_verifications(purpose='SIGNUP') 최신 레코드 조회 → 전화번호/코드 일치, 만료 여부 검증
   - 검증 성공 시 is_verified=1, verified_at=now() 처리
5) 회원가입 요청(최종 정보 입력)
   - 이메일, 비밀번호, 비밀번호 확인, 닉네임, 전화번호 입력
   - 비밀번호와 비밀번호 확인이 다르면 가입 거부 (2026-07-19 요구사항 추가, 8-2장 참고 — DB 조회 없이 가장 먼저 확인)
   - 이메일로 members를 조회 → 해당 member의 email_verifications가 is_verified=1 상태인지 확인 (미인증이면 가입 거부)
   - 해당 member의 phone_verifications(purpose='SIGNUP')가 is_verified=1이고, 그 phone 값이 이번 요청의 phone과 동일한지 확인 (미인증이거나 인증된 번호와 다른 번호를 제출하면 가입 거부, 8-1장 참고)
   - 닉네임/전화번호 중복 확인(정책상 필요 시)
   - members.nickname, members.phone 갱신
   - 비밀번호 Argon2 해시 후 member_credentials에 저장(1:1)
   - 회원가입 완료

## 5. API 설계
------------------------------------------------------------------------
### 5-1. 이메일 인증번호 발송
POST /api/mail/send-code
Request  : { "email": "user@naver.com" }
Response : { "success": true, "message": "인증번호가 발송되었습니다." }
처리 :
 - 이메일 형식 검증
 - members에 동일 email이 이미 존재하면 DUPLICATE_EMAIL 에러
 - members row 신규 생성(email만 확정, nickname/phone은 가입 완료 전까지 임시값, status='ACTIVE', role='USER')
 - 6자리 랜덤 숫자 코드 생성
 - Naver SMTP로 메일 발송
 - email_verifications에 member_id/email/verification_code/expired_at(now+5분) 저장

### 5-2. 이메일 인증번호 확인
POST /api/mail/verify-code
Request  : { "email": "user@naver.com", "code": "123456" }
Response : { "success": true, "message": "이메일 인증이 완료되었습니다." }
처리 :
 - email로 members 조회 → 없으면 EMAIL_NOT_FOUND 에러
 - 해당 member_id의 email_verifications 최신 레코드 조회
 - 만료시간 초과 시 EXPIRED_CODE 에러
 - 코드 불일치 시 INVALID_CODE 에러
 - 일치 시 is_verified=1, verified_at=now() 처리

### 5-2-1. 전화번호 SMS 인증번호 발송 (2026-07-18 요구사항 추가)
POST /api/phone/send-code
Request  : { "email": "user@naver.com", "phone": "010-1234-5678" }
Response : { "success": true, "message": "인증번호가 발송되었습니다." }
처리 :
 - 전화번호 형식 검증
 - email로 members 조회 → 없으면 EMAIL_NOT_FOUND, 해당 member의 email_verifications 미인증이면 EMAIL_NOT_VERIFIED
 - 6자리 랜덤 숫자 코드 생성
 - Ppurio SMS API로 발송 ([00.공통 가이드](../00.공통/SMS-인증-Ppurio-연동-가이드.md) 참고)
 - phone_verifications에 member_id/phone/verification_code/purpose='SIGNUP'/expired_at(now+5분) 저장

### 5-2-2. 전화번호 SMS 인증번호 확인
POST /api/phone/verify-code
Request  : { "email": "user@naver.com", "phone": "010-1234-5678", "code": "123456" }
Response : { "success": true, "message": "전화번호 인증이 완료되었습니다." }
처리 :
 - email로 members 조회 → 없으면 EMAIL_NOT_FOUND
 - 해당 member_id + purpose='SIGNUP'의 phone_verifications 최신 레코드 조회 → 없으면 PHONE_NOT_FOUND
 - phone 값이 요청의 phone과 다르면(발송 이후 전화번호를 바꿔 재요청한 경우) PHONE_NOT_FOUND로 처리(다시 발송부터)
 - 만료시간 초과 시 EXPIRED_CODE, 코드 불일치 시 INVALID_CODE
 - 일치 시 is_verified=1, verified_at=now() 처리

### 5-3. 회원가입
POST /api/members/signup
Request:
{
  "email": "user@naver.com",
  "password": "P@ssw0rd!",
  "passwordConfirm": "P@ssw0rd!",
  "nickname": "홍길동",
  "phone": "010-1234-5678"
}
Response : { "success": true, "message": "회원가입이 완료되었습니다.", "memberId": 1 }
처리 :
 - 입력값 유효성 검사 (이메일 형식, 비밀번호 규칙, 닉네임/전화번호 형식, `passwordConfirm` 필수값)
 - `password`와 `passwordConfirm`이 다르면 PASSWORD_CONFIRM_MISMATCH 에러 (2026-07-19 요구사항 추가, 8-2장 참고) — 다른 검증보다 먼저 확인해 이메일/전화번호 인증 여부와 무관하게 즉시 알려줌
 - email로 members 조회 → 없으면 EMAIL_NOT_FOUND 에러
 - 해당 member의 email_verifications가 is_verified=1 상태인지 확인 (아니면 EMAIL_NOT_VERIFIED 에러)
 - 해당 member의 phone_verifications(purpose='SIGNUP')가 is_verified=1이고 그 phone이 이번 요청의 phone과 동일한지 확인 (아니면 PHONE_NOT_VERIFIED 에러, 2026-07-18 요구사항 추가)
 - 이미 member_credentials가 존재하면 ALREADY_SIGNED_UP 에러(재가입 방지)
 - nickname/phone 중복 확인 (DUPLICATE_NICKNAME, DUPLICATE_PHONE)
 - members.nickname, members.phone 갱신
 - password → Argon2 해시 변환 후 member_credentials 신규 저장(member_id 1:1) — `passwordConfirm`은 검증에만 쓰이고 저장하지 않음

## 6. 검증 규칙
------------------------------------------------------------------------
- 이메일: 형식 검증(RFC 형식), 최대 100자
- 비밀번호: 8~20자, 영문/숫자/특수문자 조합 (정책은 추후 조정 가능)
- 비밀번호 확인(`passwordConfirm`): 필수값, `password`와 정확히 일치해야 함 (2026-07-19 요구사항 추가, 8-2장 참고)
- 닉네임: 2~10자, 특수문자 제한
- 전화번호: 010-XXXX-XXXX 형식, 숫자만 저장할지 하이픈 포함할지 결정 필요
- 인증번호: 숫자 6자리, 만료시간 5분

## 7. Argon2 암호화 설계
------------------------------------------------------------------------
- Spring Security Crypto의 Argon2PasswordEncoder 사용 (org.springframework.security.crypto.argon2)
- 파라미터 예시: saltLength=16, hashLength=32, parallelism=1, memory=1<<16(=65536KB), iterations=3
  (서버 성능에 맞춰 memory/iterations 조정 필요)
- PasswordEncoder를 Bean으로 등록하여 MemberService에서 주입받아 사용
- 저장 형식은 Argon2PasswordEncoder가 자체적으로 salt+파라미터를 포함한 인코딩 문자열을 생성하므로 별도 salt 컬럼 불필요
- 해시 결과는 member_credentials.password_hash 컬럼에 저장 (해당 컬럼 주석은 원래 BCrypt로 되어 있었으나 본 프로젝트는 Argon2로 통일)

## 7-1. 전화번호 AES-256-GCM 양방향 암호화 설계 (2026-07-18 요구사항 추가)
------------------------------------------------------------------------
비밀번호(Argon2)와 달리 전화번호는 **나중에 평문으로 다시 꺼내 써야 할 수 있어서**(예: 향후 "이메일/아이디 찾기" 기능에서 사용자가 입력한 전화번호와 대조) 단방향 해시가 아니라 **양방향 암호화**가 필요함.

### 문제: 암호화하면서 중복 확인/조회는 어떻게 하는가
AES-GCM은 매번 랜덤 IV(nonce)를 써야 안전한데(같은 키+IV 재사용은 치명적 취약점), 그러면 **같은 전화번호를 암호화해도 매번 다른 암호문**이 나온다. 지금은 `members.phone`에 DB UNIQUE 제약을 걸어 중복 가입을 막고 있는데(001-03 3-2장), 암호문이 매번 달라지면 이 UNIQUE 제약도, `existsByPhone()` 중복 조회도 더 이상 동작하지 않는다.

**해결: 암호화(복원용)와 해시(조회/중복확인용)를 분리해서 둘 다 저장**
- `phone` 컬럼: AES-256-GCM으로 암호화한 값(Base64) — 나중에 평문이 필요할 때 복호화해서 꺼내 쓰는 용도
- `phone_hash` 컬럼(신규): HMAC-SHA256으로 만든 **결정적(deterministic)** 해시값(hex) — 같은 전화번호는 항상 같은 해시가 나오므로, 이 컬럼에 UNIQUE 제약을 걸고 중복 확인/조회는 전부 이 컬럼으로 함
- 비밀번호 해시(Argon2)와의 차이: Argon2는 매번 다른 salt가 섞여 같은 비밀번호도 해시값이 다르게 나오지만(그래서 "그 자체로 조회 불가"), 여기서 쓰는 HMAC은 의도적으로 salt 없이 고정 키만 써서 **항상 같은 입력 → 같은 출력**이 나오게 함 (조회 가능해야 하므로)

### 키 관리
- AES 키(`PHONE_AES_KEY`)와 HMAC 키(`PHONE_HASH_KEY`)는 **서로 다른 키**를 사용 (하나의 키를 암호화와 해시 양쪽에 재사용하지 않는 것이 암호학적으로 안전한 관행)
- 둘 다 256비트(32바이트) 랜덤 값을 Base64로 인코딩해서 `.env`에 저장, `JWT_SECRET`과 동일한 패턴으로 애플리케이션에 주입
- 이 키가 유출되면 저장된 모든 전화번호가 복호화될 수 있으므로, `.env`와 동일하게 절대 커밋하지 않음

### 암호화 방식 상세
- 알고리즘: `AES/GCM/NoPadding`, 키 길이 256비트
- IV(nonce): 12바이트(96비트), 암호화할 때마다 `SecureRandom`으로 새로 생성 — GCM 권장 표준 길이
- 인증 태그: 128비트 (Java `Cipher`의 GCM 기본값)
- 저장 형식: `Base64(IV(12바이트) + 암호문+태그)` — IV를 암호문 앞에 붙여서 한 컬럼에 같이 저장 (복호화할 때 앞 12바이트를 IV로 다시 분리)
- `phone` 컬럼 길이: 기존 `VARCHAR(20)`(평문 기준)로는 암호문이 안 들어가서 `VARCHAR(255)`로 확장 필요

### 해시 방식 상세
- 알고리즘: `HmacSHA256`
- 입력: 검증 규칙을 통과한 전화번호 원문 그대로(`010-XXXX-XXXX` 형식, 정규화 불필요 — 이미 형식이 하나로 고정되어 있어서)
- 출력: hex 문자열(64자) → `phone_hash` 컬럼(VARCHAR(64), UNIQUE)

### 영향받는 기존 코드
- `MemberRepository.existsByPhone(String)` → `existsByPhoneHash(String)`로 변경 (평문이 아니라 해시로 조회)
- `MemberServiceImpl.signUp()`: 전화번호 중복 확인 전에 먼저 해시를 계산해야 함
- DB UNIQUE 제약: 기존 `phone` 컬럼의 UNIQUE는 제거(암호문은 어차피 매번 달라서 의미 없음), `phone_hash`에 새로 UNIQUE 추가
- 레이스 컨디션 방어(001-03 3-2장에서 만든 `saveAndFlush` + 제약이름 판별 로직)의 제약 이름도 `uk_members_phone` → `uk_members_phone_hash`로 변경 필요
- API 요청/응답 형식(001-04 연동 가이드)은 **변경 없음** — 클라이언트는 여전히 평문 전화번호를 그대로 보내면 되고, 암호화/해시는 서버 내부에서만 처리됨

## 8-1. SMS 전화번호 인증 설계 (Ppurio 연동, 2026-07-18 요구사항 추가)
------------------------------------------------------------------------
전화번호도 이메일처럼 실제로 본인 소유인지 SMS 인증번호로 확인하는 절차를 추가함. 연동 대상은 뿌리오(Ppurio) BizAPI.

### 왜 필요한가
기존에는 전화번호를 입력만 받고 검증하지 않아, 실제로 본인 것이 아닌 전화번호로도 가입이 가능했다. 전화번호는 이메일 찾기(닉네임+전화번호 조합 조회)와 향후 SMS 기반 본인인증(001-02(이메일찾기) 12장)에 쓰이는 핵심 식별값이라, 가입 시점에 실소유를 확인해두지 않으면 이 두 기능의 신뢰도가 떨어진다.

### 연동 방식 요약 (상세는 [00.공통/SMS-인증-Ppurio-연동-가이드.md](../00.공통/SMS-인증-Ppurio-연동-가이드.md) 참고)
- 토큰 발급(`POST /v1/token`, Basic 인증, 24시간 유효) → Redis에 캐싱(`ppurio:token`, TTL 23시간)
- SMS 발송(`POST /v1/message`, Bearer 토큰, 2026-07-20 정정 — 예전엔 `/v3/message`로 잘못 적혀 있었음) — 발신번호는 `070-5236-4828`로 확정(`PPURIO_SENDER_NUMBER`)
- 메시지 포맷: 네이티브 안드로이드 앱이 없으므로 `<#>`+해시 접미사 없이 일반 텍스트로 발송, 2026-07-20 실사용자 라이브 테스트 후 가독성을 위해 3줄로 줄바꿈(`[Eattyway]` / `본인확인 인증번호는 [123456]입니다.` / `5분 이내에 입력해주세요.`)
- 인증번호 생성/검증 로직(6자리, 5분 유효)은 기존 이메일 인증(`EmailVerification`/`EmailAuthService`)과 완전히 동일한 패턴을 `phone` 패키지에 그대로 미러링(4-4장, 5-2-1/5-2-2장)

### 회원가입 플로우에서의 위치
이메일 인증(2단계) 이후, 최종 가입 요청(5단계) 이전에 전화번호 SMS 인증(3~4단계)을 끼워 넣는다(2장 전체 플로우 참고). 최종 가입 시점에는 이메일 인증뿐 아니라 **전화번호 인증도 완료되어 있어야** 하고, 인증된 전화번호와 최종 제출한 전화번호가 같아야 한다(발송 이후 다른 번호로 바꿔 제출하는 것을 막기 위함) — 이는 기존 이메일 인증 검증 로직(`EMAIL_NOT_VERIFIED` 체크)과 대칭되는 `PHONE_NOT_VERIFIED` 체크를 `signUp()`에 추가하는 것으로 구현

### 기존 코드에 미치는 영향
- `MemberServiceImpl.signUp()`: `EMAIL_NOT_VERIFIED` 체크 다음에 `PHONE_NOT_VERIFIED` 체크 추가 (phone_verifications 최신 레코드의 `is_verified`와 `phone` 값 확인)
- `phone` 패키지(컨트롤러/서비스/엔티티/레포지토리) 신규 추가 — 기존 `mail` 패키지 구조를 그대로 복제
- API 요청/응답 형식: 최종 회원가입(`POST /api/members/signup`) 요청 자체의 필드는 변경 없음(여전히 email/password/nickname/phone, `passwordConfirm` 추가는 8-2장 별개 변경) — 대신 그 이전에 `POST /api/phone/send-code`, `POST /api/phone/verify-code` 2단계가 새로 필요해짐 (001-04 연동 가이드에 반영 필요)

## 8-2. 비밀번호 확인(재입력) 검증 (2026-07-19 요구사항 추가)
------------------------------------------------------------------------
코드 리뷰(사용자가 직접 체크리스트로 확인) 중 발견된 누락 항목 — 회원가입 시 비밀번호를 한 번만 입력받고 있어서, 오타가 나도 가입 시점에는 알 수 없고 이후 로그인이 실패해야만 알아채는 문제가 있었음.

### 설계
- `SignUpRequestDto`에 `passwordConfirm` 필드 추가 (`@NotBlank`만 적용 — 형식 검증은 `password` 쪽 `@Pattern`으로 이미 하고 있으므로 중복 검증 불필요)
- `MemberServiceImpl.signUp()` 맨 앞, 다른 어떤 조회/검증보다도 먼저 `password.equals(passwordConfirm)`을 확인 — 이메일/전화번호 인증 여부, 중복 여부 같은 DB 조회가 전혀 필요 없는 가장 저렴한 체크이자, 사용자 입장에서도 가장 먼저 알아야 할 실수이므로 앞단에 배치
- 불일치 시 기존 비밀번호 재설정(001-02(이메일찾기) 5-3장)에서 이미 쓰고 있는 `PASSWORD_CONFIRM_MISMATCH` 에러코드를 그대로 재사용 (동일한 성격의 검증이라 새 코드를 만들 필요 없음). 다만 기본 메시지("새 비밀번호가 일치하지 않습니다")는 비밀번호 재설정 문맥에 맞춰진 문구라 회원가입에서는 `CustomException(ErrorCode, message)` 2-인자 생성자로 "비밀번호와 비밀번호 확인이 일치하지 않습니다."로 오버라이드해서 사용
- `passwordConfirm` 값 자체는 검증에만 쓰이고 DB에는 저장하지 않음 (실제 저장은 `password`를 Argon2로 해시한 값)

## 13. 사업자 회원가입 설계 (2026-07-19 요구사항 추가)
------------------------------------------------------------------------
일반 회원가입과 별개로 "사업자 회원가입"을 분리함. 사용자가 전달한 요구사항 원문 요약:
1. 사업자 회원가입 분리
2. 사업자 회원은 일반 회원과 동일한 값(이메일/비밀번호/닉네임/전화번호)을 받고, 거기에 더해 **사업자등록증명원 업로드**를 받아야 함
3. 사업자등록증명원 검증(OCR+원본확인+진위확인) 절차가 끝나고 성공이면 회원가입 완료. 암호화/이메일 인증/전화번호 인증은 일반 회원가입과 전부 동일하게 적용
4. 로그인은 일반 회원과 입력값/API가 동일 — role로만 구분되면 됨

### 13-1. 사업자등록증명원 검증 서버 (기존에 이미 구현되어 있음)
사업자등록증명원 OCR → 원본확인 → 진위확인을 수행하는 서버가 이 저장소와 별개로 이미 만들어져 있음: `D:\SoldeskProject2_Python\receipt-biz-verify` (Python, FastAPI). 이번 설계는 이 서버를 새로 만드는 것이 아니라, **이미 있는 `POST /verify` 엔드포인트를 그대로 호출**하는 것을 전제로 함.

`POST /verify` 처리 내용 (사용자가 설명한 7단계와 대응):
1. `file`(multipart) 업로드 받음 — PDF면 PyMuPDF로 1페이지를 이미지로 변환
2. Google Gemini(`gemini-2.5-flash`)로 이미지에서 `business_number`(사업자등록번호 10자리)/`issue_number`(발급번호 14자리)/`representative_name`/`start_date`/`company_name`/`address`(사업장 소재지) OCR 추출 — `address`는 처음부터 추출되고 있었는데 이 프로젝트(Spring) 쪽 `BusinessVerificationClient`가 안 읽고 버리고 있었음(2026-07-20 발견/수정, 13-9장 참고)
3. 국세청 홈택스 "민원증명 원본 확인" 페이지를 Playwright로 자동 조작해 발급번호+사업자등록번호로 **원본 문서인지 확인** (위변조/발급 후 90일 경과 문서를 걸러냄)
4. 원본 확인 성공 시, 국세청 사업자등록정보 진위확인 API(`odcloud.kr/api/nts-businessman`)로 **실제 유효한 사업자인지 확인**
5. 성공 시 200 + `{status: "SUCCESS", extracted: {...}, origin_check: {...}, validation: {...}}`, 실패 시 400 + `{status: "<사유코드>", message: "..."}` (또는 예상 못한 오류는 500 + `{error, message}`)

이 프로젝트(Spring) 입장에서는 이 서버를 **다른 회사의 외부 API처럼 취급**하고, 응답의 `status`/`message`만 보고 성공/실패를 판단함.

### 13-2. 전체 플로우
사업자 회원가입은 일반 회원가입(2장)의 1~4단계(이메일 인증, 전화번호 SMS 인증)를 **그대로 재사용**하고, 5단계(최종 가입) 자리에 사업자용 엔드포인트가 대신 들어가는 구조.

1~4) 이메일 인증 요청/확인, 전화번호 SMS 인증 요청/확인 — 2장과 완전히 동일 (엔드포인트도 동일)
5) 사업자 회원가입 요청(최종 정보 입력 + 파일 업로드)
   - 이메일, 비밀번호, 비밀번호 확인, 닉네임, 전화번호, 사업자등록증명원 파일(`multipart/form-data`) 입력
   - 비밀번호 확인 일치 검증(8-2장과 동일)
   - 이메일 인증 완료 확인(2장과 동일)
   - 전화번호 SMS 인증 완료 확인(8-1장과 동일)
   - 닉네임/전화번호 중복 확인(2장과 동일)
   - **여기까지 통과한 뒤에만** 업로드된 파일을 사업자 인증 서버(`POST /verify`)로 전달 — 비용이 드는(OCR/Playwright/외부 API 호출) 단계라 다른 검증을 전부 통과한 요청에 대해서만 호출하도록 순서를 잡음
   - 검증 성공 시 응답의 `extracted.business_number`로 사업자등록번호 중복 확인
   - members row 완성(role='BUSINESS') + member_credentials 저장(일반 회원가입과 동일한 Argon2) + business_profiles row 신규 저장(검증 결과로 채움)
   - 회원가입 완료

### 13-5. API 설계
#### 13-5-1. 사업자 회원가입
```
POST /api/members/signup/business
Content-Type: multipart/form-data

email=user@naver.com
password=P@ssw0rd!
passwordConfirm=P@ssw0rd!
nickname=홍길동상회
phone=010-1234-5678
businessLicenseFile=(사업자등록증명원 PDF 또는 이미지 파일)
```
Response(성공, 200): `{ "success": true, "message": "사업자 회원가입이 완료되었습니다.", "memberId": 1 }` (일반 회원가입과 동일한 `SignUpResponseDto` 재사용)

처리:
- 입력값 유효성 검사(일반 회원가입과 동일 규칙) + `businessLicenseFile` 필수
- `password`/`passwordConfirm` 일치 확인 → PASSWORD_CONFIRM_MISMATCH
- email로 members 조회 → EMAIL_NOT_FOUND / 이메일 인증 확인 → EMAIL_NOT_VERIFIED
- 전화번호 인증 확인(purpose='SIGNUP', 일반 회원가입과 동일 데이터 사용) → PHONE_NOT_VERIFIED
- 이미 가입 완료 → ALREADY_SIGNED_UP / 닉네임 중복 → DUPLICATE_NICKNAME / 전화번호 중복 → DUPLICATE_PHONE
- `businessLicenseFile`을 사업자 인증 서버(`POST {business-verify.base-url}/verify`)로 전달
  - 서버가 실패(4xx) 응답 → BUSINESS_VERIFICATION_FAILED(그 서버가 알려준 사유 메시지를 그대로 전달)
  - 서버에 연결 자체가 안 됨/타임아웃 등 → BUSINESS_VERIFY_SERVICE_UNAVAILABLE
- 응답의 `business_number`로 business_profiles 중복 확인 → DUPLICATE_BUSINESS_NUMBER
- members 완성(role='BUSINESS') + member_credentials 저장(Argon2) + business_profiles 저장(verification_status='VERIFIED')

### 13-7. 로그인/기타 — 변경 없음
- **로그인**: 요구사항대로 API/입력값 전부 동일(`POST /api/members/login`, email+password). 발급되는 JWT의 `role` 클레임이 `'BUSINESS'`로 나온다는 것만 다름 — `MemberServiceImpl.login()`은 이미 `member.getRole()`을 그대로 토큰에 실어왔으므로 코드 변경이 전혀 필요 없음
- **이메일/전화번호 인증**: `POST /api/mail/*`, `POST /api/phone/*` 그대로 재사용(사업자 전용 엔드포인트를 새로 만들지 않음)
- **비밀번호 암호화**: Argon2, 일반 회원가입과 완전히 동일

### 13-8. 확인이 필요한 사항
- **사업자 인증 서버(`receipt-biz-verify`)의 기동/배포 방식**: 로컬에서는 `uvicorn`으로 수동 기동해야 함. 실서비스에서 이 서버를 어디에 상시 배포/운영할지(같은 VM인지, 별도 서버인지), Spring 서버와 어떻게 같이 뜨게 할지는 미정
- **사업자 인증 서버가 요구하는 외부 API 키**(`GEMINI_API_KEY`, `NTS_SERVICE_KEY`, `UPSTAGE_API_KEY`) 사용량/비용 한도 — 이 프로젝트(Spring) 쪽에서 직접 관리하는 값은 아니지만, 호출 실패 시 사용자에게 보여줄 메시지 수준(13-6장 BUSINESS_VERIFICATION_FAILED)을 넘어서는 세부 장애 대응은 범위 밖
- **원본확인(Playwright, 홈택스 자동화) 소요 시간**: 실제 브라우저를 띄워 홈택스 페이지를 조작하는 방식이라 수 초~수십 초가 걸릴 수 있음. Spring→Python 호출의 타임아웃 값을 얼마로 잡을지 결정 필요(현재 `BusinessVerificationClient`는 RestClient 기본 타임아웃 사용, 별도 설정 없음)
- ~~**business_address**: 사업자 인증 서버가 추출하지 않아 항상 NULL로 저장됨~~ → **(2026-07-20 정정)** 실제로는 서버가 이미 추출하고 있었고(`extracted.address`) 우리 쪽이 안 읽었을 뿐이었음 — 13-9장에서 반영/수정함
- **재시도/부분 실패 처리**: OCR은 성공했지만 원본확인이 실패하는 등 중간 단계 실패 시 사용자가 파일을 다시 올려서 재시도하는 것 외의 별도 구제 절차는 없음
- **뿌리오 SMS와 마찬가지로 실제 연동 테스트는 미완료**: 사업자 인증 서버가 이번 테스트 환경에 기동되어 있지 않아, `POST /verify` 호출 직전까지의 게이트만 검증했고 실제 OCR/원본확인/진위확인 자체는 검증하지 못함 (001-03 참고)

### 13-9. 사업장 주소 자동귀속 (2026-07-20 요구사항 추가)
사용자가 "사업자등록번호 대사로 자동 귀속"을 요청 — 07(음식점-메뉴-검색)에서 사업자가 자기 가게의 메뉴/영업시간/전화번호/사진을 직접 등록하려면, 먼저 "이 사업자 회원이 어느 음식점 주인인지"를 알아야 하는데, 사업자 회원가입 시점에 자동으로 연결해주자는 취지.

**흐름**: 사업자 회원가입(13-2장 5단계) 최종 성공 시 → `BusinessVerificationClient`가 위 13-1-2단계에서 이미 추출하던 `address`를 `BusinessProfile.businessAddress`로 저장 → `RestaurantClaimService.tryAutoClaimByAddress()`(07 패키지, 신규)가 그 주소와 정확히 일치(정규화 후 부분 문자열 포함)하는 **미소유(UNCLAIMED) 음식점이 정확히 1개**일 때만 `restaurant_managers`에 연결하고 그 음식점을 CLAIMED로 바꿈. 0개/여러 개 매칭이면 아무것도 하지 않음(안전한 기본값 — 오귀속 방지). 이 매칭 실패는 회원가입 자체를 실패시키지 않음(부가 기능이라 필수 조건이 아님).

상세 설계/구현은 [07(음식점-메뉴-검색) 001-02 설계 문서](../07.음식점-메뉴-검색/001-02.음식점-메뉴-검색-분석-설계.md)와 [001-03 구현-테스트 문서](../07.음식점-메뉴-검색/001-03.음식점-메뉴-검색-구현-테스트.md)에 정리함(이 기능은 회원가입이 아니라 07의 음식점 도메인 서비스로 구현됨 — `MemberServiceImpl`은 그 서비스를 호출만 함).

## 14. 프로필 사진 등록 안내 (2026-07-19 요구사항 추가, [005.회원정보수정](../05.회원정보수정/) 참고)
------------------------------------------------------------------------
요구사항은 "회원가입/회원정보수정/소셜로그인 전체에 프로필 사진"을 요구했으나, **일반 회원가입 API(`POST /api/members/signup`, 사업자 회원가입 포함) 자체에는 사진 업로드를 추가하지 않기로 결정함.** 이유:
- `POST /api/members/signup`은 이미 JSON 계약으로 확정/테스트돼 있음(5장) — 사진 필드를 넣으려면 전체를 `multipart/form-data`로 바꿔야 해서 기존 연동을 깨뜨림
- 사업자 회원가입(13장)은 이미 `multipart/form-data`이긴 하지만, 이것도 이미 확정된 계약이라 필드 추가는 별도 확인 없이 진행하지 않음

**대신 회원가입 → 로그인까지 마친 뒤, [005(회원정보수정)에서 구현한 프로필 사진 업로드 API](../05.회원정보수정/001-02.회원정보수정-분석-설계.md#2-8-프로필-사진-등록변경삭제-2026-07-19-요구사항-추가)(`POST /api/members/me/profile-image`)를 그대로 재사용**하도록 안내함 — 이 문서(01.회원가입) 쪽에는 추가된 코드가 없고, 프론트 연동 가이드(001-04)에만 이 흐름을 안내로 남김. 실제 파일 저장/서빙/검증 로직도 전부 005에서 한 번만 구현함(중복 구현 없음).

이 설계가 요구사항의 실제 의도("가입 화면에서 사진을 고르면 가입과 동시에 반영")와 맞는지는 확인이 필요함(005 001-02 8장에서 같은 내용으로 열어둠).
