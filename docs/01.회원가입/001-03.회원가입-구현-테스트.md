### 1-2. 의존성/설정 변경 사항
- `pom.xml`: spring-boot-starter-data-jpa, spring-boot-starter-mail, spring-boot-starter-validation,
  spring-security-crypto, mariadb-java-client, lombok 추가
  - Argon2PasswordEncoder 실행 시 `NoClassDefFoundError: org/bouncycastle/crypto/params/Argon2Parameters$Builder` 발생 →
    `org.bouncycastle:bcprov-jdk18on:1.78.1` 의존성 추가로 해결 (spring-security-crypto의 Argon2는 BouncyCastle에 위임하나 기본 스타터에는 포함되지 않음)
  - 당초 `.env` 로딩용으로 `me.paulschwarz:spring-dotenv` 라이브러리를 시도했으나, 이 프로젝트의 Spring Boot 4.0.7과 호환되지 않아
    (EnvironmentPostProcessor/RunListener가 로드되지 않음) 제거하고, Spring Boot 내장 기능인
    `spring.config.import: optional:file:.env[.properties]` 로 대체함 (.env가 `KEY=VALUE` 형식이라 properties 파서로 바로 읽힘)
- `application.properties` → `application.yml`로 교체. DB(MariaDB)/Mail(Gmail SMTP) 설정을 `${DB_URL}`, `${DB_USERNAME}`, `${DB_PASSWORD}`,
  `${MAIL_USERNAME}`, `${MAIL_APP_PASSWORD}` 환경변수로 주입받도록 구성. `spring.jpa.hibernate.ddl-auto=update`로 최초 기동 시
  members/member_credentials/email_verifications 테이블이 실제 MariaDB(soldesk_project)에 자동 생성됨을 확인.
- `.env`(gitignore 처리) / `.env.example` 신설: DB 접속정보(MariaDB, host 72.155.72.187:3306, db soldesk_project) 반영,
  `MAIL_USERNAME` / `MAIL_APP_PASSWORD`는 값이 없는 상태로 골격만 마련 → 발급받는 즉시 `.env`에 채우면 별도 코드 수정 없이 실동작
- 로컬 개발 서버 포트가 8080은 이미 다른 프로세스(Oracle TNS Listener)가 점유 중이어서 `server.port=8081`로 변경
- **메일 발송사 변경 이력**: 최초에는 설계 문서(001-02) 기준 Naver SMTP(`smtp.naver.com:465`, SSL)로 구현했으나,
  이후 실제 서비스 도메인이 `eattyway.com`으로 확정됨에 따라 Gmail SMTP(`smtp.gmail.com:587`, STARTTLS)로 전환함.
  발신 계정은 `eattyway@gmail.com`(구글 앱 비밀번호 사용), 메일 발신 표시 이름은 `Eattyway <eattyway@gmail.com>`으로 설정.
  메일 본문은 `SimpleMailMessage`(plain text) 대신 `MimeMessageHelper` 기반 HTML 메일로 변경하여 인증번호 숫자만 `<b>` 태그로 굵게 강조.
  **(2026-07-18 추가 변경)** Gmail 계정(`eattyway@gmail.com`)이 정지되어 Daum SMTP(`smtp.daum.net:465`, SSL)로 재전환함.
  발신 계정은 `eattyway@daum.net`, 메일 발신 표시 이름도 `Eattyway <eattyway@daum.net>`으로 변경.
  기존 Gmail 계정 정보(`MAIL_USERNAME`/`MAIL_APP_PASSWORD`)는 `.env`에 주석으로 백업해두고(복구 대비), 활성 값만 Daum 계정으로 교체함.
  `application.yml`의 `spring.mail.properties.mail.smtp.starttls.enable`(포트 587용)을 `spring.mail.properties.mail.smtp.ssl.enable`(포트 465 암묵적 SSL용)로 변경 — Daum SMTP는 465 포트 SSL 방식이라 STARTTLS 설정은 더 이상 쓰지 않음.
  **Daum 계정에서 발견한 이슈**: Daum 마이페이지의 IMAP/SMTP 설정값 안내에 따르면 SMTP 인증 아이디는 실제 이메일 주소(`eattyway@daum.net`)가 아니라 도메인 없는 `eattyway`(계정 접속 시 아이디)를 써야 함. 기존 코드는 `spring.mail.username`(SMTP 인증 아이디) 값을 그대로 메일 From 헤더에도 재사용하고 있었는데(`MailService.fromAddress`), 이 값을 `eattyway`로 바꾸면 From 헤더가 `Eattyway <eattyway>`처럼 유효하지 않은 이메일 형식이 되어버림 → `application.yml`에 `mail-sender.from-address`(기본값 `eattyway@daum.net`, `MAIL_FROM_ADDRESS` 환경변수로 override) 프로퍼티를 새로 추가하고, `MailService`가 From 헤더를 `spring.mail.username`이 아닌 이 값에서 읽도록 분리함. `.env`는 `MAIL_USERNAME=eattyway`(인증 아이디), `MAIL_APP_PASSWORD`는 Daum 마이페이지 > 계정 보안 > 앱 비밀번호에서 발급받은 값, `MAIL_FROM_ADDRESS=eattyway@daum.net`으로 구성.
  **(2026-07-18 재검증 완료)** VM 재기동 후 `POST /api/mail/send-code`를 `eric7378@naver.com`으로 직접 호출해 실제 메일 발송/수신까지 확인함. 처음 가짜 도메인(`example.com`)으로 테스트했을 때는 `421 4.4.4 all mx host connect fail`(수신 도메인에 MX 서버가 없어서 발생 — 인증 실패가 아님) 오류가 나서 잠깐 인증 문제인가 의심했으나, 실제 존재하는 도메인으로 재시도하니 정상 발송됨을 확인해 Daum 계정 인증 자체는 문제 없음을 확인함. 테스트로 생성된 members row는 정리함.

### 1-4. 실제 기동/검증 중 발견한 이슈
1. **JDK 버전**: 로컬 JAVA_HOME이 JDK 11이라 `pom.xml`의 `java.version=17`과 불일치, 빌드 실패.
   → STS(Spring Tool Suite) 번들 JDK 17(`sts-4.22.1.RELEASE/.../jre_17.0.11`)을 찾아 JAVA_HOME으로 지정해 해결.
   (IDE에서 별도 JRE로 등록해 실행하는 것을 권장)
2. **DB 접속 타임아웃**: 최초 기동 시 DB 서버가 꺼져 있어 `Connection timed out`. 서버 기동 후 재시도하여 정상 연결 확인.
3. **Argon2 BouncyCastle 누락**: 1-2 참고, `bcprov-jdk18on` 추가로 해결.
4. **포트 충돌**: 8080이 사전 실행 중이던 무관한 프로세스(Oracle TNS Listener)가 점유 중이라 8081로 변경.
5. **Gmail 최초 인증 실패**: 처음 전달받은 앱 비밀번호(15자리)로 시도했을 때 `Authentication failed` 발생.
   구글 계정의 2단계 인증을 켜고 앱 비밀번호를 재발급(16자리)한 뒤 정상 인증되어 실제 메일 발송까지 확인함.

## 2. Playwright 테스트
------------------------------------------------------------------------
- 위치: `Project2/e2e` (Node.js 기반 별도 테스트 프로젝트, `Project2` 빌드에는 포함되지 않음)
- 테스트 방식: Playwright의 API request context로 3개 엔드포인트를 직접 호출하는 API 레벨 E2E 테스트
- **DB 시딩(dbHelper.js)에 대한 설명**: 아래 12개 자동화 테스트를 실행한 시점에는 메일 계정이 아직 설정되지 않아 이메일 발송 자체가 항상 실패했다
  (정상 동작이며 코드 결함 아님). 이로 인해 "인증번호 발송 → 실제 수신 → 인증확인 → 가입완료"까지의 happy path를
  API만으로는 끝까지 검증할 수 없어, DB에 직접 접속해 `members`/`email_verifications` row를 미리 시딩하는 방식으로
  "인증 완료된 상태"를 재현하여 `/verify-code`, `/signup` 자체의 로직을 검증함. 각 테스트는 종료 시 시딩한 데이터를 정리(clean-up)함.
  이후 Gmail 계정이 `.env`에 반영되어 `send-code`의 실제 메일 발송/수신은 수동 curl 테스트로 별도 확인함 (2-2 참고).
  자동화 스위트(Playwright)는 아직 DB 시딩 방식을 그대로 사용 중이며, 실제 수신 확인까지 자동화하려면 메일함 조회(IMAP 등) 연동이 추가로 필요함.
- 실행 방법: `cd Project2/e2e && npm install && npx playwright test` (사전에 Spring Boot 앱이 8081 포트로 기동되어 있어야 함)

## 3. 2차 구현 (2026-07-17): "남은 작업" 2가지 항목 반영
------------------------------------------------------------------------

### 3-1. 미인증 상태로 이탈한 members row 배치 정리
이메일 인증번호 발송 시점에 `members` row를 먼저 만들어두는 구조([001-02.회원가입-분석-설계.md](001-02.회원가입-분석-설계.md) 2장)라서,
사용자가 인증을 끝까지 완료하지 않고 이탈하면 그 이메일이 `members.email` UNIQUE 제약에 영구히 남아 재가입을 막게 된다. 이를 주기적으로 정리하는 스케줄러를 추가함.

**정책**: `member_credentials`가 없는(=회원가입을 끝까지 완료하지 않은) `members` row 중 생성된 지 **24시간이 지난 것**을 매시 정각에 정리. 수치는 요구사항에 명시가 없어 임의로 정함(설정으로 조정 가능).

**구현**
- `MemberRepository.findUnverifiedMemberIdsCreatedBefore(cutoff)`: `member_credentials`에 없고 `created_at < cutoff`인 member_id 목록 조회 (JPQL `NOT IN` 서브쿼리)
- `EmailVerificationRepository.deleteByMemberIdIn(memberIds)`: FK 자식 row(`email_verifications`) 먼저 삭제
- `UnverifiedMemberCleanupScheduler`(신규, `member/scheduler` 패키지): `@Scheduled(cron = "${member.cleanup.cron:0 0 * * * *}")`로 매시 정각 실행, `@Transactional`로 자식→부모 순서로 삭제
- `Project2Application`에 `@EnableScheduling` 추가 (스케줄러가 등록만으로는 동작하지 않아 필요)
- `application.yml`: `member.cleanup.unverified-after-hours`(기본 24), `member.cleanup.cron`(기본 매시 정각) 추가, 각각 `MEMBER_CLEANUP_UNVERIFIED_AFTER_HOURS`/`MEMBER_CLEANUP_CRON` 환경변수로 override 가능

### 3-2. nickname/phone DB UNIQUE 인덱스 추가 + 레이스 컨디션 방어
**구현**
- `Member` 엔티티: `nickname`, `phone` 컬럼에 `unique = true` 추가
- **`ddl-auto=update`가 기존 테이블에는 UNIQUE 제약을 추가해주지 않는 것을 실제로 확인함** (재기동 로그에 관련 `alter table` 구문이 전혀 출력되지 않음). 새 테이블을 생성할 때는 정상 반영되지만, 이미 존재하는 테이블의 제약 추가는 Hibernate의 스키마 자동갱신이 신뢰할 수 없다는 것이 이번에 드러난 문제라, 이번에는 `ALTER TABLE members ADD CONSTRAINT uk_members_nickname UNIQUE (nickname)` / `uk_members_phone UNIQUE (phone)`를 DB에 직접 실행해서 반영함 ([001-05 문서 3번 항목](001-05.부족한-내용.md#3-ddl-autoupdate가-기존-테이블의-제약조건-변경을-반영하지-못함) 참고)
- `MemberServiceImpl.signUp()`: 기존 `existsByNickname`/`existsByPhone` 사전 체크는 그대로 유지하되(빠른 실패), `member.completeSignUp()` 이후 `memberRepository.saveAndFlush(member)`로 즉시 flush하여 동시 요청으로 사전 체크를 둘 다 통과해버린 경우에도 DB UNIQUE 제약에서 최종적으로 막히도록 함
- **삽질 기록**: 처음에는 flush 실패(`DataIntegrityViolationException`)를 잡은 뒤 다시 `existsByNickname`/`existsByPhone`으로 "어느 필드가 중복인지" 재조회하려 했으나, flush 실패로 무효화된 영속성 컨텍스트를 그 안에서 재사용하면 동일한 예외가 한 번 더 발생하며 결국 500 INTERNAL_SERVER_ERROR로 새 버렸다. 실제 동시 요청 스크립트로 재현하며 예외 체인을 직접 로그로 찍어본 결과, `DataIntegrityViolationException → org.hibernate.exception.ConstraintViolationException(getConstraintName()="uk_members_nickname") → SQLIntegrityConstraintViolationException` 구조임을 확인했고, `getMostSpecificCause()`(가장 안쪽 원인)가 아니라 체인 중간의 `ConstraintViolationException`을 직접 찾아 `getConstraintName()`으로 어떤 제약이 깨졌는지 판별하는 방식으로 재조회 없이 해결함
- 이 로직은 `MemberServiceImpl.extractConstraintName()`에 있음

**검증**: 실제로 두 개의 서로 다른 이메일로, 같은 닉네임/같은 전화번호를 동시에(`Promise.all`) 요청하는 스크립트로 재현 → 하나는 200 성공, 다른 하나는 (500이 아니라) 409 `DUPLICATE_NICKNAME`/`DUPLICATE_PHONE`으로 정상 처리되는 것을 확인함. 이 시나리오를 Playwright 테스트로도 추가함(`signup.spec.js`의 "동시에 같은 닉네임/전화번호로 가입 요청" 2개 케이스, 2-3 참고).

## 5. 5차 구현 (2026-07-18): 전화번호 AES-256-GCM 양방향 암호화
------------------------------------------------------------------------
[001-01.회원가입-요구사항.md](001-01.회원가입-요구사항.md)에 "전화번호는 이후 이메일 찾기 등에서 재사용할 수 있어야 하므로 단방향 해시가 아닌 AES-256-GCM 양방향 암호화로 저장한다"는 요구사항이 추가되어 반영함. 설계 내용은 [001-02 7-1장](001-02.회원가입-분석-설계.md#7-1-전화번호-aes-256-gcm-양방향-암호화-설계-2026-07-18-요구사항-추가) 참고.

### 5-1. 구현
- **`PhoneCryptoService`**(신규, `common/security` 패키지): 전화번호 암복호화/해시를 전담하는 컴포넌트
  - `encrypt(String)` / `decrypt(String)`: `AES/GCM/NoPadding`, 매 호출마다 `SecureRandom`으로 12바이트 IV를 새로 생성, 인증 태그 128비트, 저장 포맷은 `Base64(IV || 암호문+태그)` 하나로 합쳐 저장
  - `hash(String)`: `HmacSHA256`으로 결정적(deterministic) 해시를 생성해 조회/중복확인용으로 사용 (AES 키와 별도의 키 사용)
  - 키는 `@Value("${phone-crypto.aes-key}")`, `@Value("${phone-crypto.hash-key}")`로 주입받으며, 둘 다 256비트 랜덤 값을 Base64로 인코딩해 `.env`에 보관 (`PHONE_AES_KEY`, `PHONE_HASH_KEY`, `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`로 생성)
- **`PhoneAttributeConverter`**(신규, `member/entity` 패키지): `@Converter(autoApply = false)` + `@Component`로 등록한 JPA `AttributeConverter<String, String>`. `Member.phone` 필드에 `@Convert`로 연결해, 엔티티 저장/조회 시 암복호화가 투명하게 일어나도록 함
- **`Member` 엔티티**: `phone` 컬럼은 암호문을 저장하므로 `length`를 20→255로 확장하고 기존 `unique = true`는 제거, 새 컬럼 `phone_hash`(VARCHAR(64), `unique = true`)를 추가해 조회/중복확인은 이 컬럼으로 수행. `completeSignUp(nickname, phone, phoneHash)`로 시그니처 변경
- **`MemberRepository`**: `existsByPhone(String)` → `existsByPhoneHash(String)`로 변경 (평문 조회가 불가능해졌으므로)
- **`MemberServiceImpl.signUp()`**: 가입 시 `phoneCryptoService.hash(request.getPhone())`로 조회용 해시를 먼저 계산해 `existsByPhoneHash`로 사전 중복체크하고, `completeSignUp`에 평문 전화번호(컨버터가 저장 시 자동 암호화)와 해시를 함께 전달. 레이스 컨디션 방어용 `saveAndFlush` 예외 처리(3-2장)에서 검사하는 제약 이름도 `uk_members_phone` → `uk_members_phone_hash`로 변경

### 5-2. DB 반영
`ddl-auto=update`로 재기동 시 `phone` 컬럼 확장과 `phone_hash` 컬럼 신설(+ UNIQUE 제약)까지는 자동으로 반영됨 — 이번 사례로 "기존 테이블에 컬럼을 새로 추가할 때는 그 컬럼의 제약조건도 함께 자동 반영된다"는 것을 확인함 (기존에 알려진 한계는 "이미 존재하는 컬럼에 나중에 제약조건만 추가"하는 경우에 한정됨, [001-05 3번 항목](001-05.부족한-내용.md#3-ddl-autoupdate가-기존-테이블의-제약조건-변경을-반영하지-못함) 참고).

다만 아래 두 가지는 수동 SQL로 보정함:
1. Hibernate가 `phone_hash` UNIQUE 제약을 자동 생성한 이름(`UK3wrewxmp0wdry0hvdr1ra51g8`, 해시 기반)이 애플리케이션 코드에서 검사하는 이름(`uk_members_phone_hash`)과 달라 `ALTER TABLE members RENAME INDEX UK3wrewxmp0wdry0hvdr1ra51g8 TO uk_members_phone_hash;`로 이름을 맞춤
2. 기존에 남아있던 `uk_members_phone`(구 평문 시절의 UNIQUE 제약)은 이제 암호문 컬럼에 걸린, 의미 없는(오히려 오해를 부르는) 제약이라 `ALTER TABLE members DROP INDEX uk_members_phone;`로 제거

### 5-3. 검증
1. **암호화 확인**: 실제 회원가입 API를 호출해 DB에 저장된 `phone` 값이 입력한 평문 전화번호 문자열을 포함하지 않는 것을 직접 조회로 확인 (예: 평문 `010-3037-9999` → 저장값 `x2QOS1B2zY++DUqq68mhqcXafTwH5Q6yaetseC3jLv7oPRzREnM9mCM=`)
2. **해시 확인**: `phone_hash` 컬럼에 64자리 16진수(HMAC-SHA256, 32바이트) 문자열이 정상 저장됨을 확인
3. **복호화 정확성 확인**: (a) 회원가입 직후 로그인 API를 호출해 `Member` 엔티티가 다시 로드(컨버터의 `decrypt` 경로 통과)될 때 예외 없이 200이 반환되는 것으로 간접 확인, (b) 별도로 Node.js에서 동일한 AES-256-GCM 파라미터(같은 `PHONE_AES_KEY`)로 DB에 저장된 암호문을 직접 복호화해 원래 입력한 평문과 바이트 단위로 일치함을 독립적으로 재검증함

5. **전체 스위트 재실행**: 회원가입(9개) + 로그인/로그아웃 등 전체 34개 재실행 → 34/34 통과 (신규 케이스 포함, 기존 케이스 회귀 없음)

뿌리오 계정(`winoh7378`) 발급 + 인증키(`연동개발(API)` 메뉴) 발급 + 연동IP 등록(로컬 PC IP `106.243.251.246`)이 완료되어, `.env`의 `PPURIO_ACCOUNT`/`PPURIO_AUTH_KEY`를 채우고 서버를 재기동한 뒤 실제 문자 발송을 검증함.

**테스트 방법**: `dbHelper.insertPendingMember()`/`insertEmailVerification()`으로 이메일 인증까지 완료된 회원을 시딩한 뒤, 실제 `POST /api/phone/send-code`를 호출(전화번호 `010-4670-7378`, 사용자 본인 번호로 직접 수신 확인 요청받음).
```
POST /api/phone/send-code {"email": "...", "phone": "010-4670-7378"}
→ 200 { "success": true, "message": "인증번호가 발송되었습니다." }
```
`PpurioSmsService.sendSms()`는 응답 `code`가 1000이 아니면 예외를 던지도록 구현돼 있으므로(6-1장), 200이 반환됐다는 것 자체가 토큰 발급(`POST /v1/token`)과 SMS 발송 요청 접수(`POST /v1/message`) 양쪽 다 성공(`code: 1000`)했음을 의미함 — 서버 로그에도 예외 없이 `phone_verifications` insert만 정상 기록됨. 이것으로 6-1장에서 정정한 새 API 스펙(엔드포인트/필드명)이 실제로 맞다는 것도 함께 확인됨.
테스트에 쓴 회원 row는 `deleteMemberByEmail()`로 정리함. 전체 회귀 테스트도 재실행해 128/128 통과 확인(실 계정 연결 이후에도 기존 DB 시딩 기반 테스트들에 영향 없음).

**(2026-07-20 정정) `code: 1000`은 발송 성공을 보장하지 않음 — 실제 수신 실패 확인됨**: 사용자가 뿌리오 콘솔에서 "문자 상세보기"로 확인한 결과, 이 발송 건이 **"발송불가"로 100% 실패** 처리되어 있었음(성공 0건). 콘솔의 발송요금이 "금액 0원 / 씨앗 0톨"로 찍혀 있는 것으로 보아, 계정에 발송 가능한 잔액(씨앗/충전금/포인트)이 없는 게 원인으로 추정됨 — 계정을 만들었지만 "마이페이지 > 기업회원전환"(1장에서 언급한 무료문자 1,000건 이벤트 대상)까지는 아직 신청하지 않은 것으로 보임.

즉 뿌리오 API의 `code: 1000`은 **"요청 형식이 유효해서 접수됐다"**는 뜻일 뿐 **"통신사까지 실제로 전달됐다"**는 뜻이 아님 — 이 프로젝트의 `PpurioSmsService`는 동기 응답(`code`)만 확인하고 끝나는 구조라, 이런 비동기 발송 실패(잔액 부족, 통신사 거부 등)는 지금 구조로는 감지할 수 없음(콘솔에서 별도로 확인해야 함).

**재시도 및 최종 성공**: 사용자가 뿌리오 마이페이지에서 "기업회원전환"을 완료(회원유형 "기업 선불"로 전환, 씨앗 1,000톨 충전, 발신번호 `070-5236-4828` 인증완료 2건 확인)한 뒤, 새 회원을 다시 시딩해 `POST /api/phone/send-code`를 재호출함(`010-4670-7378`). 이번엔 `200`/`code: 1000` 응답과 함께 **사용자 단말에 실제로 문자가 수신됨을 직접 확인**받았음 — 회원가입/이메일찾기/회원정보수정 세 기능이 공유하는 `PpurioSmsService`가 실제로 정상 동작함이 최종 확인됨. 재시도 도중 Redis 연결이 일시적으로 끊겼다가(`SocketException: Connection reset`) 자동 재연결되는 것도 관찰됨(뿌리오와 무관한 별개 이슈, 재시도로 정상 처리됨).

이 확인 이후 인증번호 메시지 포맷도 가독성을 위해 한 줄에서 3줄 줄바꿈으로 변경함(`PhoneAuthService.buildMessage()`, `00.공통 가이드 4장` 참고):
```
[Eattyway]
본인확인 인증번호는 [123456]입니다.
5분 이내에 입력해주세요.
```
변경 후 전체 회귀 테스트 130/130 통과 확인(메시지 내용을 검증하는 테스트는 없어 이 변경으로 깨진 테스트 없음).

**남은 것**:
- 서버 배포 IP(Azure VM)는 아직 연동IP로 등록되지 않아, 실제 배포 환경에서는 등록 전까지 `3003`(IP 유효하지 않음) 에러가 날 수 있음(00.공통 가이드 8장 참고).

- **`application.yml`/`.env`**: `business-verify.base-url`(`BUSINESS_VERIFY_BASE_URL`, 기본값 `http://localhost:8000`), `spring.servlet.multipart.max-file-size`/`max-request-size`를 기본값 1MB에서 10MB로 상향(사업자등록증명원 스캔 PDF가 1MB를 넘는 경우가 흔함)

### 8-2. 설계 문서 작성 이후 구현 중 새로 발견한 사항
1. **`business_profiles` 테이블이 이미 존재했음**: `BusinessProfile` 엔티티를 만들고 서버를 기동했더니, `ddl-auto=update`가 `create table`이 아니라 `alter table ... add constraint`를 실행함 — 이미 테이블이 있었다는 뜻. DB를 직접 조회해보니 [DB-테이블설계.md](../00.공통/DB-테이블설계.md) 2-1장 스키마 그대로 이미 만들어져 있었고, `business_registration_number`에 `uq_business_profiles_reg_no`라는 이름의 UNIQUE 제약도 이미 걸려 있었음. 처음에 엔티티에 `uk_business_profiles_reg_number`라는 새 이름으로 제약을 하나 더 선언했더니 같은 컬럼에 UNIQUE 제약이 2개(중복) 걸리는 것을 확인 → `ALTER TABLE business_profiles DROP INDEX uk_business_profiles_reg_number`로 직접 제거하고, 엔티티의 `@Table(uniqueConstraints=...)` 이름을 기존 `uq_business_profiles_reg_no`에 맞춰 수정함(`MemberServiceImpl`의 `saveAndFlush` 예외 처리가 제약 이름으로 판별하므로 이름이 맞아야 함, 001-03 5-2장에서 겪은 것과 같은 종류의 문제)
2. **Playwright 멀티파트 요청이 전부 500으로 실패하는 문제**: `playwright.config.ts`가 `extraHTTPHeaders: { 'Content-Type': 'application/json' }`을 전역으로 강제하고 있어서, 이 파일의 모든 multipart 요청이 서버에 `Content-Type: application/json`으로 도착해 `HttpMediaTypeNotSupportedException`(500)이 남. 기본 `request` 픽스처를 재정의하는 방식으로는 안 풀려서, `business-signup.spec.js`에서만 `extraHTTPHeaders: {}`를 명시한 별도 `APIRequestContext`(`pwRequest.newContext(...)`)를 직접 만들어 사용하도록 함
3. **필수 멀티파트 파일이 없을 때 500이 나는 문제**: `businessLicenseFile`을 아예 안 보내면 Spring이 `MissingServletRequestPartException`을 던지는데, 기존 `GlobalExceptionHandler`에는 이걸 잡는 핸들러가 없어서 catch-all(`Exception.class`) 핸들러로 떨어져 500이 남. `MissingServletRequestPartException`/`MissingServletRequestParameterException`을 `INVALID_INPUT`(400)으로 매핑하는 핸들러를 추가함(다른 API에도 공통 적용됨)

### 8-3. 실제 사업자 인증 서버 호출은 검증하지 않음 (의도된 범위 제한)
뿌리오 SMS([6-2장](#6-2-실제-sms-발송은-검증하지-않음-의도된-범위-제한))와 같은 이유로, 사업자 인증 Python 서버가 이번 테스트 환경에 기동되어 있지 않아 `POST /verify` 실제 호출(OCR/원본확인/진위확인)은 검증하지 않았다(사용자 요청에 따른 의도된 범위 제한). 대신 수동 curl 테스트와 Playwright 테스트로 아래를 확인함:
- 필수 파라미터 누락, 비밀번호 규칙 위반, 비밀번호 확인 불일치, 이메일 미인증, 전화번호 미인증, 닉네임 중복 — 사업자 인증 서버를 호출하지 않고 그 이전에 정확히 걸러짐
- 이메일/전화번호 인증까지 전부 통과한 요청은 실제로 `businessVerificationClient.verify()`까지 도달해 Python 서버로 호출을 시도하고, 서버가 없으므로 `BUSINESS_VERIFY_SERVICE_UNAVAILABLE`(500)로 안전하게 처리됨 — 즉 "검증 로직 자체"는 아직 못 봤지만 "그 앞뒤 배선"은 실제로 동작함을 확인함

## 10. 10차 구현 (2026-07-20): 사업장 주소 캡처 + 음식점 자동귀속 연결
------------------------------------------------------------------------
07(음식점-메뉴-검색) 사업자 등록 기능을 위해, 사업자 회원가입 시점에 사업장 주소를 실제로 저장하고 자동귀속을 트리거하도록 반영함(001-02 13-9장 설계).

### 10-1. 발견: `BusinessVerificationClient`가 이미 추출되던 주소를 버리고 있었음
`receipt-biz-verify` 서버의 Gemini 추출 프롬프트(`_EXTRACTION_PROMPT`)에는 처음부터 `address`(사업장 소재지)가 포함돼 있었고 응답의 `extracted.address`로 내려오고 있었는데, `BusinessVerificationResult`/`BusinessVerificationClient.verify()`가 `business_number`/`company_name`/`representative_name`만 읽고 `address`는 그냥 버리고 있었음(2026-07-18 최초 구현 당시부터). **Python 서버 코드는 전혀 수정하지 않고**, Java 쪽에서 이미 오던 값을 마저 읽도록만 고침.

### 10-2. 구현
- `BusinessVerificationResult`: `address` 필드 추가
- `BusinessVerificationClient.verify()`: `extracted.get("address")`를 읽어서 결과에 포함(빈 문자열이면 그대로 빈 문자열 — null 방지)
- `BusinessProfile`: `createVerified()`에 `businessAddress` 파라미터 추가(빈 문자열/공백이면 null로 저장), `getBusinessAddress()` getter 추가
- `MemberServiceImpl.signUpBusiness()`: `businessProfileRepository.saveAndFlush(businessProfile)` 직후 `RestaurantClaimService.tryAutoClaimByAddress(memberId, businessProfileId, verified.address())` 호출 — 매칭 실패/주소 없음이어도 회원가입 자체는 그대로 성공(예외를 던지지 않음)

### 10-3. 검증
사업자 회원가입 전체 플로우(OCR/원본확인/진위확인)는 8-3장/13-8장에서부터 이미 "실 서버 미기동으로 미검증"으로 남아있던 부분이라, 이번에도 **회원가입 경로를 통한 종단 간(end-to-end) 자동귀속 테스트는 하지 못함**(같은 제약: Gemini API 키, 홈택스 Playwright 자동화, 국세청 진위확인 API가 전부 실제로 떠 있어야 함). 대신:
- `RestaurantManager`/`RestaurantClaimServiceImpl` 코드는 컴파일/서버 기동까지 확인(`restaurant_managers` 테이블에 처음으로 DDL 적용됨 — UNIQUE 제약 `uq_restaurant_managers_restaurant_member` 정상 생성 확인)
- 자동귀속으로 만들어지는 **결과물(관리자 연결 상태)을 직접 DB에 시딩**해서, 그 이후 단계(07 사업자 등록 쓰기 API)가 정상 동작하는지는 Playwright로 검증함 — [07(음식점-메뉴-검색) 001-03 구현-테스트](../07.음식점-메뉴-검색/001-03.음식점-메뉴-검색-구현-테스트.md) 참고
- 주소 매칭 알고리즘(정규화 후 부분 문자열 포함) 자체는 4-3-4장(네이버 카테고리 유사매칭)과 동일한 방식이라 그쪽 논리를 그대로 재사용 — 코드 리뷰 수준에서는 확인했지만 실제 다양한 한국 주소 표기 패턴(도로명 vs 지번, 상세주소 포함 여부 등)으로 검증하지는 못함
