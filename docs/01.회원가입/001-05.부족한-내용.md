## 1. [미착수] Playwright 자동화 스위트에 실제 메일 수신 검증 케이스 없음
------------------------------------------------------------------------
**위치**: `Project2/e2e/tests/signup.spec.js`, [001-03 2-1장](001-03.회원가입-구현-테스트.md#2-1-테스트-결과-2026-07-16-1212-통과)

이메일 인증번호 발송(`POST /api/mail/send-code`) 테스트를 실행하던 시점에는 메일 계정이 설정되지 않아 발송 자체가 항상 실패했기 때문에, "발송 → 실제 수신 → 인증확인 → 가입완료"까지의 happy path를 API만으로는 끝까지 검증할 수 없었다. 그래서 DB에 `members`/`email_verifications` row를 직접 시딩해 "인증 완료된 상태"를 재현하는 방식으로 `/verify-code`, `/signup` 자체의 로직만 검증하고 있다. 이후 Gmail 계정이 `.env`에 반영되어 실제 발송/수신은 curl로 수동 확인했지만([001-03 2-2장](001-03.회원가입-구현-테스트.md#2-2-gmail-실제-발송-수동-테스트-2026-07-16)), 자동화 스위트에는 여전히 이 경로가 없다.

**제안**: 메일함 조회(IMAP 등) 연동으로 실제 수신까지 자동화. 우선순위는 낮음 — 수동 확인은 이미 완료되어 있고, 코드 로직 자체는 DB 시딩 방식으로 커버되고 있음.

- 자동화 테스트 없음 (수동 curl 테스트로만 확인됨)

## 2. [구조적 한계, 완화됨] `ddl-auto=update`가 기존 테이블의 제약조건 변경을 반영하지 못함
------------------------------------------------------------------------
**위치**: [Member.java](../../Project2/src/main/java/com/foodtrip/foodsearch/member/entity/Member.java) (`nickname`/`phone` `unique = true`), [001-03 3-2장](001-03.회원가입-구현-테스트.md#3-2-nicknamephone-db-unique-인덱스-추가--레이스-컨디션-방어)

닉네임/전화번호에 DB UNIQUE 제약을 추가하면서 실제로 확인한 문제: `spring.jpa.hibernate.ddl-auto=update`는 **새 테이블을 생성할 때는** 엔티티의 `unique = true`를 정상 반영하지만, **이미 존재하는 테이블에는 ALTER TABLE 구문 자체를 실행하지 않는다** (재기동 로그에 관련 `alter table` 구문이 전혀 안 찍힘). 이번에는 `ALTER TABLE members ADD CONSTRAINT uk_members_nickname UNIQUE (nickname)` 등을 DB에 직접 실행해서 우회했다.

이 프로젝트에는 Flyway/Liquibase 같은 스키마 마이그레이션 도구가 없어서, 앞으로도 기존 테이블에 제약조건/인덱스를 추가·변경할 때마다 매번 실제 반영 여부를 `SHOW INDEX` 등으로 직접 확인하고 필요하면 수동 DDL을 실행해야 하는 구조적 한계가 남아있다.

**제안**: Flyway 또는 Liquibase 도입 검토 (장기적으로 스키마 변경 이력 관리 및 이런 종류의 누락을 원천 차단). 당장은 스키마 변경 시 "반영 여부 직접 확인"을 체크리스트에 넣는 정도로 완화 가능.

- 자동화 테스트로 검증할 성격의 항목은 아님 (수동으로 `SHOW INDEX FROM members`로 확인함)

## 3. [미착수, 급하지 않음] 미인증 회원 정리 배치가 단일 인스턴스를 전제로 함
------------------------------------------------------------------------
**위치**: [UnverifiedMemberCleanupScheduler.java](../../Project2/src/main/java/com/foodtrip/foodsearch/member/scheduler/UnverifiedMemberCleanupScheduler.java), [001-03 3-1장](001-03.회원가입-구현-테스트.md#3-1-미인증-상태로-이탈한-members-row-배치-정리)

`@Scheduled`로 매시 정각 실행되는 미인증 회원 정리 배치는 애플리케이션 인스턴스가 1개라는 전제로 만들어졌다. 서버가 여러 대로 확장되면 같은 배치가 여러 인스턴스에서 동시에 실행되어 중복 작업(큰 문제는 아니지만 불필요한 DB 부하)이 발생할 수 있다.

**제안**: 인스턴스가 여러 대로 늘어나는 시점에 `shedlock` 같은 분산 락 라이브러리 도입 검토 — Redis가 이제 있으므로(`shedlock-provider-redis-spring`) 별도 인프라 없이 바로 붙일 수 있음. 지금은 단일 인스턴스라 당장 문제는 없어서 미착수.

- 자동화 테스트 없음 (단일 인스턴스 환경에서만 수동 검증함)

## 4. [미착수] 이메일 인증번호(`email_verifications`)의 Redis 전환
------------------------------------------------------------------------
**위치**: [EmailVerification.java](../../Project2/src/main/java/com/foodtrip/foodsearch/mail/entity/EmailVerification.java)

이미 [001-02 설계 문서](001-02.회원가입-분석-설계.md) 4-3장에서 "Redis 등 캐시 방식으로 전환 가능"이라고 언급됐던 부분. 5분 TTL을 `EXPIRE`로 표현하면 `expired_at` 컬럼 비교 로직과 미인증 회원 정리 배치(3번 항목과 연결)가 단순해질 수 있음. 지금 당장 문제가 있는 기능은 아니라 우선순위는 낮음.

Redis/Docker 인프라 자체는 이미 구축되어 있어(`docs/00.공통/Redis-Docker-구축-가이드.md`) 착수하려면 별도 인프라 준비 없이 바로 코드만 작업하면 됨 — 로그인 쪽(로그인 실패 카운트/잠금, refresh token)은 이미 Redis로 전환 완료된 상태([002 로그인 001-03 6장](../02.로그인/001-03.로그인-구현-테스트.md#6-4차-구현-2026-07-17-redis-연동-일괄-반영) 참고).

**제안**: 우선순위가 오르면(예: 인증번호 발송량이 늘어 DB 부하가 문제되면) 착수. 지금은 미착수.

- 자동화 테스트 없음 (아직 코드 자체가 없음)
