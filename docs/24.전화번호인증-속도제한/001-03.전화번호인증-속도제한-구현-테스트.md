## 1. 신규/변경 파일
------------------------------------------------------------------------
- (신규) `com.foodtrip.foodsearch.phone.service.PhoneSmsRateLimitService` — Redis 기반 IP별 일일
  카운트/한도 체크(`checkAndRecord(String ip)`)
- (신규) `com.foodtrip.foodsearch.common.web.ClientIpUtil` — `X-Forwarded-For` 우선, 없으면
  `request.getRemoteAddr()`
- (변경) `ErrorCode` — `PHONE_SMS_DAILY_LIMIT_EXCEEDED(429)` 추가
- (변경) `PhoneAuthService` — 생성자에 `PhoneSmsRateLimitService` 주입 추가,
  `sendSignupVerificationCode(String, String)` → `sendSignupVerificationCode(String, String, String clientIp)`,
  `sendVerificationCode(Long, String, String)` → `sendVerificationCode(Long, String, String, String clientIp)`로
  시그니처 변경, `sendVerificationCode` 맨 앞에서 `phoneSmsRateLimitService.checkAndRecord(clientIp)` 호출
- (변경) `PhoneAuthController.sendCode` — `HttpServletRequest` 파라미터 추가, IP 추출해서 전달
- (변경) `MemberService`/`MemberServiceImpl` — `sendFindEmailPhoneCode`/`sendProfilePhoneCode`에
  `clientIp` 파라미터 추가
- (변경) `MemberController` — `sendFindEmailPhoneCode`/`sendProfilePhoneCode`에 `HttpServletRequest`
  파라미터 추가, IP 추출해서 서비스로 전달

## 2. 컴파일/기존 코드 영향 확인
------------------------------------------------------------------------
- `mvnw.cmd compile`, `mvnw.cmd test-compile` 둘 다 성공
- 변경한 4개 메서드 시그니처(`sendSignupVerificationCode`, `sendVerificationCode`,
  `sendFindEmailPhoneCode`, `sendProfilePhoneCode`)를 참조하는 기존 테스트 코드가 있는지
  `src/test/java` 전체를 검색했으나 없었음 — 회귀 위험 낮음
- 호출부(컨트롤러 3곳) 전부 새 파라미터를 넘기도록 함께 수정 완료, 빠뜨린 호출부 없는지
  프로젝트 전체에서 옛 시그니처로 남아있는 호출이 있는지 재검색해서 없음을 확인

## 3. 로직 검증 방식 — 코드 리뷰 + 기존 검증된 패턴과의 대조
------------------------------------------------------------------------
`PhoneSmsRateLimitService`는 이미 실사용 중인 `LoginAttemptService`(02.로그인, 2026-07-17부터 운영)와
완전히 같은 Redis 패턴(원자적 `INCR` → `EXPIRE`로 안전 TTL 설정 → 임계값 비교)을 그대로 따랐다 —
새로운 동시성 로직을 직접 검증하는 대신, 이미 몇 주간 실사용으로 검증된 패턴을 재사용하는 방식으로
리스크를 낮췄다.

**중요 — 실제 SMS 발송을 반복 트리거하는 라이브 종단 테스트(실제로 6번 요청해서 6번째가 429로
막히는지)는 이번에 진행하지 않았다.** 뿌리오(Ppurio) SMS 발송은 성공하든 실패하든 매 호출마다 실제
비용이 청구될 수 있어서, 한도 값(5회)을 검증하려고 일부러 5번을 정상 발송시키는 건 불필요한 비용
지출이라고 판단했다. 대신:
- 코드 경로상 `phoneSmsRateLimitService.checkAndRecord(clientIp)`가 `ppurioSmsService.sendSms(...)`
  **호출 이전**에 실행되도록 배치해서, 한도를 넘긴 이후 요청은 SMS 발송/DB 저장 코드에 도달하지 못하고
  예외로 즉시 반환됨을 코드 리뷰로 확인
- Redis `INCR`/`EXPIRE`/임계값 비교 로직 자체는 `LoginAttemptService`와 동일한 구조라 별도 신규
  검증 없이 기존 신뢰를 그대로 이어받음

**향후 실사용 중 확인이 필요한 부분** — 팀에서 실제로 6번 연속 SMS 인증 요청을 보내서(혹은 Redis
CLI로 `phone:sms:count:{ip}:{오늘날짜}` 키를 미리 6으로 설정해두고 요청 1번만 보내서) 6번째 요청이
`429 PHONE_SMS_DAILY_LIMIT_EXCEEDED`로 거부되는지, 그리고 다음날에는 다시 정상 발송되는지 라이브로
확인하는 것을 권장한다.
