## 1. 왜 로그인 실패 잠금과 다른 방식인가
------------------------------------------------------------------------
`LoginAttemptService`(02.로그인)는 "실패"를 카운트해서 5회 실패 시 30분 잠그는 방식이다. 로그인은
비밀번호를 몰라서 계속 틀리는 공격(무차별 대입)을 막는 게 목적이라 "실패"가 기준이 맞다.

반면 SMS 발송은 **성공/실패와 무관하게 호출 자체가 비용**이다(뿌리오 API가 실제로 문자를 보내고
과금됨). 그래서 이번엔 "실패 카운트 + 잠금" 대신 "시도 카운트 + 하루 한도"로 설계했다 — 매 호출마다
카운트를 올리고, 한도를 넘기면 그 시점부터 자정까지 카운트 키의 TTL이 다할 때까지 계속 거부한다.

------------------------------------------------------------------------
## 2. Redis 키 설계
------------------------------------------------------------------------
```
phone:sms:count:{ip}:{yyyy-MM-dd}  →  INCR, TTL 25시간
```
- 키에 날짜를 포함시켜서 **자정이 지나면 자동으로 새 카운터**가 시작된다(기존
  `login:fail:{memberId}` 방식처럼 별도 "잠금 해제" 로직이나 스케줄러가 필요 없음 — 단순히 오늘 날짜의
  키가 다르기 때문에 자연스럽게 리셋됨).
- TTL을 24시간이 아니라 25시간으로 여유를 둔 이유는 `LoginAttemptService`의 `FAIL_COUNT_SAFETY_TTL`
  설계와 같은 이유 — 자정 근처 타이밍 이슈로 키가 예상보다 일찍 사라지는 걸 방지하는 안전 마진.
- 한도를 넘긴 뒤에도 계속 호출하면 카운트는 계속 올라가지만(예: 100회 호출하면 100까지 올라감),
  `MAX_SMS_PER_IP_PER_DAY`(5)를 넘는 순간부터는 매번 예외를 던지고 실제 SMS 발송/DB 저장 이전에 막히므로
  실제 비용 발생은 없다. 카운트 값 자체가 무한정 커지는 것도 TTL이 있어 문제 없음.

## 3. 왜 컨트롤러가 아니라 서비스 계층(PhoneAuthService) 안에 넣었나
------------------------------------------------------------------------
발송 진입점이 3개(`PhoneAuthController.sendCode`, `MemberController.sendFindEmailPhoneCode`,
`MemberController.sendProfilePhoneCode`)로 나뉘어 있지만, 셋 다 결국
`PhoneAuthService.sendVerificationCode()` 하나를 호출한다. 각 컨트롤러/서비스 메서드마다 따로
체크 로직을 넣으면 3곳을 전부 똑같이 맞춰야 하고 나중에 누락되기 쉬우므로, 실제로 SMS를 보내는
단일 지점(`sendVerificationCode`) 안에 체크를 넣어서 한 번만 구현하면 3곳 모두 자동으로 적용되게 했다.

IP는 `HttpServletRequest`에서만 얻을 수 있어서 서비스 계층까지 문자열로 전달해야 했다 — 각 컨트롤러
메서드에 `HttpServletRequest httpRequest` 파라미터를 추가하고, 새로 만든 `ClientIpUtil.resolve()`로
추출한 뒤 서비스 메서드 파라미터(`clientIp`)로 그대로 흘려보내는 방식을 택했다(체감상 흔한 패턴 —
필터/인터셉터로 뽑아서 요청 스코프 빈에 담는 방식도 검토했지만, 호출 지점이 3곳뿐이라 파라미터로
직접 전달하는 게 더 단순하다고 판단).

## 4. IP 추출 — X-Forwarded-For 우선
------------------------------------------------------------------------
```java
String forwardedFor = request.getHeader("X-Forwarded-For");
if (forwardedFor != null && !forwardedFor.isBlank()) {
    return forwardedFor.split(",")[0].trim();  // "client, proxy1, proxy2" 중 맨 왼쪽
}
return request.getRemoteAddr();
```
지금 당장은 Jenkins가 이 VM 위에서 직접 앱을 실행하고 있어 리버스 프록시가 없지만(요청이 클라이언트 →
앱으로 바로 옴), `AI-서버-배포-아키텍처-계획.md`에서 논의 중인 Nginx 리버스 프록시가 나중에 도입되면
`request.getRemoteAddr()`는 Nginx 자신의 IP(항상 127.0.0.1 근처)만 보여주게 되어 이 기능이 무력화된다 —
미리 `X-Forwarded-For`를 우선 확인하도록 만들어서 나중에 프록시가 생겨도 그대로 동작하게 했다.

## 5. 한도 값(하루 5회) 선정 근거
------------------------------------------------------------------------
정상적인 사용자는 한 세션에서 보통 1~2회(운 나쁘면 오타로 재발송 1~2회 추가)면 충분하다는 가정으로,
여유를 조금 더 두어 5회로 설정했다(회원가입/이메일찾기/회원정보수정이 전부 같은 카운터를 공유하므로,
그날 여러 기능을 오가며 테스트하는 것도 고려). 정확한 최적값을 데이터로 검증한 건 아니라 향후 실사용
패턴을 보고 조정 가능 — `PhoneSmsRateLimitService.MAX_SMS_PER_IP_PER_DAY` 상수 하나만 바꾸면 된다.

## 6. 에러 응답
------------------------------------------------------------------------
`ErrorCode.PHONE_SMS_DAILY_LIMIT_EXCEEDED` — `HTTP 429 Too Many Requests`,
"SMS 인증 요청 횟수를 초과했습니다. 내일 다시 시도해주세요." 이 프로젝트의 기존 에러 응답 형식
(`{success, code, message}`, `GlobalExceptionHandler`)을 그대로 따른다 — 별도 처리 추가 불필요.
