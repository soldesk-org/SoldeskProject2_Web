# 전화번호 SMS 인증 속도 제한 (일일 횟수 제한 + IP 차단)
------------------------------------------------------------------------

------------------------------------------------------------------------
## 실행 환경
------------------------------------------------------------------------
사용하는 툴
- STS
사용하는 코드
- Spring Boot(백엔드), Redis(카운트 저장)
작업 영역
- Project2

------------------------------------------------------------------------
## 요청사항 원문 요약
------------------------------------------------------------------------
"우리 지금 회원가입이나 회원정보수정, 이메일 찾기에서 전화번호 인증 하잖아 그거 누가 악의적으로 막
여러번 시도해서 돈 나가게 할 수 있으니 그거 하루에 횟수 정해서 그 기기 또는 IP를 차단해서 더이상
요청 할 수 없게 해놓은거 맞아? 아니라면 수정해주고" — 전화번호 SMS 인증번호 발송(뿌리오 API 호출,
발송 1건마다 실제 비용 청구)에 악용 방지 장치가 있는지 확인 요청, 없으면 추가해달라는 요청.

------------------------------------------------------------------------
## 배경 — 확인 결과: 방지 장치가 전혀 없었음
------------------------------------------------------------------------
`PhoneAuthService.sendVerificationCode()`를 직접 확인한 결과, 인증번호 생성 → DB 저장 → 뿌리오(Ppurio)
SMS 발송까지 어떤 횟수 제한도 없이 호출될 때마다 무조건 실행되고 있었다. 이 메서드는 3곳에서 호출된다:

1. 회원가입(`POST /api/phone/send-code`, `PhoneAuthController`) — 이메일 인증만 통과하면 비로그인
   상태에서도 호출 가능
2. 이메일 찾기(`POST /api/members/find-email/verify-phone/send-code`) — 마찬가지로 비로그인 상태
3. 회원정보수정(`POST /api/members/me/phone/send-code`) — 로그인 필요

이메일 인증 자체는 이메일 계정 접근이 필요해 다소 진입장벽이 있지만, 그 이후 SMS 발송 단계에는
아무 제약이 없어서, 같은 이메일 계정(또는 같은 회원)으로 반복 요청하면 그때마다 실제 SMS 비용이
청구되는 구조였다. 02(로그인)의 `LoginAttemptService`(Redis INCR + TTL 기반 잠금)와 같은 보호 장치가
전화번호 인증 쪽에는 없었던 것.

## 이번 범위 정리
------------------------------------------------------------------------
- SMS 발송 요청을 **IP 기준**으로 하루 최대 5회까지만 허용, 초과 시 그날 자정까지 추가 요청을 전부
  거부(`429 PHONE_SMS_DAILY_LIMIT_EXCEEDED`)
- 3곳의 발송 진입점(회원가입/이메일찾기/회원정보수정)이 전부 `PhoneAuthService.sendVerificationCode()`
  하나를 거치므로, 그 메서드 안에 카운트 체크를 넣는 것만으로 3곳 모두 한 번에 커버
- 카운트는 `LoginAttemptService`와 동일한 패턴으로 Redis에 저장(원자적 INCR, 날짜 기준 키라서 자정에
  자연스럽게 리셋, 안전을 위한 TTL도 별도로 걸어둠)
- IP는 리버스 프록시(향후 Nginx 도입 시)를 고려해 `X-Forwarded-For` 헤더를 우선 확인하고, 없으면
  `request.getRemoteAddr()`를 사용

------------------------------------------------------------------------
## 이번 범위에서 제외된 것
------------------------------------------------------------------------
- **"기기" 단위 차단** — 요청에 명시된 "기기 또는 IP" 중 IP만 구현. 기기 식별(예: 디바이스 핑거프린팅,
  앱 설치 ID)은 이 프로젝트가 웹 기반이라 신뢰할 수 있는 기기 식별자가 없고, 별도의 클라이언트 측
  식별 로직 도입이 필요해 이번 범위에서는 제외 — IP 차단만으로도 동일 인물의 반복 시도는 대부분 막힘
- 전화번호(수신자) 기준 제한 — 예를 들어 "같은 전화번호로 하루 몇 건까지만" 같은 별도 제한은 이번에
  추가하지 않음(공격자가 IP를 바꿔가며 같은 피해자 번호로 반복 발송시키는 시나리오는 여전히 남아있는
  한계 — 필요해지면 전화번호 기준 카운트를 추가로 도입 가능)
- 영구 차단/수동 IP 블랙리스트 관리 화면 — 이번엔 "하루 한도 초과 시 그날만 차단"만 구현, 관리자가
  특정 IP를 영구 차단하는 기능은 범위 밖
- 로그인 실패 잠금(`LoginAttemptService`)처럼 "몇 회 실패하면 30분 잠금" 방식이 아니라, "하루 몇 회까지"
  방식으로 확정 — SMS는 성공/실패 여부와 무관하게 발송 자체가 비용이라 "실패 횟수"가 아니라 "시도 횟수"
  기준이 맞다고 판단
