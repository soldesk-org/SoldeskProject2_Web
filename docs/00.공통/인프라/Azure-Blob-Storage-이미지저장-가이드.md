# Azure Blob Storage 이미지 저장 가이드
------------------------------------------------------------------------
2026-08-18 추가. 프로필/영수증/리뷰/음식점 이미지를 지금까지처럼 **VM 로컬 디스크**에 저장할지,
**Azure Blob Storage**(S3의 Azure 버전)에 저장할지를 `IMAGE_STORAGE_BACKEND` 값 하나로 전환하는
기능. 기본값은 여전히 `local`이라 이 문서를 안 보고 넘어가도 지금까지와 동작이 똑같다 — 이 문서는
**실제로 Azure Blob으로 전환하기로 했을 때**, 그리고 **VM을 새로 옮길 때** 빠짐없이 따라 하기 위한
런북(runbook)이다.

> 배경: [Redis-Docker-구축-가이드.md](Redis-Docker-구축-가이드.md)와 같은 이유로 시작된 대화 —
> "지금 Azure 쓰는데 S3 안 쓴다면서 사진은 어디 저장되냐"는 질문에서, 로컬 디스크 저장의 리스크
> (VM 디스크 손상/재구축 시 사진 전부 유실, 별도 백업 없음)를 확인하고 Azure Blob Storage로 전환
> 가능한 코드부터 먼저 만들어둔 것. 아직 실제 Azure 계정 연동 전까지는 `local`이 기본값.

------------------------------------------------------------------------
## 1. 코드 구조 (이미 완료됨, 참고용)
------------------------------------------------------------------------
- `common/storage/AzureBlobStorage.java` — Azure SDK 호출부를 공유하는 헬퍼 하나. `AZURE_STORAGE_CONNECTION_STRING`이
  비어있어도 서버 기동에는 영향 없음(다른 선택적 외부 연동과 동일 원칙) — 실제로 `store()`/`delete()`가
  호출되는 시점에만 `AZURE_STORAGE_NOT_CONFIGURED`로 실패한다.
- `common/storage/{Profile,Receipt,Review,Restaurant}ImageStorageService.java` — 4개 모두 `image-storage.backend`
  설정값(`local` 또는 `azure-blob`)에 따라 로컬 디스크/Blob 중 하나로 저장. `delete()`는 URL이 로컬
  `baseUrl`로 시작하면 항상 로컬 삭제를 우선하고, 그 외는 Blob 삭제로 간주 — **backend를 나중에 전환해도
  과거에 로컬 디스크에 저장됐던 이미지 URL은 계속 정상 서빙/삭제된다**(무중단 전환 가능, 마이그레이션
  스크립트로 기존 파일을 옮길 필요 없음. 새로 올리는 사진부터만 Blob으로 감).
- 컨테이너 이름은 코드에 고정값으로 박혀 있음(각 타입별 로컬 upload-dir 폴더 이름과 1:1 대응):
  `profile-images` / `receipt-images` / `review-images` / `restaurant-images`. 컨테이너가 없으면
  첫 업로드 때 자동 생성됨 — Azure Portal에서 미리 만들어둘 필요 없음.
- **(2026-08-18 버그 수정)** 컨테이너를 자동 생성할 때 `PublicAccessType.BLOB`을 반드시 명시해야 한다.
  Azure SDK의 `createIfNotExists()`를 인자 없이 호출하면 **기본값이 비공개 컨테이너**라서, 스토리지
  계정 레벨에서 "Blob 익명 액세스"를 켜놔도 실제 업로드된 이미지가 브라우저에서 403으로 막힌다 —
  처음 구현했을 때 이 버그가 있었고, `AzureBlobStorage.upload()`에서 이미 고쳐져 있음(재발 방지용으로
  기록만 남김. 혹시 이 헬퍼를 새로 만들거나 다른 방식으로 컨테이너를 만들 경우 이 부분을 반드시 확인할 것).

## 3. (선택) 네트워킹을 VM IP로만 제한하기
------------------------------------------------------------------------
필수는 아니다 — 연결 문자열(액세스 키) 없이는 어차피 아무도 못 들어오므로 기본값("모든 네트워크")으로
둬도 보안상 큰 구멍은 아니다. 다만 "키가 유출돼도 VM 밖에서는 접근 자체가 안 되게" 하는 추가 안전장치로
추천.

**전제조건: VM의 퍼블릭 IP가 고정(Static)이어야 함.** Azure Portal → 대상 VM → 네트워킹 → 네트워크
인터페이스 → 퍼블릭 IP 설정에서 할당이 **정적**인지 먼저 확인할 것. **동적**인 상태에서 IP 제한을
걸면, VM 재시작으로 IP가 바뀌는 순간 스토리지 접근이 갑자기 막히는 사고가 난다 — 그 경우 먼저 고정
IP로 바꾼 뒤 진행.

설정 방법: 스토리지 계정 → 네트워킹 → 공용 네트워크 액세스를 "선택한 IP 주소 범위에서 사용"(또는
"선택한 네트워크")으로 변경 → VM의 퍼블릭 IP를 방화벽 규칙에 추가.

## 4. 연결 문자열 확인 및 반영
------------------------------------------------------------------------
1. 생성된 스토리지 계정 → **보안 및 네트워킹 > 액세스 키** → "키 표시" → `연결 문자열` 복사
   (형식: `DefaultEndpointsProtocol=https;AccountName=...;AccountKey=...;EndpointSuffix=core.windows.net`)
2. **절대 git에 커밋하지 말 것** — `.env`/Jenkins Credential에만 넣는다(다른 시크릿 값과 동일 원칙).
3. **로컬 개발**: `Project2/.env`에 추가
   ```
   IMAGE_STORAGE_BACKEND=azure-blob
   AZURE_STORAGE_CONNECTION_STRING=<위에서 복사한 연결 문자열>
   ```
4. **운영 배포(Jenkins)**: Jenkins Credential에 `soldesk-azure-storage-connection-string`(이름은 팀 컨벤션에
   맞춰 정하되, 다른 Credential 이름 패턴과 통일) 등록 → `Jenkinsfile`의 `withCredentials` 블록과 `.env`
   heredoc 두 곳에 `AZURE_STORAGE_CONNECTION_STRING`/`IMAGE_STORAGE_BACKEND` 바인딩 추가
   (`PASSWORD_RESET_FRONTEND_URL`을 추가했을 때와 완전히 같은 절차 — Jenkins가 매 배포마다 `.env`를
   통째로 재생성하므로, Credential에 없는 값은 다음 배포에서 빈 값으로 덮어써진다는 점 주의).
5. 배포 후 실제 이미지 업로드 → 반환된 URL이 `https://{계정명}.blob.core.windows.net/{컨테이너}/...`
   형태인지 확인 → 그 URL을 로그인 없이 새 탭에서 직접 열어서 403 없이 이미지가 뜨는지 반드시 확인
   (2장의 "Blob 익명 액세스" 설정이 실제로 통했는지 검증하는 가장 확실한 방법).

## 5. VM을 새로 옮길 때 체크리스트
------------------------------------------------------------------------
스토리지 계정은 VM과 별개의 Azure 리소스라 **VM을 재구축해도 스토리지 계정 자체는 그대로 남는다** —
다시 만들 필요 없음. VM만 옮길 때 확인할 것:

- [ ] 새 VM의 `.env`에 `IMAGE_STORAGE_BACKEND=azure-blob` + `AZURE_STORAGE_CONNECTION_STRING` 반영됐는지
      (Jenkins Credential은 VM이 바뀌어도 그대로 유지되므로 보통 자동으로 따라옴 — Jenkins 자체를
      새 VM으로 옮기는 경우에만 Credential도 다시 등록해야 함)
- [ ] 3장에서 네트워킹을 VM IP로 제한해뒀다면, 새 VM의 퍼블릭 IP로 방화벽 규칙 갱신
      (예전 IP를 방치하면 굳이 막을 이유는 없지만, 정리 차원에서 같이 지워도 됨)
- [ ] 기존 로컬 디스크(`./uploads/*`)에 있던 과거 이미지들 — VM을 통째로 새로 만드는 경우 이 폴더가
      통으로 사라진다. `local` 백엔드로 저장됐던 과거 이미지들의 URL은 새 VM에서 그대로는 안 열림
      (파일 자체가 없으므로) — **VM 재구축 전에 반드시 `./uploads/` 전체를 새 VM으로 복사**해둘 것
      (`scp -r` 등). `azure-blob`으로 저장된 이미지는 VM과 무관하게 Blob에 그대로 남아있어 영향 없음 —
      이게 애초에 이 마이그레이션을 하는 이유(VM 재구축에도 안전한 저장소).
- [ ] 새 VM에서 실제 업로드 테스트 1회 (4장 5단계와 동일하게 URL 직접 열어서 확인)

## 6. 문제 해결
------------------------------------------------------------------------
- **이미지 URL을 열면 403 Forbidden** → 십중팔구 2장의 "Blob 익명 액세스"가 "사용 안 함"이거나,
  1장에서 설명한 `PublicAccessType.BLOB` 버그가 재발한 경우(코드를 건드렸다면). 스토리지 계정 →
  컨테이너 → 해당 컨테이너의 "액세스 수준"이 "Blob(익명 Blob 읽기 액세스)"로 되어 있는지 직접 확인.
- **업로드 시 `AZURE_STORAGE_NOT_CONFIGURED` 에러** → `AZURE_STORAGE_CONNECTION_STRING`이 비어있거나
  Jenkins Credential이 안 걸려있는 상태에서 `IMAGE_STORAGE_BACKEND=azure-blob`만 켜진 경우. 서버는
  정상 기동하지만 실제 업로드 시점에 이 에러가 남 — 4장 확인.
- **과거(로컬 디스크) 이미지가 새 배포 후 갑자기 안 보임** → 5장 체크리스트의 `./uploads/` 복사를
  빠뜨린 경우. `local` 백엔드 URL은 여전히 로컬 디스크의 실제 파일을 찾으므로, 그 파일이 없는 새
  VM에서는 404가 난다.
