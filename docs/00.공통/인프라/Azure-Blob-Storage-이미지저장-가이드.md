3차 수정(**실제 원인 특정 및 최종 해결 — 아래 4장 참고**). 프로필/영수증/리뷰/음식점 이미지를 지금까지처럼
**VM 로컬 디스크**에 저장할지, **Azure Blob Storage**(S3의 Azure 버전)에 저장할지를 `IMAGE_STORAGE_BACKEND`
값 하나로 전환하는 기능. **2026-08-18 실제 전환 완료 및 라이브 검증 완료** — 지금 운영 서버는

때** 참고하는 런북(runbook)이다.

> (VM 디스크 손상/재구축 시 사진 전부 유실, 별도 백업 없음)를 확인하고 Azure Blob Storage로 전환
> 가능한 코드부터 먼저 만들어둔 것.

> **⚠️ 이 문서는 GitHub에 올라간다.** `/docs/`는 `.gitignore`에 있지만 이 폴더는 `git add -f`로

## 1. 코드 구조 (이미 완료됨, 참고용)
------------------------------------------------------------------------
- `common/storage/AzureBlobStorage.java` — Azure SDK 호출부를 공유하는 헬퍼 하나. `AZURE_STORAGE_ACCOUNT_URL`이
  비어있어도 서버 기동에는 영향 없음(다른 선택적 외부 연동과 동일 원칙) — 실제로 `store()`/`delete()`가
  호출되는 시점에만 `AZURE_STORAGE_NOT_CONFIGURED`로 실패한다.
- `common/storage/{Profile,Receipt,Review,Restaurant}ImageStorageService.java` — 4개 모두 `image-storage.backend`
  설정값(`local` 또는 `azure-blob`)에 따라 로컬 디스크/Blob 중 하나로 저장. `delete()`는 URL이 로컬
  `baseUrl`로 시작하면 항상 로컬 삭제를 우선하고, 그 외는 Blob 삭제로 간주 — **backend를 나중에 전환해도
  과거에 로컬 디스크에 저장됐던 이미지 URL은 계속 정상 서빙/삭제된다**(무중단 전환 가능, 마이그레이션
  스크립트로 기존 파일을 옮길 필요 없음. 새로 올리는 사진부터만 Blob으로 감).
- 컨테이너 이름은 코드에 고정값으로 박혀 있음(각 타입별 로컬 upload-dir 폴더 이름과 1:1 대응):
  `profile-images` / `receipt-images` / `review-images` / `restaurant-images`. 컨테이너가 없으면
  첫 업로드 때 자동 생성됨 — Azure Portal에서 미리 만들어둘 필요 없음.
- **(2026-08-18 버그 수정)** 컨테이너를 자동 생성할 때 `PublicAccessType.BLOB`을 반드시 명시해야 한다.
  Azure SDK의 `createIfNotExists()`를 인자 없이 호출하면 **기본값이 비공개 컨테이너**라서, 스토리지
  계정 레벨에서 "Blob 익명 액세스"를 켜놔도 실제 업로드된 이미지가 브라우저에서 403으로 막힌다 —
  처음 구현했을 때 이 버그가 있었고, `AzureBlobStorage.upload()`에서 이미 고쳐져 있음.
- **(2026-08-18 2차 수정, 매우 중요) 인증 방식을 연결 문자열(계정 키) → Managed Identity로 전환.**
  4장에서 자세히 설명하지만 요약하면: 이 프로젝트가 쓰는 Azure 구독에 "로컬 인증(계정 키/SAS) 금지"
  정책이 걸려있어서 계정 키 방식은 아예 동작하지 않는다. `AzureBlobStorage`는 이제
  `com.azure.identity.ManagedIdentityCredential`로 인증하고, 설정값도 `azure-storage.connection-string`
  대신 `azure-storage.account-url`(스토리지 계정 엔드포인트 URL) 하나만 있으면 된다.

## 3. 네트워킹을 좁히지 말 것 (★ 실제로 겪은 함정)
------------------------------------------------------------------------
처음엔 "VM IP/VNet만 허용"으로 네트워킹을 좁히는 걸 추가 보안장치로 고려했었다. **실제로 해보니 이건
우리 서비스 구조와 안 맞는다** — 업로드/삭제(VM이 하는 쓰기 작업)는 되지만, 일반 방문자의 브라우저가
이미지를 보려는 요청(로그인 없는 공개 조회)까지 막혀버린다. 우리 서비스는 프로필/리뷰/영수증 사진을
누구나 볼 수 있어야 하는 구조라서, **네트워킹은 반드시 "모든 네트워크에서 사용"으로 열어둬야 한다**
(2장 표 참고). 쓰기 보안은 네트워크가 아니라 Managed Identity/RBAC(4장)가 담당한다 — 네트워크를
열어도 계정 키가 없으므로 업로드/삭제는 여전히 우리 VM만 할 수 있다.

VM이 속한 VNet(`SoldeskProject1-vnet`)의 서브넷에 "서비스 엔드포인트"(Microsoft.Storage)를 추가하는
규칙 자체는 남겨둬도 무해하다(4-3장 진단 과정에서 추가했던 것) — 그냥 안 쓰일 뿐 문제는 없다.

## 4. 인증/네트워킹 설정 — 실제로 겪은 함정 전체 기록 (★ 반드시 읽을 것)
------------------------------------------------------------------------
이 기능을 실제로 켜기까지 원인 진단에 몇 시간이 걸렸다. **최종 원인은 스토리지 계정의 네트워킹(방화벽)
설정**이었는데, 그걸 알아내기까지 여러 번 잘못된 결론에 도달했었다 — 같은 시행착오를 반복하지 않도록
전체 과정을 그대로 남긴다.

### 4-1. 1차 시도: 연결 문자열(계정 키) 방식 — 실패
처음엔 표준적인 방식대로 "액세스 키 > 연결 문자열"을 복사해서 `AZURE_STORAGE_CONNECTION_STRING`에
넣는 방식으로 구현했다. 실제 배포해서 업로드해보니 **키를 완전히 새로 재생성해도 전부
`AuthorizationFailure`(403)로 거부**됐다 — 스토리지 계정의 "스토리지 계정 키 액세스 허용" 토글은
"사용"으로 켜져 있었는데도 그랬다. (SDK 에러 메시지에 "Signature did not match" 문구가 있어서 한때
"키가 틀렸나"로 오인했는데, 이건 `BlobStorageException`이 원인과 무관하게 항상 붙이는 고정 안내
문구였다 — 로그 끝까지 보면 실제 서버 응답은 `Status code 403, AuthorizationFailure`.)

### 4-2. 2차 시도: Managed Identity로 전환 — 여전히 실패
"Azure Portal의 스토리지 브라우저에서는 수동으로 컨테이너 생성이 되는데 우리 앱(계정 키 인증)만 안 된다"는
차이를 보고, 인증 방식 자체를 **VM의 시스템 관리 ID(Managed Identity) + Azure AD 인증**으로 바꿨다
(계정 키 대신 `azure-storage.account-url`만 쓰는 지금 코드 구조). 그런데 이것도 처음엔 **똑같이
`AuthorizationFailure`로 실패**했다 — IMDS로 토큰을 직접 발급받아 확인해보니 토큰 자체(`oid`, `aud`)도
정상, 스토리지 계정 IAM에 "Storage Blob 데이터 Contributor" 역할도 정확히 할당돼 있는 게 확인됐는데도
40분 넘게 계속 거부당했다. 이 시점에 "이 구독이 CSP 파트너(Azure 플랜)를 통해 발급된 구독이라 관리
그룹 레벨에 우리가 못 보는 정책이 걸려있는 것 아니냐"는 가설까지 세웠었는데 — **이건 틀린 결론이었다.**
구독 레벨 Azure Policy 할당은 실제로 확인해봐도 Defender for Cloud 기본 감사용 이니셔티브 하나뿐이었고
Deny 정책은 없었다.

### 4-3. 진짜 원인 — 스토리지 계정 네트워킹(방화벽)
막힌 진짜 이유는 **스토리지 계정의 "네트워킹" 탭, 공용 네트워크 액세스 설정**이었다. 어느 시점부턴가
이 설정이 (Portal에 "모든 네트워크"로 보였음에도 실제로는) VM에서 오는 요청조차 제대로 통과시키지
못하는 상태였던 것으로 보인다. 해결 순서:
1. 먼저 스토리지 계정 네트워킹에서 **VM이 속한 VNet(`SoldeskProject1-vnet`)의 서브넷에 "서비스
   엔드포인트"(Microsoft.Storage)를 추가**하고 저장했더니, VM에서의 요청(관리 ID 토큰으로 컨테이너
   목록 조회 등)이 **즉시 200 OK로 성공**했다 — 이게 네트워킹이 진짜 원인이었다는 결정적 증거.
2. 그런데 이 상태(네트워킹이 "선택한 네트워크"로 좁혀지고 VM의 VNet만 허용)에서 실제 이미지 업로드를
   해보니, **업로드/삭제(VM이 하는 쓰기 작업)는 되는데 업로드된 이미지 URL을 외부(VM 밖 아무 데서나)
   에서 열면 403**이 났다. 우리 서비스는 로그인 없이 누구나 이미지를 볼 수 있어야 하므로(일반 방문자
   브라우저는 그 VNet 안에 있지 않음), 쓰기만 되고 공개 읽기가 안 되는 상태로는 기능이 불완전했다.
3. **최종 해결**: 네트워킹을 다시 **"모든 네트워크에서 사용"**으로 변경 → 저장. 이 상태로 실제
   업로드(200) → 외부에서 이미지 URL 접근(200) → 삭제(200) → 삭제 후 재접근(404)까지 전부 라이브
   검증 완료. (VNet 서비스 엔드포인트 규칙은 굳이 지우지 않고 그대로 둬도 무해함 — 안 쓰일 뿐.)

**교훈**: 이 문제는 인증 방식(계정 키 vs Managed Identity)과는 무관했다. 처음에 "선택한 IP 주소
범위에서 사용"이나 "선택한 네트워크"로 되어 있었거나, Portal에 표시된 값과 실제 적용된 값이 어긋나
있었을 가능성이 높다 — **네트워킹 탭을 직접 열어서 명시적으로 "모든 네트워크에서 사용"으로 바꾸고
저장하는 행위 자체**가 문제를 해결했다. 다음에 비슷한 증상(계정/역할 설정은 다 맞는데 계속
`AuthorizationFailure`)을 겪으면, 권한 설정보다 **네트워킹 탭부터 먼저 의심할 것**.

### 4-4. Managed Identity 설정 (그대로 유지 — 계정 키보다 안전해서 되돌리지 않음)
계정 키 대신, VM 자체에 Azure AD ID를 부여하고 그 ID에 스토리지 접근 권한을 주는 방식. 계정 키 자체가
필요 없어져서 (a) 위 정책과 충돌하지 않고 (b) 유출될 시크릿이 아예 없어 더 안전하다.

**설정 절차 (Azure Portal, 최초 1회):**

1. **VM에 시스템 관리 ID 켜기**
   - VM(`SoldeskProject1`) → 왼쪽 메뉴 **"ID"**(Identity) → **"시스템 할당됨"** 탭 → 상태를
     **"켬"**으로 변경 → 저장. (이 VM 전용 Azure AD 서비스 주체가 자동으로 하나 생성됨)

2. **그 ID에 스토리지 접근 권한(RBAC) 부여**
   - 스토리지 계정(`eattywaystorage`) → 왼쪽 메뉴 **"액세스 제어(IAM)"** → **"+ 추가" → "역할 할당 추가"**
   - 역할 검색창에 **"Blob"**만 입력 → **"Storage Blob 데이터 Contributor"** 선택
     (⚠️ Azure Portal 한글 버전에서 역할 이름이 일부만 번역되어 "Storage Blob 데이터 Contributor"처럼
     영-한 혼용으로 표시된다 — 정식 영문명은 "Storage Blob Data Contributor". "Storage Blob 데이터
     소유자(Owner)"나 "Reader"와 헷갈리지 않게 정확히 "Contributor"를 선택할 것)
   - **"구성원"** 탭 → 액세스 대상 **"관리 ID"** 선택 → **"+ 멤버 선택"** → 구독에서 이 VM 이름
     (`SoldeskProject1`)으로 검색 → 선택 (구성원 유형이 "가상 머신"으로 뜨면 정상)
   - **"조건"** 탭은 건너뛰고(기본값 "조건을 추가하지 않음") **"검토 + 할당"**

3. Jenkins Credential `soldesk-azure-storage-account-url`(문자열, 값: `https://{계정명}.blob.core.windows.net`)
   등록 → `Jenkinsfile`의 `withCredentials` 블록(Test/Deploy 두 스테이지)과 `.env` heredoc에 반영
   (`PASSWORD_RESET_FRONTEND_URL`을 추가했을 때와 완전히 같은 절차).

4. 배포 후 실제 이미지 업로드 → 반환된 URL이 `https://{계정명}.blob.core.windows.net/{컨테이너}/...`
   형태인지 확인 → 그 URL을 로그인 없이 새 탭에서 직접 열어서 403 없이 이미지가 뜨는지 반드시 확인
   (2장의 "Blob 익명 액세스" 설정이 실제로 통했는지 검증하는 가장 확실한 방법).

**로컬 개발 환경 참고**: `ManagedIdentityCredential`은 실제 Azure VM 위에서만 동작한다(관리 ID가
그 VM에 귀속되므로). 로컬 개발 PC에서는 이 기능을 쓸 수 없고, 쓸 필요도 없다 — 로컬은 그냥
`IMAGE_STORAGE_BACKEND=local`(기본값)로 두면 된다.

## 5. 요금(비용)
------------------------------------------------------------------------
Blob Storage는 **VM(컴퓨팅) 비용에 비하면 사실상 무시해도 되는 수준**이다.

- **저장 용량**: Hot 티어 LRS 기준 약 **GB당 월 $0.02** (1GB에 한 달 약 25~30원 수준)
- **트랜잭션(업로드/조회 등)**: 만 건당 몇 센트 수준, 이 프로젝트 트래픽에선 사실상 0에 수렴
- 프로필/리뷰/영수증/음식점 사진 합쳐 몇 천 장(총 몇 GB) 규모라면 **월 몇백 원~1~2천 원 수준**으로 예상
- 위 4장에서 켠 **Blob 일시 삭제(7일 보관)**, **컨테이너 일시 삭제(7일)** 도 추가 스토리지 비용이
  거의 안 든다(지워진 데이터만 7일간 더 보관하는 것뿐이라 삭제를 자주 안 하면 영향 미미)
- **비용을 늘릴 수 있는 설정(피할 것)**: GRS/RA-GRS(지역 복제, 이미 2장에서 LRS로 안내함), 버전 관리
  (Versioning, 파일마다 이전 버전을 계속 남김), Cool/Archive 티어를 자주 조회하는 데 쓰는 경우(검색
  비용이 저장 비용보다 비쌈), 스토리지용 Defender(요청당 과금)

**$200~300 크레딧 구독 기준으로 체감될 정도로 깎아먹는 항목이 아니다** — 이 크레딧을 소진시키는 건
거의 항상 VM(컴퓨팅)이나 GPU 인스턴스 쪽이지, Blob Storage 저장 용량이 아니다.

## 6. VM을 새로 옮길 때 체크리스트
------------------------------------------------------------------------
스토리지 계정은 VM과 별개의 Azure 리소스라 **VM을 재구축해도 스토리지 계정 자체는 그대로 남는다** —
다시 만들 필요 없음. 다만 **Managed Identity는 VM 자체에 귀속된 리소스라 VM을 재구축하면 반드시
다시 설정해야 한다** (이 부분이 예전 연결 문자열 방식과 가장 다른 점 — 그때는 문자열 값만 복사하면
끝이었지만, 지금은 Portal 작업이 다시 필요함).

- [ ] **새 VM에 시스템 관리 ID를 다시 켜기** (4-4장 1단계와 동일) — 기존 VM의 관리 ID는 그 VM이
      삭제되면 같이 사라진다, 새 VM은 새 ID가 생성됨
- [ ] **스토리지 계정 IAM에 새 VM의 관리 ID로 "Storage Blob 데이터 Contributor" 역할 다시 할당**
      (4-4장 2단계와 동일) — 예전 VM에 할당했던 역할은 그 VM이 삭제되면 자동으로 정리되므로 신경
      안 써도 됨, 새 VM 몫만 새로 추가하면 됨
- [ ] 새 VM의 `.env`에 `IMAGE_STORAGE_BACKEND=azure-blob` + `AZURE_STORAGE_ACCOUNT_URL` 반영됐는지
      (Jenkins Credential은 VM이 바뀌어도 그대로 유지되므로 보통 자동으로 따라옴 — Jenkins 자체를
      새 VM으로 옮기는 경우에만 Credential도 다시 등록해야 함. 참고로 이 값은 시크릿이 아니라 그냥
      URL이라 재등록도 매우 간단함)
- [ ] 3장에서 네트워킹을 VM IP로 제한해뒀다면, 새 VM의 퍼블릭 IP로 방화벽 규칙 갱신
- [ ] 기존 로컬 디스크(`./uploads/*`)에 있던 과거 이미지들 — VM을 통째로 새로 만드는 경우 이 폴더가
      통으로 사라진다. `local` 백엔드로 저장됐던 과거 이미지들의 URL은 새 VM에서 그대로는 안 열림
      (파일 자체가 없으므로) — **VM 재구축 전에 반드시 `./uploads/` 전체를 새 VM으로 복사**해둘 것
      (`scp -r` 등). `azure-blob`으로 저장된 이미지는 VM과 무관하게 Blob에 그대로 남아있어 영향 없음 —
      이게 애초에 이 마이그레이션을 하는 이유(VM 재구축에도 안전한 저장소).
- [ ] 새 VM에서 실제 업로드 테스트 1회 (4-4장 4단계와 동일하게 URL 직접 열어서 확인)

## 7. 문제 해결
------------------------------------------------------------------------
- **업로드 시도 시 `AuthorizationFailure`(403)** → 확인 순서(실제로 이 순서로 원인을 찾았음, 4장 참고):
  1. **먼저 스토리지 계정 "네트워킹" 탭에서 공용 네트워크 액세스가 "모든 네트워크에서 사용"인지 확인**
     — 권한(IAM) 설정이 전부 맞아도 네트워킹이 좁혀져 있으면 똑같은 에러가 난다. 실제로 몇 시간을
     날린 원인이 이거였다(4-3장). 권한보다 먼저 이것부터 볼 것.
  2. VM의 "ID > 시스템 할당됨"이 "켬"인지
  3. 스토리지 계정 "액세스 제어(IAM) > 역할 할당"에 그 VM이 "Storage Blob 데이터 Contributor"로
     정확히 올라가 있는지(역할 이름이 "소유자"나 "Reader"로 잘못 할당되지 않았는지)
  4. 그래도 안 되면 Azure Portal "스토리지 브라우저"에서 수동 컨테이너 생성이 되는지부터 확인해서
     계정 자체 문제인지, 우리 쪽 설정 문제인지 먼저 구분할 것(4장 진단 과정 참고)
- **이미지 URL을 열면 403 Forbidden(업로드 자체는 성공했는데)** → 이것도 원인 1순위는 **네트워킹이
  "모든 네트워크"가 아닌 경우**다(3장 참고 — VM에서 하는 업로드는 되는데 외부 방문자만 막히는 정확히
  이 증상으로 나타남). 그 다음으로 2장의 "Blob 익명 액세스"가 "사용 안 함"이거나, 1장에서 설명한
  `PublicAccessType.BLOB` 버그가 재발한 경우(코드를 건드렸다면) — 스토리지 계정 → 컨테이너 → 해당
  컨테이너의 "액세스 수준"이 "Blob(익명 Blob 읽기 액세스)"로 되어 있는지 확인.
- **업로드 시 `AZURE_STORAGE_NOT_CONFIGURED` 에러** → `AZURE_STORAGE_ACCOUNT_URL`이 비어있거나
  Jenkins Credential이 안 걸려있는 상태에서 `IMAGE_STORAGE_BACKEND=azure-blob`만 켜진 경우. 서버는
  정상 기동하지만 실제 업로드 시점에 이 에러가 남 — 4-4장 3단계 확인.
- **과거(로컬 디스크) 이미지가 새 배포 후 갑자기 안 보임** → 6장 체크리스트의 `./uploads/` 복사를
  빠뜨린 경우. `local` 백엔드 URL은 여전히 로컬 디스크의 실제 파일을 찾으므로, 그 파일이 없는 새
  VM에서는 404가 난다.
