# SMS(문자) 본인인증 - 뿌리오(Ppurio) 연동 가이드
------------------------------------------------------------------------
전화번호 SMS 인증이 필요한 기능([01.회원가입](../01.회원가입/), [04.이메일찾기-비밀번호찾기](../04.이메일찾기-비밀번호찾기/), [05.회원정보수정](../05.회원정보수정/))에서
공통으로 재사용하는 Ppurio 문자연동 API 스펙 + 전화번호 인증(PhoneVerification) 공통 설계 문서
(2026-07-18 작성, **2026-07-20 API 스펙 전면 정정** — 아래 참고)
각 기능 문서에서는 이 문서를 참고만 하고, 기능별 세부 플로우/화면 문구는 각자의 001-02 설계 문서에 둠

> **2026-07-20 정정 안내**: 처음 이 문서를 작성할 때 참고했던 `https://bizppurio.github.io/`(api.bizppurio.com, `/v3/message`)는
> 구버전 문서였음. 사용자가 뿌리오 콘솔에서 실제 Swagger 문서(`https://message.ppurio.com`, OAS3)를 확인해줘서
> 엔드포인트/요청·응답 필드가 상당히 다르다는 게 드러남 — 이 문서 2~3장/5장을 전부 새 스펙 기준으로 다시 씀.
> `PpurioSmsService.java`도 같은 날 새 스펙에 맞춰 재작성됨.

## 1. 개요
------------------------------------------------------------------------
- **사용 대행사**: 뿌리오(Ppurio) — https://www.ppurio.com/
- **API 문서 (2026-07-20 정정)**: 뿌리오 콘솔 로그인 후 "연동 > 연동개발(API)" 메뉴에서 확인 가능한 Swagger 문서(`https://message.ppurio.com`, PPURIO API v1.0.0 OAS3) — 이전에 적어뒀던 `bizppurio.github.io`는 구버전이라 더 이상 참고하지 않음
- **비용** (기본단가, 부가세 포함)
  | 종류 | 단가 |
  |---|---|
  | 단문(SMS) | 21.82원 (부가세 포함 24원) |
  | 장문(LMS) | 45.46원 (부가세 포함 50원) |
  | 포토(MMS) | 90원 (부가세 포함 99원) |
  본인인증 번호는 90바이트 이내로 짧게 구성하면 단문(SMS) 단가로 발송 가능 (4장 참고)
- **혜택**: 뿌리오 신규 기업회원 전환 후 신청 시 **무료문자 1,000건** 지급 (2026-07-01 ~ 2026-07-31 이벤트, 최초 1회 한정)
- 비용/발신번호 신청 등 계정 관련 사항은 개발 범위 밖이라 "확인이 필요한 사항"(8장)으로 분리

## 2. 인증(토큰 발급) API (2026-07-20 정정)
------------------------------------------------------------------------
```
POST https://message.ppurio.com/v1/token
Authorization: Basic {Base64(account:authKey)}
Content-Type: application/json; charset=utf-8
```
- `authKey`는 계정 로그인 비밀번호가 **아니라**, 뿌리오 콘솔 "연동 > 연동개발(API)" 메뉴에서 별도로 발급받는 **"연동 개발 인증키"**. 발급 전에 "연동IP 등록"이 선행되어야 함(공식 문서 Note, 8장 참고)
응답 (200)
```json
{
  "token": "eyJ0eXAiOiJKV1QiLC...",
  "type": "Bearer",
  "expired": 20261110185520
}
```
필드명이 `accesstoken`이 아니라 **`token`**임에 주의(2026-07-18 초안 작성 당시 구버전 문서를 참고해 `accesstoken`으로 잘못 적었던 부분 — `PpurioSmsService.TokenResponse` 레코드도 `token`으로 수정됨)
- 토큰 유효기간 **24시간**(1일). 공식 문서에서도 "매 요청마다 발급하지 말고 캐싱해서 사용"을 권장, 문자연동 정보나 사용자 정보가 변경된 경우에도 재발급 필요
- **캐싱 전략**: 이 프로젝트는 이미 로그인 실패 카운트/refresh token/비밀번호 재설정 토큰을 전부 Redis에 TTL과 함께 저장하는 패턴을 쓰고 있으므로([00.공통 Redis-Docker-구축-가이드.md](Redis-Docker-구축-가이드.md)), Ppurio 토큰도 동일하게 Redis에 캐싱
  - 키: `ppurio:token`, 값: token, TTL: 23시간(공식 만료 24시간보다 여유 있게 짧게 잡아 만료 직전 사용 방지)
  - SMS 발송 직전 Redis에 토큰이 없으면(TTL 만료) `/v1/token`으로 재발급 후 캐싱
- 토큰 발급 실패 코드(400): `3001`(Authorization 헤더 유효하지 않음) / `3003`(IP 유효하지 않음 — 연동IP 미등록) / `3004`(계정 유효하지 않음) / `3007`(토큰 발행 실패) / `4004`(API 접근 권한 비활성화) / `4006`(인증키 유효하지 않음) / `4007`(인증키 미발급)

## 3. SMS 발송 API (2026-07-20 정정)
------------------------------------------------------------------------
```
POST https://message.ppurio.com/v1/message
Authorization: Bearer {token}
Content-Type: application/json; charset=utf-8
```
엔드포인트가 `/v3/message`가 아니라 **`/v1/message`**이고, 요청 바디 구조도 구버전과 상당히 다름(다건 발송/치환문구/MMS 첨부까지 지원하는 스펙으로 바뀌어서 수신자가 `targets` 배열로 감싸짐).

요청 바디 (우리가 실제로 쓰는 필드만 — 전체 스펙은 공식 Swagger 참고)
| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| account | string(20) | O | 뿌리오 계정 |
| messageType | string(3) | O | `"SMS"` 고정(우리는 90바이트 이내 단문만 사용, 1장) |
| content | string(2000) | O | 본문(SMS는 최대 90byte = 한글 최대 45자 내외) — **평문 문자열**로 전달(구버전처럼 `content.sms.message`로 감싸지 않음) |
| from | string(16) | O | 발신 번호 (뿌리오에 사전 등록된 번호만 사용 가능. 확정 발신번호: `070-5236-4828`, 8장 참고) |
| duplicateFlag | string(1) | O | 수신 번호 중복 허용 여부(`Y`/`N`) — 우리는 매번 새 refKey로 단건 발송이라 `N` 고정 |
| targetCount | number | O | 수신자 수 — 우리는 항상 `1`(단건 발송) |
| targets | array | O | 수신자 목록. 우리는 `[{ "to": "01012345678" }]`(하이픈 없이 숫자만)만 사용, `changeWord`/`name`(치환 문구)은 미사용 |
| refKey | string(32) | O | 요청 추적용 고유 키(UTF-8 최대 32바이트) — 대문자 K(`refKey`), 구버전 `refkey`와 다름 |

요청 예시
```json
{
  "account": "{PPURIO_ACCOUNT}",
  "messageType": "SMS",
  "content": "[Eattyway]\n본인확인 인증번호는 [318204]입니다.\n5분 이내에 입력해주세요.",
  "from": "07052364828",
  "duplicateFlag": "N",
  "targetCount": 1,
  "targets": [ { "to": "01012345678" } ],
  "refKey": "phoneverif-8f3c2a1b"
}
```
응답 (200, 성공)
```json
{ "code": 1000, "description": "ok", "refKey": "phoneverif-8f3c2a1b", "messageKey": "221128133505801SMS010542suchUL8P" }
```
주요 실패 코드(400): `2000`(잘못된 요청) / `3001`/`3002`/`3005`/`3006`(토큰·인증 헤더 문제) / `3003`(IP 유효하지 않음) / `3004`(계정 유효하지 않음) / `3008`(너무 많은 요청) / `4004`(API 접근 권한 비활성화) / `4006`(인증키 유효하지 않음) / `4007`(인증키 미발급)

## 4. 인증번호 메시지 포맷
------------------------------------------------------------------------
전달받은 예시 이미지(안드로이드 문자 앱 캡처)는 아래와 같은 형태였음
```
<#> 본인확인 인증번호는 [319287] 입니다.
aBcDeFgH1iJ
```
- `<#>` 접두사 + 메시지 끝의 11자리 해시값은 **안드로이드 SMS Retriever API** 전용 포맷으로, 네이티브 안드로이드 앱이 문자 내용을 자동으로 읽어(사용자가 직접 복사/입력하지 않아도) 인증번호를 채워주는 기능에 쓰인다. 해시값은 앱의 서명 키로 계산되는 "앱 고유 식별 해시"라 **네이티브 안드로이드 앱이 있어야만** 의미가 있음
- 이 프로젝트는 웹 서비스(Spring Boot + 웹 프론트)라 네이티브 안드로이드 앱이 없으므로, 기본 설계는 `<#>` + 해시 접미사 없이 **일반 텍스트 메시지**로 발송
- **(2026-07-20 실사용자 라이브 테스트 확인 후 확정)** 가독성을 위해 줄바꿈(`\n`)으로 3줄로 나눠서 발송(한 줄로 길게 이어지던 것에서 변경). `PhoneAuthService.buildMessage()`에 반영됨
  ```
  [Eattyway]
  본인확인 인증번호는 [318204]입니다.
  5분 이내에 입력해주세요.
  ```
- 추후 네이티브 앱이 생기면 `<#>` 포맷으로 전환 검토 (8장 "확인이 필요한 사항" 참고)

## 5. 계정/키 관리 (.env) (2026-07-20 정정 — PPURIO_PASSWORD → PPURIO_AUTH_KEY)
------------------------------------------------------------------------
기존 `PHONE_AES_KEY`/`PHONE_HASH_KEY`([01.회원가입 001-02 7-1장](../01.회원가입/001-02.회원가입-분석-설계.md#7-1-전화번호-aes-256-gcm-양방향-암호화-설계-2026-07-18-요구사항-추가))와 같은 패턴으로 `.env`에 추가
```
PPURIO_ACCOUNT=
PPURIO_AUTH_KEY=
PPURIO_SENDER_NUMBER=07052364828
```
- `PPURIO_ACCOUNT`: 뿌리오 계정 아이디 (토큰 발급 Basic 인증에 사용, 2장)
- `PPURIO_AUTH_KEY`(2026-07-20 이름 변경, 예전엔 `PPURIO_PASSWORD`): **계정 로그인 비밀번호가 아니라**, 뿌리오 콘솔 "연동 > 연동개발(API)" 메뉴에서 발급받는 "연동 개발 인증키" — 이 값 발급 전에 "연동IP 등록"이 선행되어야 함(공식 문서 Note, 8장 참고). 계정 로그인 비밀번호를 넣으면 토큰 발급이 `4006`(인증키가 유효하지 않음)으로 실패함
- `PPURIO_SENDER_NUMBER`: 뿌리오에 사전 등록한 발신번호. **확정: `070-5236-4828`** (API에는 하이픈 없이 `07052364828`로 전달, 3장 `from` 필드)

## 6. 공통 PhoneVerification(전화번호 인증) 설계
------------------------------------------------------------------------
기존 이메일 인증([01.회원가입 001-02 4-3장](../01.회원가입/001-02.회원가입-분석-설계.md) `EmailVerification`/`EmailAuthService`/`MailService`)과 동일한 구조를 그대로 미러링해서, 회원가입과 이메일 찾기 양쪽에서 재사용 가능하게 설계

### 6-1. 패키지 구조 (제안)
```
com.foodtrip.foodsearch
 └─ phone
     ├─ controller  PhoneAuthController      (POST /api/phone/send-code, /api/phone/verify-code)
     ├─ service     PhoneAuthService          (인증번호 생성/검증 비즈니스 로직, email의 EmailAuthService 대응)
     │              PpurioSmsService          (Ppurio 토큰 발급/캐싱 + SMS 발송, mail의 MailService 대응)
     ├─ dto         SendPhoneCodeRequestDto, VerifyPhoneCodeRequestDto, PhoneResponseDto
     ├─ entity      PhoneVerification         (email의 EmailVerification 대응)
     └─ repository  PhoneVerificationRepository
```

### 6-2. 데이터 모델: phone_verifications (신규 테이블)
`email_verifications`와 동일한 구조로 설계 — 회원가입 시점과 이메일 찾기 시점 둘 다 **이미 members row(member_id)가 존재하는 상태에서** 인증을 요청하므로 (회원가입은 이메일 인증 이후 단계, 이메일 찾기는 닉네임+전화번호로 이미 회원을 특정한 이후 단계) member_id FK 필수 제약을 그대로 사용 가능
| 컬럼명 | 타입 | 제약조건 | 설명 |
|---|---|---|---|
| phone_verification_id | BIGINT UNSIGNED | PK, AI | 고유번호 |
| member_id | BIGINT UNSIGNED | FK→members, NOT NULL | 인증 대상 회원 |
| phone | VARCHAR(20) | NOT NULL | 인증 대상 전화번호(평문, `010-XXXX-XXXX`) — SMS를 실제로 보내야 하므로 암호화하지 않음. 인증 완료/만료 후에는 값 자체가 더 이상 의미 없어지는 단기 데이터 |
| verification_code | VARCHAR(20) | NOT NULL | 인증번호(6자리 숫자) |
| purpose | VARCHAR(20) | NOT NULL | `SIGNUP`(회원가입) / `FIND_EMAIL`(이메일 찾기) — 같은 회원이 두 기능에서 동시에 인증을 진행해도 섞이지 않도록 구분 |
| is_verified | TINYINT(1) | NOT NULL, DEFAULT 0 | 인증 성공 여부 |
| expired_at | DATETIME | NOT NULL | 만료시각(발급시각 + 5분, 이메일 인증과 동일 정책) |
| verified_at | DATETIME | NULL | 인증 완료 시각 |
| created_at | DATETIME | NOT NULL | 생성일시 |

- `email_verifications`와 마찬가지로 인증 이력을 남기는 로그성 테이블이라 매 요청마다 새 row를 추가하는 방식(갱신이 아니라 insert), 조회는 "해당 member_id+purpose의 최신 row"
- 미인증 상태로 오래 남은 row 정리는 기존 `UnverifiedMemberCleanupScheduler`와 별개로 필요 여부 검토 (8장)

### 6-3. PhoneAuthService 처리 흐름 (이메일 인증과 대응)
| 이메일 인증 (기존) | 전화번호 인증 (신규, 대응 관계) |
|---|---|
| `POST /api/mail/send-code` | `POST /api/phone/send-code` |
| members row 조회/생성 후 6자리 코드 생성 | member_id + 전화번호로 6자리 코드 생성 (member_id는 각 기능의 문맥에 따라 이미 정해져 있음, 7장/9장 참고) |
| `EmailVerificationRepository`에 저장 후 `MailService.sendVerificationCode()` | `PhoneVerificationRepository`에 저장 후 `PpurioSmsService.sendVerificationSms()` |
| `POST /api/mail/verify-code` | `POST /api/phone/verify-code` |
| 최신 레코드 조회 → 만료/불일치 검증 → `is_verified=1` | 동일 (purpose까지 함께 비교) |

### 6-4. 예외/에러코드 (공통 정의, ErrorCode에 추가)
| 코드 | 상황 | HTTP Status |
|---|---|---|
| PHONE_NOT_FOUND | 발송 이력이 없는 전화번호로 확인 요청 | 400 |
| INVALID_CODE | 인증번호 불일치 (기존 이메일 인증과 같은 코드 재사용 — 채널이 달라도 "코드가 틀렸다"는 의미는 동일) | 400 |
| EXPIRED_CODE | 인증번호 만료 (기존 이메일 인증과 같은 코드 재사용) | 400 |
| PHONE_NOT_VERIFIED | 전화번호 인증 미완료 상태로 다음 단계 진행 시도 | 400 |
| SMS_SEND_FAIL | SMS 발송 실패 (Ppurio API 에러, MAIL_SEND_FAIL과 대응) | 500 |

## 7. 재사용 컨텍스트별 차이점
------------------------------------------------------------------------
`PhoneAuthService`/`PpurioSmsService`는 공통으로 재사용하되, "누구를 대상으로 인증을 진행하는지"는 기능마다 다르므로 각 기능의 001-02 설계 문서에서 아래와 같이 구체화함
- **회원가입**: [001-02 8-1장](../01.회원가입/001-02.회원가입-분석-설계.md#8-1-sms-전화번호-인증-설계-ppurio-연동-2026-07-18-요구사항-추가) — 이메일 인증 이후, 최종 가입 이전 단계에서 진행 (purpose=`SIGNUP`)
