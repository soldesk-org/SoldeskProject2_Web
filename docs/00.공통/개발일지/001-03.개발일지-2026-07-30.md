## 1. GitHub 브랜치 전략(GitFlow) 실제 구축
- `feature/*` = 각자 기능 개발, `develop` = 통합, `main` = 배포 전용 구조를 Web 저장소에 실제로 적용
- `develop`과 `main`이 서로 다른 이력으로 갈라져 73개 파일이 충돌하는 상태였음을 발견 — main의 현재 내용
  (이번에 세션에서 실제 코드로 채운 것)을 기준으로 develop을 강제 정렬해서 정리
- 실제 작업이 있던 2개 브랜치(`web-frontend-pages`, `web-map-responsive`)는 PR로 정상 병합, 07-16 이후
  방치돼 있던 빈 스켈레톤 브랜치 3개는 develop 최신 코드로 갱신(`web-notion-test`는 개인 테스트용이라 제외)
- `GitHub-브랜치전략.md`, `Web-저장소-브랜치-구조.md` 문서로 현재 상태와 흐름 정리

## 2. Jenkins CI/CD 파이프라인 신규 구축 (Build→Test→Archive→Deploy 전체)
- Azure VM에 Jenkins 설치(Java 21, apt 키 문제, systemd 오버라이드), GitHub Webhook 연결까지 실제로 구축
- Jenkins Credentials에 `.env`의 거의 모든 값(34개)을 등록해야 Spring 컨텍스트 로딩이 되는 걸 확인하며
  하나씩 채움, `junit` 플러그인 누락·war 패키징 아카이브 패턴 등 실제 빌드 실패 5건을 순서대로 해결
- 이어서 Deploy 단계까지 구현 — Jenkins가 이 VM 위에서 직접 실행되므로 scp/ssh 없이 war 복사 + systemd
  재시작으로 배포되게 구성(`soldesk-app.service` 신규, jenkins 계정 전용 sudoers 규칙 추가)
- `when { branch 'main' }` 조건이 이 Job(Multibranch 아님)에서 항상 무시되던 문제, 배포 스크립트 마지막
  진단 명령이 sudoers 미매칭으로 빌드를 거짓 실패 처리하던 문제, VM에 없는 HTTPS 키스토어 때문에 앱이
  계속 크래시하던 문제까지 실제로 겪고 그 자리에서 수정 — 최종적으로 `main` push 한 번으로 Build부터
  실제 서비스 재기동까지 전부 자동으로 동작하는 것을 라이브로 확인

## 4. Azure NSG 포트 개방 및 외부 접속 확인
- 배포된 앱이 VM 내부(`localhost:8081`)에서는 응답하는데 외부에서는 접속이 안 되는 문제 확인 — Azure NSG에
  8081이 안 열려있던 것이 원인
- `Allow-App-8081` 규칙 추가 후 외부에서 `http://72.155.72.187:8081/` 접속 성공까지 확인
- 추후 도메인 연결 시에는 80번 포트로 전환할 계획 — 관련 내용 문서에 반영
