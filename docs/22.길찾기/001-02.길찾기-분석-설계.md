## 1. 패키지 구조
------------------------------------------------------------------------
```
com.foodtrip.foodsearch
 └─ directions (신규 패키지)
     ├─ client      NcpDirectionsClient (NCP Direction 5 호출)
     ├─ dto         DirectionsResponseDto
     └─ controller  DirectionsController (공개 API)
```
15(주차장-정보)의 `ParkingLotController`와 같은 톤 — 별도 서비스 계층 없이 클라이언트를 컨트롤러가 바로
호출한다(중간에 끼워넣을 우리 쪽 비즈니스 로직이 없어서, 15의 `ParkingLotServiceImpl`처럼 거리 계산/
병합 같은 가공이 필요한 경우와 다름).

## 2. 핵심 설계 결정
------------------------------------------------------------------------
### 2-1. 서버가 대신 호출하는 프록시 구조
NCP Direction 5는 Client ID/Secret으로 인증하는 서버 전용 API라, 브라우저가 직접 호출할 수 없다(001-01
배경 참고). 그래서:
1. 프론트가 `GET /api/directions?startLat=&startLng=&goalLat=&goalLng=`를 우리 서버에 요청
2. `NcpDirectionsClient`가 그 좌표를 그대로 NCP Direction 5에 전달, 인증 헤더는 서버가 붙임
3. 응답 중 필요한 값만 추려서(`DirectionsResponseDto`) 프론트에 돌려줌

Secret 값이 프론트/네트워크 응답(우리 서버→NCP 구간)에는 노출되지만, **브라우저→우리 서버 구간에는
전혀 노출되지 않는다** — 08(영수증OCR)이 Upstage API 키를 서버에만 두는 것과 같은 이유.

### 2-2. 음식점 상세 DTO를 확장하지 않고 별도 공개 API로 분리
15(주차장-정보) 2-5장과 동일한 이유 — `RestaurantDetailResponseDto`를 건드리지 않고
`GET /api/directions`를 완전히 별도 API로 분리했다. 프론트가 이미 갖고 있는 음식점 좌표(상세 조회
응답)와 브라우저 geolocation으로 얻은 현재 위치, 이 두 좌표 쌍만 넘기면 된다.

### 2-3. 응답에서 추려낸 값
NCP 원본 응답은 훨씬 많은 정보(턴바이턴 안내, 도로 구간별 혼잡도/속도, bbox 등)를 주지만, 001-01에서
정한 범위대로 `DirectionsResponseDto`에는 다음만 담는다:
- `distanceM`(총 거리, m), `durationMs`(예상 소요시간, ms)
- `tollFare`(통행료), `taxiFare`(택시요금 추정), `fuelPrice`(리터당 유가 추정치 — NCP가 소요 유류비
  계산에 쓰는 기준 단가로 보이며, 정확한 의미는 API 문서로 재확인 필요)
- `path`: [경도, 위도] 순서 좌표 배열 그대로(NCP 원본과 동일 순서) — 프론트가 지도 라이브러리에 맞게
  뒤집어서 씀(Naver Maps는 `LatLng(위도, 경도)` 순서라 프론트에서 변환)

### 2-4. 인증/권한 — 공개 API
15(주차장-정보) 근처 조회와 같은 톤: 로그인 불필요. 길찾기 자체가 회원 개인 데이터와 무관하고, 좌표
두 쌍만 있으면 되는 순수 조회 기능이라 인가를 걸 이유가 없다고 판단.

## 3. API 설계
------------------------------------------------------------------------
```
GET /api/directions?startLat={위도}&startLng={경도}&goalLat={위도}&goalLng={경도}
```
응답: `{ distanceM, durationMs, tollFare, taxiFare, fuelPrice, path: [[경도,위도], ...] }`

------------------------------------------------------------------------

## 7. 확인이 필요한 사항 / 남은 작업
------------------------------------------------------------------------
- NCP Direction 5의 일일/월간 호출 한도를 확인하지 않음(무료 제공량이 있는지, 초과 시 과금 정책 등)
- 경로가 여러 옵션(`traoptimal` 외에 `trafast`/`tracomfort` 등)으로도 오는지 원본 응답에서 다른 키가
  있는지 전체 구조를 다 살펴보지는 않음 — 이번엔 `traoptimal`(추천 경로로 추정) 첫 번째 결과만 사용
- 도보/대중교통 경로, 턴바이턴 안내, 경유지 전부 이번 범위 밖(001-01 참고)
- 현재 위치를 못 가져오는 경우(위치 권한 거부 등)의 대체 동작은 에러 메시지 표시뿐 — 수동 좌표 입력 같은
  대안은 없음
