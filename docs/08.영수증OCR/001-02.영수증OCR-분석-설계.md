# 영수증 OCR 분석·설계
------------------------------------------------------------------------
[001-01.영수증OCR-요청사항.md](001-01.영수증OCR-요청사항.md) 기반 분석/설계 문서

> **⚠️ 2026-07-22 갱신 공지**: 이 문서 작성(2026-07-21) 이후, 07(음식점-메뉴-검색)이 카카오 로컬 API ToS
> 준수 문제로 전면 재작성되면서(`docs/07.음식점-메뉴-검색/001-07`) `restaurantId`가 숫자(`Long`)가 아니라
> **카카오 장소 id 문자열**로, `restaurants` 테이블에는 상호명이 더 이상 저장되지 않는 구조로 바뀌었다.
> 이 변화가 아래 5장/6장/7장에 그대로 영향을 미쳤다 — 각 장에 인라인으로 갱신 표시해둠.

## 1. 범위 정리
------------------------------------------------------------------------
001-01에서 확정한 대로, 이번 기능은 "영수증 이미지를 업로드하면 이미 만들어져 있는 Python OCR 서버
(`receipt-biz-verify`)로 전달해 상호명/일시/금액/메뉴목록을 받고, **그 영수증이 리뷰 대상 음식점 방문이
맞는지 검증**해서 `receipts`에 저장하는 것"까지가 범위다. 리뷰 작성/수정/삭제 자체(별점, 키워드 태그,
리뷰 본문 등)는 "3. 사용자 기능"에서 별도로 다룬다 — 이 기능은 그 화면에 넘겨줄 "OCR 결과 + 인증 여부"를
만드는 백엔드까지만 담당한다.

## 3. DB 스키마 변경
------------------------------------------------------------------------
`docs/00.공통/DB-테이블설계.md` 4장의 기존 설계에서 한 가지 변경이 필요하다.

| 테이블 | 변경 | 이유 |
|---|---|---|
| `receipts` | `transaction_id VARCHAR(50) NULL` 컬럼 추가, `UNIQUE` 제약 | Python 서버가 주는 승인번호/영수증번호/바코드 값 — 중복 리뷰 등록 방지의 핵심 키(001-01 참고). `NULL` 허용(OCR이 못 찾을 수 있음)이지만 값이 있으면 유일해야 함(MySQL은 NULL 여러 개는 UNIQUE 위반 아님 — 정상 동작) |

나머지(`receipts`의 `parsed_store_name`/`parsed_payment_date`/`parsed_total_amount`/`ocr_status`,
`receipt_items`, `ocr_processing_logs`)는 기존 설계 그대로 사용한다. `ddl-auto=update`로 안전하게 컬럼만
추가된다(006/07에서 이미 여러 번 쓴 방식).

`ocr_raw_text`(TEXT, 기존 컬럼)에는 Python 응답 JSON 원문을 그대로 문자열로 저장한다 — 서버가 OCR
원본 텍스트 줄(`lines`)까지는 응답으로 안 주기 때문에(001-01 참고), 나중에 파싱 결과를 재검토할 필요가
생기면 최소한 구조화된 응답 JSON이라도 남겨두는 용도.

## 4. Python 서버 연동 (`ReceiptOcrClient`)
------------------------------------------------------------------------
`BusinessVerificationClient`(01(회원가입))와 같은 서버·같은 설정값(`business-verify.base-url`)을 그대로
재사용한다 — 새 설정 키를 만들지 않는다(같은 FastAPI 앱이 라우터만 다르게 서빙하므로).

```java
public class ReceiptOcrClient {
    // BusinessVerificationClient와 동일하게 HttpClient.Version.HTTP_1_1 강제
    // (JdkClientHttpRequestFactory) — 평문 HTTP 내부 Python 서버 연동 시 반복적으로 겪은 문제 예방.

    public ReceiptOcrClient(@Value("${business-verify.base-url}") String baseUrl) { ... }

    public ReceiptOcrResult parse(MultipartFile file) {
        // POST /parse-receipt, multipart 필드명 "file" (BusinessVerificationClient.verify()와 동일한
        // MultipartBodyBuilder 패턴)
        // 성공(200): ReceiptOcrResult로 매핑
        // 실패(4xx/5xx): 응답 바디의 "error" 코드를 그대로 살려서 CustomException으로 변환(5장 참고) —
        //   "parsed"(부분 인식 결과)가 있으면 같이 담아 상위로 전달(재입력 화면에 보여줄 수 있게)
    }
}
```

```java
public record ReceiptOcrResult(
        String storeName, String orderDatetime, List<MenuItemResult> menuItems,
        Integer totalPrice, String transactionId) {
    public record MenuItemResult(String name, Integer price) {}
}
```

Python 서버가 주는 에러 코드(001-01 표)는 그대로 우리 `ErrorCode`에 매핑한다(6장).

## 5. 핵심 처리 흐름 (`ReceiptServiceImpl.uploadAndParse()`)
------------------------------------------------------------------------
> **(2026-07-22 갱신)** 아래 2단계와 7단계는 카카오 전환으로 실제 구현이 달라졌다 — 갱신 표시된 부분이
> 현재 코드(`ReceiptServiceImpl`) 기준이다.

1. 로그인 필수 확인(`resolveMemberId()`, 07 `RestaurantOwnerServiceImpl`과 동일한 "무효 토큰=바로 401"
   패턴 — 조회 API의 선택적 인증과 다름)
2. **(2026-07-22 변경)** 더 이상 "존재 확인 후 없으면 404"가 아니다 — 카카오 place id는 우리 DB에 없는 게
   정상이므로(07의 "부가정보만 지연 생성" 패턴, 07 001-07 2-1장), `restaurantRepository
   .findByRestaurantIdAndDeletedAtIsNull(restaurantId).orElseGet(() -> ...save(Restaurant.createExtras
   (restaurantId)))`로 **없으면 그 자리에서 부가정보 행을 새로 만든다**. `RESTAURANT_NOT_FOUND`는 이 경로에서
   더 이상 발생하지 않음(7장 에러 코드 표 갱신 참고)
3. `ReceiptImageStorageService.store()`로 이미지를 로컬 디스크에 저장
4. `Receipt.createPending(memberId, restaurantId 후보 없이 시작, imagePath)`로 `receipts` 레코드 생성
   (`ocr_status=PENDING`) — 이 시점엔 아직 `restaurant_id`를 안 채운다(매칭 성공해야 채움, 8장 참고)
5. `ReceiptOcrClient.parse()` 호출
   - **실패 시**: `ocr_status=FAILED`로 갱신, `ocr_processing_logs`에 실패 기록(에러코드/메시지) 남기고
     `CustomException`을 그대로 던져 API 응답으로 실패를 알림(부분 인식 결과가 있으면 같이 반환 — 6장)
   - **성공 시**: 다음 단계로 진행
6. **중복 검사**: `transactionId`가 있고, 이미 다른 `receipts`에 같은 값이 저장돼 있으면
   `DUPLICATE_RECEIPT`로 실패 처리(어뷰징 방지, 001-01 핵심 요구사항)
7. **음식점 매칭(인증 판정)**: **(2026-07-22 변경)** `matchesRestaurant(ocrStoreName, restaurant.getName())`이
   아니라 `matchesRestaurant(ocrStoreName, restaurantName)` — `restaurants` 테이블에 상호명을 더 이상 저장하지
   않으므로(카카오 ToS, 07 001-07 2-1장), 매칭에 쓸 상호명을 **프론트가 요청 파라미터로 직접 함께 보낸다**
   (6-1장 `restaurantName` 신규 필드). 판정 로직 자체(정규화 후 완전 일치 또는 양방향 부분 문자열 포함)는
   그대로. 성공하면 `receipt.claim(restaurantId)`로 `restaurant_id` 채우고 인증 성공 플래그, 실패하면
   `restaurant_id`는 NULL로 남기고 미인증 처리(9-2장 — 리뷰 작성 자체를 막을지는 미확정)
8. `parsed_store_name`/`parsed_payment_date`/`parsed_total_amount`/`transaction_id`/`ocr_raw_text`를
   `receipts`에 저장, `ocr_status=SUCCESS`
9. `menu_items` 배열을 `ReceiptItem.create()`로 각각 `receipt_items`에 저장
10. `ocr_processing_logs`에 성공 기록(소요시간 포함)
11. `ReceiptUploadResponseDto`(OCR 결과 + 인증 여부)를 응답으로 반환 — 리뷰 작성 화면이 이 값으로 폼을
    미리 채우고 인증 뱃지를 표시하는 데 사용(001-01 4장 참고, 실제 화면은 이번 범위 아님)

## 6. API 명세
------------------------------------------------------------------------
### 6-1. 영수증 업로드 + OCR + 인증
```
POST /api/receipts
Content-Type: multipart/form-data
Authorization: Bearer {accessToken} (필수)
필드: image(파일), restaurantId(카카오 장소 id, 문자열), restaurantName(2026-07-22 신규 필수 필드 —
     상호명을 더 이상 DB에 저장하지 않아, 매칭 판정에 쓸 상호명을 프론트가 직접 함께 보낸다. 프론트는
     검색 결과/상세 화면에서 이미 들고 있는 카카오 상호명을 그대로 실어 보내면 됨)
```

Response(200):
```json
{
  "success": true,
  "receiptId": 1,
  "storeName": "OO식당",
  "orderDatetime": "2026-07-21 14:30",
  "totalPrice": 45000,
  "menuItems": [ { "name": "된장찌개", "price": 9000 }, ... ],
  "verified": true,
  "restaurantId": "16421356"
}
```
**(2026-07-22 변경)** `restaurantId`가 더 이상 숫자가 아니라 카카오 장소 id 문자열로 내려간다.
`verified=false`면 인식은 성공했지만 리뷰 대상 음식점과 상호명이 안 맞았다는 뜻(`restaurantId`는 null로
내려감) — 9-2장 확정 전까지는 이 경우에도 200으로 응답하고 프론트가 "미인증으로 계속 진행"할지 판단하게
한다(잠정).

Response(422, OCR 부분 실패 — Python 서버 에러를 그대로 전달):
```json
{ "success": false, "code": "RECEIPT_STORE_NAME_NOT_FOUND", "message": "상호명을 인식하지 못했습니다.",
  "parsed": { "orderDatetime": "2026-07-21 14:30", "totalPrice": 45000, ... } }
```

Response(409, 중복 영수증):
```json
{ "success": false, "code": "DUPLICATE_RECEIPT", "message": "이미 사용된 영수증입니다." }
```

### 6-2. 조회(선택, 필요시)
```
GET /api/receipts/{receiptId}
```
본인이 업로드한 영수증만 조회 가능(다른 회원 것 조회 시 `RESTAURANT_ACCESS_DENIED`류 처리 필요 — 9-4장).

## 8. 잠정 설계로 확정한 것 (001-01의 "확인 필요" 항목에 대한 1차 판단)
------------------------------------------------------------------------
- **음식점 매칭 규칙**: 정규화 후 완전 일치 우선, 안 되면 양방향 부분 문자열 포함(07 카테고리/주소 매칭과
  같은 톤) — 다만 리뷰 인증은 오탐 시 신뢰도 문제가 07의 "카테고리 자동분류 실패해도 그냥 미분류"보다
  심각할 수 있어, 정확도가 실제로 낮으면 나중에 더 엄격한 기준(완전 일치만 인증 처리)으로 좁힐 수 있음.
- **매칭 실패해도 리뷰 작성 자체는 막지 않음(잠정)**: `verified=false`로 응답하고 프론트가 "미인증 리뷰"로
  계속 쓸 수 있게 하는 쪽을 잠정 기본값으로 둠 — OCR 인식률이 100%가 아닌 이상 인증 실패를 리뷰 작성
  차단으로 이어가면 사용성이 너무 나빠질 수 있다고 판단. 팀 논의로 뒤집힐 수 있음.
- **재시도**: 이번 범위에서는 별도 "재시도" API를 만들지 않음 — 실패하면 프론트가 사진을 다시 찍어
  같은 `POST /api/receipts`를 다시 호출하는 것으로 충분하다고 판단(각 호출이 새 `receipts` 레코드를
  만듦, 실패한 레코드는 그대로 남아 `ocr_processing_logs` 이력으로 확인 가능).
- **이미지 보관**: 사업자등록증명원(01)과 달리 영수증은 리뷰의 "인증 근거"로 계속 남아있어야 자연스러워
  당분간 파기하지 않는 쪽으로 잠정 결정 — 개인정보처리방침 8장의 보유기간은 "리뷰 삭제 시" 또는
  "회원 탈퇴 시"로 맞추는 것을 제안(최종 확정은 팀 논의 필요).
- **파일 크기/형식**: 05/07과 동일하게 jpg/png/gif/webp, 5MB로 통일.

## 9. 남은 확인 사항
------------------------------------------------------------------------
1. Upstage API 키(Python 서버 쪽 `UPSTAGE_API_KEY`) 실제 설정 여부 — 없어도 동작은 하지만 인식률에 영향.
2. 매칭 실패 시 리뷰 작성을 막을지(8장 잠정 결정, 팀 최종 확인 필요).
3. `GET /api/receipts/{receiptId}` 같은 조회 API가 실제로 필요한지(리뷰 작성 화면이 업로드 응답만으로
   충분할 수도 있음) — 프론트/리뷰 기능 설계 시점에 재확인.
4. 본인 영수증만 조회 가능하게 하는 권한 체크의 정확한 에러코드(07의 `RESTAURANT_ACCESS_DENIED`를
   재사용할지 새 코드를 만들지).
5. `transaction_id` UNIQUE 제약을 DB 레벨에서 강제할지, 애플리케이션 레벨 사전 조회로만 막을지(동시
   업로드 레이스 컨디션 고려 시 DB UNIQUE가 더 안전 — 이번 설계는 DB UNIQUE 전제로 3장 작성함).
