## 1. 구현 결과 (2026-07-21)
------------------------------------------------------------------------
### 1-1. 실제 구현 파일
설계(001-02 2장)대로 신규 `receipt` 패키지로 분리해서 구현했다.

```
com.foodtrip.foodsearch
 └─ receipt (신규 패키지)
     ├─ entity      Receipt, ReceiptItem, OcrProcessingLog
     ├─ repository  ReceiptRepository, ReceiptItemRepository, OcrProcessingLogRepository
     ├─ dto         ReceiptUploadResponseDto, ReceiptItemResponseDto
     ├─ client      ReceiptOcrClient, ReceiptOcrResult(record)
     ├─ service     ReceiptService/Impl, ReceiptFailureRecorder, ReceiptSuccessRecorder(2-2장 참고)
     └─ controller  ReceiptController (1개 엔드포인트)
```

`common/storage/ReceiptImageStorageService`(신규) — `RestaurantImageStorageService`(07)와 완전히 같은
로컬 디스크 저장 패턴. `StaticResourceConfig`에 `/receipt-images/**` 정적 서빙 추가.

신규 `ErrorCode` 12개 추가(001-02 7장 표 그대로): `RECEIPT_EMPTY_FILE`(400), `RECEIPT_INVALID_IMAGE`(400),
`RECEIPT_NO_TEXT_DETECTED`(422), `RECEIPT_PARSE_FAILED`(422), `RECEIPT_STORE_NAME_NOT_FOUND`(422),
`RECEIPT_ORDER_DATETIME_NOT_FOUND`(422), `RECEIPT_TRANSACTION_ID_NOT_FOUND`(422),
`RECEIPT_OCR_SERVICE_UNAVAILABLE`(500), `DUPLICATE_RECEIPT`(409), `INVALID_RECEIPT_IMAGE`(400),
`RECEIPT_NOT_FOUND`(404, 예비), `RECEIPT_ACCESS_DENIED`(403, 예비 — 조회 API를 실제로 안 만들어서 아직 미사용).

### 1-2. API 구현 목록
| API | 인증 | 설명 |
|---|---|---|
| POST /api/receipts | 필수 | 영수증 업로드 → OCR → 방문 인증 판정, `multipart/form-data`(restaurantId, image) |

001-02 6-2장의 조회 API(`GET /api/receipts/{receiptId}`)는 "필요시"로 남겨뒀던 항목이라 이번엔 만들지
않음(001-02 9-3장 — 리뷰 작성 화면 설계 시점에 재확인하기로 확정).

### 1-3. DB 스키마 변경 — `receipts.transaction_id` 컬럼 추가
설계(001-02 3장) 그대로 `receipts`에 `transaction_id VARCHAR(50) UNIQUE NULL` 컬럼을 추가했다.
`ddl-auto=update`로 안전하게 반영됨(006/07에서 이미 여러 번 쓴 패턴) — 실제 서버 기동 로그로 컬럼 생성과
UNIQUE 인덱스(`Key: UNI`) 생성까지 확인함.

## 2. Python 서버 연동 확인 (2026-07-21)
------------------------------------------------------------------------
### 2-1. 실제 서버 코드 확인 및 실행 환경 문제 해결
`SoldeskProject2_Python/receipt-biz-verify`(사업자등록증명원 검증과 같은 서버, `receipt_ocr.py` 라우터)를
직접 실행해서 검증하려 했으나, 이 PC(마이그레이션된 새 PC)에서 `uvicorn main:app` 기동 시
`PyMuPDF`(fitz) 네이티브 DLL 로드 실패로 서버 자체가 안 뜨는 문제가 있었음
(`ImportError: DLL load failed while importing _extra`). `pip install --force-reinstall --no-cache-dir
PyMuPDF`로 재설치하니 해결됨 — 이 PC의 venv가 이전 PC에서 그대로 옮겨오면서 네이티브 바이너리가
깨진 것으로 추정(이 세션에서 이미 여러 번 겪은 "마이그레이션 후 재설정 필요" 패턴과 같은 종류).

서버가 뜨면(`RapidOCR` 모델 로딩까지 포함해서 기동에 수 초 소요) `GET /health` → `{"status":"ok"}`로
정상 확인.

### 2-2. 실데이터 종단 간(end-to-end) 테스트
합성 영수증 이미지(PIL로 한글 텍스트 직접 렌더링, `맑은 고딕` 폰트)를 만들어 실제 OCR 파이프라인
전체를 검증함 — RapidOCR 실제 인식 → 우리 서버 저장 → DB 확인까지 전부 실물 데이터로 확인.

**성공 + 방문 인증 성공 케이스**: "주도락 강남점"(실제 DB에 있는 음식점, `restaurant_id=119`) 상호명이
적힌 영수증 이미지를 그 음식점 ID로 업로드:
```json
{"receiptId":1,"storeName":"주도락 강남점","orderDatetime":"2026-07-21 14:30","totalPrice":17000,
 "menuItems":[{"name":"김치찌개","price":9000},{"name":"된장찌개","price":8000}],
 "verified":true,"restaurantId":119,"success":true}
```
DB 확인: `receipts.restaurant_id=119`, `transaction_id="12345678"`(영수증에 적은 승인번호 그대로 인식),
`receipt_items` 2건, `ocr_processing_logs`에 성공 기록(처리시간 12.6초 — 로컬 CPU 기준 RapidOCR 추론
시간, 실사용 환경에서는 GPU/서버 사양에 따라 달라질 수 있음) 전부 정확히 저장됨.

**중복 업로드 차단**: 같은 이미지(같은 `transaction_id`)를 다시 업로드 → `409 DUPLICATE_RECEIPT` 확인.

**방문 인증 실패(불일치) 케이스**: "엉뚱한식당"이라고 적힌 영수증을 "주도락 강남점"(`restaurant_id=119`)
앞으로 업로드 → `{"verified":false,"restaurantId":null}`로 정상 응답(200, 실패가 아니라 "미인증 성공"으로
처리하는 001-02 8장 잠정 설계 그대로 동작).

**OCR 인식 실패 케이스**: 텍스트가 전혀 없는 흰 배경 이미지 업로드 → `422 RECEIPT_NO_TEXT_DETECTED` 확인.

**인증/존재 검증**: `Authorization` 헤더 없이 호출 → `401 NOT_LOGGED_IN`. 존재하지 않는 `restaurantId`로
호출 → `404 RESTAURANT_NOT_FOUND`.

## 3. 실데이터 테스트 중 발견하고 고친 버그
------------------------------------------------------------------------
### 3-1. 실패 기록이 트랜잭션 롤백으로 통째로 사라지는 버그
**증상**: 텍스트 없는 흰 이미지를 업로드해서 `422 RECEIPT_NO_TEXT_DETECTED` 응답은 정상으로 받았는데,
DB를 확인해보니 그 시도에 대한 `receipts`/`ocr_processing_logs` 행이 **하나도 없었음**(응답은 실패인데
실패 기록 자체가 안 남는 상황).

**원인**: `ReceiptServiceImpl.uploadAndParse()`를 처음엔 클래스 전체 `@Transactional`로 감쌌는데, OCR
호출이 실패해서 `catch` 블록 안에서 "실패 기록"(`receipt.markFailed()` + `ocrProcessingLogRepository.save()`)을
저장한 뒤 바로 `throw e`로 같은 예외를 다시 던지고 있었음 — Spring이 이 메서드 전체를 하나의 트랜잭션으로
보고, unchecked 예외가 그 트랜잭션 밖으로 던져지는 순간 트랜잭션 전체(방금 저장한 "실패 기록"까지 포함)를
롤백시켜버림. 결과적으로 실패를 기록하려던 코드가 스스로 그 기록을 지워버리는 상황이었음.

**수정**: `ReceiptServiceImpl`에서 클래스 레벨 `@Transactional`을 제거하고, "실패 기록"과 "성공 기록"을
각각 별도 컴포넌트(`ReceiptFailureRecorder`/`ReceiptSuccessRecorder`)로 분리해서 자기 자신의 트랜잭션
안에서 커밋되도록 함(`ReceiptFailureRecorder`는 `Propagation.REQUIRES_NEW`로 바깥 트랜잭션과 완전히
독립시킴). 초기 `PENDING` 영수증 저장도 별도 트랜잭션으로 즉시 커밋되게 바뀜.

**재검증**: 같은 흰 이미지로 다시 테스트 → 이번엔 `receipts.ocr_status=FAILED`,
`ocr_processing_logs.status=FAILED`(에러 메시지 포함)가 정상적으로 남는 것을 실제로 확인함.
