## 기능 정리하기
------------------------------------------------------------------------
현재 해당 기능은 프론트 연결하지 않고 개발만 하기(지금까지 다른 기능들과 동일한 방침).

음식점·메뉴 검색(07) 파트는 지도 쪽 남은 작업(카테고리 공식 목록 확정, AI 추천 검색 등)을 뒤로 미루고,
다음 순서로 영수증 OCR 기능부터 진행함 — 2026-07-21 확정된 남은 작업 순서:
1. 사용자 기능(리뷰 작성·수정·삭제/즐겨찾기 등록·취소/검색 기록 조회·삭제/마이페이지)
2. AI 연결 기능(검색 문장→FastAPI 전달, 추천 결과 수신, 음BTI 응답값, 추천 결과 저장/조회, Python 서버 오류 처리)
3. **영수증 OCR 기능 — 이번 문서, 먼저 진행**

**목적(2026-07-21 확정)**: 영수증 OCR은 단순히 텍스트를 뽑아내는 게 아니라, **그 영수증이 실제로 리뷰를
쓰려는 그 음식점을 방문했다는 증거가 맞는지 검증**하는 용도임. OCR로 읽은 상호명이 리뷰 대상 음식점과
일치하는지 확인해서, 검증에 성공하면 리뷰에 "인증" 표시를 붙일 수 있게 하는 게 핵심 목표.

요청사항 원문(정리):
- 영수증 이미지 받기
- Python OCR 서버로 전달
- 상호명·날짜·금액 결과 받기
- 결과 저장 및 리뷰 작성 화면 연결

### API 스펙 (`receipt_ocr.py` 실제 코드 기준)
```
POST /parse-receipt
Content-Type: multipart/form-data
필드명: file (이미지 파일)
```

**성공 응답(200)**:
```json
{
  "store_name": "상호명 또는 null",
  "order_datetime": "2026-07-21 14:30 형식 문자열 또는 null",
  "menu_items": [ { "name": "메뉴명", "price": 12000 }, ... ],
  "total_price": 45000,
  "transaction_id": "승인번호/영수증번호/바코드 중 하나(중복 등록 방지용 고유값) 또는 null"
}
```

**실패 응답**(전부 `{ "error": "코드", "message": "...", "parsed": {...부분인식결과...} }` 형태, `parsed`는
있을 수도 없을 수도 있음):
| error 코드 | HTTP | 상황 |
|---|---|---|
| EMPTY_FILE | 400 | 빈 파일 |
| INVALID_IMAGE | 400 | 이미지 디코딩 실패 |
| NO_TEXT_DETECTED | 422 | 이미지에서 글자를 전혀 못 읽음 |
| RECEIPT_PARSE_FAILED | 422 | 글자는 읽었는데 영수증 정보(상호/메뉴/금액)를 하나도 못 뽑음 |
| STORE_NAME_NOT_FOUND | 422 | 상호명만 인식 실패(나머지는 성공) |
| ORDER_DATETIME_NOT_FOUND | 422 | 주문일시만 인식 실패 |
| TRANSACTION_ID_NOT_FOUND | 422 | 승인번호/영수증번호/바코드를 하나도 못 찾음 |
| OCR_PROCESSING_FAILED | 500 | 그 외 서버 내부 오류 |

**동작 방식(참고)**: 1차로 RapidOCR(무료, 로컬 실행)로 정규식 기반 파싱을 시도하고, 결과가 의심스러우면
(주요 필드가 비었거나 상호명이 메뉴명 목록에 섞여 들어간 경우 등) `UPSTAGE_API_KEY`가 설정된 경우에만
Upstage AI로 이미지를 다시 보여주고 교정을 받음(선택적 2차 보정 — 키 없으면 1차 결과 그대로 씀).

**`transaction_id`가 특히 중요함**: 승인번호/영수증번호/영수증 바코드 중 하나를 뽑아주는데, 이게
"중복 등록 방지용 고유값"이라고 코드 주석에 명시돼 있음 — **같은 영수증으로 여러 번 리뷰를 쓰는 어뷰징을
막는 용도로 우리 쪽에서 활용해야 함**(같은 `transaction_id`가 이미 저장돼 있으면 재사용 거부 등). 지금
`receipts` 테이블(DB-테이블설계.md 4-1장)에는 이 값을 저장할 컬럼이 없음 — 분석-설계 단계에서 컬럼 추가
필요(6장 참고).

## 비슷한 기존 연동 패턴 — 사업자등록증명원 OCR(01(회원가입) 참고)

`BusinessVerificationClient`가 이미 이 서버의 `/verify`(사업자등록증명원용)를 호출하고 있음 — 멀티파트

HTTP 내부 Python 서버와 통신할 때 JDK HttpClient의 기본 HTTP/2 업그레이드 시도 때문에 요청이 깨지는
문제를 여러 번 겪었고(01/07/001-06 문서에 각각 기록됨), 그때마다 이 방식으로 예방/해결했음.

## 영수증 OCR 기능 범위(안)
------------------------------------------------------------------------
- 영수증 이미지 업로드 API(멀티파트, 로그인 필요) — `receipts` 레코드 생성(`ocr_status=PENDING`)
- `ReceiptOcrClient`로 Python 서버 `/parse-receipt` 호출
- 결과 저장 — `parsed_store_name`/`parsed_payment_date`/`parsed_total_amount`를 `receipts`에 저장,
  `menu_items` 배열은 `receipt_items`에 각각 저장, `ocr_status`를 SUCCESS/FAILED로 갱신,
  `ocr_processing_logs`에 처리 기록 남기기(성공/실패 코드, 소요시간)
- **음식점 방문 인증**: 인식된 `store_name`을 리뷰 작성 대상 음식점(`restaurants.name`)과 비교해서
  일치 여부 판정 — 일치하면 `receipts.restaurant_id` 채우고 "인증" 처리, 불일치/인식실패면 미인증 처리
  (매칭 규칙은 07(음식점-메뉴-검색)의 사업장 주소 자동귀속과 비슷하게 "정규화 후 부분 문자열 포함"
  방식을 우선 검토 — 정확한 기준은 분석-설계에서 확정)
- **중복 방지**: `transaction_id`가 이미 다른 리뷰에 쓰였으면 재사용 거부(어뷰징 방지)
- 리뷰 작성 화면과 연결 — OCR 결과(상호명/날짜/금액/메뉴목록/인증여부)를 리뷰 작성 폼에 미리 채워주는
  용도로 넘겨줌(리뷰 작성 기능 자체는 "사용자 기능"으로 별도 분류, 이번 범위 아님 — 4장 참고)

## 확인이 필요한 것 (분석-설계 단계에서 다룰 항목)
------------------------------------------------------------------------
1. **`receipts` 테이블에 `transaction_id` 저장 컬럼 추가 필요** — 현재 스키마에 없음, 중복 방지 로직의
   핵심 값이라 반드시 추가해야 함(UNIQUE 제약 여부도 같이 결정).
2. **음식점 매칭 규칙**: "정규화 후 부분 문자열 포함"으로 할지, 더 엄격한 기준(정확히 일치 등)으로 할지 —
   틀리게 인증해주면 신뢰도 문제가 생기니 07의 카테고리/주소 매칭보다 더 보수적으로 가야 할 수도 있음.
3. **매칭 실패 시 처리**: 상호명이 안 읽히거나 다른 가게로 인식되면 리뷰 자체를 막을지, "미인증 리뷰"로는
   계속 쓸 수 있게 할지 확인 필요.
4. **재시도 정책**: Python 서버가 422로 부분 인식 결과(`parsed`)를 같이 주니까, 실패해도 사용자가 그
   부분 결과를 보고 직접 수정해서 넘어갈 수 있게 할지, 사진을 다시 찍게만 할지 확인 필요.
5. **이미지 보관 정책**: 개인정보처리방침(docs/09.약관/개인정보처리방침.md) 8장에도 이미 "영수증 이미지"
   보유기간이 미확정으로 남아있어 이번에 같이 정해야 함.
6. **파일 크기/형식 제한**: 프로필/음식점 사진(05/07)과 동일한 정책(jpg/png/gif/webp, 5MB)을 그대로 쓸지
   확인 필요.
7. **Upstage API 키 운영 여부**: Python 서버 쪽 `UPSTAGE_API_KEY`가 설정돼 있어야 2차 AI 보정이 동작함 —
   이 프로젝트 담당(Python 쪽) 팀원이 키를 발급/설정해뒀는지 확인 필요(없어도 1차 무료 파서만으로 동작은 함).
